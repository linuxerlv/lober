## 为什么必须自建 CA

Lober 部署在气隙内网（`SPEC.md` 顶部「目标环境」），不可能连到任何公网 CA
（Let's Encrypt 之类都需要走 ACME 挑战，要求外网可达）。唯一可行的路径是
自建一个内网根 CA，签发的证书只在内网范围内被信任——**人面**的运维浏览器
需要显式导入这个 CA 的证书才会信任它签发的服务端证书。

> **范围更新（2026-09）**：本 CA 现在只用于签发人面（控制台）的服务端
> 证书。机器面（iPXE ↔ 网关）已明确放弃 TLS，永久保持明文 HTTP，不需要
> 也不会为机器面域名签发证书——见 `docs/tls-与安全启动-范围决定.md`。
> 本文档下方仍保留少量「若给机器面签证书」相关的历史行文（用于说明为何
> 当初的设计要用域名而不是 IP、CA 证书为何要嵌入 iPXE 等），这些是**已
> 放弃能力的技术记录**，不是当前需要执行的步骤，均已在对应位置标注。

## 目录里的脚本

| 文件 | 做什么 |
|---|---|
| `gen-ca.sh` | 生成 CA 私钥与自签名根证书 |
| `issue-cert.sh` | 用 CA 私钥签发服务端证书（当前范围：仅人面，见上方「范围更新」） |

两个脚本都只依赖 `openssl`，可以在没有 Go 工具链、没有网络的机器上跑。
两者都支持 `--dry-run`：只打印将要执行的 openssl 命令，不生成文件、
不接触私钥，用来在正式执行前核对参数是否正确。

## CA 私钥怎么产生与保管

**CA 私钥绝不能生成在装机服务器上，也不能留在任何联网机器上。**

理由（计划任务 2 原文）：装机服务器在装机 VLAN 上有服务暴露（`/boot.ipxe`、
`/v1/boot` 等无认证端点，见 `SPEC.md` §9.1）——那台机器本身就是攻击面。
一旦 CA 私钥泄露，整个信任体系失效：攻击者可以签发任意域名的证书，
中间人攻击人面的 HTTPS 流量，而且这种失效无法通过撤销单张证书来补救，
唯一的处置是整个内网重建信任链（换 CA、重新分发、重新导入运维浏览器）。
（此前版本这里写「重编 iPXE」——机器面已放弃 TLS，CA 轮换不再涉及 iPXE，
这条后果已相应收窄。）

推荐流程：

1. 找一台**离线、专用**的机器（或至少是与生产网络物理隔离、用完即断网的
   笔记本）。
2. 在这台机器上运行 `gen-ca.sh`，生成 CA 私钥时会提示输入一个密码短语——
   这个密码短语加密保护私钥文件本身，即使私钥文件的存储介质泄露，没有
   密码短语也无法用它签发证书。密码短语不要写进任何脚本或配置文件，
   按组织的密钥管理规范保管（例如拆分给两名人员各记一半，或用组织已有的
   密码管理工具）。
3. CA 私钥生成后，把它移到离线介质（加密 U 盘、硬件安全模块），从这台
   机器的本地磁盘删除。
4. 每次需要签发或续签证书时，才把这台离线机器接上私钥介质，运行
   `issue-cert.sh`，用完立即断开介质并重新离线保管。

CA 证书（不是私钥）是公开信息，可以自由分发——它就是接下来要导入运维
浏览器信任存储的那份文件（不再需要嵌入 iPXE 二进制，机器面已放弃 TLS）。

```bash
# 在离线机器上：
bash gen-ca.sh --out-dir /path/to/offline-media/lober-ca

# 核对生成结果：
#   /path/to/offline-media/lober-ca/ca.key.pem   权限 400，CA 私钥
#   /path/to/offline-media/lober-ca/ca.cert.pem  权限 444，CA 证书
```

`gen-ca.sh` 中的 `CA_SUBJECT`（组织名、单位名）默认是占位符
`CHANGE-ME-ORG-NAME` / `CHANGE-ME-UNIT`，部署前必须通过
`LOBER_CA_SUBJECT` 环境变量或直接编辑脚本改成真实值——这个字段会出现在
每一张由此 CA 签发证书的签发者信息里。

## 签发脚本怎么用

`issue-cert.sh` 在同一台能访问 CA 私钥的（离线）机器上运行：

```bash
bash issue-cert.sh \
  --ca-dir /path/to/offline-media/lober-ca \
  --domain console.lober.internal \
  --out-dir ./server-certs
```

只签人面域名（`console.lober.internal` 或你的实际域名）——机器面域名
（`boot.lober.internal`）不需要签，签给它的证书不会被任何客户端用到
（机器面永久保持明文 HTTP，见 `docs/tls-与安全启动-范围决定.md`）。

（此前版本这里同时给两个域名签一张证书，对应「机器面与人面各一个，或
一个含两个域名」的历史设计——这是已放弃能力的历史行文，`--domain` 支持
多次传入进同一张证书 SAN 列表这个机制本身没有变化，只是当前范围下只会
用到一次。）

签发完成后，把 `./server-certs/` 下的 `*.cert.pem` 与 `*.key.pem` 带出
离线机器，交给负责 nginx TLS 配置的人（见下面「与 nginx/dnsmasq 的边界」）。
CA 私钥留在离线机器上，不要跟着一起带出。

## CN/SAN 必须是域名，不是 IP

**这是一条硬性要求，`issue-cert.sh` 会拒绝看起来像 IP 字面量的 `--domain`
参数。**

理由（`SPEC.md` §1.3）：人面域名（`console.lober.internal` 或你的实际
域名）由 dnsmasq/DNS 管理，控制台的 `console.listen`、nginx 人面
`server_name`、以及运维浏览器实际访问的地址都应该用同一个域名。证书的
CN/SAN 必须与这个域名一致，否则 TLS 客户端（浏览器）在校验证书时会
发现「你访问的域名与证书上的域名不匹配」而拒绝连接或报警告。

反过来说，如果证书签给了 IP（比如 `10.10.0.1`），一旦将来因为任何原因
需要换 IP（重新分配网段、迁移机房），就必须重新签发证书并重新分发——
而用域名的话，换 IP 只需要改 DNS 记录，证书完全不用动。这正是
`SPEC.md` §1.3 那句「将来签发证书时 CN 能对上，不必回头修改所有 URL 与
模板」的具体含义，本次范围决定后这句话只适用于人面域名。

（`gateway_base`/`artifact_base` 同样要求填域名而不是 IP，但那是机器面
配置项，理由独立于 TLS——机器面永久不签证书，见
`docs/tls-与安全启动-范围决定.md`。这两个字段用域名的理由见
`deploy/lober.yaml.example` 该字段自己的注释，本文档不重复展开。）

## 有效期与轮换节奏

**服务端证书与 CA 证书的有效期要分开看，因为它们触发的运维动作完全不同。**

| 证书 | 建议有效期 | 到期/轮换触发的动作 |
|---|---|---|
| CA 根证书 | 数十年（`gen-ca.sh` 默认 3650 天 = 10 年，可按需调大） | 重新分发到所有需要信任这个 CA 的运维浏览器（不再涉及 iPXE，见下方说明） |
| 服务端证书（人面） | 数年（`issue-cert.sh` 默认 825 天） | 只需替换 nginx 加载的证书文件并 reload |

**范围更新（2026-09）**：本节此前的设计假设服务端证书会被机器面 TLS
使用，因此强调「嵌入 iPXE 二进制的是 CA 证书本身，不是某一张具体的服务端
证书」这条决定——这条决定本身（嵌 CA 而非嵌服务端证书）在工程原理上仍然
正确，但**当前范围下机器面不上 TLS，iPXE 完全不会嵌入任何证书**，这条
决定描述的场景已不适用于当前部署。保留这段历史行文是为了：若未来重新
考虑机器面 TLS（见 `docs/tls-与安全启动-范围决定.md` 第 6 节），这条
「嵌 CA 而非嵌服务端证书」的原理判断可以直接复用，不需要重新推导。

有效期数值本身的选择依据（人面范围下仍然适用）：

- CA 证书选长（10 年起）：常规运维不需要频繁触碰 CA 层面的信任分发。
  代价是一旦 CA 私钥泄露，需要重建的信任范围更大，这也是为什么 CA 私钥
  的离线保管（上一节）比服务端证书的保管更严格。
- 服务端证书选 825 天（约 2.25 年）是一个成熟折中：比公网 CA/Browser
  Forum 目前对公开可信证书的 398 天上限宽松得多（那条规则不约束内网自建
  CA），但也没有长到「泄露后补救窗口过长」的程度。

## 轮换时哪些地方要同步更新（最容易漏的一条）

**这是最容易漏的一条，因为 CA 轮换与服务端证书轮换要更新的清单完全不同。**

### 服务端证书轮换（常规节奏，数年一次）

1. 用 `issue-cert.sh` 签发新证书（只签人面域名，沿用同一个 CA，不需要
   接触 CA 私钥之外的任何新东西）。
2. 替换 nginx 配置里 `ssl_certificate` / `ssl_certificate_key` 指向的文件
   （具体配置段落见 `deploy/nginx/lober.conf` 的人面 server 块）。
3. `nginx -s reload`（或对应的服务重启方式）。
4. 用 curl 或浏览器验证新证书已生效（检查有效期与 SAN）。
5. **不需要**：通知运维重新导入 CA（CA 本身没有换，只是换了 CA 签发的
   下级证书）。

### CA 证书轮换（罕见，数十年一次，或私钥怀疑泄露时的应急操作）

这是全链路最贵的操作，清单必须完整，否则会出现「新证书签发了，但某处
还在验旧 CA，连接失败」的现场排查困境：

1. 用 `gen-ca.sh` 生成新的 CA 私钥与根证书（新目录，不覆盖旧的——两代 CA
   在过渡期可能需要并存一段时间，见下方「过渡期」）。
2. 用新 CA 的 `issue-cert.sh` 重新签发人面服务端证书（不管旧证书是否
   还没到期）。
3. 替换 nginx 的证书文件并 reload（同上）。
4. 把新 CA 证书重新分发给所有运维的浏览器/机器（导入信任存储）。
5. 确认没有任何配置文件、脚本、文档里还引用着旧 CA 的证书路径或指纹。
6. 过渡期结束、确认所有需要访问的客户端都已切换后，才考虑销毁旧 CA 私钥
   （若这次轮换是因为私钥泄露，旧私钥应立即视为已泄露处理，而不是等
   「过渡期结束」）。

**范围更新（2026-09）**：本清单此前包含「重新编译全部四种架构的 iPXE
二进体，把新 CA 证书通过 `TRUST=` 嵌入」与「重新分发新编译的 iPXE 二进体
到 TFTP 目录」两步——这两步曾是 CA 轮换里工期最长的部分。机器面已放弃
TLS，iPXE 从未信任过这个 CA，因此 **CA 轮换不再涉及 iPXE**，上面的清单
已相应精简。若未来重新考虑机器面 TLS（见
`docs/tls-与安全启动-范围决定.md` 第 6 节），这两步需要重新加回来，
详细步骤仍可参考 `deploy/ipxe/README.md`（该文件未删除）。

**过渡期**：如果条件允许（不是私钥泄露的应急场景），可以让 nginx 同时
提供新旧两条证书链一段时间，给运维浏览器完成信任锚点更新留缓冲。

## 公钥分发：当前只有一个目标

| 目标 | 分发方式 | 成本 |
|---|---|---|
| 控制台浏览器（运维人面） | 把 CA 证书导入运维机器或浏览器的信任存储 | 低，一次性操作，一台机器几分钟 |

**范围更新（2026-09）**：本节此前还列了「iPXE（机器面）：嵌入二进体，
需要重新编译，且每次 CA 轮换都要重编重发」一行——这正是 `SPEC.md` §1.5
说 TLS 在这套栈里最贵的部分，本次范围决定已放弃机器面 TLS，这一行不再
适用。这条历史记录本身仍有参考价值（量化了「若做机器面 TLS，分发成本
高在哪」），完整内容见 `deploy/ipxe/README.md`（未删除）与
`docs/tls-与安全启动-范围决定.md` 第 2 节。

网关本身不需要分发 CA 证书——它是服务端，只需要加载自己的服务端证书与
私钥（在 nginx 里），不需要验证任何客户端证书（机器面不做 mTLS，见
`docs/phase4-mtls-决策.md`）。

## 与 nginx/dnsmasq 的边界

本 README 与本目录的脚本只负责 CA 与证书本身。把签发出的证书接进 nginx
的 TLS 监听配置，是本实现计划的**任务 3**，由另一位 agent 负责修改
`deploy/nginx/lober.conf`——本目录不修改那个文件，也不重复展开它的配置
细节。dnsmasq 侧的改动（如果有）同理，见任务 6，改的是
`deploy/dnsmasq/lober.conf`。
