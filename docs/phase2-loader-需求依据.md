## 1. 七个扩展点里，哪几个真的需要接外部系统？

**当前无法回答，缺 Phase 1 运行期依据。**

`internal/core/contract/provider.go` 定义了七个接口
（`IPAMProviderV1` / `DNSProviderV1` / `InventoryProviderV1` / `NotifyProviderV1` /
`HeartbeatProviderV1` / `TemplateResolver` / `DiskPlanner`），但接口存在不代表
外部系统存在——M1 阶段的内置实现（`internal/config/config.go` 里
`Provider.IPAM` 默认 `static`、`Provider.DNS` 默认 `noop`、`Provider.Resolver`
默认 `rule-based`）目前是唯一实现，尚无任何真实外部系统被接入，因为还没有
真机部署来产生「需要接哪个 IPAM/DNS/CMDB」这类需求。

SPEC 与契约层能提供的是**分类依据**，不是**具体系统名单**：

| 依据来源 | 提供了什么 | 没提供什么 |
|---|---|---|
| §7.4 失败语义表（阻塞建任务 vs 只告警 vs 只记录，见下节引用） | 哪几类扩展点对可靠性要求更高 | 具体是哪个厂商的 IPAM、哪个协议的 CMDB |
| §7.1 接口清单 | 七个扩展点各自的方法签名与调用时机 | 部署现场是否真的有外部系统对接这些方法，还是内置实现就够用到 Phase 2 结束 |
| `internal/config/config.go` 的 Provider 结构 | IPAM/DNS/Resolver 目前只是字符串开关，未定义任何 exec/http 参数字段 | 这本身证明「加载器所需的配置结构还不存在」，即任务 6 是全新工作，不是扩展现有代码 |

**必须等 Phase 1 上真机之后才有依据。** 具体要观测什么见第 5 节。

## 2. 每个需要外部集成的扩展点，用 exec 还是 http？

**判据能给，映射表不能给**——因为映射表的输入（哪个扩展点接了什么系统）
来自问题 1，而问题 1 现在答不出来。

SPEC §7.2 给出的判据是条件式的，摘录如下（依据：SPEC §7.2「选型判据」段）：

> 外部系统集成 → `exec` / `http`。气隙环境下改 shell 脚本是 30 秒的事，
> 改 Go 插件要在外网编译、打包、走审批、传入内网。DNS 注册、告警推送这类
> 几行 curl 的集成用 gRPC 是纯负担。

这条判据本身不区分 exec 与 http 二者——它区分的是「exec/http 这一组」对
「grpc」。exec 与 http 之间怎么选，计划任务 3/4 的动机段给出了更具体的
经验法则：

- **对方已有 webhook/REST 接口** → http（计划任务 4 动机：「让它直接收 POST
  比包一层脚本简单」）
- **对方是命令行工具或需要本地执行逻辑**（如调一个内部 CLI、读一个只在
  本机可见的文件）→ exec（计划任务 3 动机：「气隙环境下 exec 是最实用的
  加载方式」）

**这条子判据现在就能用来分类，一旦知道了具体系统。** 例如：如果 Phase 1
观测到 DNS provider 需要接一个内部 DNS 管理系统的 REST API，直接可判定为
http；如果 Inventory provider 需要跑一个只在内网某台机器上能访问 CMDB
数据库的查询脚本，直接可判定为 exec。**判据已经齐备，缺的是判据的输入**。

## 3. 有没有哪个扩展点其实是「有真逻辑」的？

**部分能从失败语义表推断出倾向，但不能下定论。**

§7.4 的失败语义表（`internal/core/contract/provider.go` 的
`failurePolicyTable`，与 SPEC §7.4 逐行对应）：

| provider | 失败语义 | 依据 |
|---|---|---|
| IPAM | `FailurePolicyBlock`（阻塞建任务） | SPEC §7.4：「IP 没申请到不能装」 |
| TemplateResolver | `FailurePolicyBlock` | SPEC §7.4：「决策出不来无法继续」 |
| DiskPlanner | `FailurePolicyBlock` | 同上 |
| Inventory | `FailurePolicyBlock`（允许人工录入兜底） | SPEC §7.4 |
| DNS | `FailurePolicyWarnOnly` | SPEC §7.4：「一次 DNS 抖动不该把已经装好的机器标成失败」 |
| Notify | `FailurePolicyWarnOnly` | 同上 |
| Heartbeat | `FailurePolicyRecordOnly` | SPEC §6.6：辅助通道，非主通道 |

**这张表回答的是「哪些失败会拖累建任务或装机」，不是「哪个扩展点的集成逻辑
复杂」**——二者是两个不同的维度，容易混淆：

- **阻塞类（IPAM/TemplateResolver/DiskPlanner/Inventory）对加载器的可靠性
  要求明显更高**：这四个的失败会直接阻塞建任务，因此加载器本身的超时、
  重试放弃、熔断行为（计划任务 5）设计得不稳健，故障会直接表现为「建不了
  任务」，比只告警类扩展点的加载器 bug 严重得多。这是本节能确定回答的部分。
- **但「阻塞」不等于「有真逻辑」。** §7.2 定义「有真逻辑的集成」举的例子是
  IPAM、CMDB——巧合的是 IPAM 恰好也在阻塞类里，但这是因为 IPAM 申请 IP
  本身既复杂（真逻辑）又关键（阻塞），两个属性叠在一个 provider 上，不能
  由此推出「阻塞类 = 有真逻辑」的一般规律。TemplateResolver 和 DiskPlanner
  也阻塞，但 §7.6 明确说它们是纯决策，MVP 靠规则表/具名策略实现，没有外部
  IO，谈不上「有真逻辑的集成」——阻塞不来自集成复杂度，来自决策结果对流程
  的必要性。

**结论：** 「是否有真逻辑」这一问题的答案依赖具体接入了什么系统的协议
复杂度（例如 IPAM 是简单的分配释放，还是要走复杂的审批流），这仍然是
问题 1 的未知数在下游产生的连锁未知。唯一能确定的是：**如果** Phase 1
发现某个扩展点需要接一个协议复杂、需要保持连接状态或做多步交互的外部
系统，它应该归 gRPC（Phase 3）而不是勉强塞进 exec——这条是 SPEC §7.2
的既定判据，不依赖实测；实测要解决的是「有没有这样的扩展点存在」。

## 4. 纯决策的两个（TemplateResolver、DiskPlanner）需要外部化吗？

**SPEC §7.6 已经给出明确答案：不需要，且给出了判定信号。**

契约代码本身也印证了这条设计意图——`TemplateResolver` 与 `DiskPlanner`
两个接口刻意不带 `Ping` 方法（对比其余五个接口都带 `Ping`）。
`internal/core/contract/provider.go` 的注释直接写明理由：

> 纯决策，不带探活方法也不做 IO：这套系统会擦盘，决策函数若行为不完全
> 确定则故障无法复现，因此本接口刻意不提供 Ping——纯函数不需要健康检查，
> 加了反而暗示「它可能因为外部依赖不可用而失败」，这与「纯决策」的定位
> 矛盾。

这不是尚未决定，是**已经决定不做**，且决定被编码进了接口形状本身（少一个
方法），不只是文档里的一句话。

SPEC §7.6 给出的引入信号（决定何时重新考虑）：

> 引入脚本引擎的信号：规则表开始长出嵌套条件，或运维反复要求「这批机器
> 特殊处理」。

**这条信号需要 Phase 1 运行期才能观测**——「规则表是否长出嵌套条件」是
一个动态属性，只有在真实的 TemplateResolver 规则表（按 `os + version +
vendor + product` 匹配）随着接入的机型增多而演化时才能看出。MVP 刚启动时
规则表必然是平的（几条记录，没有条件分支），这件事本身不构成推迟的理由，
而是需要持续观察的指标。

**结论：** 两个纯决策扩展点在 Phase 2 阶段不做外部化，这是 SPEC 既定结论，
不依赖 Phase 1 实测——实测要看的不是「现在需不需要」（不需要，已确定），
而是「什么时候需要」（规则表复杂度的增长速率，属于 Phase 2/3 边界之外的
持续观测项，不阻塞 phase2-03 的开工判断）。

## 5. 必须等 Phase 1 上真机之后才有依据的部分，以及具体观测什么

问题 1（哪些扩展点真需要外部集成）与问题 3 的「有没有真逻辑」的具体判定，
都依赖以下观测项。这些观测项在 Phase 1 集成完成、真机跑通之后才能收集：

| 观测项 | 从哪里看 | 支持做 exec 的观测结果 | 支持做 http 的观测结果 | 支持「三个 shell 脚本就够」的观测结果 |
|---|---|---|---|---|
| 建任务时是否有运维反复手动改 `resolved_params` 里的 IP/主机名字段 | 控制台的任务事件表 + 运维口头反馈 | 需要接一个内网工具查询/命令行调用 | 目标系统本就暴露 REST/webhook | 手动改的频率低、字段少，static 内置实现的表单直填够用——**不做加载器** |
| IPAM/DNS/Inventory 的内置实现（`static`/`noop`/`rule-based`）在真实清单/建任务流程中是否已经暴露不足 | `internal/provider`（M7 落地后）的调用日志、控制台任务失败事件里 provider 相关的 `failure_reason` | 不足表现为「需要调一个外部工具才能拿到正确值」 | 不足表现为「需要通知一个已有 webhook 的系统」 | 完全没暴露不足，内置实现在观察期内一直够用 |
| 目标外部系统（如有）暴露的接口形态 | 与该系统对接方确认协议文档；若无外部系统则此项无观测对象 | 命令行工具、SDK、只能本地跑的脚本、无网络接口 | 已有 HTTP/REST API 或 webhook 端点 | 不适用（因为不存在需要接的外部系统） |
| TemplateResolver 的规则表行数与条件复杂度随机型增加的变化趋势 | `internal/provider`（M7）里规则表的实际配置文件/代码，定期 review | 不适用（TemplateResolver 不用 exec/http，见问题 4） | 不适用 | 规则表仍是平的（无嵌套条件）→ 维持内置，不外部化 |
| DiskPlanner 是否收到「这批机器要特殊处理」的运维诉求 | 运维工单/控制台的磁盘规划失败反馈 | 不适用 | 不适用 | 没有此类诉求 → 维持内置策略，不外部化 |
| provider 调用失败率与响应耗时的真实分布 | task_event 表按 `source=provider` 过滤 | 无网络往返，失败通常是脚本 bug 或权限问题 | 存在网络失败与业务失败两类需区分（计划任务 4 第 3 条） | 失败率极低、发生频率不足以证明「值得投入加载器基建」 |

观测的最小前提：**至少有一个非纯决策的扩展点（IPAM/DNS/Inventory/Notify/
Heartbeat）在真机场景下暴露出「内置实现不够用」，且能说清楚不够用的具体
形态（要接什么、那东西提供什么接口）。** 没有这个前提，上表列的观测项无从
收集——这也是本文档在第 0 节直接给出「推迟」结论的原因：不是观测结果指向
推迟，是观测这件事本身尚未发生。

## 6. 开工判据：满足什么条件才启动任务 2 及之后

**判据（可判定，而非「等情况明朗」这类不可判定的话）：**

启动 phase2-03 任务 2 及之后，需同时满足：

1. **Phase 1 全部完成并已在至少一台真机（或高保真本地环境，如 QEMU 虚拟机
   跑通完整装机流程）上跑通过至少一次端到端装机**——即计划文件开头「前置：
   Phase 1 全部完成」这一条已成立，不是仍在并行开发中。
2. **能对第 1 节表格里的「哪几个扩展点真的需要接外部系统」给出至少一个
   具体答案**——具体到「某扩展点 + 某外部系统名称/类型 + 接入方式
   （REST API / 命令行工具 / 数据库）」，不是「以后可能需要接 CMDB」这种
   假设性描述。
3. **对该具体答案，能用 SPEC §7.2 的判据（本文档第 2 节）推导出 exec 还是
   http**，或者明确判定为「有真逻辑，应等 Phase 3 的 gRPC」（本文档第 3
   节），三者选一，且推导过程写得出来（不是直觉判断）。

**任一条不满足，维持当前状态：** 内置实现（static/noop/rule-based）继续
支撑 Phase 1 的功能范围，phase2-03 整体推迟，回头做 Phase 2 的其它并行
计划（P2-01/02/04/05）。这不是消极等待——按 SPEC §7.6，"接口边界是真正
有价值的部分，加载机制可以后补"，M1 已经把七个接口定稳，后补加载器不需要
改动已有代码，推迟没有技术债务成本。

**不满足判据时，若仍想推进 phase2-03，正确的下一步不是写加载器代码，是
先把某个具体外部系统的对接需求做实**（例如：运维明确提出要接某个真实
IPAM 系统，说清楚协议），再回来对照本文档判定加载器类型。

## 7. 倾向性建议（基于 SPEC 推理，非实测）

**声明：以下建议全部基于 SPEC 条款的既定判据推导，不基于任何实测数据——
因为实测数据不存在（Phase 1 尚未上真机）。这是推理结论，不是观测结论，
标注区别是为了防止阅读者把它当成已验证的事实。**

若第 6 节的开工判据满足、且确实发现有扩展点需要接外部系点，按 SPEC §7.2
的选型判据推理出的倾向：

- **外部系统集成（IPAM/DNS/Inventory/Notify 等接第三方系统的场景）倾向
  exec/http，不倾向 grpc**，理由是气隙环境下改一个 shell 脚本是 30 秒的事，
  改 Go 插件要在外网编译、打包、走审批、传入内网——这条运维现实在气隙
  部署场景下的权重压倒「gRPC 类型更安全」的工程偏好。DNS 注册、告警推送
  这类几行 curl 就能表达的集成，上 gRPC 是纯负担（SPEC §7.2 原文判断）。
- **真有复杂协议、需要保持连接或多步交互的集成（SPEC §7.2 举例 IPAM、
  CMDB 的复杂场景），倾向 gRPC，且推到 Phase 3**——不在 phase2-03 范围内。
  注意 IPAM 这个名字在两条判据里都出现（简单场景 exec/http，复杂场景
  gRPC）：区分点在于该 IPAM 系统实际的协议复杂度，不是「IPAM 这个扩展点
  天然该用哪种」，选型判据作用于具体接入的系统，不作用于扩展点名字本身。
- **纯决策（TemplateResolver、DiskPlanner）倾向继续用内置策略，暂不上
  Starlark**——这是 SPEC §7.6 的既定结论（本文档第 4 节已详述），倾向度
  最高、确定性也最高，因为它甚至不依赖「有没有外部系统」这个未知数，只
  依赖规则表复杂度这一个可持续观测的指标。
