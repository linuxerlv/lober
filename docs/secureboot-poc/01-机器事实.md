## 背景机制（已核实）

UEFI Secure Boot 的信任存放在几个 UEFI 变量里：

| 变量 | 内容 | 来源 |
|---|---|---|
| `PK`（Platform Key） | 平台密钥，厂商出厂预置，控制整个信任链的根 | [Debian Wiki SecureBoot](https://wiki.debian.org/SecureBoot)（已核实，2026-07-19 修订） |
| `KEK`（Key Exchange Key） | 通常含微软的 KEK，用于批准对 `db`/`dbx` 的更新 | 同上 |
| `db` | 允许列表：被信任签名/哈希的清单，出厂机默认含微软的两个 CA（"Microsoft Corporation UEFI CA 2011" 与新机型上的 "Windows UEFI CA 2023"） | 同上，含实机 dmesg 输出样例 |
| `dbx` | 撤销列表：被撤销的签名/哈希 | 同上 |
| `MokListRT` | 用户通过 MOK 机制注册的额外密钥，独立于 `db`，由 shim 维护而非固件本身 | 同上 |

`mokutil` 是查询这些状态的标准工具（[rhboot/mokutil](https://raw.githubusercontent.com/rhboot/mokutil/master/README) 项目，已核实为真实仓库，但其 README 本身只有一行说明，具体命令语义以 Debian Wiki 的实操记录为准，来源同上）：

```bash
# 已核实：命令与预期输出格式来自 Debian Wiki 实操记录
sudo mokutil --sb-state
# 预期输出（举例）：SecureBoot enabled  或  SecureBoot disabled

sudo mokutil --list-enrolled
# 列出当前 MOK 列表里的密钥

sudo mokutil --db
# 列出 db（固件允许列表）里的证书，2024+ 机型上用来判断
# 是否已经是 "Windows UEFI CA 2023"（而不是旧的 "...UEFI CA 2011"）——
# 若只有新 CA 而没有旧 CA，某些还只被旧 CA 签过的第三方 shim 会被拒绝，
# 这一条本身就是「厂商与型号分布」要核查的具体例子之一（见问题 5）
```

内核日志里也能看到已加载的证书（同一来源给出的实机样例）：

```
[    1.378223] Loading compiled-in X.509 certificates
[    1.398449] integrity: Loading X.509 certificate: UEFI:db
[    1.399705] integrity: Loaded X.509 cert 'Lenovo Ltd.: ThinkPad Product CA 2012: ...'
[    1.402315] integrity: Loading X.509 certificate: UEFI:db
[    1.404966] integrity: Loaded X.509 cert 'Microsoft Corporation UEFI CA 2011: ...'
```

## 要回答的五个问题

### 问题 1：机房里的机器有多少台开启了 Secure Boot？

**未能核实** —— 需要实机盘点。

**待实机验证的步骤（具体命令与预期输出）：**

```bash
# 前置：机器已装好任意 Linux（哪怕是临时 live 系统），能登录 shell
sudo mokutil --sb-state
```

预期输出只有两种：

```
SecureBoot enabled
```

或

```
SecureBoot disabled
```

**批量做法：** 把上面这条命令塞进现有的资产盘点脚本／CMDB 采集任务里，
对机房全量机器跑一遍，按型号汇总。若机器还没装任何系统（裸机），
可以从 UEFI Shell 里跑等价查询（`bcfg` 或直接看 Setup 界面的 Secure Boot 开关项，
不同厂商菜单路径不同，无法在此给出通用命令，需人到现场记录该型号的具体菜单路径）。

**完成标志（供运维核对）：** 一张「型号 → 台数 → Secure Boot 开启台数」的表。

### 问题 2：能否批量关闭？

**通用机制已核实，具体机型是否支持批量、走哪条通道未能核实。**

**已核实的机制层面事实：**
UEFI Secure Boot 的开关本身是一个固件配置项（存在 `SetupMode`/`PK` 相关变量里），
不是操作系统层面能直接改的东西——但 Linux 侧有个例外：`mokutil` 提供了一条
**从操作系统内部临时关闭签名校验**的路径（不等于修改固件的 Secure Boot 开关，
而是让 shim 对自己链下的东西不做校验），来源同上（Debian Wiki）：

```bash
sudo mokutil --disable-validation
# 会提示设置一个 8-16 位密码，重启后需要在固件的 MOK Manager 界面
# 逐字符输入该密码确认（这一步必须在物理机或有远程 KVM 的场景下完成，
# 纯 SSH 无法确认，因为固件界面在带外）
```

这条路径**不是**「批量改固件设置」，是「让已经跑起来的 shim+Linux 组合放行」，
且仍需要一次性的现场交互确认（見下方与任务 3 的交互代价对比）。
**它与本条问题「能否批量关闭 Secure Boot」不是同一件事**，
本条问题问的是**固件层面的开关**。

**真正的固件层面批量关闭要看两条通道，均未能核实是否被我们的机型支持：**

1. **BMC/Redfish 接口**：多数服务器级 BMC（iDRAC、iLO、XClarity 等）支持通过 Redfish
   `ComputerSystem` 资源的 `Boot.SecureBootEnable` 等字段远程改写，但**具体字段名与
   是否支持写操作因厂商固件版本而异**，本环境无法连到任何真实 BMC 核实
2. **固件配置工具的脚本化接口**（如 Dell 的 `racadm`、HPE 的 `conrep`/`iLOrest`）：
   同样因厂商而异

**待实机验证的步骤：**

```bash
# 若机器有 Redfish 接口（先确认 BMC IP 与凭据，示例用占位值）
curl -k -u USERNAME:PASSWORD \
  https://<BMC_IP_占位_必须替换>/redfish/v1/Systems/System.Embedded.1 \
  | grep -i securebootenable
# 预期：能看到当前 Secure Boot 状态字段；若该请求 404 或字段不存在，
# 说明这台 BMC 的固件版本不支持该字段，需查厂商文档核实等价路径
```

**若第 2 与第 3 个问题的答案是「能批量关且允许」，本 PoC 可以就此结束**（计划原文）。
这是本 PoC 里权重最高的一个待验证项。

### 问题 3：关闭 Secure Boot 是否被安全策略允许？

**这是一个组织流程问题，不是技术事实，本文档无法代答**——
需要问机房所属安全或合规团队：装机 VLAN（隔离网段，SPEC §1.5 前提）内、
装机窗口内临时关闭 Secure Boot，是否触发需要审批的合规条款。

**给运维的判断依据（计划原文的论证，已在此复述以便决策时引用）：**
装机 VLAN 是隔离的、装机过程本身受控，这个窗口内关闭 Secure Boot 的风险
远小于维护一整套三级签名链的复杂度与撤销风险（见 `05-结论.md`）。
但这是工程判断，最终仍需合规团队确认是否有强制性规定挡住这条路。

### 问题 4：固件是否支持向中间引导器的信任列表注册密钥？

**机制本身已核实（这就是 MOK，见上方背景机制），具体固件界面是否提供
该功能的入口未能核实**——理论上只要固件运行了 shim 提供的 MOK Manager
（`mmx64.efi` 等），这个能力就存在，但**要在目标机型的固件启动流程里
实际看到这个界面出现过一次**才能确认。

**待实机验证的步骤：**

1. 在一台目标机型上装好任意带 shim 的 Linux 发行版（Secure Boot 保持默认开启）
2. 执行 `sudo mokutil --import <任意测试用 .der 证书文件>`，设置一次性密码
3. 重启，**观察固件是否在启动过程中弹出一个蓝底文字界面，标题类似
   "Perform MOK management"**——这就是待核实的「固件是否支持」的直接证据：
   若从头到尾直接进了系统、没有出现这个界面，说明这台固件的启动链没有
   正确调用 shim 的 MOK Manager（可能是固件本身绕过了 shim，也可能是
   shim 版本或配置问题），需要进一步排查而不是直接判定「不支持」

**预期输出（正常情况下）：** 该界面会要求逐字符输入刚设置的一次性密码，
确认后选择 "Enroll the key"，之后再次重启即完成注册。

### 问题 5：厂商与型号的分布

**未能核实** —— 需要资产盘点数据。与问题 1 同一批脚本可以顺带采集：

```bash
sudo dmidecode -s system-manufacturer
sudo dmidecode -s system-product-name
sudo dmidecode -s bios-version
```

**这一项的价值：** 若机房只有一两种型号，后续任务（尤其任务 2 的中间引导器
兼容性验证、任务 3 的 MOK 注册流程验证）的范围会小很多——**只需要在
每种型号上各验一次，而不是每台机器验一次**。

**厂商固件差异已知会影响的点（来自本轮调研中反复出现的信号，
但没有查到能覆盖「所有厂商」的统一文档，标注未能核实）：**
Debian Wiki 提到 2024 年后的新机型可能只预置 "Windows UEFI CA 2023"
而不含旧的 "Microsoft Corporation UEFI CA 2011"（[来源同上](https://wiki.debian.org/SecureBoot)，
已核实存在这个已知问题，编号 `bug 1112197`）——这意味着若目标机型较新，
需要额外确认拿到的中间引导器（任务 2）是被哪个 CA 签的，两个 CA 签的
shim 不能互换假设兼容。

## 本任务的结论

**未能核实机房实际情况，无法在本文档里给出「继续 PoC」或「改用关闭流程」
中的最终选择**——这个选择依赖问题 1/2/3 的实机答案，而三者都指向
「需要在目标主机与 BMC 上实际操作」。

**给运维的行动项（按顺序）：**

1. 先跑问题 1、5 的采集脚本，得到「多少台、什么型号」
2. 挑 1-2 台代表性机型，跑问题 2 的 Redfish/racadm 探测
3. 若探测结果是「能批量关且合规允许」——**PoC 到此结束**，
   直接采用「装机时关 Secure Boot」的运维流程（该流程的具体步骤见
   `05-结论.md` 的「若改用关闭流程」一节），不必再看 02/03/04 三份文档
4. 若探测结果是「不能批量关，或合规不允许」——继续看 `02-中间引导器.md`

**本文档标注的所有「已核实」项均可直接复用**（MOK 机制、`mokutil` 命令语义、
db/dbx/PK/KEK 的角色）——它们不随机房具体情况变化，是继续 PoC 时的共同基础。
