# 04 目标 OS 内核的签名链

> **文档性质：** iPXE 加载内核时的验证机制——**已核实，直接读取 iPXE 源码得出，
> 带具体文件与行号**。这是本轮调研里最重要的一份，结论与计划原文预期的方向一致，
> 但机制细节比计划原文猜测的更明确、也更值得警惕。

对应计划：任务 4。

---

## 先说结论，再展开证据

**计划原文的猜测——「iPXE 的内核加载可能绕过固件的签名验证，因为它是
自己实现的加载器」——已核实为真，而且不是"可能"，是 iPXE 自己在源码
注释里明确写出来的设计决定，不是意外行为。**

**iPXE 会主动"拆除"shim 对下一跳（内核）的验证能力**，具体机制如下。

---

## 证据：iPXE 源码里的 shim 处理逻辑

**已核实，直接读取 iPXE 官方仓库源码**（`ipxe/ipxe` 仓库 master 分支，
本轮通过 `raw.githubusercontent.com` 取得并完整读取）：

### 第一步：iPXE 判断是否需要 shim

`src/image/efi_image.c`（已核实，第 273-280 行）：

```c
/* Use shim instead of directly executing image if applicable */
shim = ( efi_can_load ( image ) ?
     NULL : find_image_tag ( &efi_shim ) );
exec = ( shim ? shim : image );
```

**含义：** iPXE 先尝试判断目标镜像（比如一个 Linux 内核）能不能被固件
的标准 `LoadImage()` 直接接受。**如果不能**（最常见的原因就是 Secure Boot
开启且内核没有被固件信任的密钥签过），iPXE 才会去找一个叫 `shim` 的
镜像标签（也就是我们在 `02-中间引导器.md`/`03-签名与注册.md` 里处理的
那个 shim.efi），**把它当作真正要执行的对象**，让固件的 `LoadImage()`
去校验 shim（shim 是被信任的），再由 shim 内部去处理内核。

**这一步是标准链路，符合预期**，与计划原文描述的三级链一致。

### 第二步：iPXE 安装对 shim 的"特殊处理"

`src/image/efi_image.c`（已核实，第 337-343 行）：

```c
/* Install shim special handling if applicable */
if ( shim &&
     ( ( rc = efi_shim_install ( shim, device, &cmdline ) ) != 0 ) ) {
```

这一步调用的 `efi_shim_install()` 定义在 `src/interface/efi/efi_shim.c`
（已核实，完整文件已读取）。这个文件开头的注释直接说明了设计意图
（第 46-69 行，原文）：

> The UEFI shim is gradually becoming less capable of directly executing
> a Linux kernel image, due to an ever increasing list of assumptions
> that it will only ever be used in conjunction with a second stage
> loader binary such as GRUB... shim will erroneously complain if the
> image that it loads and executes does not in turn call in to the
> "shim lock protocol" to verify a separate newly loaded binary before
> calling ExitBootServices()... **Experience shows that there is
> unfortunately no point in trying to get a fix for this upstreamed
> into shim. We therefore default to reducing the Secure Boot attack
> surface by removing, where possible, this spurious requirement.**

**翻译要点：** shim 原本期望"自己的下一跳还会再调用一次 shim 的验证协议
（shim lock protocol）来验证*它自己*的下一跳"（这是 grub 的行为模式——
grub 加载 vmlinuz 前，会用这个协议再验证一次）。**但 iPXE 直接加载内核，
不会再调用这个协议**——而 shim 发现"没人调用验证协议"时会报错拒绝继续。
**iPXE 的解法不是去调用验证协议，是让 shim 认为验证协议已经被调用过了。**

### 第三步：具体怎么"拆除"——`efi_shim_unlock()`

`src/interface/efi/efi_shim.c`（已核实，第 145-185 行）：

```c
static void efi_shim_unlock ( void ) {
    ...
    /* Locate shim lock protocol(s) */
    bs->LocateHandleBuffer ( ByProtocol, protocol, NULL, &num_handles, &handles );
    /* Unlock each shim lock */
    for ( i = 0 ; i < num_handles ; i++ ) {
        efi_open ( handles[i], protocol, &lock );
        /* Unlock shim lock */
        lock->Verify ( empty, sizeof ( empty ) );
        ...
    }
}
```

**这就是核心动作：** shim 安装了一个叫 `EFI_SHIM_LOCK_PROTOCOL` 的接口
（GUID 已核实，见 `src/include/ipxe/efi/Protocol/ShimLock.h`，
`{0x605dab50, 0xe046, 0x4300, ...}`），这个接口只有一个函数 `Verify(buffer, size)`，
**本应是第二阶段引导器（如 grub）在加载*它自己的*下一跳（内核）前
调用一次，让 shim 帮忙做真正的签名校验**。

**iPXE 找到这个接口，然后传一个空指针、长度 0 去调用 `Verify()`**——
不是绕过它，是**直接调用它一次，用空数据"消费"掉它的调用义务**，
让 shim 认为"验证已经发生过了"，之后 shim 就不会再拦截、不会再检查
真正要执行的内核有没有被正确签名。

**触发时机**（`efi_shim_get_memory_map()`，第 264-293 行，已核实）：
iPXE 把这个"解锁"动作挂在了 `GetMemoryMap()` 这个 boot services 函数上——
`GetMemoryMap()` 是任何 EFI 程序在调用 `ExitBootServices()`（正式脱离
固件环境、开始跑操作系统）之前**必须调用的标准步骤**。iPXE 用这一点
作为"内核即将要正式启动了"的信号，在这个信号出现时执行解锁。

## 这意味着什么（对照计划原文的表格）

计划原文给了这张表：

| 情况 | 处理 |
|---|---|
| 目标 OS 是主流发行版 | 它的内核已被发行版签名... 可能可以直接工作 |
| 目标 OS 是自封装的镜像（P3-03） | 镜像里的内核要自己签，或保持发行版原样的内核 |

**已核实的事实推翻了这张表的前提**——不管内核有没有被正确签名，
**iPXE 都不会真的去检查**。具体展开：

- **若目标 OS 是主流发行版、内核确实被发行版正确签过**：能正常启动，
  表面上"看起来"验证生效了，但那只是因为内核恰好是合法的，
  不是因为 iPXE 真的验证了它——**换一个没签名的内核，一样能启动**
- **若目标 OS 是自封装镜像、内核没签名或签名不对**：**同样能正常启动**——
  iPXE 不会因为内核没签名而拒绝加载

**这正是计划原文担心的"意外"，已核实确实如此：
Secure Boot 在内核这一级实际上是失效的。**

## 这个失效的边界在哪里（不要过度推论）

**已核实仍然生效的部分：**

1. **shim.efi 本身的加载**——固件对 shim 的验证是标准的 `LoadImage()`/
   `StartImage()` 路径，iPXE 没有、也无法绕过这一步（这一步发生在
   iPXE 本身获得控制权**之前**，是固件直接做的）
2. **iPXE.efi 本身的加载**——同理，固件（或链载它的第一级 shim）验证
   iPXE 二进体的签名，这一步 iPXE 无法对自己动手（`03-签名与注册.md`
   处理的正是这一级）
3. **内核启动后，Linux 内核自己的 lockdown 模式**——这是完全独立于
   固件校验之外的另一层机制（[Debian Wiki](https://wiki.debian.org/SecureBoot)，
   已核实）：当内核检测到自己是在 Secure Boot 模式下启动的（这个检测
   与"是否真的被验证过签名"无关，只看 UEFI 变量里的 Secure Boot 状态），
   会自动进入 lockdown 模式，**限制加载未签名的内核模块、禁用 kexec 到
   未签名内核、禁止用户态直接访问物理内存/IO 端口等**。**这一层不受
   本文档描述的"iPXE 解锁"影响，因为它是内核自己检测状态后的行为**，
   不依赖 shim 是否真的验证过它

**已核实失效的部分：**

- **"固件确认这个具体内核二进制真的被信任的密钥签过"这一步验证本身**——
  iPXE 让它形同虚设

**结论怎么表述才准确：** 不是"Secure Boot 在这个系统上完全没用"，
是"**固件对内核二进本身的签名校验被 iPXE 绕过了，但内核启动后的
lockdown 限制依然生效**"——两者是不同层面的保护，不要混为一谈。

## initrd 是否在验证范围内

**已核实，答案是同一套逻辑覆盖 initrd**——从 `efi_image.c` 的调用路径看，
`efi_shim_install()` 是在"加载一个 EFI 镜像"的通用路径上触发的，
initrd 本身不是一个独立的 EFI 可执行镜像（它是内核通过 `initrd=` 参数
或 UEFI 的 `LINUX_EFI_INITRD_MEDIA_GUID` 机制接收的数据），
**不经过 `LoadImage()`/shim 验证这条路径，从设计上就不在"签名验证"
的范围内**——这与是否使用 iPXE 无关，是 Linux/shim 生态本身的既有设计
（initrd 的完整性理论上依赖内核自身对 initrd 内容的信任，而不是
Secure Boot 链）。**这一条不是"未能核实"，是"该问题的前提本身在这套
生态里就不成立"**——initrd 从来不是签名验证链的一环。

## 待实机验证的部分

**上述全部结论来自源码分析，属于"设计上会发生什么"，但没有在真机上
观察到实际的启动过程与固件日志。**

**待实机验证的步骤：**

```bash
# 用一个故意没签名（或签名错误）的测试内核，走完整链路
# 固件 -> shim -> iPXE -> 这个内核
# 若上述分析正确，预期结果是：内核正常启动，没有任何 Secure Boot 报错
```

**预期观察点：**

1. 启动过程中不应出现任何 "Security Violation" 或等价错误
2. 内核启动后，`dmesg | grep -i secureboot` 或 `mokutil --sb-state`
   应仍显示 Secure Boot 为 enabled（**固件状态没变，只是这一级验证被
   跳过了，不是 Secure Boot 被关闭了**——这个区分很重要，向运维汇报时
   不要说成"Secure Boot 失效了"，要说"内核签名这一级校验被绕过了"）
3. 若内核确实支持 lockdown（多数现代发行版默认开启），`dmesg | grep -i lockdown`
   应能看到 lockdown 已生效的迹象，即使内核本身没被正确签名过
