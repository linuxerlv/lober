## 先纠正计划原文的一处假设

计划原文写的链路方向是「固件 → 一个被微软签过的中间引导器 → 自签的 iPXE →
目标 OS 的内核」，把 shim 当作**固件信任的第一跳、直接链载我们的 iPXE**。

**实机机制与这个假设一致，但有一个更省事的变体需要先排除**——
iPXE 官方从 2026-03-06 起在其文档站发布了**预编译且已签名**的 shim+iPXE 组合
（[ipxe.org/secboot](https://ipxe.org/secboot)，已核实，页面标注最后修改日期
2026/03/06 14:59）：

```
ipxeboot/x86_64-sb/
├── ipxe.efi          （iPXE 主体，签名覆盖在 ipxe-shim.efi 的信任链下）
├── ipxe-shim.efi      （微软签过的 shim，DEFAULT_LOADER 编译时已指向 ipxe.efi）
├── shimx64.efi
├── snponly.efi
└── snponly-shim.efi
```

DHCP 直接发 `ipxe-shim.efi` 的路径即可，**它会自动链载同目录下的 `ipxe.efi`，
不需要生成密钥、不需要签名、不需要 MOK 注册**（已核实，同上来源，release
资产地址 `github.com/ipxe/ipxe/releases/latest/download/ipxeboot.tar.gz`
本轮已用 `curl -I` 核实为真实存在的下载链接，302 重定向到具体版本 tag）。

**但这条路径对本项目不适用**，原因是这份预编译二进制**明确不能定制**
（同一来源原话：「You cannot build your own version of iPXE with the precise
features that you need, because UEFI Secure Boot is specifically designed
to stop you from doing that」）——而 SPEC §1.5 与 P4-02 计划要求的
`TRUST=` 嵌入内网 CA 是一次**必须自定义构建**的操作。**所以本项目绕不开
自签 + MOK 注册这条路**，02/03 两份文档仍按计划原文的假设继续。

**这个排除本身是有价值的信息**：如果将来某个子系统只需要跑官方无改动的
iPXE（不需要嵌自己的 CA、不需要自定义协议支持），官方预编译组合是
零成本的选项，应优先使用而不是走自签流程。

## 要验证的三件事

### 1. 从哪里获取被微软签过的中间引导器？

**已核实：** shim 是一个独立的开源项目（[rhboot/shim](https://raw.githubusercontent.com/rhboot/shim/main/README.md)），
不是某个发行版专属的东西。它的角色（shim 自己的 README 原文，已核实）：

> shim is a trivial EFI application that, when run, attempts to open and
> execute another application... it will then validate the binary against
> a built-in certificate. If this succeeds and if the binary or signing key
> are not forbidden then shim will relocate and execute the binary.

**获取渠道有两种，均已核实存在：**

| 渠道 | 具体形态 | 是否被微软签过 |
|---|---|---|
| 发行版包 | Debian 的 `shim-signed`、RHEL/Fedora 同名思路的包 | 是——包本身就是被微软签过的二进制，发行版负责在其内嵌入自己的 CA 证书（[Debian Wiki](https://wiki.debian.org/SecureBoot)：「a small UEFI loader called shim which is signed by Microsoft and embeds Debian's signing keys」，已核实） |
| 自建 | 从 shim 源码 `make VENDOR_CERT_FILE=pub.cer` 编译（[shim BUILDING 文档](https://raw.githubusercontent.com/rhboot/shim/main/BUILDING)，已核实） | **否**——自建的 shim 不会被微软签名，等于没解决问题，只是把「谁的 shim 被信任」这个问题换了个位置。**shim 项目的审查与签名流程由 Microsoft/各发行版把关，个人或小团队自建 shim 拿不到微软签名** |

**结论：本项目必须用发行版包提供的、已经被微软签过的 shim 二进制**，
不能自己编译 shim（编译 shim 只在「我们自己就是一个被微软认可的发行版/
厂商」的场景下有意义，那不是本项目的情况）。

**核心待验证问题——拿发行版 A 的 shim 去链载我们的 iPXE 是否可行：**

**已核实的机制（来自 shim 源码 `shim.c`，本轮直接读取并核对）：**
shim 决定「下一跳加载谁」靠一个叫 `second_stage` 的变量，赋值逻辑是：

```c
// shim.c 第 490 行，已核实
second_stage = (optional_second_stage) ? optional_second_stage : DEFAULT_LOADER;
```

`DEFAULT_LOADER` 是**编译时常量**，按架构分别是（`shim.h`，已核实）：

| 架构 | `DEFAULT_LOADER` 编译期默认值 |
|---|---|
| x64 | `\grubx64.efi` |
| ia32 | `\grubia32.efi` |
| aa64 (ARM64) | `\grubaa64.efi` |
| arm | `\grubarm.efi` |
| riscv64 | `\grubriscv64.efi` |

发行版打包 shim 时通常**不改这个编译期常量**（它是 grub 生态的产物），
意味着一个 Debian 的 `shim-signed` 二进制默认只会去找同目录下的
`grubx64.efi`，**不会自动找我们的 iPXE**。

**`optional_second_stage` 的来源（已核实，`shim.c` 第 942-993 行）：**
它不是编译期常量，是**运行时从 shim 同目录下的 `options.csv` 文件读出的**——
该文件第一个逗号前的字段就是要加载的第二阶段文件名。

**这意味着我们有两条路径，不需要重新编译发行版的 shim：**

| 路径 | 做法 | 代价 |
|---|---|---|
| A：改名 | 把我们的 `ipxe.efi` 直接改名为 `grubx64.efi`（对应架构），放在 shim 同目录 | 简单，但文件名与内容不符，排查时容易让人以为装的是 grub |
| B：`options.csv` | 在 shim 同目录放一个 `options.csv`，内容首字段写 `ipxe.efi`（真实文件名） | 更清晰，且是 shim 官方支持的机制，**推荐这条** |

**待实机验证的步骤：**

```bash
# 前置：已有一台目标机型，UEFI Secure Boot 保持开启
# 1. 从发行版仓库拿到已签名的 shim（示例用 Debian 命名，实际按目标发行版调整）
#    文件通常在 /usr/lib/shim/ 或类似路径，具体位置随发行版而异
# 2. 把我们的自签 iPXE（03-签名与注册.md 产出）与 options.csv 放进同一目录：
mkdir -p /srv/tftp/secureboot/
cp /path/to/shimx64.efi /srv/tftp/secureboot/BOOTX64.EFI
cp /path/to/ipxe.efi     /srv/tftp/secureboot/ipxe.efi
printf 'ipxe.efi\n' > /srv/tftp/secureboot/options.csv
# 3. DHCP 指向 BOOTX64.EFI（即 shim），让 shim 去读 options.csv 找到 ipxe.efi
```

预期结果（若一切工作正常）：机器 PXE 启动后，先看到 shim 加载
（可能一闪而过，不一定有明显提示），随后应该看到 iPXE 自己的启动横幅
（`iPXE initialising devices...` 之类）。若卡在黑屏或直接报
`Security Violation`，说明验证在这一跳失败——**这正是任务 3 要处理的
「iPXE 还没被签名/密钥还没注册」的预期失败**，不代表 shim 侧配置错了。

### 2. 它的版本与固件的撤销列表

**已核实的机制：** shim 的撤销走两条路（[shim SBAT.md](https://raw.githubusercontent.com/rhboot/shim/main/SBAT.md)，
已核实）——传统的 `dbx`（按二进制哈希或证书撤销）与较新的 SBAT
（按「生成号」撤销，同一签名密钥下的旧版本可被整体标记为不再信任而不需要
逐个哈希）。

**已核实的历史撤销记录**（[shim SbatLevel_Variable.txt](https://raw.githubusercontent.com/rhboot/shim/main/SbatLevel_Variable.txt)，
项目官方维护的撤销记录文件，已核实）——过去四年发生过至少 8 次 shim/grub
生成号提升，对应多个 CVE：

| 日期 | 触发的 CVE |
|---|---|
| 2022-05-24 | CVE-2022-28737（shim）等 |
| 2022-11-15 | CVE-2022-2601、CVE-2022-3775（grub） |
| 2023-01-29 / 01-29-50 | Debian grub 补丁遗漏 + 一个未公开利用的 shim bug |
| 2023-09-19 | CVE-2023-4692、CVE-2023-4693（grub ntfs 模块） |
| 2024-01-09 | CVE-2023-40546 至 40551（shim 六个 CVE 一起修） |
| 2024-04-09 | 多个累积修复 |
| 2025-02-18 | 2025 年 2 月 grub CVE |
| 2025-05-10 | Proxmox 专用 grub 问题 |

**结论：撤销不是理论风险，是历史上大约每 3-6 个月发生一次的真实事件**——
这个频率是 `05-结论.md` 评估维护成本时的关键依据。

**待实机验证的步骤（确认拿到的具体版本没被撤销）：**

```bash
sudo mokutil --list-sbat-revocations 2>/dev/null || echo "该 mokutil 版本可能不支持此选项，改用："
# 或读取当前固件里的 SbatLevel 变量原始内容比对
sudo mokutil --list-enrolled
```

预期输出应能看到当前固件接受的最低生成号；将其与目标 shim 二进制自身的
`.sbat` 段（`objcopy -O binary --only-section=.sbat shimx64.efi /dev/stdout`）
比较，若二进制声明的生成号低于固件已强制的最低值，加载会被拒绝——
这个比较本身就是「确认没被撤销」的操作性定义。
