# 05 综合结论与建议

> **文档性质：** 本文档是对 01-04 四份文档的综合判断，判断本身基于
> 已核实的机制事实与已核实但需实机验证的开放问题两部分。**可行性结论
> 依赖 01 里未能核实的机房实际情况**——本文档给出的是「若机房情况如此
> 则如何判断」的条件性结论，不是一个不依赖实机数据的最终判决。

对应计划：任务 5。

---

## 一、可行性结论

**三级签名链本身机制上走得通（02/03/04 已逐项核实），但代价大概率不可接受，
除非 01 里未能核实的「批量注册替代路径」被证实存在。**

分层给出判断：

| 层级 | 是否走得通 | 依据 |
|---|---|---|
| shim 的获取与链载 iPXE | **走得通** | 02：用发行版签名包 + `options.csv`，不需要重新编译 shim |
| iPXE 的自签名 | **走得通** | 03：`sbsign` 命令确定，2048 位 RSA 密钥 |
| 密钥注册进固件 MOK 列表 | **走得通，但强制逐台交互** | 03：MOK 确认按协议设计要求物理/带外控制台确认，**这是故意如此设计的，不是可以优化掉的实现细节** |
| 内核这一级的实际保护 | **形同虚设** | 04：iPXE 主动解锁 shim 的验证接口，内核签名是否正确不影响能否启动 |

**把这四层合起来看，得到的画像是：**
我们会付出「维护一整套证书生成、签名工具链、逐台 MOK 交互确认」的
完整成本，**换来的却是内核这一级实际上没有验证**——固件确实会拒绝
未经我们密钥签名的 iPXE 二进体本身，但一旦 iPXE 跑起来，它能加载
任何内核，不管内核签没签。

**这不是「走不通」，是「走得通但收益与代价不成比例」**——
计划原文列出的三种结局里，这属于第二种：**走得通但代价不可接受**。

## 二、若走得通，完整的部署流程（供参考，不建议直接实施）

1. 从目标发行版仓库取已签名的 shim 二进体（不自建）
2. 生成一对 2048 位 RSA 签名密钥（`03-签名与注册.md` 步骤 1），私钥离线保存
3. 每次编译 iPXE 后（与 P4-02 共用编译动作，见下方「衔接」一节），
   用 `sbsign` 签名产出的 `ipxe.efi`（`03-签名与注册.md` 步骤 2）
4. 部署 TFTP 目录：shim 二进体改名为固定引导文件名（如 `BOOTX64.EFI`），
   同目录放 `options.csv`（内容为真实的 iPXE 文件名）与签名后的 `ipxe.efi`
5. DHCP 配置指向 shim 二进体的路径
6. **每台新机器上架时**：装机前或装机中，人工（或远程 KVM 会话）完成
   一次 `mokutil --import` + 重启确认 MOK Manager 界面的交互操作
   （`03-签名与注册.md` 步骤 3 的完整流程）
7. 验证：一台目标机型上完整走通「固件 → shim → 自签 iPXE → 目标内核」

**第 6 步是这个流程里唯一不能自动化的环节**，且发生频率等于新机器
上架频率——如果装机是这套系统存在的核心目的（本项目就是），
**这一步的存在直接削弱了自动化装机的价值**。

## 三、维护成本评估

### 密钥轮换时要做什么

签名密钥（区别于 P4-02 的 TLS CA）一旦生成，**理论上可以长期使用**——
它不像 TLS 证书那样有强制有效期，MOK 本身没有到期机制。
真正触发轮换的场景是**私钥疑似泄露**：一旦泄露，需要生成新密钥对，
重新签名所有 iPXE 二进体，**并在每台已注册旧密钥的机器上重新走一次
第 6 步的交互注册**——这个成本与「新机型上架」同量级，但触发原因是
安全事故而非计划内的维护窗口，往往需要在更紧迫的时间压力下完成。

### 新机型上架时要做什么

若新机型的固件版本较新（2024 年后，见 `01-机器事实.md` 提到的
"Windows UEFI CA 2023" 问题），**需要先确认拿到的 shim 是被哪个 CA
签的**——若只有旧 CA 签名而新机型固件只预置了新 CA，会在第一层
（shim 加载）就失败，需要额外操作补充 CA（`01-机器事实.md` 已给出
对应的核对步骤）。这是一个新增的、计划原文没有预见到的排查维度。

### 中间引导器被撤销时要做什么（计划原文点名的"最麻烦"一项）

**`02-中间引导器.md` 已用官方撤销记录证实这不是假设性风险**——
过去四年（2021 至 2025）有据可查的 shim/grub 生成号提升发生了至少
8 次，平均每 3-6 个月一次。**一旦我们依赖的 shim 版本被撤销**：

1. 所有依赖它的机器，下次开机时会在固件层直接拒绝加载 shim
   （这一步是固件强制的，不因为我们后面几级配置对不对而改变）
2. **这个撤销由厂商推送的固件更新带来，不在我们控制范围内**——
   我们既不能阻止撤销发生，也不能提前很久预知具体撤销时间
3. 应对手段只有：**提前跟踪 shim 项目的撤销公告**（订阅
   [rhboot/shim 仓库](https://github.com/rhboot/shim) 的 release 通知，
   或定期检查 `SbatLevel_Variable.txt` 是否有新记录），在撤销正式推送前
   主动升级到未被撤销的 shim 版本——**这是一项需要持续投入的运维工作，
   不是一次性配置**

**这是本方案里唯一「后果影响所有机器、且不受我们控制」的风险点**——
其他风险（密钥泄露、MOK 交互）都是我们能主动管理节奏的，撤销不是。

## 四、建议

**建议：改用关闭 Secure Boot 的装机流程（计划原文列出的三种结局的第 2 种）。**

**理由的权重排序：**

1. **内核这一级验证形同虚设是决定性因素**——如果三级链的最后一跳
   本来就不提供实质保护，那么维护整条链的意义主要剩下「让 shim 与
   iPXE 这两跳的完整性可信」，但这个收益不足以抵消「每台机器强制
   一次交互注册」与「撤销时全员遇险」两项成本
2. **MOK 交互注册与自动化装机的目标直接冲突**——这是本项目存在的
   核心价值主张，不应该为了一项实际保护有限的功能而妥协
3. **iPXE 项目自己的官方立场也支持这个方向**——iPXE 官方文档
   （[ipxe.org/secboot](https://ipxe.org/secboot)，已核实）原话：
   「UEFI Secure Boot is primarily a form of pay-to-play security theatre...
   Enabling UEFI Secure Boot does not prevent malicious code from running
   on your system, but does prevent you from building and running your
   own code on your system.」——这不是我们的一家之言，是维护这套
   生态最深的项目给出的评价

**若 `01-机器事实.md` 里未能核实的「批量注册替代路径」被证实存在**
（比如某个 BMC 真的支持通过 Redfish 批量写入 MOK 等价列表），
**结论需要重新评估**——那会消除本建议里权重最高的第 2 项理由，
届时可以只针对「内核验证形同虚设」这一项单独权衡是否仍要放弃。

### 若采用关闭流程：具体做法

**装机前关闭：** 走 `01-机器事实.md` 问题 2 探索的 BMC/Redfish 或
厂商配置工具路径（本环境未能核实具体机型是否支持，需运维在真实
BMC 上核实并固化成脚本）。

**装完后是否开启——需要验证的点（计划原文特别要求）：**
若关闭 Secure Boot 装完系统后重新打开，**已装好的系统能否正常启动**
取决于目标系统本身的 bootloader 有没有被正确签名——若目标发行版
用的是标准的、已签名的 grub+shim 组合（多数主流发行版默认如此），
重新开启后能正常启动；**若目标是本项目 Phase 3 提到的自封装镜像
且没有走标准的 shim/grub 链**，重新开启 Secure Boot 后**可能直接
无法启动**（因为这个镜像的 bootloader 从未被设计为在 Secure Boot
下运行）。**这一条本身是一个待实机验证的具体问题**：

```bash
# 待实机验证：
# 1. 关闭 Secure Boot，装机（走本系统正常装机流程）
# 2. 装完后重新开启 Secure Boot
# 3. 重启，观察是否正常进入系统
# 预期：主流发行版应正常启动；自封装镜像需单独验证
```

**批量操作方式：** 与 `01-机器事实.md` 问题 2 是同一个技术问题——
批量关闭 Secure Boot 与批量开启是对称的操作，用同一套 BMC/Redfish
或厂商工具路径，只是改写的字段值相反。

## 五、与本项目的衔接：避免与 P4-02 各做一遍

**SPEC §1.5 决定 MVP 不上 TLS 的理由原文：** 「HTTPS 在这套栈里最贵的
部分是 iPXE 需重新编译（带 crypto、用 TRUST= 嵌内网 CA），之后每次
证书轮换都要重编重发引导文件，**叠加 Secure Boot 签名链后风险与
工期都显著上升**。」

**已核实的交集边界（`03-签名与注册.md` 已展开，此处总结结论）：**

**共享的部分：**

1. **编译动作本身**——P4-02 任务 4 要求「iPXE 需重新编译」以支持
   `DOWNLOAD_PROTO_HTTPS` 与嵌入 TLS CA；本 PoC 若走三级链方案，
   同样需要一个自定义编译的 iPXE（因为官方预编译的 Secure-Boot 版本
   明确不可定制，`02-中间引导器.md` 已核实并排除这条捷径）。
   **两者对"需要一台能编译 iPXE 的外网机器、需要维护构建脚本"这件事
   是完全同一份基础设施**，不需要分别搭建
2. **二进体分发与版本管理**——P4-02 任务 4 已经要求记录自编 iPXE 二进体
   的 sha256（因为不能从官方下载处复核）；若同时叠加本 PoC 的签名，
   还需要额外记录签名证书指纹——**这是同一份"自编二进体台账"上的
   两个字段，不是两份独立台账**

**不共享、必须分别处理的部分（`03-签名与注册.md` 已用表格核实）：**

1. **密钥本身不同**——TLS CA 密钥与 Secure Boot 签名密钥是两套独立的
   密钥材料，**不能合并、不能互相替代**，混淆会造成排查困难（这正是
   计划原文特别要求记录清楚的一点）
2. **嵌入方式不同**——`TRUST=` 是把 CA 指纹编译进二进体内部
   （iPXE 自己的信任列表）；Secure Boot 签名是对编译产物这个 PE 文件
   做外部签名（`sbsign`），**签名动作发生在编译完成之后，是两个独立的
   构建步骤，不是同一条 make 命令能同时做完的**

**给两边实现者的具体建议：** 若 P4-02 与本 PoC 的后续实现计划（如果
建议是"实施"）分别派给不同的人或不同的会话执行，**至少让"自编 iPXE
的编译脚本与产出物存放位置"这一份基础设施只建一次、两边共用**，
不要各自重复搭建一套编译环境。

## 六、这个 PoC 花了多少时间

**本次调研（不含目标主机实机验证部分）：**

- 阅读计划、SPEC 相关章节、文件系统契约：约 15 分钟等效工作量
- 通过 curl 抓取并阅读的一手来源：shim 项目（README/BUILDING/SBAT.md/
  SbatLevel_Variable.txt/ShimLock.h/shim.c/shim.h 源码本身）、mokutil
  项目、Debian Wiki SecureBoot 页面、iPXE 项目源码
  （efi_shim.c/efi_shim.h/efi_image.c/crypto.h）与官方文档
  （ipxe.org 的 secboot/crypto/cmd:shim/appnote:buildtargets 四页）、
  iPXE 官方 threat model 文档，共约 20 次网络请求，多数一次成功，
  少量因路径猜测错误或 api.github.com 限流需要重试
- 撰写五份文档：约 40 分钟等效工作量

**没有发生的、原本可能耗费大量时间的环节：**
因为本环境无法实机验证，跳过了「实机测试失败后反复排查配置」这个
通常最耗时的环节——**这意味着实际投入远小于一次完整的、带实机验证
的 PoC**。真正的时间成本集中在两处，供未来参考类似"技术风险最高"项目：

1. **读一手源码定位到具体机制的时间，远小于查阅二手教程的时间**——
   本次最关键的发现（iPXE 主动解锁 shim 验证接口）来自直接读
   `efi_shim.c` 的 400 行源码与注释，而不是任何教程或博客
2. **官方项目自己的立场声明（iPXE 的 threat model 与 secboot 页面）
   比工程判断更有说服力**——若只靠工程经验判断"这条链可能不牢固"，
   说服力远不如引用维护者自己写的"这是故意这样设计的"

**给运维的时间参考：** 若走完整实机验证路径（每层都要在真机上测一遍，
且第 3 层的 MOK 交互确认无法脚本化加速），预计比本次纯文档调研
多消耗数倍时间，**且很大程度取决于机房里能拿到多少台不同型号的
测试机**——型号越多，02/03 两层要重复验证的次数越多。
