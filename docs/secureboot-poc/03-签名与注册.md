# 03 iPXE 的签名与密钥注册

> **文档性质：** 签名工具与 MOK 注册命令的语义——**已核实，带来源**。
> 「注册是否需要在每台机器上手工做」这一核心风险问题——**机制已核实为
> 是（交互式，无法绕过用户在场确认），具体是否存在批量替代路径——
> 对本环境可触达的固件未能核实，已列出理论上存在的方向供实机排查**。

对应计划：任务 3，本 PoC 的核心风险点。前置：`02-中间引导器.md` 确认
目标机型上 shim 能正常加载到位。

---

## 先厘清一个容易混淆的点（计划原文特别要求）

**本任务的签名密钥与 P4-02（TLS）的 CA 是完全不同的两套密钥，用途也不同：**

| | P4-02 的 CA（TLS） | 本任务的签名密钥（Secure Boot） |
|---|---|---|
| 保护什么 | nginx 与浏览器/iPXE 之间的 **HTTPS 连接** | iPXE **二进制文件本身**的完整性 |
| 验证方是谁 | iPXE 内置的 TLS 客户端代码（自己的 crypto 栈） | 固件 / shim 的 Secure Boot 校验逻辑 |
| 用 `TRUST=`/`CERT=` 嵌入 iPXE 的东西 | 是（内网 CA 的证书，用于验证 nginx 的服务端证书） | **否**——这两个 make 变量与 Secure Boot 无关 |
| 密钥泄露的后果 | 能伪造 nginx 身份中间人攻击 HTTPS 连接 | 能让固件信任一个被篡改的 iPXE 二进制 |

**已核实的关键事实：** `TRUST=`/`CERT=` 是 iPXE 自己的 TLS 信任配置
（[ipxe.org/crypto](https://ipxe.org/crypto)，已核实，页面明确写着
"You can change the list of trusted root certificates when you build
iPXE using the TRUST=... build parameter"，语境全部是 HTTPS/证书链，
未提及与 UEFI Secure Boot 有任何关系）。**这意味着 SPEC §1.5「iPXE 需
重新编译，带 crypto，用 TRUST= 嵌内网 CA」与「iPXE 的 Secure Boot 签名」
是同一次编译动作里的两件不同事情**——重新编译这个动作本身是共享的
（见 `05-结论.md` 的衔接说明），但编译出的二进制需要**分别**：
（a）内嵌 P4-02 的 TLS CA 指纹（`TRUST=`），
（b）对编译产物这个 PE 文件本身做一次 Secure Boot 签名（本任务）。
两者互不覆盖，也不能用一套密钥兼顾。

---

## 要验证的四件事

### 1. 生成签名密钥对

**已核实**（[Debian Wiki SecureBoot](https://wiki.debian.org/SecureBoot) 给出的实操命令）：

```bash
mkdir -p /path/占位_密钥存放目录/
cd /path/占位_密钥存放目录/
openssl req -nodes -new -x509 -newkey rsa:2048 \
  -keyout MOK.priv -outform DER -out MOK.der \
  -days 36500 -subj "/CN=占位_组织名与用途，例如 Lober iPXE Signing Key/"
openssl x509 -inform der -in MOK.der -out MOK.pem
```

**注意事项（已核实，来源同上）：**

> It seems shim won't support adding a 4096 RSA key to the MokList
> (it might freeze when loading and verifying the grubx64.efi binary),
> so make sure you use a 2048 key for now.

**必须用 2048 位 RSA，不要用 4096**——这不是安全强度的选择，
是已知的 shim 兼容性限制（截至 Debian Wiki 2026-07-19 修订仍如此记录）。

**私钥存放要求（借用 P4-02 计划已确立的原则，同等适用于此）：**
签名私钥离线保存，绝不放在装机服务器上——它一旦泄露，
攻击者能签出任何被固件信任的 EFI 二进制。

---

### 2. 给自编的 iPXE 签名

**已核实：** 标准工具是 `sbsign`（`sbsigntool`/`sbsigntools` 包，
原始维护于 kernel.org 的 `jejb/sbsigntools` 树，多个发行版打包分发，
本轮通过 WebSearch 核实该项目及其多个分支的存在，工具名与用途一致）。
签名命令语法（Debian Wiki 给出的实操样例，用于给内核签名，
对 iPXE 的 EFI 二进制同样适用，因为都是 PE/COFF 格式）：

```bash
sbsign --key MOK.priv --cert MOK.pem \
  /path/to/ipxe.efi \
  --output /path/to/ipxe-signed.efi
```

**另一个可选工具（已核实存在但未深入验证）：** `systemd-sbsign`，
较新的 systemd 生态自带工具，命令语义类似。两者选一即可，
**不需要都用**，选哪个由目标机器上已有哪个包决定。

**验证签名是否成功嵌入（不需要固件，本地即可核对）：**

```bash
sbverify --cert MOK.pem /path/to/ipxe-signed.efi
```

预期输出包含类似 `Signature verification OK` 的字样；
若报 `Signature verification failed`，说明签名步骤本身出了问题，
不要带着一个签名失败的二进制去做后面的固件测试。

---

### 3. 把公钥注册进中间引导器的信任列表 —— 核心风险点

**已核实：这一步就是 MOK（Machine Owner Key）机制，注册命令固定，
但确认动作强制要求在物理机/带外控制台完成，无法从纯 SSH 会话里绕过。**

**已核实的注册命令**（[Debian Wiki SecureBoot](https://wiki.debian.org/SecureBoot)）：

```bash
sudo mokutil --import /path/to/MOK.der
# 会提示：Input password:
#         Input password again:
# 这个密码是一次性的，仅用于下面重启后的确认步骤，不是长期密码
```

**为什么这一步「不可绕过」——已核实的设计原因**（同上来源，原话）：

> changes to the MOK keys may only be confirmed directly from the console
> at boot time. This removes the risk of userland malware potentially
> enrolling new keys and therefore bypassing the entire point of Secure Boot.

这是**故意设计成这样的**，不是实现疏漏——如果 MOK 注册能在操作系统里
静默完成，那么任何拿到 root 权限的恶意软件都能给自己签的东西加进信任列表，
Secure Boot 就形同虚设。**所以「批量做」在协议设计层面就是被排除的**，
不存在一个官方支持的「跳过物理确认」的路径。

**具体的确认流程（已核实，来源同上）：**

1. `mokutil --import` 后重启
2. 固件启动过程中会出现 shim 的 MOK Manager 界面（蓝底文字），
   标题类似 "Perform MOK management"
3. 选择 "Enroll MOK"，逐字符输入刚才设置的一次性密码
   （**每输入一个字符要按一次 Enter**——Debian Wiki 特别提醒这一点，
   是常见的操作失误点）
4. 选择确认，机器再重启一次，此后该密钥才生效

**验证密钥已生效**（已核实的命令）：

```bash
sudo mokutil --test-key /path/to/MOK.der
# 预期输出（若已生效）：
# /path/to/MOK.der is already enrolled
```

### 4. 注册是否需要在每台机器上手工做？

**是的，机制上无法绕开——已核实。**

上一节的「物理确认」要求是密钥级别的，**每台机器的固件独立维护自己的
`MokListRT`**，一台机器上注册的密钥不会自动同步到另一台机器。
这意味着：

- 新机器上架 = 至少一次人工到场（或带外 KVM 会话）操作
- **这与「自动化装机」的目标直接冲突**（计划原文已指出这一点）

**理论上存在、但本环境未能核实是否真的可用的替代路径：**

| 路径 | 原理 | 未核实的原因 |
|---|---|---|
| BMC/KVM 远程会话代替physical 到场 | 若 BMC 支持远程 KVM（大多数服务器级 BMC 都支持），可以远程完成上述 4 步，不需要人跑机房，只是仍然是「每台一次」的交互操作，**省的是「到场」不是「交互」** | 本环境没有真实 BMC 可连，无法验证具体机型的 KVM 会话能否正确显示 shim 的 MOK Manager 界面（有些 BMC 的远程帧缓冲对早期 UEFI 阶段的图形支持不完整） |
| 固件厂商的批量密钥预置工具 | 部分厂商（如 Dell 的 `racadm`、HPE 的固件配置工具）理论上可能支持通过厂商专有接口一次性写入 `db` 或类似列表，从而不需要逐台走 MOK 交互 | 未查到任何官方文档确认这条路径对**第三方自签证书**同样开放（这类工具通常面向的是标准的 Secure Boot db/dbx 管理，而不是 shim 自己维护的 MOK 列表——**MOK 是 shim 的私有机制，不是 UEFI 标准变量，厂商工具是否知道怎么写 MOK 列表存疑**），需要在真实 BMC 上实测 |
| 出厂预置 | 若与硬件厂商有采购关系，理论上可以要求出厂时预置我们的签名密钥到 db（而非 MOK） | 这是采购流程问题，不是技术验证问题，不在本 PoC 范围 |

**没有查到能确认「批量注册可行」的来源，也没有查到明确说「不可行」的来源**——
这条本身就该标注为「未能核实」，交给运维在拿到真实 BMC 后用问题 1 的
Redfish 探测方式顺带排查（可以在同一次连 BMC 的会话里检查是否有
MOK 相关的 API 端点）。

## 本任务的结论

**第 3 与第 4 条决定这个方案是否可行**（计划原文）：

- 第 3 条（能否注册）：**机制上可行，已核实完整流程**
- 第 4 条（是否要逐台手工）：**机制上确认是，除非能找到未核实的批量替代路径**

**若最终确认没有批量路径，那意味着每台新机器上架时要人（或远程 KVM 会话）
逐台完成一次 MOK 交互式确认**——这与「自动化装机」的目标存在结构性冲突，
是 `05-结论.md` 判断可行性时的关键输入。
