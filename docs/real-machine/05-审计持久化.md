# 05 审计持久化：从「只写进程日志」到「落库可查」

> 本文档记录 P2-audit 这次契约变更：修补 SPEC §9.4 审计能力的两层缺口。
> 依据：SPEC §9.4；`internal/core/contract/store.go` 的 `AuditStore` 类型
> 文档；`docs/contracts/http-console.md`「变更记录 2」。

## 缺口是什么，为什么比表面看到的更深

`docs/contracts/http-console.md` 的「变更记录 1」（补 `POST /hooks/{id}/reject`
那一次）已经记录了一层缺口：驳回理由只在驳回发生的**当次响应**里可见，
作者若当时不在场就永远查不到。但那条记录本身低估了问题的深度——它说
「审计日志本来就没有读接口」，暗示只缺一个查询端点。核实后发现还有
**第二层、更根本的缺口**：

`cmd/lober/auditlog.go` 此前的唯一生产实现（`slogAuditLogger`）只是把
审计记录用 `log/slog` 写到标准错误（交给 journald 收），而
`internal/store/sqlite/schema/001_init.sql` 第 174 行早就建好了
`audit_log` 表（`id` / `ts` / `actor` / `action` / `target` /
`detail_json` 六列，与 `contract.AuditLogger.Log` 的四个参数逐一对应），
**却从未被任何 Go 代码写入**。那个文件自己的注释也承认了这是绕过：

> 正解方向是给 contract.Store 补一个 AuditLogStore 窄接口并由 M2 实现，
> 装配点直接复用 Store 而不是另起一个基于 slog 的实现。

两层缺口叠加的后果：进程重启后全部历史审计记录消失（slog 只是打到
stderr，不是持久化存储），且即便进程还在运行，也没有任何编程接口能把
「谁在什么时候驳回了哪个 hook、理由是什么」查回来——只能靠人工翻
journald 的原始文本日志，且要求运维精确知道去哪台机器、哪个时间窗口找。
对一个「hook 能以 root 身份在分区之前运行、能力等同擦掉整台机器」的
系统（SPEC §9.4），这是真实的合规与追溯缺口，不是「体验不够好」。

## 怎么补的：五步契约变更流程

按 M1 定的流程走完全部五步（`internal/core/contract` 的包注释明确要求
「新增 Store 方法 → 先往 conformance 套件加断言 → 两个实现各自补齐 →
套件变绿即集成完成」，本次额外加了「接上调用方」作为第五步，因为前四步
只解决「能查」，不解决「谁在查、查什么」）：

1. **改接口**（`internal/core/contract/store.go`）：新增
   `AuditRecord`/`AuditFilter` 类型与 `AuditStore` 窄接口
   （`AppendAudit`/`ListAudit`），纳入组合 `Store` 接口。
2. **改 conformance 断言**（`internal/core/contract/conformance/store.go`）：
   新增五条子测试，见下方「conformance 断言覆盖了什么」。
3. **改内存实现**（`internal/core/fake/store.go`）：`audit` 字段是一个
   append-only 切片，`ListAudit` 遍历、按 `Filter` 筛选、按 `TS` 倒序、
   `Limit` 截断。
4. **改真实现**（`internal/store/sqlite/audit.go`，新建）：直接读写
   `audit_log` 表；`detail` 是自由文本，JSON 编码后存进既有的
   `detail_json` 列（复用列类型，不代表 detail 本身有结构，详见该文件
   的注释）。
5. **接上调用方**：`cmd/lober/auditlog.go` 换成落库实现；
   `internal/console` 新增 `Deps.AuditQuery` 与
   `GET /hooks/{id}/audit`。

第四步之后跑了两个实现各自的 conformance 套件（见下方「验证」），两者
全绿，证明「内存实现与 SQLite 实现对同一份行为契约表现一致」——这正是
两步契约变更能并行开发的前提，也是本次没有踩到的坑（schema 明确禁止改，
所以两个实现从一开始就针对同一份列定义）。

## `AuditLogger`（写）与 `AuditStore`（读+写）为什么是两个接口

`contract.AuditLogger`（`service.go`）在本次变更后仍然只有 `Log` 一个
方法，没有被合并进 `AuditStore`。理由是窄接口族的一贯原则：审计中间件
（`internal/console/audit.go` 的 `auditMiddleware`）与 `hook.go` 的
`handleRejectHook` 只需要「写一条、不关心写到哪、失败也不影响主流程」
这一个能力，把查询方法也塞进同一个接口会让这些纯写入的调用点被迫依赖
一个它们从不使用的能力。

装配点（`cmd/lober/wire.go`）现在的接法：

```
Audit:      newAuditLogger(st, clock)   // dbAuditLogger，内部持有 st 与 clock
AuditQuery: st                          // 同一个 sqlite.Store 实例
```

`dbAuditLogger.Log` 内部把调用委托给 `AuditStore.AppendAudit`；
`console.Deps.AuditQuery` 直接是同一个 `st`，`GET /hooks/{id}/audit`
调用 `AuditQuery.ListAudit`。两条路径共享同一个持久化后端，写的和查的
是同一份数据——这也是测试环境踩到并修复的一个真实 bug（见下方「测试
环境的一个真实教训」）。

## 取舍：审计写库失败为什么不能让操作整体失败，但也不能被无声吞掉

`dbAuditLogger.Log` 落库失败时**返回 `nil`**（调用方感知不到失败），但
在 slog 里留一条 `Level=Error`、显式标注 `audit_persist_failed` 的记录。

理由与 SPEC §6.3「遥测失败不杀装机」是同一类判断：审计中间件与
`handleRejectHook` 都是在业务操作**已经成功之后**才调用 `Log`。如果把
落库失败原样返回给调用方、调用方又把这个错误当整体失败处理，就会出现
「hook 审批已经生效，但因为审计表暂时写不进去（比如磁盘满、SQLite 忙锁
超时），运维看到一个 500」这种荒谬结果——审计是事后追责的辅助能力，
不应该有资格阻塞它本该记录的那个操作。这里的说法换成本系统的场景是
「审计失败不该让运维改不了配置、批不了 hook」。

但失败不能被静默吞掉：用 `Level=Error`（而不是 Info）与专门的
`audit_persist_failed` 标签，让运维在日常按级别筛日志时能看到「审计
系统本身出了问题」，这与把错误直接吞掉（等同于什么都没发生）不同——是
「不让审计故障升级成业务故障，但也不让审计故障无声无息」之间的中间
地带。具体实现见 `cmd/lober/auditlog.go` 的 `dbAuditLogger.Log`。

## 新端点：`GET /hooks/{id}/audit`

**形态**：按 hook id 查该 hook 的审计记录，`limit` 可选查询参数（默认
1000，与其它列表端点一致），返回 `AuditRecordItem[]`（按 `ts` 倒序，
最新的在前），套用与其它 28 条端点相同的响应包裹。完整契约描述与
失败形态见 `docs/contracts/http-console.md` 第 4 节「hook」，编号 29；
变更记录见该文档文首「变更记录 2」。

**为什么是 `/hooks/{id}/audit` 而不是全局 `/audit?target=`**：全局端点
需要更粗放的权限（至少 admin），否则任何持有任意一个审计相关权限码的
用户都能查看全部资源的审计流；挂在 `/hooks/{id}` 之下则天然把授权范围
收窄到「与这一个 hook 有关的人」。当前唯一的消费场景（hook 页面查驳回
理由）也只需要按 hook 维度查。全局查询留给确有需要时再补——那时可以
复用同一个 `contract.AuditStore`，不需要再改契约。

**权限**：`hook-author`（`hook:write`）或 `hook-approver`
（`hook:approve`）之一即可，`admin` 通过角色聚合权限码天然满足（见
`internal/console/rbac.go` 的 `roleCodes` 表：`roleAdmin` 已经聚合了
`codeHookWrite` 与 `codeHookApprove`，不需要在 handler 里单独判断
admin）。**不开放给 `operator`/`viewer`**——审计记录含操作人信息
（`actor` 字段），SPEC §9.4 按敏感操作分级授权，与这个 hook 的审批
流程无关的角色不应看到谁驳回过、驳回了什么。判定逻辑在
`handleHookAudit` 内部完成（不在路由层用单一权限码卡死），与
`handleApproveHook`/`handleRejectHook` 的既有风格一致——因为这是
「多个权限码之一即可」的 OR 语义，`requireCode` 中间件只能表达单一
权限码的 AND 语义。

## conformance 断言覆盖了什么

五条新断言（`internal/core/contract/conformance/store.go`），每条都在
断言失败信息里写明「为什么这条重要」：

| 断言 | 为什么重要 |
|---|---|
| `testAuditAppendThenListByTarget` | 写入后必须能按 target 查回来——这是两层缺口修补的核心诉求，如果查不到，查询面就是摆设 |
| `testAuditDetailRoundTrip` | detail 落进 JSON 列（`detail_json`），JSON 列最容易在编解码时掉字段或错误转义特殊字符；专门构造含引号、换行、中文的 detail 覆盖 `handleRejectHook` 实际写入的形态 |
| `testAuditOrderedDescendingWithLimit` | 按时间倒序 + limit 生效——审计页面打开时最想看到的是最近发生的事，且不应要求调用方先取全量再截断 |
| `testAuditListEmptyIsNotError` | 查不到时返回空而不是错误——没有审计记录是正常状态（一个从未被驳回过的 hook），不是异常 |
| `testAuditFilterByTimeRange` | 按时间范围过滤——运维排查「今天上午的驳回」这类问题需要按时间窗口而不是逐条翻 |

两个实现（`internal/core/fake`、`internal/store/sqlite`）跑同一套断言
全绿，是「契约变更做对了」的证明（两者行为不会分叉）。

## 测试环境的一个真实教训：Deps.Audit 与 Deps.AuditQuery 必须指向同一份数据

写 `GET /hooks/{id}/audit` 的端到端测试时，第一版失败了——驳回一个
hook 之后立刻查审计，结果是空数组。根因：`internal/console` 的测试
夹具（`stub_test.go`）里，`Deps.Audit` 是一个独立的 `stubAuditLogger`
（只记进自己的 `entries` 切片），而 `Deps.AuditQuery` 指向另一个独立的
`fake.Store`——两者互不相通，与生产环境下 `Audit`（`dbAuditLogger`
委托给 `AuditStore.AppendAudit`）和 `AuditQuery`（直接是同一个
`sqlite.Store`）共享同一份持久化数据的关系不一致。

修法：让 `stubAuditLogger.Log` 在 `store` 字段非 nil 时，把每条记录
也写透到那个 `contract.AuditStore`（保留 `entries`/`all()` 供只需要
断言「中间件确实调用了 Log」的既有测试使用），`newTestServer` 里把
`Deps.Audit` 与 `Deps.AuditQuery` 接到同一个 `fake.Store` 实例——这样
测试环境的接线关系才真正镜像生产环境，之后端到端测试一次通过。这个
坑本身也说明了为什么本任务的验证要求是「真的驳回一次 hook 再查一次
审计记录」，而不是分别验证写路径和读路径——两条路径接在一起才是
真正在修的缺口。

## UI 侧还需要做什么（留给后续，本轮只做后端）

本轮明确不碰 `web/**`——现有 UI 从驳回响应里读理由的行为（
`hookRejectResponse.Reason`）仍然有效，不受影响。后续要做的：

1. **hook 详情/列表页加一个「审计记录」标签或面板**，调用
   `GET /hooks/{id}/audit`，展示 actor/action/target/detail/ts 五列，
   按 ts 倒序（端点已经排好序，前端不需要再排）。
2. **权限收敛**：前端应根据 `GET /auth/codes` 返回的权限码
   （`hook:write`/`hook:approve`）决定是否显示这个标签，与后端的
   403 判定保持一致的用户体验（无权限时不该让用户点进去才看到报错）。
3. **驳回成功后的引导**：`POST /hooks/{id}/reject` 的响应仍然回显
   `reason`，前端可以在驳回成功的提示里附带「后续可在审计记录里查看」
   的说明，把两条路径（当场回显、事后查询）在体验上串起来。
4. **与 `docs/superpowers/plans/2026-09-20-lober-phase4-04-audit.md`
   的关系**：那份 Phase 4 计划的任务 2「操作审计查询」假设了「Phase 1
   已经在写审计记录……本计划不新增采集，只做查询与导出」——这个假设
   在本次修补之前是**不成立的**（审计记录只写 slog，不落库，无法被
   任何查询接口消费）。本次变更是那份计划能够落地的前提：
   `contract.AuditStore` 提供的 `AuditFilter`（target/时间范围/limit）
   已经覆盖了该计划「操作人、时间范围、动作类型、目标资源」四项查询
   条件里的三项（时间范围、目标资源；配合 `ListAudit` 返回的
   `Actor`/`Action` 字段，调用方在应用层过滤即可覆盖剩余两项，规模
   与 `HookStore.ListHooks` 的取回后过滤是同一类取舍）。该计划的任务 1
   （任务溯源视图）、任务 3-5（报表、导出、页面）仍然是后续独立工作，
   本次变更不覆盖。
