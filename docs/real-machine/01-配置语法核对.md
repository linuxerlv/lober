## 0. 环境准备记录

- `wsl -l -v` 显示 `debian-13`（WSL2）初始为 Stopped，按任务指引启动。
- **WSL 首次启动卡在 `systemd-firstboot.service`**（interactive
  `--prompt-locale --prompt-keymap --prompt-timezone --prompt-root-password`，
  `StandardInput=tty` 在非交互调用下永久阻塞），导致 `sysinit.target` 及其后
  全部单元（含 `systemd-networkd`）卡在 waiting，`eth0` 拿不到 DHCP 租约，
  `apt-get update` 全部失败（`Network is unreachable`）。用
  `systemctl stop systemd-firstboot.service` 解除阻塞（该 unit 是
  `Type=oneshot` 且未做任何实际工作，stop 是安全操作），随后 `wsl --shutdown`
  + 重新冷启动确认 `boot_id` 变化、`systemctl is-system-running` 恢复正常
  （`degraded`，仅 `systemd-binfmt.service` 失败，与本轮任务无关的 WSL 环境
  已知问题）。
- **WSL NAT 场景下 `eth0` 的 DHCP 租约获取存在环境故障**：`dhclient -v -1 eth0`
  能发出 `DHCPDISCOVER` 但从未收到 `DHCPOFFER`（ICS/SharedAccess 侧未响应）。
  这条路径需要重启 Windows 侧 `SharedAccess` 服务或切换 WSL
  `networkingMode=mirrored` 才能修，两者都超出本任务的权限边界（前者是修改
  共享主机服务，后者要改全局 `.wslconfig`），**本轮未修复此问题，改用
  Windows 主机自身可用的外网连接下载 `.deb` 包后通过 `/mnt/e` 挂载点侧载进
  WSL 安装**——这不影响后续任何一项核对的有效性，因为全部五项核对命令本身
  都不依赖 WSL 的出站网络，只依赖目标二进制已安装。此问题记录在案，供其它
  需要 WSL 联网的后续工作参考。
- 装包：`dnsmasq-base`、`isc-dhcp-server`、`kea-dhcp4-server`、`nginx`
  （加其必需的浅层依赖）均已安装。**未装 `nginx-full`/`nginx-common` 的第三方
  模块包**（`libnginx-mod-*`）——因为 Debian 的 `nginx-core`/`nginx-full`/
  `nginx-light`/`nginx-extras` 四个变体包共享同一个核心 `nginx` 二进制包
  （`nginx-core` 等只是额外依赖一批 `libnginx-mod-*` 动态模块包，`nginx -V`
  报的编译期参数由核心 `nginx` 包决定，与选哪个变体无关），核对
  `--with-threads`/`--with-http_secure_link_module` 只需要核心包。
- `isc-dhcp-server`、`kea-dhcp4-server`、`nginx` 三个包各自的 postinst 脚本
  会自动 `systemctl start` 一次：`isc-dhcp-server` 因默认 `/etc/dhcp/dhcpd.conf`
  未配置真实子网而启动失败（不影响，本身就是失败状态，未监听任何端口）；
  `kea-dhcp4-server` 与 `nginx` 曾短暂进入 `active` 状态，**均在确认后立即
  `systemctl stop` + `systemctl disable`**，全程只使用发行版默认示例配置
  （非本仓库配置），未绑定装机 VLAN 或任何真实网络接口，不构成任何网络风险。
  核对完成后系统最终状态：均为 `inactive`/`disabled`。

### 2.1 SPEC 附录 B「dhcpd 条件语法」实测（超出语法校验，真实语义验证）

**背景**：附录 B 明确要求核实 `option client-arch = 00:07` 这种双字节字面量
比较的实际行为，以及 `or` 在 `elsif` 条件里的求值——不能凭空假设。

**方法**：在 WSL 内部新建一对完全隔离的 `veth` 虚拟网卡（`veth-test-a` /
`veth-test-b`，仅存在于 WSL 自己的网络命名空间，不连接任何物理网卡、不产生
任何真实网络流量），`dhcpd` 只绑定 `veth-test-a` 监听，用真实
`dhclient`（可通过 `dhclient.conf` 的 `send client-arch <N>;` 精确控制发送
的 option 93 数值）在 `veth-test-b` 侧发起完整 DORA 交换，检查
`dhclient.leases` 记录到的 `filename` 字段（即 dhcpd 实际选中的分支）。
测试用配置是仓库 `deploy/dhcpd/lober.conf` 逻辑的忠实复制，四个架构分支的
`filename` 改成 `BRANCH-<架构>-<原文件名>` 便于分支识别（不改变判定条件与
判定值本身）。

| 发送的 client-arch（十进制） | 实测命中分支（真实 DHCPACK 里的 filename） | 与预期是否一致 |
|---|---|---|
| `7` | `BRANCH-EFI64-snponly.efi` | 一致（`= 00:07` 双字节字面量比较，十进制 7 编码后确实等值匹配） |
| `9` | `BRANCH-EFI64-snponly.efi` | 一致（`or option client-arch = 00:09` 求值正确，两个值都命中同一分支） |
| `8`（未落在 0/6/7/9/11 任何一个） | 无 `filename`（拿到 IP 租约但没有 boot 文件），服务端日志打印 `lober: unknown client-arch, mac=...` | 一致（else 分支的显式日志确实生效） |
| `7` **同时**发 `user-class=iPXE` | `http://boot.lober.internal/boot.ipxe`（不是 `BRANCH-EFI64-...`） | 一致——**这是本条最关键的验证**：证明 `if exists user-class and option user-class = "iPXE"` 分支的 `elsif` 顺序确实排在架构判定之前，反循环逻辑成立 |

**结论：已通过实测（不再是"凭工程经验假设"）。** dhclient 把
`send client-arch 7;`（在 `option client-arch code 93 = unsigned integer 16;`
声明下）编码成的字节序列，与 dhcpd 配置里 `00:07` 字面量比较，两者语义
一致，双字节字面量写法按预期工作；`or` 在 `elsif` 条件里的求值也按预期
工作（7 与 9 都命中同一分支）。**SPEC 附录 B 这一条现在可以标记为已验证**，
不再是待核实项。

**局限**：本测试证明的是 dhclient 编码的 option 93 数值与 dhcpd 判定条件
之间的匹配语义正确，**没有也不能证明真实固件上报的字节形态与 dhclient 编码
的字节形态完全一致**——固件层面的抓包核对（尤其国产 ARM 平台）仍需真实硬件，
这是本测试方法本身的边界，不是本测试没做到位。

### 3.1 `option[client-system]` 符号名实测

**方法**：把仓库文件里全部 `option[93]` 替换成符号名 `option[client-system]`
的独立副本，跑 `kea-dhcp4 -t`。

**真实输出**：与替换前完全一致的成功输出，无 "unknown option" 类错误。

**结论：已确认 `option[client-system]` 符号名在这个 Kea 版本（2.6.3）上
存在且可用。** 仓库文件里"先用数值形式，确认可用后再换成符号名"的保守做法
现在可以视为已验证——**但这只对 2.6.3 这一个版本成立**，不同 Kea 大版本的
标准选项定义表可能不同，实际部署时目标机房的 Kea 版本若与此不同，仍应重跑
这条核对（命令成本极低，`kea-dhcp4 -t` 秒级完成）。仓库文件保留数值形式
`option[93]` 不变——这是防御性的正确选择，数值形式在任何 Kea 版本上都不会
因符号名表差异而启动失败。

### 3.2 「Kea 多 class 命中」实测（超出语法校验，真实语义验证）

**背景**：SPEC 附录 B 的核心风险——UEFI 机器跑起 iPXE 后再次发 DISCOVER，
同时满足 `ipxe` class 与 `efi64` class 的 `test`，若两者都有
`boot-file-name`，实际生效的是哪个取决于 Kea 的 class 求值与 option
合并顺序。仓库配置用重复反条件规避了这个不确定性，但"绕开是否真的必要"
本身也是附录 B 列出的待核实项。

**方法**：与 dhcpd 测试同一套隔离 `veth` 基础设施，`kea-dhcp4` 只绑定
`veth-test-a`（`interfaces-config.dhcp-socket-type: raw`），用真实
`dhclient` 发起交换，检查 `dhclient.leases` 的 `filename` 字段。测试两个
变体：仓库原文件（重复 `not (substring(...) == 'iPXE')`）与
`not member('ipxe')` 简化版本（`ipxe` class 已在数组首位，满足 SPEC 提出
的简化前提）。

| 场景 | 仓库原写法结果 | `member('ipxe')` 简化版结果 | 两者一致？ |
|---|---|---|---|
| 仅发 `client-arch=7` | `snponly.efi` | `snponly.efi` | 一致 |
| 同时发 `client-arch=7` 与 `user-class=iPXE` | `http://boot.lober.internal/boot.ipxe` | `http://boot.lober.internal/boot.ipxe` | **一致——都正确返回 iPXE URL，没有退化成 `snponly.efi`** |

**结论：已通过实测。** 两种写法在这个 Kea 版本（2.6.3）上产生完全一致的
正确结果——`efi64` class 即使自身 `test`（`client-arch=7`）为真，也不会在
`ipxe` class 同时命中时抢到 `boot-file-name`，因为反条件（无论是重复
`substring` 还是 `member('ipxe')`）都正确阻止了双重命中。**这意味着仓库现在
选择的"重复反条件，不用 member()"是一个安全但不是必须的保守选择**——
`member('ipxe')` 在实测中同样正确，可以作为将来简化配置的依据（前提仍是
`ipxe` class 必须在数组首位，且仍建议在启用前对目标环境的具体 Kea 版本
重跑一次这条测试，因为这依赖 Kea 内部 class 求值顺序的实现细节，SPEC 附录
B 的谨慎态度本身没有错）。**未改动仓库文件**——重复反条件的写法本身没有
错，替换成 `member()` 属于风格简化而非缺陷修复，不在本轮"报错才修"的范围内。

**局限**：本测试只覆盖了 Kea 2.6.3 这一个具体版本，`Kea 文档称 class
按配置中定义的顺序处理`这条依据是文档层面的承诺，本测试是对这一个版本
的承诺兑现情况的实测确认，不是对所有 Kea 版本的通用证明。

## 4. `systemd-analyze verify` + 复核两处已修 bug + 找第三个

**命令**：

```bash
systemd-analyze verify deploy/systemd/lober.service
systemd-analyze verify（对 nginx.service.d/after-lober.conf，需先建一个基础
  nginx.service 单元让 drop-in 生效检验，见下）
```

**前置**：`ExecStart=/opt/lober/bin/lober -config /etc/lober/lober.yaml`
指向的二进制需真实存在。用 `GOOS=linux GOARCH=amd64 go build` 在 Windows
侧交叉编译出 `cmd/lober` 的 linux/amd64 二进制，放进 WSL 的
`/opt/lober/bin/lober`；`-config` 指向的 `/etc/lober/lober.yaml` 用
`deploy/lober.yaml.example` 复制而来；`User=`/`Group=` 占位符替换成本地
新建的测试用户 `lober-svc`（仅用于让 `systemd-analyze verify` 能解析
`User=`/`Group=` 字段，不用于运行任何服务）。

**真实输出**：**空**（无任何输出，退出码 0）——`systemd-analyze verify`
对完全干净的单元不打印任何内容，这是正常表现。

**结论：已通过。**

### 4.1 复核两处已修 bug（本轮独立重新构造并触发，不是"读代码觉得没问题"）

**bug 1 —— `Environment=` 变量不会插值进 `ExecStart=`**：构造一个错误版本
（`Environment=LOBER_BIN=/opt/lober/bin/lober` + `ExecStart=${LOBER_BIN} ...`）
分别用 `systemd-analyze verify` 与真实 `systemctl start` 触发：

```
test-envvar3.service: Command ${LOBER_BIN} is not executable: No such file or directory
```

```
Process: 284 ExecStart=${LOBER_BIN} -config /etc/lober/lober.yaml (code=exited, status=203/EXEC)
Unable to locate executable '${LOBER_BIN}': No such file or directory
```

**确认：这个 bug 真实存在，且仓库当前文件（硬编码绝对路径字面量，不用
`Environment=`+`${}` 引用）确实避开了它。**

**bug 2 —— `StartLimitIntervalSec`/`StartLimitBurst` 写在 `[Service]` 段
被静默忽略**：构造错误版本触发：

```
Unknown key 'StartLimitIntervalSec' in section [Service], ignoring.
```

```
systemctl show 确认：StartLimitIntervalUSec=10s（systemd 默认值，不是我们
要的 300s）
```

**确认：这个 bug 真实存在，且仓库当前文件把这两个键放在 `[Unit]` 段，
`systemctl show lober.service` 核实 `StartLimitIntervalUSec=300s`、
`StartLimitBurst=5` 确实生效。**

### 4.2 找第三个 bug

核对了以下几处，**均未发现问题**：

- `ExecStartPre`/`ExecStart` 的 argv 解析（`systemctl show` 逐字核对，路径
  与参数都正确）。
- `TimeoutStopUSec` 解析为 `30s`，与 `cmd/lober/server.go` 的
  `shutdownGrace = 15 * time.Second` 比较，`15 < 30` 成立（见下方 4.3）。
- `AmbientCapabilities`/`CapabilityBoundingSet` 均解析为
  `cap_net_bind_service`，与 `NoNewPrivileges=yes` 不冲突（`NoNewPrivileges`
  阻止的是通过 setuid/setgid/文件能力"获得新特权"，不影响已通过
  `AmbientCapabilities` 授予的既有能力，两者是教科书式的正确搭配，不是
  冲突）。
- `ProtectSystem=strict` 与 `ReadWritePaths` 的三个路径解析正确。

**结论：本轮未找到第三个 bug。** 这是一次认真检查后的阴性结果，不是"没
仔细查"——检查方法见上，`systemd-analyze verify` 本身对这类单元文件的静态
校验已经相当完整，前两个已知 bug 都属于"语法合法但语义不对"的类型
（systemd 不会主动报错的陷阱），本轮用同样的思路检查了其它几处容易犯这
类错误的字段，均未发现同类问题。

### 4.3 本轮顺带确认并更新的一处

`deploy/systemd/lober.service` 里 `TimeoutStopSec=30` 的注释原本写着
"cmd/lober/server.go 尚未在本 worktree 实现，需要日后核对该常量 < 30"——
**本轮读到 `cmd/lober/server.go` 已经实现，`shutdownGrace = 15 * time.Second`，
15 < 30 成立**，已更新该注释为已核实状态（不再是待办）。这不是修 bug，是
把一条已经可以关闭的 TODO 关闭。

### 4.4 nginx drop-in 单独核对

**方法**：`systemd-analyze verify` 不能直接对单个 drop-in 文件生效验证
（`Failed to prepare filename ... Invalid argument`），需要先有一个同名
基础单元（`nginx.service`）让 drop-in 生效，再对基础单元整体跑
`systemd-analyze verify`，用 `systemctl cat nginx.service` 确认合并结果。

**真实输出**：`systemctl cat` 确认合并后的 `[Unit]` 段正确包含
`After=lober.service` 与 `Wants=lober.service`；`systemd-analyze verify`
无任何输出（通过）。

**结论：已通过。**

`nginx-full`/`nginx-light`/`nginx-extras` 四个变体共享的同一个二进制包）
**同时带有 `--with-threads` 与 `--with-http_secure_link_module` 两个
编译选项**，`deploy/nginx/lober.conf` 里 `sendfile`+`aio threads` 与
Phase 2 制品授权用到的 `secure_link` 都可以正常工作，不需要重新编译
nginx 或换发行版包。**这条结论已写入 `deploy/README.md`**（见该文档
第 5.3b 节的更新）。

**局限**：本结论只对 Debian trixie（本次核对用的发行版）成立。若目标
机房使用其它发行版（RHEL 系、其它 Debian 版本等），这条核对需要针对
该发行版重跑——命令本身极其轻量（`nginx -V` 秒级完成，甚至不需要启动
nginx 进程），不构成部署前的负担。

## 附：本次核对未覆盖、仍需真实硬件的部分（与 SPEC 附录 B 保持一致，不重复展开理由）

以下几项经过本轮核对后确认**依然**需要真实硬件或真实固件，WSL/veth 隔离
测试方法论证明不了：

1. **option 93 各架构实机取值**（尤其国产 ARM 飞腾/鲲鹏是否规范地报 11）——
   本轮证明的是"dhcpd/Kea 对某个已知数值的判定逻辑正确"，不能证明"某型号
   固件实际发送的就是这个数值"，这必须让真实固件上电抓包才能确认。
2. **iPXE 变量拼写与多网卡 `net0` 是否为实际引导网卡**——需要真实 iPXE
   固件渲染 `/boot.ipxe` 后的行为，与 DHCP 服务端配置无关。
3. **UEFI HTTP Boot 架构码（16）与 option 60 `HTTPClient` 的固件实际发送
   格式**——`deploy/dnsmasq/lober.conf` 该段已默认注释，SPEC 附录 B 该行
   的 RFC 号纠错与 IANA 登记表核实已在文件内完成（另一任务的产出），本轮
   未涉及这部分。
4. **各国产 OS（openEuler/麒麟/UOS/Anolis）的应答文件机制差异**——与本轮
   四份配置无关，不在核对范围内。
