# Phase 4 mTLS 范围决策

> 对应实现计划 `docs/superpowers/plans/2026-09-20-lober-phase4-02-tls.md` 任务 5。
> 依据 `SPEC.md` §11 Phase 4（"TLS + mTLS"）、§4.2（首次请求必然无认证）、
> §9.1（三道准入闸门）、§9.4（权限分级）、§1.6（`X-Real-IP` 反代陷阱）。

## 结论

| 范围 | 决策 |
|---|---|
| **机器面（iPXE、装机中的裸机）** | **不做 mTLS** |
| **人面（控制台，运维浏览器）** | **有条件做**——技术上可行，但需运维评估证书分发/吊销的持续负担是否值得，本文档给出权衡依据，不代本项目团队做最终选择 |

---

## 机器面：不做 mTLS

### 核心困难：裸机在获得身份之前没有凭据

`SPEC.md` §4.2 明确写了这个协议事实：

> **第一次请求必须无认证，token 在响应中签发。** 机器刚上电只有固件，
> token 不可能先于首次接触存在。

mTLS 的前提是客户端持有一张私钥对应的证书，并在 TLS 握手阶段出示它。但
一台刚上电的裸机，在拿到装机任务之前，唯一拥有的软件是固件里的网络引导栈
（PXE ROM 或 UEFI 固件的网络驱动）与后续加载的 iPXE 二进制——它没有、也不
可能有一张"这台机器专属"的客户端证书，因为**这台机器的身份（是哪台机器、
该不该被装机）恰恰是这个协议要去确立的东西，不是协议开始之前就已知的输入**。

这与 §9.1 描述的核心风险面是同一件事的两个层面：`/v1/boot` 必须无认证才能
工作（否则没有任务的机器连"查一下有没有任务"这个动作都做不到），而 mTLS
要求认证先于业务逻辑——两者在协议顺序上直接冲突。

### 三个可能的答案，都有代价（计划任务 5 原文的框架，本文档补充分析）

| 方案 | 具体做法 | 代价 | 是否可行 |
|---|---|---|---|
| **共享客户端证书** | 把同一张证书与私钥嵌进 iPXE 二进制，全网所有机器用同一张证书做 mTLS 握手 | 私钥和 CA 证书一样，一旦嵌进二进制就等于公开（气隙环境下二进制会被带到多台机器的 TFTP 服务器/内网上，任何能读到这个二进制的人都能提取出私钥）。此时"客户端证书"退化成一个**所有机器共享的静态密钥**，它验证的是"你是持有这个共享密钥的人"，不是"你是哪一台具体的机器"——这与不加密传输一个共享 token 没有本质区别，只是多了一层 TLS 握手的仪式感，不提供真正的客户端身份区分能力 | **不可行**：不提供实际安全收益，却引入"私钥内嵌二进制"这个新的泄露面（比 CA 证书泄露更糟——CA 证书泄露还能靠吊销单张证书补救的思路都不适用，因为泄露的直接就是能通过 mTLS 校验的凭据本身） |
| **每台机器一个证书** | 给每台已知的机器（按 SN/MAC）签发专属客户端证书，编译进为该机器定制的 iPXE 二进制 | 要求"按机器编译 iPXE 二进制"——这与 §1.3、§4.7 反复强调的"DHCP 与 iPXE 二进制架构无关、全网共用、新增机器零改动"设计原则正面冲突。批量装机场景下（本系统面向的场景，见 §0.3"目标 OS"表暗示的机群规模）需要为每一台新机器单独编译、单独维护一份 TFTP 文件名到证书的映射，运维复杂度随机器数线性增长 | **运维上不可行**：与本系统"加一个新 OS 家族只加模板，DHCP 与 nginx 零改动"（§4.7 末段）这条设计收益完全相悖，等于为 mTLS 牺牲了本系统在别处刻意保留的可扩展性 |
| **机器面不做 mTLS** | 保持现状，机器面继续依赖 §9.1 的三道闸门 | 无新增技术复杂度；"代价"是没有 mTLS 提供的传输层客户端身份校验 | **推荐** |

### 为什么"机器面不做 mTLS"不是降级

这是本文档要明确论证的关键点，不能只是回避问题：

**§9.1 的三道闸门与 mTLS 防的是两类不同的风险，前者更强，不是后者的弱化替代：**

1. **默认拒绝**（`/v1/boot` 查不到 `pending` task 即返回 `no_task`）+
   **SN 清单选取加 MAC 双因子**（§4.3）+ **attempt 计数封顶** ——
   这三道闸门回答的问题是**"这台具体的机器，有没有被运维明确授权装机"**。
   判据是机器的身份属性（SN、MAC）与业务状态（是否存在 pending 任务）。

2. **mTLS** 回答的问题是**"发起这次 TCP 连接的对端，有没有出示一张受信任
   的客户端证书"**。判据是连接层面的凭据持有，与"这是不是被授权装机的那台
   具体机器"是两个独立的问题。

一台**持有共享客户端证书但 SN 不在清单里的机器**（计划任务 5 原文举的反例），
用 mTLS 方案时依然能通过 TLS 握手（它有那张全网共享的证书），但依然会在
§4.3 的 SN/MAC 校验这一步被拦下、拿不到 token。反过来，一台**没有客户端
证书但 SN/MAC 都对得上**的机器，在当前设计（不做 mTLS）下能正常装机——
而这正是期望行为：这台机器就是运维要装的那台机器，不应该因为缺一张证书
被挡在外面。

**结论**：§9.1 的三道闸门做的是"业务层身份与授权校验"，比 mTLS 能做到的
"连接层凭据校验"更贴近这个系统真正要防的风险（"错误的机器被装机"），也更
不容易被"一张全网共享的证书"这种退化实现悄悄削弱。**在裸机场景下，为
mTLS 付出上面两种代价（不安全的共享私钥，或不可扩展的逐机器证书）换不来
比现有三道闸门更强的保护，机器面不做 mTLS 是一个基于实际威胁模型的正确
判断，不是图省事的降级。**

### 传输层保护的缺口仍然存在，但由别的机制承担

不做 mTLS 不等于机器面的 TLS 配置可以马虎——服务端仍然要做单向 TLS（本
计划任务 3 已完成的 nginx 配置），保护的是"防窃听、防中间人篡改响应内容"。
mTLS 本来要补的是"防止无关方连上来发请求"这一层，机器面靠 §9.1 的准入
控制在应用层（而不是传输层）实现同等甚至更强的效果，`SPEC.md` §1.5 末段
"MVP 无 TLS，故 token 与默认拒绝是唯一的防线"这句话在上了单向 TLS 之后
仍然部分适用——token 与默认拒绝依然是拦截"未授权装机"的主力机制，TLS
（无论单向还是双向）都不替代它们，只是让传输过程本身更安全。

## 人面：有条件做

### 人面做 mTLS 有实际意义

与机器面不同，人面（控制台）的客户端是**运维人员使用的机器**——数量少
（个位数运维，`SPEC.md` §9.4 已经这样描述这个系统的操作员规模）、身份在
部署前就已知、可以逐台管理。这消除了机器面遇到的核心困难："裸机没有身份"
在人面不成立，运维的笔记本/工作站在接入系统之前就是一个已知实体，可以
提前给它签发一张专属客户端证书。

**人面 mTLS 防的是什么**：一个拿到了密码（用户名+密码，控制台现有的
认证方式）但不在授权设备上的攻击者。这类场景包括密码被钓鱼、被记录在
不安全的地方、或运维本人的账号密码被冒用——mTLS 要求攻击者同时拿到
"密码"与"这台已注册设备上的私钥"两个东西，比单一密码认证多一层门槛。

### 人面 mTLS 是叠加，不是替代

**这一点必须写清楚，因为很容易被误解为"上了 mTLS 就可以放松密码要求"：**

`SPEC.md` 没有把 mTLS 定位为密码认证的替代品，本文档同样不建议这样理解。
理由：

1. **密码认证与证书认证防的攻击面不完全重叠。** 密码可能被钓鱼、弱密码
   暴力破解、或社会工程套取；客户端证书可能因为设备被盗、设备管理疏漏
   （比如运维离职后设备没有及时收回）而落入他人之手。两种凭据同时要求
   （而不是二选一）才能让"攻破一种凭据就能登录"的攻击路径变成"必须同时
   攻破两种凭据"。
2. **`SPEC.md` §9.4 的权限分级**（建任务、hook 编写、hook 审批、provider
   配置四类操作分别对应不同权限，`admin` 汇总最高权限）本身没有假设传输层
   身份校验的存在，四类操作各自的敏感度判断是独立于 mTLS 是否启用的——
   加了 mTLS 不改变任何一类操作原有的权限要求。
3. **上 mTLS 后放松密码要求，等于把系统的安全性绑定在"设备不丢、私钥不被
   提取"这一个假设上**，而这恰恰是"证书分发与吊销"这个持续运维负担存在
   的原因（见下一节）——如果假设不成立（设备丢失、私钥泄露）而密码要求
   又被放松了，系统的实际防护水平反而低于"只有密码"的现状。

### 若做人面 mTLS，要处理的运维问题：证书分发与吊销

**这是本节要重点权衡的成本，不能只列举收益不谈负担：**

- **分发**：每一位运维、每一台会用来登录控制台的设备，都需要生成一张
  客户端证书并安装进浏览器或系统的证书存储。首次接入有一次性成本，
  但"新增一名运维"或"运维更换设备"都会重复触发这个流程。
- **吊销**：运维离职、设备丢失或更换、私钥怀疑泄露时，对应证书必须被
  吊销，否则失效的凭据继续能用来登录。吊销需要维护一份吊销列表（CRL）
  或在线校验机制（OCSP），并让 nginx 的 mTLS 校验配置持续加载最新的
  吊销状态——**这不是一次性配置，是持续运维负担**：每一次人员变动都要
  记得去更新吊销列表，遗漏一次就是一个本该失效但仍然有效的凭据留在系统里。
- **与 CA 证书轮换的耦合**：若人面与机器面共用同一个内网 CA（`deploy/ca/`
  的产出物），人面客户端证书的签发与吊销流程需要与 `deploy/ca/README.md`
  已经写明的 CA/服务端证书轮换节奏协调，避免两条轮换节奏互相踩踏
  （例如 CA 轮换时，所有已分发的人面客户端证书是否也要求重新签发，取决于
  它们是否直接由 CA 签发还是由某个中间层签发——这个细节留给实际部署时
  的证书链设计决定，本文档不预先规定）。

### 在个位数运维场景下的权衡

`SPEC.md` §9.4 描述的运维规模是个位数。**这个规模下，"证书分发与吊销"这项
持续负担的绝对工作量不大（几个人的证书好管理），但"值不值得为此建立一整套
流程"是另一个问题：**

- 如果这几位运维本身就在一个受控的办公网络里工作（VPN、公司域内设备管理、
  已有的终端管理体系），mTLS 带来的增量安全收益可能相对有限——现有的
  网络边界与设备管理已经过滤掉了"任意设备接入"这类风险，mTLS 是在此基础
  上再加一层。
- 如果运维需要在不受控的网络环境（家庭网络、临时出差设备）访问控制台，
  mTLS 的收益会更明显——它能防住"密码在不受信任的网络上被截获后被任意
  设备拿来登录"这类场景，而这恰恰是密码单一认证的薄弱环节。

**本文档的立场：技术上可行，机制上是密码认证的合理补强，但"是否值得为此
建立并长期维护一套证书分发/吊销流程"取决于团队实际的运维规模、设备管理
现状与风险偏好，这是一个组织决策而非纯技术判断——本文档不代团队做这个
最终选择，只提供足够的权衡依据供决策。** 若团队选择不做，现有的密码认证
加上"控制台只在管理网可达"（§1.4 的网络隔离）已经构成合理的基线防护。

## 与 SPEC §11 "TLS + mTLS" 的关系

`SPEC.md` §11 把 Phase 4 列为"TLS + mTLS"，字面上似乎要求两者都做。本文档
的结论是**范围细化，不是偏离**：TLS（单向，机器面 + 人面）按计划任务 2-4、6
落地；mTLS 按机器面的协议现实（§4.2）与人面的成本权衡，收窄为"机器面不做，
人面有条件做"。这个细化理由已经在上文完整展开，供后续团队在 §11 的框架
下理解这个范围收窄不是遗漏，而是基于协议约束与运维成本的明确决策。
