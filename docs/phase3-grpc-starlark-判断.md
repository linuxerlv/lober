## gRPC 的三个问题

### 问题 1：P2-03 落地后，哪些 provider 用了 exec 或 http？它们够用吗？

**答不出。** 可配的位置有五个（`internal/config/config.go` 的
`IPAMLoader` / `DNSLoader` / `InventoryLoader` / `NotifyLoader` /
`HeartbeatLoader`），`exec` 与 `http` 两种加载器都已实现并有测试覆盖
（`internal/provider/loader/`）。

**但没有任何生产使用记录。** 本仓库的验证形态是 curl 模拟打点的端到端脚本加两台
QEMU 虚拟机的引导链实测；`docs/real-machine/08-loaders.md` 记录的是「部署示例与
真机核对文档」，不是「某个 IPAM 接了 exec 加载器跑了两个月」的运行经验。

「够用」的反面在计划里列得很具体：脚本太长难维护、需要连接池或长连接、需要在多次
调用间保持状态、单次调用的启动开销成为瓶颈。**这四条每一条都只能由真实负载回答**，
而目前没有真实负载。

### 问题 2：那些不够用的集成，是「有真逻辑」的吗？

**不适用。** 问题 1 没有「不够用的集成」这个集合。

按 §7.2 的判据分类，五个扩展点里 IPAM 与 Inventory 属于「可能有真逻辑」，
DNS 注册与告警推送属于「几行 curl 的集成用 gRPC 是纯负担」，心跳探测是内置实现
（icmp/tcp）本来就不需要外部化。**这是按接口性质做的先验分类，不是运行证据。**

### 问题 3：它们的实现方要不要用 Go 写？

**答不出。** 没有实现方——本系统尚未交付给任何机房，不存在「某个团队要写一个
IPAM 插件」这件事。

## Starlark 的两个问题

### 问题 4：模板解析的规则表现在有多少条？有嵌套条件吗？

**这一条有确切答案，且结论是明确的「不需要」。**

规则表的结构是**完全平的**：`internal/provider/resolver.go` 的 `ResolverRule`
只有四个匹配维度（`os_family` / `version` / `vendor` / `product`），全部是字符串
相等比较，没有任何嵌套、布尔组合或表达式。

**更关键的一条：规则表在生产路径上根本没有被使用。**
`LoadRulesYAML` 的文件注释写明「当前没有调用点在生产路径上使用它
（factory.go 目前总是传空规则给 NewTemplateResolver）」——也就是说
`NewTemplateResolver` 收到的永远是空规则表，走的是那条「全匹配到默认模板」的兜底
规则。

**规则表条数 = 0，嵌套条件 = 0。** §7.6 的引入信号（「规则表开始长出嵌套条件」）
不仅没有触发，而且距离触发还差一步：规则表得先被真正用起来。

### 问题 5：运维提过多少次「这批机器特殊处理」？

**零次。** 没有运维使用者——系统未交付。

## 为什么仍然实现

使用者在被明确告知「P3-04 的两项开工前提都未满足，SPEC 与计划都说依据不足时推迟
也是有效交付」之后，仍然选择把这一半一起做掉。这是知情决定，不是误判。

**可以为这个决定辩护的一点：** 两半都是**加法**而非改法——gRPC 加载器是
`loader` 包里并列的第三种实现，Starlark 是 `TemplateResolver` 的一个可选后端。
两者都不改动既有的 exec/http 加载器与规则表解析器的任何行为，配置里不选就完全不
生效。因此「做早了」的代价是维护面变大，而不是现有功能变脆。

**这个代价是实在的，要记住：** §7.6 已经警告过具体后果——「会花两周做加载、版本
协商、隔离，然后发现实际只需要三个 shell 脚本」。本轮做出来的 gRPC 加载器与
Starlark 引擎，在第一个真实使用者出现之前，都属于**未被任何真实需求验证过的抽象**。

## 将来回头看时要做的事

系统真正投产、跑过一段时间之后，重新回答上面五个问题。三种可能：

1. **确认需要** → 本轮的实现直接可用，把当时的依据补记进本文档。
2. **确认不需要** → **删掉它们**，不要因为「已经写了」就留着。留一个没人用的
   抽象层的成本是持续的：每次改 provider 接口都要同步三种加载器，每次审计依赖
   都要解释 `go-plugin` 与 `starlark` 为什么在依赖树里。
3. **需要的形态与本轮实现的不同** → 按真实需求重写，把本轮的实现当作一次探索
   而不是既有资产。**沉没成本不是保留的理由。**

第 2 与第 3 种可能都以「删掉」开头，这是本文档最值得记住的一句。
