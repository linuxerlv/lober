任务 3、4 的 WSL `make check` 同样退出 0。用户用例覆盖审计失败回滚、两次并发更新只有一个成功、并发撞用户名、禁用后恢复、不可修改身份及建档时间、字节序分页、默认 100 条与取消的上下文。控制台 HTTP 用例使用真实 PostgreSQL，验证当前角色、禁用状态、权限、审计、panic、SSE 查询令牌范围及令牌不进日志。通知中心并发发布和退订在 race 下通过。

任务 4 的文档当前有 2 条路径、7 个组件，使用本机 Python jsonschema 对[OpenAPI 官方 3.0 Schema](https://spec.openapis.org/oas/3.0/schema/2024-10-18)独立校验通过；原始结果在 `task4-oas-validation.log`。官方 schema SHA256 为 `2385f5bbb8c37878daae73baeabe7f34b2f022a4a8c049329ee61f71796f039c`。Go 测试另验证路由对账、真实字段、递归引用、路径参数、独立文档对象和重复编码确定性。

任务 5 的 WSL `make check` 退出 0。真实 HTTP 用例验证登录失败、TTL、登出、五角色权限、陈旧 Rev、禁用后恢复、改密后旧会话失效及初始管理员强制改密。PBKDF2 使用真实 600000 次迭代，随机盐与独立 Python 已知答案互相校验；正常和 race 测试均保留实际成本。请求不能改写强制改密标记，同一口令也不能解除它，口令及散列不出现在响应中。

任务 6 的 WSL `make check` 退出 0（控制台 race 160.613 秒），通过真实 PostgreSQL 验证主机的 SN 规范化、整条替换、零值清空、修订冲突、分页和过滤。CSV 预演不写库、不审计，任一错误正式提交返回 422 并保留完整行计划，正确行也不写入；成功提交由仓储事务一次完成并逐台审计。解析覆盖 BOM、CRLF、多行引号的物理行号、重复规范化 SN 的所有位置、坏表头、占位 SN、非法 UTF-8/NUL。数据库读失败返回 500，不伪装为新建。当前 OpenAPI 为 9 条路径、19 个组件，独立校验通过 `task6-oas-validation.log`，CSV 的媒体类型与预演/导入两种结果均入文档。

详细输出与后续恢复台账在仓库内 `.superpowers/sdd/2026-10-12-layer5-console/`：`baseline-check.log`、各任务的 `taskN-green.log` / `taskN-check.log`、OpenAPI 校验日志及 `progress.md`。不把当前阶段的通过表述为整层完成，独立整层审查安排在 15 项任务完成后。

## 已作出的接缝调整

任务 10 的 WSL `make check` 退出 0（控制台 race 400.139 秒），功能测试通过（8.820 秒）。预览调真实 `snapshot.Build` 与 `render.Render`，菜单、应答文件和运行脚本逐字节与直接调用渲染器一致；包含每个实际执行插槽的运行脚本及钉住摘要的 hook 原文。文件名复用渲染器的暂存约定，不能因 catalog 只有应答/附属文件的固定名字就跳过菜单和脚本。相同请求输出确定，预览不建任务、不写审计；显式指定的主机或 ISO 不存在时立即返回 404，不回退示例。参数和渲染错误按核心类别返回 409/422，整份文件包不部分返回。

未指定的 ISO、主机、固件及服务地址标明示例，预览令牌和 finalize 令牌始终为示例，即使用了真实主机和 ISO 也不谎称为真实下发凭据。可显式选择模板勾选的系，菜单固件独立于主机登记元数据。样例制品由现有必需角色和格式系统值词表产生；样例产品/edition 明确标注为示例。实际内置模板声明的 13 个系逐一验证，Windows Desktop 另验证自定义模板管线；未知 ESXi 示例明确不可用，真实 ESXi 使用磁盘上原始 boot.cfg，保留模块顺序、嵌套路径和未知字段。原始配置缺失不会用伪造配置补齐。真机安装资格仍依照第 3/4 层交接边界留给第 7 层。

插槽清单由真实扫描器产生，按首次正文出现顺序列出，位置按 rune 计；错误和后续重名位置也返回版本化问题对象。五角色均可只读预览/查询插槽。新增 `BootConfig` 和 `PreviewEndpoints` 窄接缝待任务 14 注入实际目录和服务地址；任务 12 使用同一渲染帮助函数查看固化的任务快照。当前 39 条路径、62 个组件通过独立 OpenAPI 校验，原始文档保存在 `task10-openapi.json`。

任务 9 的 WSL `make check` 退出 0（控制台普通测试 90.933 秒，race 342.995 秒），生命周期功能测试通过真实 PostgreSQL（9.975 秒），覆盖 hook 与模板各五个端点的五角色权限。状态写操作都要求正数客户端 `?rev=`；缺失、格式错误返回 400，陈旧修订或非法转换返回 409，不写失败审计。审批人取当前登录用户，不能用请求字段冒充；作者审批自己及未通过激活判定返回结构化 422。批准在仓储事务里锁住当前版本和被引用的 hook 后重新判定，提交后引用被废弃仍会挡住审批，记录继续停在 review。

按总 spec §5.2，提交是进入待审批，返回当前诊断；完备性阻断发生在批准，而非保存或提交。驳回须给出非空、非纯空白的可存文本，理由原样进审计。validate 正确返回 `ok` 和小写问题列表，不改状态、Rev 或审计；引用读取使用请求上下文，真实数据库失败返回 500，不伪装成缺失引用。旧示例的有效 kickstart 夹具漏了现有目录要求的 firstboot，及版本审计目标漏了 `@1`，已按当前规则修正。当前 37 条路径、57 个组件通过独立 schema 校验，原始文档保存在 `task9-openapi.json`。

任务 8 的 WSL `make check` 退出 0（控制台 race 238.888 秒），完整控制台无缓存测试通过（43.772 秒），仓储、内置内容与激活判定均为实际实现。验证草稿允许不完备内容，缺失或陈旧 Rev 被拒，同一 Rev 的并发保存只有一个成功；作者等元数据和派生来源不能由请求改写。已审批来源可开新草稿，已有草稿会阻止再次开版本，删除的版本号不重发；派生整份复制但不改来源。内置内容只读，模板引用的 hook 草稿也受到删除保护。草稿操作不写审计，改名单独写审计。

旧计划保存示例错误地用当前 Rev 覆盖客户端 Rev，现已保留客户端值。旧示例声称 `activation.Template(t, nil)` 会跳过引用检查，但实际代码会报 `hook_ref_missing`；现在每页合并钉住的版本键、批量读真实 hook，再产生诊断。非法草稿键留给激活判定，不能阻断读取。嵌套 DTO 将参数、实现、取值来源、实例、选项及派生键映射为小写 JSON，保留零/false 指针和空数组/对象；核心存储 JSON 与 golden 保持原样。新增回归测试复现了 OpenAPI 丢失匿名私有结构的公开字段，生成器现与 JSON 的可见性一致。当前 27 条路径、55 个组件通过独立 schema 校验（`task8-oas-validation.log`）。

任务 7 的 WSL `make check` 退出 0（控制台 race 213.160 秒），功能测试已通过真实 PostgreSQL，ISO 来源操作用记录调用的替身。新增 `/isos/{id}/progress` 直接读第 4 层已有的来源、计数、修订号和区间；读取期间发生上传时重读，避免混合旧计数和新区间。新增 `/isos/{id}/sources` 支持补齐未登记的主介质或必需附加来源，来源替换仍不在这个接口中。来源登记失败保留已创建记录，并通过 `Location` 暴露其 ID，方便查询、补登记或删除。

分片使用二进制媒体和必填 `Content-Range`，范围须符合登记的总大小；流式读取也能拒绝过短或过长的未知长度请求，校验发生在第 4 层暂存分片之前。多个已知大小来源累计估算暂存需求并防溢出，本地原始介质不计暂存复制。新增 `iso_space_insufficient` 原因，给出剩余空间、缺口和下一步，代码表对账为 94 项。OpenAPI 的当前 18 条路径、32 个组件独立校验通过 `task7-oas-validation.log`。

删除只调用装配点提供的 `ISODeletion` 窄接口，缺少它时失败，不绕过清理协议直接删行。第 4 层的 `ISOSource` 原签名保持不变；真实 `iso.Sources` 仍可结构性满足接口。任务 14 必须验证删除快照先持久化、数据库删除提交后才清理字节，以及启动时的恢复和清理重试；任务 7 只证明控制台委托边界，尚未声称后台获取、导入或清理已经接通。

- 沿用既有确认设计和计划，在现有分支顺序实现，不重开设计流程或创建新 worktree。
- 第 4 层已经落地：任务 7/14 接入真实 ISO 服务、启动恢复、来源调度及持久化删除后清理；控制台仍只依赖自己声明的窄接口。任务控制继续明确返回第 7 层尚未实现，不写临时重试安全规则。
- 核心 JSON 与 golden 字段保持原样，控制台在边界转换成小写字段的 DTO。错误展示文案集中在 `model/codes.go`；绑定只接受一个 JSON 值。
- 系统值全局词表包含最终第 3 层实际登记的 11 项；作者能力表的限制保持原样。
- 装配点守卫已登记，包数下限暂为 0，任务 14 创建真实包时改为 1。新规则的反例经完整 `checkModule` 运行，不额外引入 lib/pq 依赖。
- 默认校验服务连接超时后，通过 goproxy.cn 的签名校验镜像取得依赖；没有关闭 checksum 校验。

用户仓储已经纠正旧计划示例的 Rev 缺失比较、错误的读库帮助函数签名、空口令漏检及无依据的显示名长度限制。用户字段问题使用专用原因代码，不误报为 UTF-8/NUL。

JSON 绑定的回归测试真实复现了非法 UTF-8 被标准解码器替换成 U+FFFD 的问题；现在先验证原始 JSON 字节再做类型绑定。查询令牌由 SSE 路由声明决定，不能只凭 `/stream` 后缀绕过；单条领域错误保留类别对应状态码。OpenAPI 实际生成组件定义，不把悬空引用推迟给第 6 层；时钟必须注入，不在控制台兜底读真实时间。

HTTP 更新已要求客户端 Rev，坏的 limit 不再静默变成默认值；初始管理员强制改密已持久化并由服务端执行。任务 14 的初始化仍须设置这一标记。主机入口按仓储调用方契约先规范化 SN，CSV 属性值原样保留，错误批次不会被筛成部分导入。下一项是任务 11：向导五步与整批任务提交。后台恢复调度与持久化删除清理仍由任务 14 完成。
