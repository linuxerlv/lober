## 验证

任务 3、4 的 WSL `make check` 同样退出 0。用户用例覆盖审计失败回滚、两次并发更新只有一个成功、并发撞用户名、禁用后恢复、不可修改身份及建档时间、字节序分页、默认 100 条与取消的上下文。控制台 HTTP 用例使用真实 PostgreSQL，验证当前角色、禁用状态、权限、审计、panic、SSE 查询令牌范围及令牌不进日志。通知中心并发发布和退订在 race 下通过。

任务 4 的文档当前有 2 条路径、7 个组件，使用本机 Python jsonschema 对[OpenAPI 官方 3.0 Schema](https://spec.openapis.org/oas/3.0/schema/2024-10-18)独立校验通过；原始结果在 `task4-oas-validation.log`。官方 schema SHA256 为 `2385f5bbb8c37878daae73baeabe7f34b2f022a4a8c049329ee61f71796f039c`。Go 测试另验证路由对账、真实字段、递归引用、路径参数、独立文档对象和重复编码确定性。

详细输出与后续恢复台账在仓库内 `.superpowers/sdd/2026-10-12-layer5-console/`：`baseline-check.log`、各任务的 `taskN-green.log` / `taskN-check.log`、OpenAPI 校验日志及 `progress.md`。不把当前阶段的通过表述为整层完成，独立整层审查安排在 15 项任务完成后。

## 已作出的接缝调整

- 沿用既有确认设计和计划，在现有分支顺序实现，不重开设计流程或创建新 worktree。
- 第 4 层已经落地：任务 7/14 接入真实 ISO 服务、启动恢复、来源调度及持久化删除后清理；控制台仍只依赖自己声明的窄接口。任务控制继续明确返回第 7 层尚未实现，不写临时重试安全规则。
- 核心 JSON 与 golden 字段保持原样，控制台在边界转换成小写字段的 DTO。错误展示文案集中在 `model/codes.go`；绑定只接受一个 JSON 值。
- 系统值全局词表包含最终第 3 层实际登记的 11 项；作者能力表的限制保持原样。
- 装配点守卫已登记，包数下限暂为 0，任务 14 创建真实包时改为 1。新规则的反例经完整 `checkModule` 运行，不额外引入 lib/pq 依赖。
- 默认校验服务连接超时后，通过 goproxy.cn 的签名校验镜像取得依赖；没有关闭 checksum 校验。

用户仓储已经纠正旧计划示例的 Rev 缺失比较、错误的读库帮助函数签名、空口令漏检及无依据的显示名长度限制。用户字段问题使用专用原因代码，不误报为 UTF-8/NUL。

JSON 绑定的回归测试真实复现了非法 UTF-8 被标准解码器替换成 U+FFFD 的问题；现在先验证原始 JSON 字节再做类型绑定。查询令牌由 SSE 路由声明决定，不能只凭 `/stream` 后缀绕过；单条领域错误保留类别对应状态码。OpenAPI 实际生成组件定义，不把悬空引用推迟给第 6 层；时钟必须注入，不在控制台兜底读真实时间。

下一项是任务 5。HTTP 更新须带入客户端 Rev，查询坏的 limit 不能静默变成默认值；初始管理员强制改密必须持久化并在服务端执行，不能只给前端提示。认证测试将走真实 HTTP 登录，已有私有会话夹具只用于独立中间件测试。
