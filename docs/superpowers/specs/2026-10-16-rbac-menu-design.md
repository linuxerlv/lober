# RBAC 菜单配置与前后端权限修复设计

日期：2026-10-16

状态：会话设计已获用户确认，本文待用户审阅；尚未开始产品代码实现。

## 1. 用户目标和验收范围

管理员能够在线选择一个既有角色，勾选该角色可见的菜单并保存。配置持久化，重启后保留。与此同时修复本次审查确认的登录字段不一致、登出未撤销会话、首次强制改密没有入口、写操作按钮缺少权限判断，以及前后端角色路由矩阵冲突。

保留 viewer、operator、hook-author、hook-approver、admin 五个角色和现有 16 个权限码。一个账号对应一个角色。本轮不增加自定义角色、权限码编辑器或多角色合并规则。

用户于本次会话明确要求“都加上，这个功能+问题修复”，并确认了菜单配置、权限联动、默认配置、认证修复、强制改密和验证六项设计。

## 2. 选择的方案

采用“后端保存菜单 ID，前端维护可信路由定义”的方案。后端返回用户当前可见菜单 ID 和权限码；前端以这些数据过滤本地路由、生成导航和控制按钮。

相比返回任意组件路径的后端动态路由，这一方案沿用现有 Vben 本地页面结构，避免数据库保存组件实现细节。相比只在浏览器保存配置，它能跨用户、跨进程持久化，并在服务端验证管理员权限、版本冲突和配置审计。

菜单可见性和操作权限分别生效：隐藏菜单禁止通过前端路由进入对应页面；它不撤销角色原有 API 权限。给角色显示某个菜单也不授予任何额外写入或审批权限。API 继续逐请求读取当前用户并执行权限码鉴权。

## 3. 菜单目录与默认值

菜单目录在 console 层集中定义固定 ID、显示名称、顺序、进入页面所需权限和是否必须保留。浏览器只使用目录 ID 映射可信的本地路由，不从服务端加载任意 URL 或组件。

| 菜单 ID | 对应页面 | 进入页面所需权限 |
| --- | --- | --- |
| tasks | 任务列表、详情和建任务入口 | task:read；建任务子路由另外要求 task:create |
| hosts | 主机清单 | host:read |
| templates | 模板与预览 | template:read |
| hooks | hook 管理 | hook:read |
| isos | 现有制品集页面，路由保留 /artifact-sets | iso:read |
| tools | 模板调试工具 | template:read |
| reports | 现有报表与审计页面 | audit:read |
| role-menus | 新增角色菜单配置页面 | user:manage |

尚未配置的角色默认显示其权限允许进入的全部菜单。因此五种角色均能读取主机、ISO、hook、模板和任务；仅 admin 默认拥有 reports、role-menus。写入和审批操作继续按对应权限码控制。

管理员只能选择目标角色权限允许进入的菜单。未知菜单 ID、重复 ID、非法角色、越出角色权限的菜单返回 400，整个保存失败。admin 的 role-menus 必须保留，不能取消。

非管理员角色允许保存空菜单列表。空列表表示明确禁止进入所有业务页面，与从未配置、使用默认值的状态不同。此时显示“暂无可访问菜单”的已登录页面，仍可改密和登出。

本轮不新增报表统计后端。既有页面调用旧契约的问题，在影响本轮权限、按钮操作或验收路径的范围内对齐当前接口；不以此设计承诺完整重建全部报表功能。

## 4. 持久化与并发

新增 RoleMenus 仓储能力，由 store.Store 聚合，console 只依赖对应窄接口。PostgreSQL 新增 role_menu_settings 表：

| 字段 | 约束与含义 |
| --- | --- |
| role | 主键；限定五种角色 |
| menu_ids | 非空 JSONB 字符串数组；允许空数组 |
| rev | 正整数；乐观锁修订号 |

缺少记录时返回默认配置和 rev=0。第一次保存以 rev=0 创建记录，随后 rev 递增。两个客户端基于相同 rev 保存时最多一个成功；另一个返回 409，页面保留编辑内容并提示重新读取。默认读取不写数据库、不产生审计。

配置更新与 role.menus.update 审计在同一事务提交。审计包含当前登录管理员、目标角色、变更前后菜单 ID 和注入时间；审计写入失败则配置回滚。配置 ID 按目录顺序规范化，保证比较和审计稳定。

沿用 GORM AutoMigrate、schema.go 表结构断言、现有读写事务和错误映射。新增行类型必须同时登记到 models 和 tables。升级旧库时只新增表，已有用户角色与权限映射保持原值；不覆盖已经保存的菜单设置。

## 5. HTTP 契约

所有新接口沿用 /console/v1 前缀、当前 envelope、实际 HTTP 状态码和统一路由描述表。

| 方法与路径 | 权限 | 行为 |
| --- | --- | --- |
| GET /roles/menus | user:manage | 返回固定菜单目录、五角色权限允许的菜单、当前选择及各角色 rev |
| PUT /roles/:role/menus | user:manage | 请求 {menuIds: string[], rev: number}，验证并保存单角色配置，返回规范化配置及新 rev |
| POST /auth/password | @any | 请求 {currentPassword: string, newPassword: string}，仅修改当前登录用户自己的密码 |

GET /user/info 保留现有 username、displayName、role、permissions、disabled、createdAt、rev、passwordChangeRequired，新增 menuIds 和 menuRev。role 是单个角色；不另外维护 roles 数组作为第二份服务端数据。

POST /auth/login 继续返回 {token, expiresAt, user}，其中 user 使用与 /user/info 一致的当前用户响应。前端在唯一适配层映射为 Vben 所需的 accessToken、roles=[role]、realName=displayName 和 accessCodes=permissions。移除对不存在的 /auth/codes 的运行时依赖，清理重复旧认证实现的误导性契约说明。

菜单信息查询错误必须返回错误，不以默认菜单掩盖数据库故障。普通用户管理列表不必加载其他账号的菜单配置；菜单字段属于当前会话信息和专用配置接口。

新接口纳入 OpenAPI 生成、路由权限登记检查及审计检查。现有 user:manage 足以限定管理员操作，无需增加权限码。

## 6. 密码与会话

修改密码接口只操作当前会话用户，用户名由认证结果获取，不接受目标用户名或角色。必须验证旧密码、非空且可存储的新密码，并拒绝新旧密码相同。错误说明不返回口令或散列。

继续使用既有 PBKDF2 格式和 credentials 并发门：派生散列在锁外进行，提交前在锁内复查当前凭据、禁用状态和客户端读取的用户修订号，防止并发管理员改密被覆盖。更新只替换密码并清除 passwordChangeRequired，不接受角色或其他账号字段。

密码更新与 user.password.change 审计在同一事务提交；成功后在同一凭据发布保护范围内撤销该用户所有会话，包括当前会话。前端清空认证状态，显示成功提示并回到登录页，使用新密码重新登录。

强制改密状态允许查询当前用户、修改自己密码和登出；其他业务 API 继续返回 403。旧的管理员更新用户接口保持兼容，但不作为前端首次改密入口。

登出通过已配置 Bearer token 的 requestClient 发送。已过期会话返回 401 时清理本地状态；网络故障或其他错误明确显示退出失败，允许重试，不将尚未撤销的服务端会话显示成成功退出。重新认证路径应避免 401 与 logout 相互调用形成循环。

## 7. 前端路由与配置页面

新增仅 admin 可进入的“角色与菜单”页：角色选择、可选菜单复选框、必选入口标识、保存与重新读取。没有操作权限的项目不提供选择；后端仍独立验证。保存期间禁止重复提交；409 保留编辑内容并提示版本冲突。

前端业务路由以 menuId 和接口权限作为过滤依据，替代各处手写、已经与后端不一致的角色白名单。每个子路由继承父菜单限制，建任务另外要求 task:create。路由过滤也作用于手工输入 URL，不能只隐藏导航项。

菜单配置变化和账号角色变化在下次导航、窗口重新聚焦时读取最新 /user/info 并生效；停留页面通过不重叠的 30 秒检查更新。退出或组件卸载时清理计时和事件监听。无法完成刷新时提示错误，不将刷新失败当成权限变更，也不静默扩大可见范围。

比较 role、permissions、menuIds、menuRev 和 passwordChangeRequired 判断是否需要重建动态路由。重建前清除旧动态路由、过期标签页和对应菜单，防止上一次登录或已撤销菜单的页面残留。若当前页面已不可访问，跳到第一个允许的业务页面；没有菜单则进入空权限页。登录首页同样从允许页面计算，不再无条件进入 /tasks。

新增强制改密页和已登录空权限页；它们不依赖业务菜单授权。改密守卫先于普通首页跳转，防止带 token 的用户在登录页和业务页之间循环。

## 8. 按钮和业务请求

使用统一的权限码判断，应用到以下入口及其提交处理：

| 业务操作 | 权限码 |
| --- | --- |
| 主机新增、编辑、删除、导入 | host:write |
| 任务创建及创建页 | task:create |
| 任务取消、重试 | task:cancel、task:retry |
| ISO 登记、来源、上传、取消、重试、重导、废弃和删除 | iso:write |
| hook 新建、编辑、建版本、提交和校验 | hook:write |
| hook 审批、驳回和废弃 | hook:approve |
| 模板新建、编辑、建版本、提交和校验 | template:write |
| 模板审批、驳回和废弃 | template:approve |
| 审计查询及导出 | audit:read |
| 角色菜单配置 | user:manage |

没有权限时隐藏写操作入口；提交函数再次检查，处理页面停留期间发生的权限变化。已有状态、修订号和禁止自我审批等业务限制继续执行。相关按钮的请求路径、版本号和 rev 对齐当前后端，例如提交 hook 使用 /hooks/:id/versions/:version/submit，不能继续调用旧版 /hooks/:id/approve。

后端错误始终是最终执行结果；前端不因按钮可见而跳过错误处理。只读用户能完成允许的读取与预览，不应在页面初始化时触发写接口。

## 9. 验证与交付标准

1. 仓储真实 PostgreSQL 测试：默认缺省、空菜单、创建、更新、重启后读取、相同 rev 并发竞争、审计失败回滚和旧库新增表。
2. HTTP 测试：全部新接口无 token 返回 401，非 admin 配置菜单返回 403，非法角色与菜单返回 400，陈旧 rev 返回 409；同角色另一个用户读取到已保存配置，其他角色不受影响。
3. 认证测试：真实响应字段经过适配后完成登录；改密验证旧密码及相同密码限制；首次改密拦截业务；改密和登出后的旧 token 均被拒绝；并发凭据更新不会补发或保留旧密码会话。
4. 前端行为测试：五角色路由与权限码一致；隐藏菜单不能通过 URL 进入；空菜单和作者/审批人首页正常；旧路由移除；配置冲突保留编辑；登出失败可重试；改密守卫不会循环；viewer 没有写操作按钮。
5. 浏览器联调：管理员修改某角色菜单，另一会话按约定时机刷新；刷新浏览器和重启服务后配置保留；确认首次改密、重新登录、登出和角色对应操作入口。
6. 运行适用的 Go 测试、race、vet、架构守卫、Wire 生成漂移检查，以及前端类型检查、相关测试和生产构建。按当前环境使用 WSL 中的 Go 和测试库。只在真实通过后报告通过，缺失环境或既有失败单独记录。

构建产物、当前接口契约和使用说明随实现更新，确保部署后能使用新增页面。工作区中已经存在的其他改动不回退、不混入本功能提交。实现开始时按 using-git-worktrees 检查可复用工作区并选择基线，避免丢失用户未提交改动。

## 10. 文档自检

本设计明确了固定角色范围、菜单和操作权限区别、空列表语义、admin 必留入口、并发版本、审计事务、首次改密及会话失效、动态路由移除、刷新时机和具体验收标准。各接口与数据字段已给出确定名称；未承诺新增自定义角色或完整报表后端。
