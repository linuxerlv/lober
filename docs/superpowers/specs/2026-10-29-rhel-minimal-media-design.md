# AlmaLinux、Rocky Linux 最小安装盘支持设计

状态：待确认。尚未修改产品代码。

## 目标

按正常页面流程导入两系的官方 minimal 安装盘，并完成真实装机。
沿用后端四层约定。测试在 lober VM 执行，客户机建在云服务器。

## 已核实的限制

- 两张 10.2 来源的 minimal 盘只有 `Minimal` 仓库。当前代码固定要求 `BaseOS`、`AppStream`。
- 已从官方 Alma 和中科大 Rocky 镜像小范围读取真实 `.treeinfo`，两者都明确声明 `Minimal` 分组。
- Alma 10.2 下载路径中的盘内版本字段实际为 `10`，Rocky 为 `10.2`。识别结果保留真实字段，不按文件名改版本。
- 上述小范围读取未验证完整镜像。真实导入前仍须验证可信签名清单和完整文件摘要。
- 两盘公开清单都有基础系统、curl、远程登录软件，未列 `qemu-guest-agent`。

## 方案选择

采用：根据真实元数据明确识别 minimal，保留现有完整盘要求。

直接把两个仓库改成可选，会让损坏的完整盘通过；继续下载完整盘又不符合节省空间的目标。因此不采用这两种办法。

## 四层约定

| 位置 | 责任 |
|---|---|
| 领域层 `internal/domain/media` | 根据系列和 `.treeinfo` 的明确分组声明判断布局，返回安装树根及必须存在的仓库路径。只处理事实，不读文件。 |
| 应用层 `internal/application/media` | 有界读取真实元数据，调用领域规则，把确定的根和路径交给提取计划。保留身份、摘要、状态和发布顺序。 |
| 文件实现 `internal/infrastructure/media` | 按计划复制并复核实际文件、路径和来源。不能因缺文件自行降级。 |
| 页面与接口 | 继续使用现有导入、预览和任务流程。无需新增请求参数或数据库字段。 |

优先复用 `Identified.RepoRoot` 和 `ExtractionPlan.RepoPaths`。完整盘继续走原规则。

应用确定新布局后，提取器直接消费该计划，不能再用 `importRepoRoot` 另算一次。仓库路径相对于计划中的安装树根；根目录保留 `.treeinfo`。原完整盘路径计算保留，但不能覆盖明确的 minimal 计划。

## 必须满足的行为

1. 只有 AlmaLinux、Rocky Linux 的明确 minimal 分组可选择新布局。文件名和备注不参与判断。
2. 分组清单、分组段、仓库和包目录须相互一致。重复冲突、混合布局和危险路径拒绝导入。
3. minimal 安装树根保留 `.treeinfo`，仓库检查落在 `Minimal/repodata/repomd.xml`。引导文件和安装器镜像仍来自原位置。
4. 完整盘缺少 `AppStream` 时仍失败。即使旁边有 `Minimal` 目录也不回退。
5. 保留原有路径、链接、非空文件、来源变化和发布所有权检查。同版本不同介质不覆盖旧发布树。
6. 不修改官方镜像，不伪造仓库，不关闭签名检查，也不把导入器扩成软件包管理器。

## 装机与验收

先采用 minimal 盘原生提供的基础包。验收仍覆盖序列号、目标磁盘、系统版本、网络、远程登录、配置执行、临时材料清理及一次正常重启。

建议使用受控测试账号登录客户机串口，取得真实主机公钥，再用严格核对密钥的 SSH 验收。串口必须绑定本轮客户 UUID、运行进程及其启动标记和原串口设备，防止连错机器。公钥写入独立的固定密钥文件，不能靠首次网络连接自动接受，也不能关闭检查。登录或取证失败就停在失败，不降级放行。

没有客户管理助手时，SSH 仍须核验系统、序列号、磁盘、网络、配置及临时材料清理；需要管理员权限的检查必须真实执行，不能跳过。只发出一次正常重启，确认启动编号变化、机器编号/根分区标识/分区及软件包记录不变、任务和事件不变且没有重装。

客户管理助手不是最小盘自带包，缺少它时单列“未验证该助手”，不能宣称通过。若必须保留助手验收，则另行定义可信补充软件源，不能悄悄加包或改来源。

代码测试先证明当前导入会拒绝真实 minimal 布局，再实现最小改动。覆盖合法两系、原完整盘、缺仓库、冲突声明、危险路径和发布保护。焦点测试及完整 `make check` 均在 lober VM 执行，并做独立审查。

每系分别走：完整镜像验签 → 页面导入 → 完整预览 → 创建任务 → 云端客户机装机 → 系统及正常重启验收 → 页面刷新与重登录。

## 空间和范围

保留已经通过的 Debian、Ubuntu 镜像及全部失败记录。后续 Alma、Rocky 优先 minimal；Ubuntu 继续 Server，openSUSE 继续当前支持的离线安装盘。

约 25 GiB 只是介质预算目标，不能当作实际总占用承诺。原件、展开文件、工作区和客户机磁盘分别记录。

本次不增加 Ubuntu Mini、openSUSE 网络盘、Windows 或 ESXi 支持。

## 2026-10-30 真实装机发现的兼容性修正

首轮 AlmaLinux 真实安装失败，不能按镜像 ready 判定装机通过。原安装器请求 `install//.treeinfo`、`install//treeinfo` 均为 404，随后回落请求不存在的根级 `repodata/repomd.xml`；真实 `install/.treeinfo` 和 `install/Minimal/repodata/repomd.xml` 均存在且摘要正确。安装器将答案里的仓库地址再拼接 `/`，所以 Kickstart 的仓库系统值必须去掉末尾分隔符。只修正该格式的 repo 地址；不改真实仓库根、不复制伪造元数据、不放宽静态文件路径检查，也不改变 stage2 和其他格式的地址。

真实安装环境的 `pyanaconda/anaconda_logging.py` 使用 `*.* @@%s`，即 TCP 日志传输。现有服务仅监听 UDP。沿用原 `machine.syslogListen` 地址同时支持 UDP 与原生 TCP 换行日志，保留 UDP 行为、来源 IP 的有效凭证租约、任务轮次、终态忽略和日志清理规则。TCP 必须限制连接数、单条消息大小和空闲时间；取消或启动失败必须关闭监听及活动连接。对端地址只能取真实连接，不信任转发头，不新增认证旁路、数据库字段或配置字段。

两个修正先分别补能编译且真实失败的回归用例，再实现。全部检查仍由唯一执行者在 lober VM 跑；修后焦点检查、原完整 `make check` 和独立审查通过后，用真实提交构建新候选。原失败任务、客户磁盘、串口记录和旧运行基准保留。重新装机必须使用新任务，并明确区分旧失败与新结果。日志只有在实际安装期间收到且来源、任务吻合才算通过。

此补充修复已批准 Linux 装机目标暴露的缺陷，不增加支持系统范围。远程 HTTP 上传缺少浏览器校验能力另列限制；本次 localhost 正常页面续传不代表远程 HTTP 或生产 HTTPS 上传已验收。

## 2026-10-30：真实任务日志集中到达时页面卡住

Alma02 已完成真实安装和一次正常重启。最后任务页无法正常操作，阻碍既定的完整页面验收。对照使用相同任务、首批200条和完整5473条历史：禁止实时流时页面通过；原生流下卡在状态标签，栈落表格布局更新；保留原生连接和 onopen、仅诊断跳过 task 消息处理时，5273条真实消息在311毫秒内到达且页面全部分页通过。由此定位到原消息处理组合路径，不声称 merge、表格或详情读取中某一处已单独证实为主因。全部对照仅作诊断，不能算最终通过。

收敛方案：沿用原事件协议和完整历史，在页面将集中消息合并处理，限制表格刷新和详情重读频率。保持按seq去重排序、游标、当前页、最新状态和终态记录；不丢弃旧日志，不截断历史，不关闭真实事件流，不修改后台接口或表格依赖。定时刷新须有上限并在离开页面时清理。控制器选择最多约100毫秒一批作为内部实现预算，用户操作及完整信息不变。

备选的关闭流会失去实时能力，删除历史会破坏完整验收，升级表格库会扩大风险，均不采用。这是修复已批准真实装机验收中的故障，沿用用户继续实施授权；不增加新的产品范围。先以集中回放测试取得真实失败，再最小实现、VM前端检查、独立审查，最后以未拦截的真实页面刷新/退出重登录完成验收。
