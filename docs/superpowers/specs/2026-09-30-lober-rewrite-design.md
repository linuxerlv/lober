## 1. 目标与范围

按以下要点重写 lober：

- ISO、模板、hook 各自独立；主机、ISO、模板到建任务时才配到一起
- ISO 属于一个族、一个系；模板属于一个族，可以勾多个系
- 模板由多个 hook 拼成，hook 是组件，数量不限；模板可以派生，派生后可以替换其中的 hook
- 主机先登记，向导里搜索多选，批量建任务
- 系统自带每种应答格式一个模板
- ISO 可以远程下载、浏览器上传，或登记服务器本地路径

代码从零重建，分七层依次做（§7.4），不参照旧代码。

不带的旧能力：

| 旧能力 | 处理 |
|---|---|
| 服务端磁盘规划、inspect 硬件采集 | 分区 hook 在装机时选盘；要固定用哪块盘，写进主机属性，经参数传给分区 hook |
| provider 插件体系：网卡规划、IPAM、DNS 登记、告警通知、Starlark，以及 gRPC、exec、HTTP 三种加载方式 | IP 来自主机登记；不做告警，失败只在控制台可见 |
| facts 读写端点、心跳插件 | 不做 |
| 决策 dry-run | 由预览取代 |
| MAC 双因子 | 身份只认 SN（C6、C32）。SN 打错、恰好撞上另一台机器，是接受的残留风险 |
| 镜像直写、机器面 TLS、Secure Boot | 不做 |

照旧保留：任务钉住它引用的模板版本、hook 版本和 ISO；被引用的对象只能废弃，不能删除；RBAC 与审计；系统写上盘之后的失败不自动重装；目标机上的凭据清理；信号遥测与分阶段超时；引导链（静态 DHCP、两跳 iPXE、按系出菜单、引导时校验架构与固件）。

## 2. 概念

### 2.1 族、系与格式

族给人分组，固定三个：linux、windows、esxi。

系是发行版一级。每个系属于一个族，对应一种应答格式。同一发行版跨大版本换了安装器的，按安装器拆成两个系，目前只有 SUSE：15 用 AutoYaST，16 用 Agama。版本号是 ISO 的属性，不单独成系。首批内置的系：

| 族 | 系 | 格式 |
|---|---|---|
| linux | RHEL、Rocky Linux、AlmaLinux、openEuler、OpenCloudOS | kickstart |
| linux | Debian | preseed |
| linux | Ubuntu | autoinstall |
| linux | SLES 15、openSUSE Leap 15 | AutoYaST |
| linux | SLES 16、openSUSE Leap 16 | Agama |
| windows | Windows Server、Windows 桌面版 | unattend |
| esxi | ESXi | ESXi ks |

格式决定四件事：支持哪些执行时机、必需哪些系统部件、要给机器下发哪些文件、每个时机里能用哪些解释器。每个系另外登记：怎样按内容识别它、仓库树怎样算完整、固件要求（ESXi 只走 UEFI）、要求哪些附加来源。附加来源目前只有一项：Debian 要同版本的官方 netboot 包，因为 netinst ISO 里的 initrd 是光驱版，不能网络装机（ce9cd56 实测）。

执行时机是一张全局词表，按先后排：装前、装后（在安装环境）、装后（在目标系统内）、首次开机。每种格式支持其中一部分。两个时机的先后如果由正文书写位置决定、而不是由安装器决定，它们在次序上同级。例如 kickstart 的 `%post --nochroot` 与 `%post` 按出现顺序执行，两者同级。

### 2.2 ISO

ISO 属于一个族、一个系，创建时就要声明，这时字节可能还在下载或上传。字节到齐后按内容复核系，并识别版本和架构；Windows 还要列出 ISO 里有哪些 edition。

导入把内核、initrd 和仓库树解到 nginx 发布的目录。Ubuntu 和 Windows 有额外要求：

- Ubuntu：安装器启动后要经 HTTP 把整张 ISO 下进内存（内核参数 `url=`），所以原始 ISO 也要发布到制品目录，目标机内存要比 ISO 大出一截。旧系统的 Ubuntu 菜单缺这个参数，那条路径不可能装通。
- Windows：安装源放进 SMB 共享；WinPE 直接用 ISO 里的 `boot/bcd`、`boot/boot.sdi`、`sources/boot.wim`，经 wimboot 引导（待真机核实）。

ISO 不知道任何模板。

### 2.3 主机

SN 是主机唯一的身份。架构和固件是可选属性，登记了就参与兼容性校验。其余属性都是自定义键值（IP 与前缀、主机名、机架位、业务网卡的 MAC、VLAN 号等），系统不解释，只供参数引用。主机可以单台登记，也可以用 CSV 批量导入，CSV 有哪些列就登记哪些属性。

### 2.4 hook：组件

一个 hook 是一个功能，比如「LVM 分区」「配业务网」「装监控 agent」，相当于 Vue 模板里的一个 Element 组件。它声明一组参数（相当于 props），由全部实现共用。每份实现属于一个族，可以覆盖该族的多个系，分两种：

- 片段：一段用该格式语法写的文本，渲染时放进插槽。分区、软件包这类声明式内容属于这种。片段覆盖的系必须同格式。
- 脚本：装机时在目标机上执行，声明解释器与适用时机。可以跨格式，只要解释器和时机在它覆盖的每个系里都可用。

同一个 hook 在不同系可以是不同种类。例如「SSH 公钥」在 kickstart 里是一行 `sshkey` 指令（片段），在 Debian 里只能靠装后脚本写 authorized_keys（脚本）。

hook 只有一层：实现里不能引用插槽或别的 hook。组件套组件会带来循环引用和版本连锁，这一版不做。

### 2.5 模板

模板只有一份正文，属于一个族，可以勾该族里同一种格式的多个系。正文由作者按该格式写，系统不解析它的语法，只识别四类占位符：

| 占位符 | 作用 |
|---|---|
| 插槽 | 正文里挂 hook 的有名位置，名字和个数由模板定。片段插槽在渲染时展开成槽里的各个片段。执行插槽要声明执行时机，在正文里只展开成一行命令，装机时由这行命令取回并依次执行槽里的脚本，所以 preseed 那种只能写一行的位置也放得下 |
| 系统部件 | 格式要求的系统代码，如 syslog 指向、首次开机脚手架、凭据清理。必须有，换不掉，相当于框架自带的组件 |
| 系统值 | 系统按任务填入的值，如安装源地址、网关地址。模板因此不用知道 ISO |
| 参数引用 | 模板自己声明的参数 |

其他 `{{…}}`（如 cloud-init 的 Jinja）原样保留；lober 自己命名空间下写错的占位符报错。多行内容展开时，每一行都套用占位符所在行的缩进，因为 autoinstall 是 YAML。

示意如下（省略了插槽的类型与时机标注，占位符的确切写法在第 1 层计划里定）：

```
cmdline
url --url={{iso:repo}}
{{lober:syslog}}
{{slot:分区}}
%packages
{{slot:软件包}}
%end
%post
{{slot:装后配置}}
{{lober:firstboot}}
{{lober:cleanup}}
%end
```

模板另带一张装配表，记录每个插槽按顺序放哪些 hook，以及每个 hook 实例的参数取值来源（写死的值、某个主机属性，或留给操作员在向导里填），并决定向导里能不能改。同一个 hook 可以在一个模板里出现多次，各带一组参数，比如两块业务网卡各配一次。

模板名字唯一，内容可以重复。派生产生一份独立副本，并记下来源模板和版本；来源出了新版本时，派生模板会收到提示和差异，但不会被自动修改。「用 b 覆盖 a」就是在副本里把插槽中的 a 原位替换成 b，插槽和顺序不变，同名参数的取值沿用。

### 2.6 参数

模板和 hook 都能声明参数，每个参数都有类型。进入正文或片段的值只能是不会改变应答文件结构的受限类型（IP、主机名、整数、枚举、磁盘路径、包名列表等）；自由文本只能进脚本，经环境变量传入。正文和片段里引用的参数一律必填：它们没有条件语法，缺值只能渲染出空值，旧系统出过两次这样的问题（072cf91、7d22dfa）。

取值来源有四种：模板写死的值、hook 的默认值、主机属性、操作员填写。被引用的主机属性没登记，就当作没有值。取值范围也可以来自 ISO，比如 Windows 的 edition。

### 2.7 装机任务

一个任务引用一台主机、一个 ISO、一个模板，外加这台主机的参数取值。批量创建就是每台主机一个任务，同一批用同一个 ISO 和模板，全部校验通过才一起创建。任务一建成就固化成快照：模板版本、hook 版本、ISO，以及全部参数取值。之后的渲染只读快照。

一台主机同一时刻最多有一个未结束的任务（C31）。上一个结束后，可以给它再建一个，按主机列出的任务就是它的装机历史。失败后重试沿用同一个任务。

### 2.8 内置内容

七种格式各一个内置模板，由内置 hook 拼成。首批内置 hook 是分区、软件包、网络、账号与 SSH 公钥。每个 hook 按格式写实现，同格式的系共用一份，有差异的系（比如包名不同）单独一份；其余内容写在正文里。

| 格式 | 内置模板勾的系 | 验证版本 |
|---|---|---|
| kickstart | RHEL、Rocky Linux、AlmaLinux、openEuler、OpenCloudOS | OpenCloudOS 9.6，另加 Rocky 或 AlmaLinux 9 |
| preseed | Debian | 13 |
| autoinstall | Ubuntu | 24.04 |
| AutoYaST | SLES 15、openSUSE Leap 15 | Leap 15.6 |
| Agama | SLES 16、openSUSE Leap 16 | Leap 16.0 |
| unattend | Windows Server | 2016–2025，按 edition 参数区分；真装只验 2025 |
| ESXi ks | ESXi | 8、9 |

内置模板和 hook 只读，出厂即已审批，随 lober 版本发布新版本，旧版本保留。只有模板能派生，hook 不能。要改内置模板，就先派生；要把其中的 hook a 换成 b，先看 b 在不在，不在就新建一个，再在派生出的模板里按 §2.5 的「用 b 覆盖 a」原位替换。

## 3. 契约

总则：校验不过就拒绝操作，并说清缺了什么、下一步怎么办，不做静默降级。校验分四个时点：保存、激活（审批）、建任务、引导。能存成 UTF-8 文本的草稿都能存，完备性只在激活时要求。文本必须是合法的 UTF-8、不含 NUL：数据库存不下 NUL，非法的字节存进去再取出来也不是原来的字节，按原字节算的摘要就对不上；所以 Windows 上存成 UTF-16 或 GBK 的脚本要先转成 UTF-8 再上传。主机、ISO、模板能不能配到一起，要到建任务时才查，因为在那之前它们互不知道对方。

**族、系与格式**

- C1 族固定三个。系是发行版一级，每个系属于一个族，对应一种应答格式；同一发行版跨大版本换了安装器的，拆成两个系。格式共七种：kickstart、preseed、autoinstall、AutoYaST、Agama、unattend、ESXi ks。执行时机表、必需的系统部件、下发文件清单、各时机可用的解释器都由格式决定。族、系、格式都由系统内置，用户不能增改，新增要发新版本。

**ISO**

- C2 创建时必须声明族和系，且系属于该族。
- C3 字节到齐后按内容识别系，识别结果与声明不符就拒绝导入，并同时给出声明值和识别值。填了期望 SHA256 的，内容必须一致。该系要求的附加来源必须齐备，且版本与 ISO 一致。
- C4 内容相同（SHA256 相同）的 ISO 只导入一次。
- C5 只有导入完成、并且通过完整性判定的 ISO 能用于建任务。导入完成的 ISO 必须带版本和架构，完整性判定要求族、系、架构、版本和 ISO 提供的取值集合都合法。版本会成为制品目录里的一段路径，所以首字符必须是字母或数字，. 与 .. 都不合法。导入在置为可用之前做这项判定；状态是可用、记录却不完整的 ISO，建任务时同样不能用，并指出是哪一项不对。

**主机**

- C6 SN 是主机唯一的身份，规范化后全局唯一。拒收空 SN 和已知的占位 SN（如 To Be Filled By O.E.M.）。
- C7 其他属性都可选。架构和固件参与兼容性校验，其余属性系统不解释，只供参数引用。

**hook**

- C8 一份实现只属于一个族，可以覆盖该族的多个系；同一个 hook 里，一个系最多出现在一份实现中。实现要么是片段，要么是脚本。片段覆盖的系必须同格式；脚本可以跨格式，但声明的时机和解释器在它覆盖的每个系里都必须可用。实现里不能引用插槽或别的 hook。
- C9 参数声明由整个 hook 共用，实现里引用的参数必须都声明过。
- C10 脚本实现要声明解释器和适用时机，解释器在这些时机里必须可用。可用表由系统按格式维护，比如 Debian 安装期只有 busybox sh。
- C11 脚本 hook 有超时，并标明是否必需：必需的失败则任务失败，非必需的失败记下后继续。hook 给默认值，模板可以按实例改。

**模板**

- C12 名字规范化后唯一，内容允许重复。模板名与 hook 名只能由英文字母、数字和美式键盘上可见的符号组成（可打印 ASCII），1–64 个字符，不能有空格、中文或其他字符；规范化只去掉首尾空白，大小写不同的算同名。以 `lober:` 开头的名字（比较不分大小写）留给内置内容，用户用了就拒绝；内置内容的名字必须带这个前缀。只收 ASCII，是因为系统不做 Unicode 规范化，看着一样的中文、全角或带不可见字符的写法会绕过唯一约束。插槽名和参数、选项的显示名不受这条限制，可以用中文。
- C13 只有一份正文，属于一个族，可以勾该族的多个系；这些系必须同格式，正文按这种格式写。族和系可以先留空，没勾系的模板不能激活。
- C14 插槽只来自正文：名字、类型和执行时机都写在正文的占位符里，不在别处另存。插槽名不能重复，执行时机必须在该格式的时机表里。
- C15 该格式的每个必需系统部件，正文里都必须恰好出现一次。
- C16 装配表只能引用正文里存在的插槽。对模板勾的每个系，插槽里的每个 hook 都要有覆盖这个系的实现；实现种类要和插槽类型一致；放进执行插槽的，适用时机要包含该插槽的时机。
- C17 同一个 hook 可以在一个模板里出现多次，每次各有一组参数。
- C18 系统占位符以外的正文原样输出。系统不解析也不校验应答文件语法，语法只能靠预览和真装机验证。

**参数**

- C19 每个参数都有类型，取值必须通过类型校验。进入正文或片段的值只能是不会改变应答文件结构的受限类型，自由文本只能进脚本。
- C20 装配表里，模板为每个参数指定取值来源（写死的值或某个主机属性），并决定向导里能不能改；模板没指定的，沿用 hook 的默认值。被引用的属性主机没登记，就当作没有值。正文和片段里引用的参数一律必填。最后仍然没有值的必填参数，向导里每台主机都得填。
- C21 取值范围来自 ISO 的参数（如 Windows 的 edition），值必须在该 ISO 实际提供的集合里。

**版本、审批与派生**

- C22 模板和 hook 审批后才能用于建任务，草稿可以预览。审批人不能是作者。已审批的模板只能引用已审批的 hook 版本。
- C23 已审批的版本不可修改，修改会产生新版本，要重新审批。模板引用的是 hook 的具体版本，hook 出了新版本，模板不会自动跟随。向导里每个模板只提供它当前的已审批版本。
- C24 只有模板能派生，hook 不能。派生产生一份独立副本，并记下来源模板和版本，来源之后的修改不影响它。来源出了新版本时，派生模板会收到提示和差异，但不会被自动修改。
- C25 内置模板和 hook 只读，出厂即已审批，随 lober 版本发布新版本，旧版本保留。
- C26 被模板或任务引用的对象只能废弃，不能删除。主机没有废弃状态，被任务引用过就只能留着（§8）。废弃的对象不能再被新引用，新建任务经模板间接引用也算；已建的任务不受影响。

**装机任务**

- C27 一个任务引用一台主机、一个 ISO、一个模板；ISO 的系必须是模板所勾的系之一。渲染时，每个 hook 取覆盖该系的实现。
- C28 架构和固件校验两次。建任务时按主机登记值校验，登记了才校验。引导时按机器实际上报的值校验，这一次必做，不符则任务失败、不签发 token。
- C29 任务一建成就固化：模板版本、hook 版本、ISO，以及全部参数值（包括从主机属性取来的值）。之后的任何修改都不影响它。
- C30 批量建任务是原子的：任何一台不通过，一台都不建，并逐台列出原因。
- C31 一台主机同一时刻最多有一个未结束的任务。
- C32 引导时只按 SN 匹配任务，查不到就不签发 token，也不留记录。
- C33 状态只进不退，推进只看执行时机的先后；同一时机内以及同级时机之间，插槽谁先谁后不影响状态。
- C34 安装器完成、机器开始重启进新系统之后的失败，不能自动重装，也不能一键重试，因为数据可能已经在盘上。
- C35 预览和实际下发走同一个渲染，输入相同，输出就逐字节相同（token 除外）。

## 4. 接口

每个接口写明负责什么、不负责什么、谁实现、谁调用。

### 4.1 层 1 核心模型

只做判定和变换：不读库，不碰时钟、文件和网络，不依赖任何其他模块。

- 族系目录：登记族、系、格式的关系，以及 §2.1 所列的每种格式、每个系的属性；iPXE 上报的构建架构与 ISO 架构怎样对应也在这里定义（BIOS 的 iPXE 是 32 位构建，报 i386）。还带两份机器面约定：地址格式（渲染按它写地址，网关按它注册路由），以及制品目录布局（导入按它写文件，ISO 记录只存相对路径，渲染据此拼出完整地址，nginx 部署配置也按它写）。目录内置在程序里（C1），几乎所有模块都读它。
- 正文扫描：把模板正文或片段切成原文和占位符，给出插槽（名字、类型、时机）、系统部件、参数引用、系统值引用，并标出写错的占位符；不管应答文件本身的语法（C18）。控制台用它做保存和激活校验，并给编辑器列出插槽；渲染用它展开占位符。两边必须用同一份，否则会出现编辑器里有这个插槽、渲染时却找不到的情况。
- 激活判定：判断 hook 或模板在审批前是否完备。hook 按 C8–C11 查，模板按 C13–C17、C19、C22 查。入参由调用方凑齐（比如模板连同它引用的各个 hook 版本），结果是通过，或逐条列出原因。由控制台调用。
- 参数求值：输入是参数声明（模板的，加上每个 hook 实例的）、装配表里的取值来源、主机属性、ISO 提供的取值范围、操作员填的值。输出两样：向导里逐台显示的表单（哪些锁定、哪些能改、预填什么），以及最终取值或逐项错误（C19–C21）。由控制台调用。
- 准入判定：判断这台主机、这个 ISO、这个模板能不能建任务，逐台给出原因（C5、C22、C26、C27、C31，C28 在建任务时的那一次校验，以及 C21 里不看主机就能判定的那部分：ISO 提供了参数要的取值集合）。同一套规则也用来筛候选：给定主机，列出能用的 ISO；给定 ISO，列出能用的模板。向导的筛选和建任务的校验都调用它，两边就不会不一致。
- 快照构建：把选定的主机、ISO、模板版本、hook 版本和参数取值，整理成渲染需要的完整输入。建任务时，结果随任务固化（C29）；预览时现算现用。C35 靠的就是全系统只有这一份。

### 4.2 层 2 存储

- 仓储：各类对象的持久化，以及只有数据库才守得住的约束：SN 唯一、hook 名与模板名唯一（C6、C12）；已审批的版本不可修改（C23）；被引用的对象不能删除（C26）；批量建任务原子提交（C30）；一台主机只有一个未结束的任务（C31）；状态推进不被并发写覆盖（C33）。实现只有 PostgreSQL 一份。契约测试连测试环境的真实库（§6.4），找不到连接串就失败，不跳过。调用方是控制台、网关、状态机、ISO 模块和内置内容装载。
- 范围：本层的仓储管主机、ISO 的记录与状态、hook、模板、任务（批量建，以及状态的条件推进）、事件（任务的追加式日志）和审计。ISO 的获取来源（下载断点、上传分片、本地路径）推迟到第 4 层，用户、角色与会话推迟到第 5 层，在那之前审计里的操作者只是一个字符串。推迟是安全的：建表用 GORM 的 AutoMigrate，它能给已有的库加表、加列、加索引；它改不了已有的索引和约束，所以本层建的表，索引和约束一次定对，由每次启动时的表结构断言守住（§7.2 第 2 条）。以后哪一层要改它们，得先写一步删掉旧定义的升级动作。
- 并发兜底：仓储不另写业务规则。控制台先调层 1 的判定，给出可读的原因（§6.2 第 1 条）；审批和建任务时，仓储在写入的那个事务里，对加锁后读到的最新数据重跑层 1 的同一个判定（审批重跑激活判定，建任务重跑准入判定），不通过就整个回滚，返回层 1 给的问题（建任务时另把没登记的主机逐台报出来）。两次判定之间别人改了数据（比如引用的 hook 刚被废弃，主机刚被删掉或刚建了别的任务），也漏不过去，判定规则仍然只有层 1 一份。数据库的约束（唯一与部分唯一索引、外键、CHECK）是最后一道防线。
- 名字放在身份上：每个 hook、每个模板各有一个身份，名字记在身份上，各版本共用，hook 之间、模板之间规范化后各自唯一；改名是单独的操作，要审计。每个身份同时最多一个未审批的版本（草稿或待审批）。
- 已审批和已废弃的版本永不删除，只能删草稿。这比 C26 严：C26 只禁止删被引用的。删的草稿是一个身份仅剩的版本时，身份一起删掉，名字随之空出来。

### 4.3 层 3 渲染与内置内容

- 渲染：输入是快照，加上本次请求的系统值（token、网关与制品等地址）。输出是机器要的某一个文件：引导菜单、应答文件、附属文件（Ubuntu 的 meta-data、ESXi 的 boot.cfg、Windows 的 WinPE 启动脚本），或某个执行插槽的运行脚本。纯函数，不读库，同样的输入逐字节产出同样的结果。只有网关和预览调用它，别处都不自己拼应答文件。
- 内置内容：七个内置模板和它们用到的 hook，随程序发布。放在这一层，是因为它们的正确性靠渲染的 golden 测试守着。启动时由装配点装载（§6.2 第 11 条）。

### 4.4 层 4 ISO

- 来源获取：登记来源（远程链接、浏览器上传、服务器本地路径），把字节取到本地。支持断点续传，进程重启后能接着取；校验期望的 SHA256，报告进度。远程链接先过 SSRF 校验：只放行 http 与 https，拒绝回环和链路本地地址，按解析出的 IP 直连，每一跳重定向都重新校验。它只管把字节取齐，不管内容是什么。控制台调用它来登记来源、上传分片、查进度、取消和重试。
- 导入：字节到齐后识别系、版本和架构（Windows 另列 edition），与声明比对（C3），按 SHA256 去重（C4），按制品目录布局解出文件，写好清单后置为可用（C5）。异步执行，进程重启后能恢复。由来源获取在字节到齐时触发，控制台也可以手动重新导入。

### 4.5 层 5 控制台

- 控制台 API：给人用的全部 HTTP 接口，覆盖主机的登记与 CSV 导入；ISO 与 hook；模板的编辑、派生、审批、废弃与预览；向导（候选 ISO、候选模板、参数表单、批量建任务）；任务的列表、详情、进度推送、取消与重试；用户、权限与审计。它只做编排：从仓储取数据，交给层 1 判定，再把结果写回仓储，自己不写业务规则。

### 4.6 层 6 前端

- 技术栈：沿用 `web/` 里的 vue-vben-admin 5.x Element Plus 版（`apps/web-ele`，上游版本记在 `web/UPSTREAM_PIN.md`），即 Vue 3 全家桶：Vue 3 + TypeScript + Vite + Vue Router + Pinia + vue-i18n，组件用 Element Plus，表单与表格走 vben 的表单和 VxeTable 适配层，请求走 `@vben/request`，单测用 vitest。页面一律写成 `.vue` 单文件组件，不手写 HTML 页面，也不引入别的 UI 框架。重写的是 `apps/web-ele` 里的业务页面、路由、接口封装和状态；vben 的上游包（`web/packages/`）和应用骨架保留不改。
- 向导与编辑器：只调用控制台 API。插槽列表、候选筛选、参数表单都由服务端给出，前端不解析正文，也不判断兼容性，否则规则会分裂成两份。

### 4.7 层 7 执行链

- 网关：面向机器的接口。引导时按 SN 匹配任务，按机器实际上报的架构和固件校验，然后签发 token（C28、C32）。之后下发应答文件、附属文件、执行插槽的运行脚本和 hook 脚本，并接收信号。给不给某个文件，看它在不在该格式的下发清单里，以及任务当前的状态。渲染交给层 3，状态推进交给状态机。
- 状态机：把信号和超时转成任务状态。状态只进不退（C33），超时按时机分段计算，失败要分类；系统写上盘之后的失败不自动重装（C34）。网关收到的信号、超时扫描、控制台的取消与重试，都经过它。
- 事件与日志：收集信号、hook 输出和安装器的 syslog，按任务归档，失败时附上最后一段日志。控制台读它来展示进度和失败原因。

### 4.8 装配点与外部组件

- 装配点（`cmd/lober`）：唯一知道每个接口由谁实现的地方，负责把它们接起来（§6）。
- nginx、DHCP、SMB：外部组件，部署时配一次。nginx 发大文件（内核、initrd、仓库树、Ubuntu 的原始 ISO），SMB 让 Windows 安装程序读取系统本体。
- 部署平台：lober 只部署在 Linux 上，make check 交叉编译 linux/amd64 就是为此（§7.1）。被装的目标机可以是 Windows 或 ESXi，那是应答文件和脚本在目标机上怎么跑的事，与 lober 部署在哪无关。

## 5. 接口怎么工作

四条主流程，括号里是契约编号。

### 5.1 建 ISO

1. 操作员选族和系（选项来自族系目录），填名字、来源和可选的期望 SHA256；Debian 还要给 netboot 包的来源。控制台确认系属于该族（C2）。能事先知道大小的，先查磁盘余量，不够就拒绝，并说明还差多少。然后建一条「获取中」的 ISO 记录，交给来源获取。
2. 来源获取把字节取到本地，控制台随时可以查进度或取消：
   - 远程链接：服务端下载，断了从已落盘处续传，进程重启后接着下。
   - 浏览器上传：分片上传，同一片传两次只算一次。刷新页面后重新选同一个文件，只补缺的片。
   - 服务器本地路径：必须在配置允许的目录里。文件原地读取，归运维管理，lober 不复制也不删除。
3. 字节到齐后算 SHA256。填了期望值却对不上，置为失败（C3）。与某个未失败的 ISO 内容相同，也置为失败，并指向那一个（C4）。
4. 导入异步执行，状态为「导入中」。按特征文件识别系、版本和架构，Windows 还要列出 edition。识别出的系与声明不符就失败，并给出两边的值；附加来源不齐或版本不一致也失败（C3）。通过后按制品目录布局解出内核、initrd 和仓库树；Ubuntu 另发布原始 ISO，Windows 另把安装源放进 SMB 共享。写好清单、ISO 记录通过完整性判定后置为「可用」（C5）。
5. 下载或上传得到的原始字节默认保留，删 ISO 时一并删除。被任务引用过的 ISO 删不掉（C26），它的原始字节也就一直占着磁盘，见 §8。导入失败的 ISO 可以直接重新导入，不用重新获取字节。

### 5.2 写模板与 hook

1. 新建或派生。新建时填名字，族和系可以先空着；勾了第一个系之后，界面只列出同格式的系（C13）。派生复制来源的族、系、正文和装配表，并记下来源和版本（C24）。内置模板只能派生（C25）。
2. 编辑正文。每次保存，控制台都调正文扫描，把插槽清单和占位符错误返回给编辑器。草稿有错也照样保存，只要能存成 UTF-8 文本（§3 总则）。编辑器里的插槽列表只用服务端返回的。
3. 装配。给每个插槽按顺序放 hook，为每个实例指定参数来源，并定下向导里能不能改（C20）。hook 选择器按激活判定的同一条规则逐个核对：能放进该插槽的正常列出，放不进的灰显并写明原因（C16）。草稿可以引用草稿版的 hook。
4. 预览。选一个真实 ISO，或者只选模板勾的某个系；主机可选；参数按向导的方式填。之后走快照构建和渲染，与真实下发是同一条路（C35）。结果包含机器会取到的全部文件：菜单、应答文件、附属文件，以及各执行插槽的运行脚本。指定的主机或 ISO 找不到就报错，不改用示例数据；没指定的部分用示例值，并标明是示例。
5. 审批。作者提交后，审批人批准或驳回，驳回要写理由。激活判定通过才能批准（C13–C17、C19、C22）。批准后的版本不能再改，再编辑会生成新的草稿版本；新版本批准之前，旧版本照常可用（C23）。来源模板出了新版本时，派生模板的编辑器会提示并给出差异（C24）。

hook 的流程不同：不能派生（§2.8），也没有正文、装配和预览这三步。新建时填名字，然后先写参数声明，再逐份写实现。每份实现勾一个族下的若干系，选片段或脚本；片段只能勾同格式的系，脚本还要选解释器和执行时机。审批同第 5 步，按 C8–C11 判定。hook 不单独预览，要看效果，就放进模板里预览。在模板里换 hook 是第 3 步装配时做的：要换上的 hook b 不存在，就先照这里的流程建一个，再在插槽里按 §2.5 的「用 b 覆盖 a」原位替换。

### 5.3 建任务

主机要先登记。单台直接填写。CSV 导入先解析，逐行标出新建、更新或错误，操作员确认后一次提交。已登记的 SN 按更新处理，不影响已建的任务，因为任务的参数已经固化（C29）。

1. 选主机：按 SN 或任意属性搜索，可以多选。已有未结束任务的主机照常列出，但不能选，并写明原因（C31）。
2. 选 ISO：准入判定对选中的主机逐台核对。只列出可用且未废弃的 ISO；与其中某几台的登记架构或固件冲突的，灰显并写明是哪几台（C28）。
3. 选模板：准入判定按选定的 ISO 筛选，只列出已审批、未废弃、没有引用已废弃 hook、勾了该 ISO 的系，并且该 ISO 提供了模板及其 hook 的参数要的取值集合（如 Windows 的 edition）的模板（C21、C22、C26、C27），每个模板取当前的已审批版本（C23）。回退去换 ISO 时，已选的模板如果不再兼容，就清空并提示。
4. 填参数：参数求值给出一张逐台的表，每行一台主机。锁定的参数只显示；能改的已按主机属性或默认值预填；必填但没有值的标红。一整列可以批量填写。取值由服务端校验，错误落到具体的单元格（C19–C21）。
5. 确认：列出每台的 SN 和登记属性，以及选定的 ISO 和模板版本。任意一台都能点开预览，查看渲染出来的文件。
6. 提交：服务端不信任前端的筛选结果，逐台重跑准入判定和参数求值。全部通过后逐台构建快照，由仓储一次建出全部任务（C29、C30）。任何一台不通过，就一台都不建，并逐台返回原因。两个人同时给同一台主机建任务时，由仓储兜底（C31）：它在事务里对加锁后的最新数据再跑一遍准入判定（§4.2）。任务建成就进入「等待引导」，不需要再确认一次。每个任务记一条审计（§6.2 第 8 条）。

### 5.4 装机

1. 机器由操作员上电。DHCP 按架构下发 iPXE，iPXE 取全网共用的静态引导脚本，再把 SN、架构和固件带给网关。
2. 网关按 SN 查找未结束的任务（C32），找不到就让机器从本地盘启动，不留记录。找到后先按机器实际上报的值校验架构和固件（C28）：校验不过，就置任务失败、不签发 token，同样让机器从本地盘启动；通过，就签发 token，任务进入「引导中」，按快照渲染出菜单返回。只有「等待引导」和「引导中」的任务会下发菜单，重复的引导请求要计次，超过上限就失败。其他状态下的引导请求一律让机器从本地盘启动，所以装完重启不会被再装一遍。
3. 机器从 nginx 取内核、initrd 和仓库，从网关取应答文件。网关先查文件名在不在该格式的下发清单里、任务状态是否允许，再按快照渲染（C29、C35）。第一次取到应答文件时，任务进入「安装中」。
4. 片段 hook 在渲染时已经写进应答文件，由安装器自己处理，不单独报信号。执行插槽在正文里是一行命令，它从网关取回本插槽的运行脚本；运行脚本再按摘要逐个取回 hook 脚本，校验 SHA256 后依次执行，并为插槽和每个 hook 报告开始、结束和退出码。首次开机时机的脚本在重启前就取好，放在目标盘上，重启后只有发信号还需要网络。
5. 网关把信号交给状态机。重复投递按服务端序号去重。状态推进只看执行时机的先后（C33），迟到的早期信号只记为事件，不回退状态。安装器完成后进入「重启中」，新系统起来后进入「初始化中」，首次开机脚本跑完后进入「完成」。最后清理目标机上的凭据：应答文件副本里的密码哈希，以及首次开机用的 token。
6. 失败有三个来源：必需的 hook 返回非零（插槽中止并上报），某个执行时机超时（由超时扫描发现，进程重启也不会漏），引导校验不通过。失败事件带上执行时机、hook、退出码、日志尾部和安装器 syslog 的尾部。进入「重启中」之前的失败可以重试，重试沿用原来的快照。之后的失败不能自动重装，也不能一键重试（C34）；界面把这类失败和装机失败分开显示，提示人工处理。
7. 安装器 syslog、hook 输出和信号都按任务归档，控制台从这里读取，向界面推送进度。

## 6. 接口与实现者怎么配合

### 6.1 总则与依赖方向

- 只有装配点知道每个接口由谁实现。它负责读配置、建实例、注入依赖、管理启动和停止；其他模块只拿到自己用得到的值。
- 实现模块之间互不引用。需要别的模块的能力时，由调用方声明一个只含所需操作的接口，装配点注入实现。由架构测试检查。
- 层 1 和渲染不读库、不碰时钟，也不做文件和网络 IO。入参由调用方凑齐，当前时间也由调用方传入。
- 数据以仓储为准。通知和前端状态都只是提示，丢了或过期了，从仓储重读就能恢复。

依赖方向：层 1 不依赖任何模块。存储契约只依赖层 1，按聚合划分能力（主机、ISO 与来源、hook、模板、任务、事件、审计、用户），实现只有 PostgreSQL 一份，契约测试连测试环境的真实库，找不到连接串就失败，不跳过（§6.4）。渲染与内置内容只依赖层 1。ISO、控制台、网关、状态机、事件与日志依赖层 1、存储契约里自己用到的能力，以及自己声明的接口。装配点依赖全部模块。

### 6.2 接缝

1. 判定：控制台凑入参，层 1 返回结构化结果。准入判定、激活判定和参数求值要用的对象（主机、ISO、模板及其引用的 hook 版本），由控制台从仓储取齐后传入。结果包含原因类别、涉及的对象（哪台主机、哪个插槽、哪个参数），以及一句中文说明和下一步。控制台按原因类别映射 HTTP 状态码，前端按涉及的对象把错误标到具体的行或单元格。说明文字只在层 1 写一次，所以向导里灰显的原因和建任务被拒的原因完全相同。
2. 快照：控制台构建，仓储保存，网关读取。网关只读任务上固化的那份，从不现算（C29）。预览现算，但与建任务调用同一个快照构建和同一个渲染（C35）。渲染还要系统值：token，以及网关、制品、syslog、SMB 的地址。这组地址由装配点从配置构造一次，同一份交给网关和控制台，所以预览里的地址与真实下发一致；预览里的 token 是示例值。旧系统的预览自己拼渲染输入，新增 SSH 公钥字段时只改了网关那条路径（ab81d37）。
3. 机器面的两份约定（地址格式、制品目录布局）放在层 1 的族系目录里。另有一个测试：渲染出来的每个地址，网关都必须能路由到。
4. 网关、状态机、仓储的分工：网关决定给不给（SN 能否匹配、架构和固件是否通过、文件是否在下发清单里、任务状态是否允许）；状态机决定能不能转（C33、C34）；仓储保证并发下只转一次——状态推进是条件更新，当前状态和版本都与预期一致才写入，冲突时由状态机重读后再判断。token 由网关生成，和「进入引导中」一起写入，所以两台机器报同一个 SN 同时来引导时，只有一台能拿到 token。超时扫描归状态机，由装配点启停并注入时钟。控制台的取消和重试也经过状态机，所以 C34 只在状态机里实现一次。
5. hook 脚本只对快照里钉住的摘要放行：网关收到取 hook 脚本的请求，先确认这个摘要在该任务的快照里，再从仓储取出正文。一个任务的 token 取不到别的任务的脚本；草稿不会进入快照，所以任何 token 都取不到草稿。旧系统把 hook 正文写进 nginx 目录，出过正文根本没落盘的问题（d9d744a），改由网关从库里发，这类故障就不会再有。
6. ISO 模块：控制台声明它需要的来源操作（登记、上传分片、取消、重试获取、重新导入），由 ISO 模块实现、装配点注入。进度和状态由 ISO 模块经存储契约写回 ISO 记录，控制台只读这条记录。启动时装配点调用 ISO 模块的恢复操作，把没取完的来源和没导完的导入继续做完。各个目录（nginx 目录、SMB 目录、暂存目录、允许登记的本地目录）由装配点注入。
7. 事件与日志：syslog 接收器归事件模块。安装器发出的 syslog 不带任务号，只能按源 IP 归档：网关每收到一个带有效 token 的请求，就经注入的接口通知事件模块「这个 IP 现在属于任务 X」。新系统起来后，业务网生效，源 IP 可能会变，之后的 syslog 就归不到任务上，这段时间的进度只能靠带 token 的信号。hook 输出的最后 4 KB 随信号正文上报。
8. 写操作与审计同一个事务：会改变系统行为的写操作——登记和修改主机（含 CSV 批量）、登记来源、hook 与模板的审批和废弃、建任务、取消、重试、用户和权限变更——在存储契约里各是一个完整操作，动作和审计记录要么一起写入，要么都不写入。批量建任务也是一个操作建出全部任务（C30）。调用方接触不到事务。审计按对象写：批量建任务、CSV 导入这类一次改多个对象的操作，每个对象各记一条；每条审计只指向一个对象，按主机或任务查审计才查得全。要审计的操作以存储契约为准，上面只列了大类，契约里还有删除主机，建、废弃与删除 ISO，提交与驳回审批，以及 hook 与模板的改名。编辑草稿（新建、保存、开新版本、派生、删除草稿）和上传分片不写审计；导入时对 ISO 记录的系统更新、系统自己发起的状态推进（由引导请求、信号与超时引起）、事件，以及内置内容的装载也不写。审计记录从哪来，见 §6.3。
9. 进度推送：状态机和事件模块写入之后，经进程内的通知中心发出「任务 X 有更新」，通知不带数据。控制台的推送连接收到后，按事件序号从仓储补读，再推给前端。通知丢了也不会出错，下一次补读会补齐。仓储操作返回时事务已经提交，之后才发通知。
10. 前后端以 OpenAPI 为契约：控制台的每个接口都有 OpenAPI 描述，前端的请求和响应类型由它生成，另有测试检查每条注册的路由都有描述。旧前端里有一个调用 GET /templates 的函数，后端从没实现这个接口。本机前端工具链受限，生成步骤要能用现有工具跑起来，具体做法在第 6 层计划里定。
11. 内置内容在启动时装载：装配点把程序自带的内置模板和 hook 按「ID + 版本」写入仓储（内置内容带着自己固定的 ID），已存在且内容相同的跳过。库里同一版本的内容和程序自带的不一致，就拒绝启动并说明原因：那说明有人改了内置内容却没有升版本号，继续运行的话，同一个版本号会对应两份内容。名字放在身份上（§4.2），内置的和用户建的共用一个名字空间：内置内容的名字被用户建的 hook 或模板占了，同样拒绝启动。所以名字前缀 `lober:` 只给内置内容用（C12）：用户新建、派生和改名时用了它，在第 1 层的名字规则里就被拦下；装载内置内容反过来要求名字必须带这个前缀。名字随身份定下，以后的版本不能换名，换了名同样拒绝启动；要改名，只能换一个新 ID。

### 6.3 切面与 wire

装配点用 goforj/wire（google/wire 的维护分支，API 兼容）：每个模块导出自己的一组构造函数，装配点只写一个注入函数，构造顺序由 wire 生成。wire 本身没有切面功能，同一类型也只允许一个提供者，所以切面写成装饰器（包在接口外面、在调用前后加逻辑的一层），由 wire 负责套上。

| 位置 | 切面 | 怎么挂 |
|---|---|---|
| HTTP 接口（控制台、网关） | 认证、权限、审计声明、请求日志、panic 兜底 | 路由表声明每条路由的方法、路径、权限码和审计动作，由 gin 中间件链执行 |
| 模块接口 | 调用日志（操作名、耗时、结果、错误、任务号或 ISO 号），调用慢了告警 | 装配点用 wire 套在每个实现外面，每个实现只套一次，所有调用方拿到的都是套好的那一份 |
| 后台任务（超时扫描、ISO 下载与导入、syslog 接收） | 看护：panic 时记日志并按退避重启，不让整个进程退出 | 装配点启动时套上 |

模块接口上的调用日志能揪出一类具体问题：网关收信号一律回 200，状态机的返回结果被直接丢掉，旧系统信号序号那个缺陷就是这样藏住的（66d6f5f）。状态机外面套上日志，每一次「重复投递、未推进」都会留下记录。

切面的契约：对被包的接口透明，不改入参、返回值和错误。错误尤其要原样透传，因为调用方靠 `errors.Is` 识别「重复投递」这类情况。重试、超时会改变语义，不做成切面，留在各模块内部。切面的套用顺序由装配点统一定死。

事务不做成切面。把事务放进 ctx 一路往下传有三个问题：事务里触发的副作用会先于提交执行（登记来源后马上启动下载，下载协程可能读不到还没提交的 ISO 记录；进度通知也可能推出一条最终会回滚的变更）；加锁的先后会散到各个调用方，仓储在一个操作里定死的加锁顺序就守不住，两条调用链按不同顺序锁同一批行，会互相等死（导入主机和批量建任务都要锁主机行，现在两处都按 SN 升序加锁，才没有撞上）；只要有一个仓储方法没用 ctx 里的事务，它就不在事务里，而且不会报错。所以审计是声明式的，但仍在仓储的同一个事务里写：路由表声明审计动作，中间件按当前用户和动作生成审计记录，处理函数把它原样交给仓储的写操作。需要审计的写操作没收到审计记录就拒绝执行，漏了声明，测试里会直接报错。

装饰器倾向用 gowrap 按模板生成：每个切面写成一份模板（日志用 slog 自己写），go generate 给每个标注过的接口生成装饰器，接口一改，重新生成即可。gowrap 的维护状态写计划前核实，不合格就改成手写。

wire 和 gowrap 都在 go.mod 里用 tool 指令钉住版本，通过 `go tool` 调用，不依赖全局安装。生成的代码提交入库；make check 会重新生成一遍并比对，不一致就失败。wire 只管构造和清理，不管启停：后台任务的启动顺序和优雅退出，仍由装配点显式编排。

### 6.4 测试环境与生产环境

存储只有 PostgreSQL 一份实现，测试和生产都连真实的库，分成两个环境。

- 同一份代码：两个环境跑的是同一份存储实现（pgstore），建表用同一套 AutoMigrate，每次打开库都做同一套表结构断言（§4.2）。区别只在连哪个库。
- 测试环境：专用的角色与库，都叫 `lober_test`。角色不是超级用户，不能建库，但拥有这个库，可以在里面建 schema。每个用例新建一个临时 schema，用完删掉，所以几个测试同时跑也互不干扰。用例可以并行，但同时打开的仓储数要限住：每个仓储有自己的连接池，而几个测试进程共用一个 `max_connections`，不限就会撑满。限多少由测试夹具定。连接串只从两处读：环境变量 `LOBER_TEST_PG_DSN`，或模块根目录（或它的任一上级目录）下的 `.pgtest.dsn` 文件。往上级找是为了并行克隆：克隆出来的工作树没有这个文件（它不入库），靠往上找才读到主目录那一份。两处都没有，测试直接失败，不跳过：跳过会让 make check 在存储层零覆盖的情况下变绿。
- 生产环境：这一版只定到「连接串由装配点读配置得到」这一层，配置从哪来、写成什么格式，等装配点在第 5 层出现时再定（§7.4）。存储和其他模块都不自己读环境变量或配置文件来取连接串，上面那两处只有测试夹具读，所以配错一个变量，不会让生产连到测试库。
- 两边共同的约定：写事务的隔离级别固定为 READ COMMITTED，由 pgstore 开事务时指定，不取库或角色的默认值；加锁后重读最新数据（§4.2 的并发兜底）靠的就是这一级的语义。两个环境用同一个 PostgreSQL 大版本，因为表结构断言比对的是 PostgreSQL 规范化之后的定义文本，换了大版本，同样的定义可能写成不同的文本。

## 7. 测试、验收与建造顺序

### 7.1 测试放在哪

- 特性分支，跟代码一起提交：单元测试、存储契约测试（连测试环境的 PostgreSQL，§6.4）、渲染 golden、架构测试。make check 在格式、vet、测试、竞态检测之外再加两项：交叉编译到 linux/amd64（旧系统出过在 Windows 上能编译、却编不出 Linux 版的问题，5089a86）；比对生成代码（wire、gowrap、OpenAPI 类型）。
- test 分支：lobertest 的接口测试（L1，起真服务打 HTTP）和真装机测试（L2）。

### 7.2 每层的出口判据

make check 全绿之外：

1. 核心模型：第 3 节契约里归本层判定的，每条至少一正一反两个用例。正文扫描对七种格式各有样例，其中包括 Ubuntu 正文里 cloud-init 自己的 `{{ }}`，要原样保留。
2. 存储：只有 PostgreSQL 一份实现，契约测试连测试环境的真实库全部通过（§6.4），找不到连接串就失败，不跳过。§4.2 列的约束都有用例；写操作与审计同一个事务也要有用例（注入失败时两者都不落库）。表结构要有断言，防 AutoMigrate 的索引盲区。
3. 渲染与内置内容：七个内置模板各有 golden，BIOS 和 UEFI 分开。新 golden 要和旧系统的产出逐行对照，差异逐条写明理由；旧系统只有 OpenCloudOS 9.6 真装通过过，其余格式的旧产出只能当参考。另外：渲染出的每个地址都符合机器面地址格式；执行插槽展开后只有一行；运行脚本用目标环境的 shell（busybox sh、bash）做语法检查。
4. ISO：断点续传覆盖两种情况，中途杀进程，以及库里记的进度比盘上多；SSRF 每条规则一个用例；同一分片重复上传只算一次，续传只补缺的片；导入要用本机的两张真 ISO（Debian 13.6 netinst、OpenCloudOS 9.6）跑通，不能只用合成的小镜像，旧系统的 ISO 9660 解析器就是到了真镜像上才出问题（dab857b）。
5. 控制台：每个接口都有 HTTP 测试（存储连测试环境的 PostgreSQL，§6.4），外加权限矩阵；每条路由都有 OpenAPI 描述；每个要审计的写操作都留下审计记录；批量建任务只要一台不过，就一台都不建。合入后，test 分支的接口测试改接新接口。
6. 前端：`vue-tsc` 类型检查、ESLint、vitest 单测和 `vite build` 都通过；在浏览器里走通四条流程：登记主机（含 CSV）；建 ISO；派生内置模板、换一个 hook 再审批；用向导批量建任务。
7. 执行链：网关和状态机的单测覆盖按 SN 匹配、引导校验、文件放行、乱序与重复信号、分段超时、C34。部署配置（nginx、DHCP、systemd、SMB）在这一层重写，并有测试检查制品下载不限流（e8940b0）。合入后在 test 分支跑真装机测试。

旧系统的修复逐条变成回归用例，放在能抓住它的最低一层，对照表见附录 A。

### 7.3 系统验收

- 七种格式各真装一次：从向导建任务，到虚拟机装完、状态进入「完成」，再用注入的 SSH 公钥登录。Windows Server 2025 自带 OpenSSH，同样用公钥登录。
- 一次提交两台以上，全部到「完成」。本机资源有限，可以依次上电。
- 失败路径：必需 hook 返回非零时任务失败，事件里带着 hook、退出码和日志尾部；重启进新系统之后的失败不能重试。
- ISO：远程下载到一半杀掉 lober，重启后能续传完成并导入；浏览器上传中途刷新页面，能补传完成。

| 格式 | 验收介质 | 本机 | 还缺什么 |

| kickstart | OpenCloudOS 9.6 | 有 | 可再加 Rocky 或 AlmaLinux 9，能下载 |
| preseed | Debian 13.6 netinst | 有 | 同版本 netboot 包，能下载 |
| autoinstall | Ubuntu 24.04 server | 无 | 能下载 |

### 7.4 建造顺序与旧代码退场

- 开工前：主目录里原有的未提交改动已丢弃；不打标签，也不参照旧代码；main 不动，继续是旧产品。
- 七层依次做：核心模型、存储、渲染与内置内容、ISO、控制台、前端、执行链。每层一个 `feat/<层名>` 分支，直接在主目录上开，不用 git worktree；层内并行的任务各在 `.tmp/wf/` 下的本地克隆里做，逐个并回该分支。只写代码和单测；make check 全绿、评审通过后合入 dev。
- 第 1 层的第一个提交把旧系统从 dev 上删掉，从空树开始写；`web/` 暂不动，留到第 6 层重写其中的业务页面。旧提交留在 git 历史里，但实现不读取、不照搬旧代码。
- 一份总 spec（本文）加每层一份实现计划。每层的计划等上一层合入 dev 后再写，依据已经写出来的真实接口。
- 装配点在第 5 层第一次出现，这时能起控制台；第 7 层再补上网关和状态机。
- 系统验收在 test 分支上全部通过后，dev 并入 main，旧系统退场。还没合并的旧分支和对应的工作树（`feat/four-layer` 等）到时作废，删之前逐个确认。

## 9. 与此前设计的关系

这组需求此前有两组设计（49956df、051179c）。09-29 那组在 `feat/four-layer` 上实现了四个提交（删除镜像直写、新增族），没有合入 dev。本文推翻了其中几处：

| 事项 | 此前 | 本文 |
|---|---|---|
| 模板正文 | 一个模板内含每个家族一份正文 | 一份正文，勾同格式的多个系 |
| 系的粒度 | 六个家族：rhel、debian、ubuntu、suse、windows、esxi | 发行版一级，SUSE 按安装器拆开 |
| 阶段 | 正文里占位符的出现顺序就是阶段 | 插槽；执行插槽声明执行时机 |
| hook | 只有可执行一类（09-28 的设计有过片段与脚本两类，09-29 删掉） | 片段与脚本两类，hook 即组件 |
| 派生 | 快照复制，后来改为不记血缘 | 快照复制，记下来源和版本，提示差异 |
| 主机身份 | SN 加 MAC 双因子 | 只认 SN |
| 服务端决策 | 磁盘规划、网卡规划等 provider | 不做，交给 hook 和主机属性 |

## 附录 B 外部事实（2026-09-30 核实）

- SLES 16 与 openSUSE Leap 16 的安装器是 Agama，自动安装读 JSON 或 Jsonnet profile；AutoYaST profile 只能部分转换，不是直接替代。Leap 16.0 于 2025-10-01 发布。见 [Using AutoYaST Profiles with Agama](https://documentation.suse.com/sles/16.0/html/SLES-x86-64-agama-autoyast-profiles/)、[Automated Installation Using Agama](https://documentation.suse.com/sles/16.0/html/SLES-x86-64-agama-automated-installation/index.html)、[Install openSUSE Leap 16](https://computingforgeeks.com/install-opensuse-leap-16/)。
- ESXi 7.0 于 2025-10-02 停止一般支持；9.0 于 2025-06 发布，改名回 ESX。见 [vSphere 7 to reach End of Service](https://blogs.vmware.com/cloud-foundation/2025/03/31/reminder-vsphere-7-to-reach-end-of-service-october-2-2025/)、[ESXi Build Numbers & End of Support Dates](https://medhacloud.com/blog/esxi-versions)。
- Windows Server 2025 于 2024-11-01 GA，是当前 LTSC，自带 OpenSSH（远程 SSH 访问默认关闭）；2012 与 2012 R2 的 ESU 于 2026-10-13 结束。见 [Windows Server release information](https://learn.microsoft.com/en-us/windows/release-health/windows-server-release-info)、[Get started with OpenSSH Server for Windows](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse)。
- wimboot 的官方流程是 HTTP 引导 WinPE，再连 Windows 文件服务器安装系统本体。WinPE 要另加可选组件才有 PowerShell。见 [iPXE: WinPE](https://ipxe.org/howto/winpe)、[WinPE: Adding PowerShell support](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpe-adding-powershell-support-to-windows-pe)。
- Ubuntu live server 网络安装要经内核参数 `url=` 取整张 ISO；加 `cloud-config-url=/dev/null` 可避免重复下载。见 [Automated Ubuntu Installation](https://eradman.com/posts/automated-ubuntu-install.html)。
- kickstart 里同一类的多个段按出现顺序执行。见 [What is the ordering of %post sections in a kickstart file](https://unix.stackexchange.com/questions/626820/what-is-the-ordering-of-post-sections-in-a-kickstart-file)。
- google/wire 于 2025-08-25 归档；goforj/wire 是维护中的分支，API 兼容，要求 Go 1.25 以上。wire 没有装饰器功能，同一类型只允许一个提供者。见 [goforj/wire](https://github.com/goforj/wire)、[FAQ](https://github.com/goforj/wire/blob/main/docs/faq.md)。
