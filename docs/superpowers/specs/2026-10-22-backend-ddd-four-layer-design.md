# 后端四层架构与模块契约设计

日期：2026-10-22。

状态：用户已于 2026-10-22 审阅确认。只整理目标和验收约定，尚未修改业务代码。本文不是已完成的重构，也不是实施计划。

## 1. 目标和范围

用户确认的问题是代码难维护、业务规则分散。目标是统一为接口层、应用层、领域层、基础设施层，让各模块通过契约协作，并用自动检查阻止职责重新混杂。

成功标准不是目录改成四个名字，而是每条业务规则有唯一归属，每个跨模块调用有明确约定，每次写入的失败、并发和审计行为都能测试。

本次重构保留现有业务行为、数据库约束、数据格式和对外接口。登录方案、角色变化、主机字段扩展属于独立功能变更。尚未实现的任务执行能力继续明确返回不可用，不在重构时伪装完成。

本方案与同日的 `2026-10-22-console-contract-auth-design.md` 协同：该文管前后端接口和登录功能，本文管后端内部结构。两份文档当前均为草案，不能将彼此的建议当作已实施事实。

## 3. 方案比较和建议

| 方案 | 收益 | 代价与风险 |
| --- | --- | --- |
| 只增加应用层，其他目录不动 | 改动少，能先拆请求处理 | 最终仍有多套目录含义，不符合统一四层的目标 |
| 四层结构，逐个业务模块迁移，推荐 | 目标统一，每步可以验收和回退 | 过渡期需要明确限定旧代码的使用范围 |
| 一次重写所有模块和模型 | 可以一次整理命名 | 难区分搬迁错误和业务变化，回归范围过大 |

采用第二种方案。先确定契约和依赖检查，再沿完整业务流程迁移，最后删除过渡入口。

## 4. 四层职责与目录

```text
internal/
  interfaces/
    console/                 网页请求、鉴权入口、输入输出转换、流式响应
  application/
    hosts/                   主机操作流程
    authoring/               hook 和模板编写、审批流程
    tasks/                   装机向导、创建任务、任务查询和控制流程
    media/                   镜像来源、导入、取消和恢复流程
    identity/                用户和权限操作流程
    audit/                   审计查询流程
    ports/                   多个流程共用的少量外部能力约定
  domain/
    catalog/                 随程序发布的业务目录和静态能力
    model/                   业务对象及其自身规则
    activation/              激活和审批条件
    admission/               装机准入条件
    params/                  参数求值
    snapshot/                快照构建
    scan/                    模板内容分析
    render/                  纯内存的安装内容生成
    repository/              按业务对象拆开的仓储契约、查询条件和错误
  infrastructure/
    persistence/pgstore/     数据库记录、转换、事务、迁移和仓储实现
    persistence/pgtest/      真实数据库测试设施
    media/                   文件、网络、镜像工具和目录操作
    builtin/                 随程序打包的内置内容
    notification/            进程内通知实现
  archtest/                  四层和模块边界自动检查
cmd/lober/                   读取配置、组装对象、启动和停止
```

这是目标目录，不要求一次搬完。`cmd/lober` 是组装入口，不是第五个业务层。

领域层保留现有 `model` 与纯规则包，不强迫把每个规则改成对象方法。对象自身的合法性由对象负责；涉及多个对象的规则由明确的规则包负责。

`domain/model` 是受控的共同模型，不是随意放代码的公共目录。Host 归主机模块，ISO 与来源归镜像模块，Hook/Template 归编写模块，Task/Snapshot 归任务模块，User 归身份模块。跨模块引用固定身份或已冻结的内容，不复制可修改的业务状态。

纯渲染保留在领域层，因为它只根据输入生成安装内容。加载内置文件、读取制品和启动外部工具归基础设施。现有 `store.Source`、`store.User` 等业务类型移入所属领域表示；分页和查询契约不携带数据库实现类型。

## 5. 依赖规则

| 位置 | 可以依赖 | 不允许依赖 |
| --- | --- | --- |
| 接口层 | 应用层入口、必要的领域值类型、网页服务库 | 仓储契约、数据库、基础设施实现、领域判定入口 |
| 应用层 | 领域层、自己声明的外部能力接口 | 网页服务库、数据库实现、基础设施实现 |
| 领域层 | 受限标准库、明确允许的领域包 | 其余三层、数据库库、文件和网络操作、读取当前时间与随机数 |
| 基础设施层 | 领域层、所实现的应用层外部能力接口、所需第三方库 | 接口层、应用服务的具体实现 |
| 组装入口 | 四层公开入口 | 业务判定和流程实现 |

运行时可以由应用层调用注入的数据库实现。代码依赖仍指向接口，不导入数据库实现包。领域层不需要知道谁调用自己。

应用模块不能直接导入另一个应用模块的具体服务。跨模块能力由调用方声明小接口，组装入口连接实现。共同外部能力才进入 `application/ports`，不能把所有模块接口集中成一个总接口。

基础设施之间需要协作时也通过小接口注入，不能形成数据库实现、文件实现、通知实现互相导入的网。

## 6. 契约先行

契约分三类，各有唯一来源，不为内部方法再手写一份独立的机器描述文件。

| 契约 | 唯一来源 | 如何检查 |
| --- | --- | --- |
| 对外请求和响应 | 现有对外行为；正式启用契约文件后由该文件接管 | 路由、请求、响应、权限和错误映射测试 |
| 应用操作和模块能力 | Go 接口、命令和结果类型、方法旁的中文约定 | 接口实现检查、应用行为测试、模块调用测试 |
| 数据保存 | `domain/repository` 下按对象拆分的接口及其约定 | 真实数据库契约、并发和回滚测试 |

对外契约文件的引入由同日控制台设计负责。四层迁移不能等待登录功能完成，也不能同时维护两份相互独立的对外契约来源。

每个公开操作必须写清以下内容：

1. 操作目的、归属模块、允许谁调用。
2. 输入格式、必填项、大小限制，以及谁负责规范化。
3. 成功结果、结果顺序和空结果形式。
4. 稳定错误类别、业务原因代码，以及多个错误的优先顺序。
5. 写入范围，哪些数据必须一起成功或一起失败。
6. 重复调用的结果，是否允许重试，怎样识别版本冲突。
7. 并发时依赖什么最新事实，哪些条件必须在提交时再次检查。
8. 审计内容、通知时机、取消与超时行为。

不适用的项目明确标注原因。不能只写方法签名就称为契约完成。

领域问题使用统一的原因代码、对象定位和中文解释。应用层传递问题；接口层负责映射网页响应状态；数据库实现负责把数据库冲突转换成约定错误。调用方不能通过错误文字判断分支。

业务对象、网页输入输出类型、数据库记录保持分离。生成的请求类型不进入领域层，数据库字段标记也不进入领域对象。

## 7. 业务规则与事务归属

“一条规则一份实现”不意味着只检查一次。同一个领域判定可以用于页面预览、正式提交和事务内复查，禁止各处重写条件。

应用层负责组织业务步骤。仓储实现负责锁、版本条件、唯一约束、数据转换，以及约定的原子写入。原子写入指相关修改全部成功或全部撤销。

先保留现有按业务操作设计的原子仓储接口，例如批量创建任务并记录审计。不引入可以执行任意数据库操作的通用事务回调，也不把数据库事务对象交给上层。

数据库实现允许在锁定后读取最新事实，再调用纯领域规则。它不能自行决定新的业务政策。该允许项必须点名测试，避免被误判为基础设施中禁止一切业务规则调用。

“同一主机只能有一个未结束任务”“当前可选审批版本”“引用对象未废弃”等条件要分别列入提交契约。进程内锁只保护当前进程，不能代替数据库并发保证。

现有代码中最新审批版本的选择包含控制台进程内锁。迁移前须补充与审批、废弃并发的真实数据库测试，核实事务保护范围。若发现旧实现缺口，单列修复及行为影响，不能假定搬迁就已解决。

审计与业务写入在同一事务。提交成功后才能发通知；事务失败不发通知。当前通知用于提示调用方重新读取事实，丢通知可以补读。若以后要求每条外部事件必达，应另行设计持久化消息机制。

## 8. 首个迁移模块：任务创建

接口层只做请求解析、获取已验证的操作者、调用应用入口和转换响应。业务权限判断由应用入口保证，避免其他入口绕过；网页凭据解析仍属于接口层。

建议应用入口包括查询可选主机、查询可选镜像、查询可选模板、计算参数、预览和提交任务。输入是普通 Go 类型，不能携带网页请求上下文；允许标准的 `context.Context` 传递取消信号。

应用层取齐主机、镜像、模板和 hook 版本，调用统一的选择规则、准入规则、参数求值和快照构建，再请求仓储原子创建。当前时间、编号生成和发布清单通过明确的接口或值注入。

内置版本是否可选由纯规则判断，当前发布清单由外部提供。领域规则不读取打包文件。已有任务继续使用冻结版本，不跟随新发布清单漂移。

提交契约至少覆盖：

1. 任一主机不满足条件时，整批不创建，整批不写审计。
2. 同一主机并发提交，最多产生一个未结束任务；失败方得到约定的冲突或业务问题。
3. 审批、废弃、修改主机与提交并发时，以契约规定的提交事实为准；不能只依赖页面预检查。
4. 快照冻结所选内容和参数，读取旧任务不重新计算。
5. 审计使用可信操作者信息，浏览器不能伪造创建人和创建时间。
6. 提交成功后通知；提交失败时不通知。

取消和重试只迁移现有调用契约及不可用行为。本方案不实现装机执行状态机。

## 9. 防止边界再次混乱

扩展现有 `internal/archtest`，加入四层和模块依赖白名单。新增包必须归类，没有归类就失败，防止新目录成为绕过规则的入口。

检查基础设施只能引用明确的应用能力接口包，不能笼统放行整个应用层。将这些接口放在模块的 `port` 子包，或受控的共同 `ports` 包，使导入路径检查可以区分接口与服务实现。

为守卫编写故意违规的样例，证明接口层直连数据库、应用层导入网页服务库、领域层读文件、模块互相导入服务都会失败。保留扫描完整性和构建约束检查，避免检查空跑。

临时兼容入口按“调用方、允许调用的旧包、清除阶段”逐项登记。禁止通配放行整个旧目录。已迁移模块不得再调用旧业务流程。所有模块迁移完成后，兼容入口数量必须为零。

每次契约修改同时提交调用方变化、实现变化和行为测试。改变字段含义、错误含义、并发保证或审计范围，都属于契约变更，不能以内部重构名义悄悄改变。

## 10. 迁移顺序和验收

1. 盘点公开操作、规则、调用关系和现有测试。建立契约清单，记录现有行为与已知缺口。
2. 建立四层目录与过渡依赖规则，迁移纯领域代码和仓储契约，更新组装和生成代码。
3. 迁移任务向导和创建任务，跑通从网页入口到真实数据库的完整流程。
4. 迁移 hook 与模板的编写、审批及内置内容选择流程。
5. 迁移主机、镜像、用户权限、审计查询和通知；镜像迁移同时覆盖后台恢复、取消和资源释放。
6. 清除旧路径和兼容入口，核对对外接口、配置、数据库迁移及生成结果。

每个模块独立命名分支，先通过模块验收，再按仓库流程进入 develop 集成。缺陷能够按模块回退。test、preview、main 的推进仍按仓库规定执行。

后端改动必须通过 `make check`，包括依赖守卫、格式、静态检查、测试、竞态检查、Linux 编译和组装代码漂移检查。真实数据库契约测试必须有测试连接；未执行不能报告通过。

另外验证请求响应兼容、业务问题兼容、数据库保存结果、并发冲突、审计原子性和提交后通知。纯搬迁复用现有测试；新增测试聚焦此前未覆盖的边界，不为每个转发方法重复测试。

完成标准：接口层没有业务流程和仓储调用；领域规则没有外部操作；模块间只通过已登记契约协作；原有保护没有减少；临时兼容入口清零；全套检查有实际结果。
