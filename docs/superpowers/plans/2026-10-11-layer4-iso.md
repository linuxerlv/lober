## 范围

本层要做的：catalog 补四份静态事实、来源获取（远程/上传/本地路径）、导入（解析、识别、解出制品、清单）、存储契约扩 `ISOSources`、守卫加「ISO」层。

- 真装机验证（Windows 固件分套、ESXi 原生 firstboot、Agama 产品 ID）——第 7 层
- 把 render 三处硬编码的角色表改成读 catalog——本层任务 9，**前提是第 3 层已合入 dev**（本分支从 dev 开出，那时还没有 render）

不在本层：L-8 的全局词表（归第 5 层）、S3-10。

**开工前必须知道的一件事：ESXi 首版导不出 ready 的 ISO。** ESXi 的版本号不在 ISO 的任何文件里（`boot.cfg` 只有 `title=Loading ESXi installer` 这类字样，旧系统也从来没从内容里取到过它），而 `model.ISO.Validate` 要求 ready 的 ISO 必须带合法版本（C5）。首版的做法是明确报 `iso_version_missing` 并把这条记进 spec §8，**不是猜一个取法**——猜错的版本会成为制品目录里的一段路径，错了要到真装机才发现。所以本层的「七种格式」实际是六种能走通全流程加一种明确失败，第 7 层真机时坐实版本取法再补。

为什么这样切：

- `iso9660` 单独成包：它是唯一要在真镜像上活下来的部件（附录 A `dab857b`：旧系统的解析器在真实镜像上必然失败），隔离出来才能用真 ISO 单测它，也不用把 lober 的概念带进解析器。它只依赖标准库，守卫按第 4 层的规则查。
- catalog 与第 4 层分开：判定规则是随程序发布的静态事实（C1），放在第 1 层；第 4 层只执行。附录 A 的 `65883a5` 是「仓库判据用错且有三份副本」，这一层不许再犯。
- `internal/iso` 内按职责分文件（本地/远程/上传/识别/解出/导入各一个），不按技术层分：来源获取的三种来源共用一套状态机，导入的七种格式共用一套解出流程。

## 全局约定

- 本层的函数不读库（经注入的 `store.Store`）、不碰时钟（当前时间由调用方传入）、不起协程。文件与网络 IO 是本层的本职，目录由装配点注入（spec §6.2 第 6 条）。
- 中文说明只写在 `codes.go`，本层的错误用第 1 层的原因代码体系，需要新代码时照例追加到 `extraCodes` 末尾，并同步 `codes_align_test` 的断言。
- 产出逐字节确定：map 要排序后遍历，不依赖 Go map 的迭代顺序。制品目录里的文件名由角色与路径拼出，不含时间戳与随机串（`.tmp-{isoID}` 除外，它由 ISO 的 ID 定，同一个 ISO 重导得到同一个名字）。
- 每个任务只留一个提交，评审修正并入时压成一个。
- 新加的包必须同时给守卫加一条规则（第 3 层定下的）：守卫全模块列包，归不到任何层的包一律报违规。常量与引用它的用例必须在同一次改动里一起加。

### 任务 0：catalog 补四份静态事实

**目标：** 把识别线索、仓库树判据、附加来源、必需制品角色放进第 1 层的目录，第 4 层据此识别与校验。（第 1 层计划第 22 行、spec §2.1、附录 A `65883a5`）

**文件：**
- 创建：`internal/core/catalog/media.go` —— 四张表与取用函数
- 测试：`internal/core/catalog/media_test.go`

**接口契约：**

```go
// Marker 是一条文件线索：ISO 里 Path 存在，且它的内容含有 Contains 里的每一个片段。
// Contains 为空表示只看路径存在。多个 Marker 是合取：全部命中才算命中。
type Marker struct {
	Path     string
	Contains []string
}

// ExtraSource 是一个系要的附加来源（spec §2.1）。目前只有 Debian 的 netboot 包。
type ExtraSource struct {
	Role          string   // 来源的角色名，Debian 是 netboot
	SameVersion   bool     // 要求这份来源的版本与主介质识别出的版本一致（ce9cd56）
	RolesFromExtra []string // 取自附加来源而不是主介质的角色：Debian 是 kernel 与 initrd
}

// formatMediaRow 是格式级线索：ISO 里出现这些，就是这种格式。
type formatMediaRow struct {
	format  Format
	markers []Marker
}

// seriesMediaRow 是一个系的介质事实。
type seriesMediaRow struct {
	series Series
	// markers 是系级文件线索，在格式内区分。unattend 的两个系留空：
	// 它们的系要看 install.wim 的 editions，不是看文件在不在（见 editionHints）。
	markers []Marker
	// editionHints 是 edition 线索，只对 unattend 的两个系用：install.wim 里某个
	// edition 的 NAME 或 FLAGS 含有这些片段中的任意一个，就算这个系。
	editionHints []string
	// probe 是从哪份特征文件里取版本与架构、用什么解析器。
	probe probeKind
	// repoPaths 是仓库根必须包含的路径，相对仓库根，空表示这个格式不建仓库树。
	repoPaths []string
	// extraSource 是这个系要的附加来源，没有时为 nil。
	extraSource *ExtraSource
	// roles 是导入后制品集里必须有的角色（见 §7.1 的表）。
	roles []string
}

// probeKind 是特征文件的种类，第 4 层按它选解析器。
type probeKind string

const (
	probeTreeinfo probeKind = "treeinfo" // .treeinfo，INI，[general] 的 name/version/arch
	probeDiskInfo probeKind = "diskinfo" // .disk/info，一行文本
	probeProducts probeKind = "products" // SUSE 的 media.1/products，管道分隔
	probeBootCfg  probeKind = "bootcfg"  // ESXi 的 boot.cfg 加 efi/boot/bootx64.efi
	probeWIM      probeKind = "wim"      // sources/install.wim 的 XML 索引
)

func SeriesMedia(s Series) (seriesMediaRow, bool)
func FormatMedia(f Format) (formatMediaRow, bool)
func Formats() []Format             // 按 formatMediaTable 的顺序，第 4 层按它逐个试
func RequiredRoles(s Series) []string
func ExtraSourceOf(s Series) (*ExtraSource, bool)
func RepoPaths(s Series) []string
func SeriesByEdition(f Format, names, flags []string) (Series, bool)
```

`Formats` 是新函数（`series.go` 已有的是 `Families`）。**「该格式下有哪些系」不要新写**——`series.go` 的 `SeriesOfFormat(f Format) []Series` 已经给的就是按 `seriesTable` 顺序的那些系，任务 6 直接用它。第 4 层认不出系时要报「认出了什么格式、那个格式下有哪些系」，也用同一个函数拼说明。

表的内容：

`formatMediaTable` 按这个顺序排，**顺序本身就是对歧义的处理，不能因为「看起来更整齐」而重排**：

| 顺序 | 格式 | markers | 为什么在这个位置 |
|---|---|---|---|
| 1 | kickstart | `.treeinfo` 存在 | 必须排在 SUSE 之前：现代 RHEL 也有 `repodata/repomd.xml`，排反了会把 RHEL 认成 SUSE，机器拿到 AutoYaST 应答文件而安装器根本不认 |
| 2 | autoinstall | `.disk/info` 存在且含 `Ubuntu` | 必须排在 preseed 之前：Ubuntu 的 ISO 也有 `dists/` |
| 3 | preseed | `.disk/info` 存在且含 `Debian`；`dists/` 存在 | 排在 autoinstall 之后，见上一行 |
| 4 | autoyast、agama | `repodata/repomd.xml` 与 `media.1/products` 都存在；`boot/x86_64/loader/` 存在 | 两个都要：单用 `repomd.xml` 分不出现代 RHEL，`media.1/products` 是 SUSE 专属 |
| 5 | esxi-ks | `boot.cfg` 与 `efi/boot/bootx64.efi` 都存在 | 两个都要：单靠 `boot.cfg` 太弱，单靠 `bootx64.efi` 更不行——任何 UEFI 可引导镜像都有那个路径 |
| 6 | unattend | `sources/install.wim` 存在 | |

第 4、5 两行的依据是旧系统实证过的（2026-09-23 对 Leap 15.6 实测：`content` 文件是 404，openSUSE 官方文档明说 content 识别法自 SLE15/Leap 15 起已废止，改用 `repodata/` 与 `media.1/products`；ESXi 的 `efi/boot/bootx64.efi` 同理有实测依据）。**`content` 这个文件不要用**——SUSE 15 以后的安装介质里没有它，这是本任务最容易照旧资料写错的一格。

**覆盖清单：**
- 七种格式的格式级线索各自命中；把某个 marker 的路径删掉、或把内容里的片段改掉，就不命中
- **顺序**：把 `Formats()` 的顺序改一下，kickstart 的树不许落到 SUSE 头上、Ubuntu 的树不许落到 preseed 头上（这两条是顺序的护栏，`Formats()` 一改就红）

- autoyast/agama 的两个 marker 缺一不可：只有 `repodata/repomd.xml` 不命中（这一条防的是把现代 RHEL 认成 SUSE）

```go
type SourceKind string

const (
	SourceRemote SourceKind = "remote" // 远程链接
	SourceUpload SourceKind = "upload" // 浏览器上传
	SourceLocal  SourceKind = "local"  // 服务器本地路径
)

// SourceState 是来源的状态。字面量会存进数据库，发布后不能改名。
type SourceState string

const (
	SourcePending   SourceState = "pending"   // 登记了还没开始取
	SourceFetching  SourceState = "fetching"  // 正在取
	SourceFetched   SourceState = "fetched"   // 字节到齐
	SourceFailed    SourceState = "failed"    // 取失败
	SourceCancelled SourceState = "cancelled" // 操作员取消
)

// Source 是一条获取来源，由 (ISOID, Role) 定键：Role 为空是主介质，
// 附加来源用 catalog.ExtraSource.Role 给的名字（Debian 是 netboot）。
type Source struct {
	ISOID          string
	Role           string
	Kind           SourceKind
	URL            string // remote 的链接
	Path           string // local 的服务器路径
	TotalSize      int64  // upload 登记的总大小；remote 从 Content-Length 得知后回填
	ExpectedSHA256 string // 登记时填的期望值，可空（C3）
	Fetched        int64  // 已确认落盘的字节数
	State          SourceState
	Error          string // 失败的原因，可存文本
	Rev            int64  // 乐观锁，由仓储维护
}

// Range 是一段已确认落盘的字节区间 [Start, Start+Length)。
type Range struct {
	Start  int64
	Length int64
}

type ISOSources interface {
	// SaveSource 登记或整体更新一个来源，与审计同一个事务（spec §6.2 第 8 条：登记来源要审计）。
	// 零值 Audit 表示不审计，供系统内部的进度更新用。登记时 Rev 置 1。
	SaveSource(ctx context.Context, src Source, a Audit) (Source, error)
	// GetSource 按 (isoID, role) 取，没有时第二个返回值为 false。
	GetSource(ctx context.Context, isoID, role string) (Source, bool, error)
	// SourcesOf 取这个 ISO 的全部来源，按 Role 排序（主介质在前，它是空串）。
	SourcesOf(ctx context.Context, isoID string) ([]Source, error)
	// ListUnfinishedSources 取还没取完的来源，按 ISOID、Role 排序，给装配点启动恢复用。
	ListUnfinishedSources(ctx context.Context) ([]Source, error)
	// DeleteSource 删一条来源，连同它确认的区间。零值 Audit 表示不审计。
	DeleteSource(ctx context.Context, isoID, role string, a Audit) error
	// SaveRange 记一段已确认的字节区间，重复存同一段只算一次（按 Start 覆盖）。
	SaveRange(ctx context.Context, isoID, role string, start, length int64) error
	// RangesOf 取这个来源已确认的区间，按 Start 升序、互不重叠、已合并。
	RangesOf(ctx context.Context, isoID, role string) ([]Range, error)
}
```

`CheckSource` 查入参（不查库）：`ISOID` 合 `CheckID`；`Role` 与 `URL`、`Path` 都是可存文本；`Kind` 是三种之一，且 `Kind` 与 `URL`/`Path` 对齐（remote 要 URL、local 要 Path、upload 两个都不要）；`ExpectedSHA256` 为空或 64 位小写十六进制（照 `CheckISOText` 的 `lowerHexSHA256`）；`Fetched` 不小于 0 且不大于 `TotalSize`（`TotalSize` 为 0 表示还不知道大小，不查）；`State` 是六种之一。不合的报 `ErrInvalid`。

**分片大小不登记**：第 5 层的 `Upload` 传的是 `offset` 加一段内容，分片多大由客户端定，服务端只记区间。所以 `Source` 上没有 `ChunkSize`，存储按区间而不是按固定分片——客户端换一个分片大小续传也照样成立。

`CheckSourceTransition(from, to SourceState) error` 是状态的转换表：`pending → fetching/failed/cancelled`、`fetching → fetched/failed/cancelled`、`fetched/failed/cancelled → pending`（重试时清掉重来）。`SaveSource` 在事务里读到现有的来源之后调它，对不上报 `ErrConflict`。**进度更新（`Fetched` 变化）只在前是 `fetching` 时受理**，这一条同时防着下载协程与控制台的取消互相覆盖。

### 任务 3：ISO 9660 只读解析器

**目标：** 把一份 ISO 9660 镜像读成 `fs.FS`，让真镜像上的路径取得出文件。（附录 A `dab857b`、`41fe0ee`）

**文件：**
- 创建：`internal/iso/iso9660/iso9660.go`
- 创建：`internal/iso/iso9660/doc.go`
- 测试：`internal/iso/iso9660/iso9660_test.go`、`realiso_test.go`

**接口契约：**

```go
// Package iso9660 把 ISO 9660 镜像读成只读的 fs.FS。它只依赖标准库，
// 不知道 lober 的任何概念：镜像里有什么路径、哪些路径有意义，由调用方决定。
package iso9660

// Open 解析 r 里的 ISO 9660 镜像，返回一个只读的 fs.FS。r 必须是 io.ReaderAt，
// 并且能给出总长（io.ReaderAt 加 Size() int64，os.File 两者都满足）。
//
// 路径一律小写：ISO 9660 的文件名本来大写，带 Rock Ridge 或 Joliet 扩展的镜像另有一个
// 保留原样写法的命名空间。解析器按 Joliet（UCS-2）→ Rock Ridge → 纯 ISO 9660 的顺序取
// 第一个可用的命名空间，取到的名字原样保留，纯 ISO 9660 的大写名字小写化之后才放进 fs——
// 旧系统漏了这一步，ESXi 的引导器与内核抽不出来（41fe0ee）。
//
// 目录记录跨扇区、一个目录有很多条目、符号链接（Rock Ridge 的 NM/PX/SL 条目）都要能走通。
func Open(r SizeReader) (fs.FS, error)

// SizeReader 是 Open 要的：能按偏移读，也知道自己有多长。
type SizeReader interface {
	io.ReaderAt
	Size() int64
}
```

实现要点（写给实现者的约束，不是源码）：

- 从扇区 16 读卷描述符，跳过类型 255 的终止符；先找 Supplemental Volume Descriptor（类型 2，Joliet，按 Escape Sequence 认出 UCS-2 的级别），再找 Primary（类型 1）。两个命名空间分别建一棵目录树，`fs.FS` 只暴露 Joliet 那一棵；没有 Joliet 时用 Rock Ridge；两者都没有才用纯 ISO 9660。
- 目录记录里的文件名段：`;1` 版本号后缀去掉；`.` 与 `..` 跳过；纯 ISO 9660 的名字带 `.` 分隔符时按 8.3 拆开再小写化拼接。
- Rock Ridge 的 `NM` 条目给出完整名字（可含 `/` 以外的任意字符，含大写与小写），有它就用它替换文件名段；`PX` 给权限位（要认符号链接的 `S_IFLNK`）；`SL` 给链接目标——符号链接要在 `fs.FS` 里真的能 `ReadLink`，否则第 4 层解出的树会缺文件。
- 目录记录可能跨扇区（一个 2048 字节的扇区装不下一条记录时，记录在下一个扇区继续），必须按扇区边界续读，不能假设一条记录整个在一个扇区里。
- 目录可能很大（Debian 的 `pool/` 有上万个条目），要支持跨多个扇区顺序读下去，直到记录的剩余长度为 0。
- 只读，不解压，不写临时文件。`fs.ReadFile`、`fs.WalkDir`、`fs.ReadLink` 都要能用。

**覆盖清单：**
- 合成镜像：只有 Primary 描述符的纯 ISO 9660 镜像；带 Joliet 的；带 Rock Ridge 的；两者都带的（取 Joliet）
- 文件名：带 `;1` 后缀的、8.3 短名带 `.` 的、纯大写的（小写化）、Rock Ridge 给出大小写混合的（原样保留）
- 目录：根目录、嵌套目录、一个目录有很多条目（跨多个扇区）、一条目录记录跨扇区
- 符号链接：Rock Ridge 的符号链接能 `ReadLink`，`fs.WalkDir` 能走过去
- 错误：不是 ISO 9660（没有卷描述符）、`r` 太短、读出错
- 真 ISO：由 `LOBER_TEST_REAL_ISO` 开关跑，未设则 `t.Skip`。用例：打开镜像、走完整棵树、断言几个已知路径存在（`isolinux/`、`Packages/`、`dists/` 之类按镜像实际内容断言）、读出其中一个文件的前若干字节非空

- [x] **重构 + commit：** `make check` 全绿后 commit（`feat(iso): ISO 9660 只读解析器`）。

**风险：** **造一份合成 ISO 9660 镜像是这个任务的主要工作量**，比解析器本身小不了多少。造的时候注意：卷描述符要在扇区 16，路径表可以置空（很多实现不看它），目录记录的剩余长度字段要算对。真镜像上的边界（跨扇区记录、超大目录、Rock Ridge 的符号链接）在合成镜像里要各造一例，否则 `dab857b` 那一类问题照样漏过去。真 ISO 用例跳过时不报红，所以它不能是唯一的防线。

`local.go`：`CheckLocalPath(roots []string, p string) error` 判 `p` 经 `filepath.Abs` 与 `filepath.Clean` 之后落在 `roots` 里某一个之下（按路径段比，不是字符串前缀——`/srv/iso` 与 `/srv/iso2` 不是包含关系）。不合法时返回 `iso_source_rejected` 加对应理由。

`source.go` 是三种来源共用的落盘与状态机：

- `stagingPath(isoID, role)` = `{Staging}/{isoID}.{role}.part`，role 为空时省掉那一段
- 边写边算 SHA256（`crypto/sha256` 的 `io.Writer` 包装）
- `resumeOffset(isoID, role)`：取盘上 `.part` 的实际大小，比仓储里记的 `Fetched` 短就按盘上来（**库里记的进度比盘上多时以盘为准**，spec §7.2 第 4 条点名的第二个续调用例），同时把仓储里的值改回实际大小
- `finishFetch`：比对 `ExpectedSHA256`，不符报 `iso_content_mismatch`；相符就把 `.part` 改名为 `{isoID}.{role}`（去掉 `.part`），来源置 `fetched`

`remote.go`：先 `CheckURL`，再 `GET`；服务端回 206 就从 `resumeOffset` 发 `Range: bytes=N-`，回 200 就从头再来（服务端不支持 Range），回 416 说明服务端认为没有更多字节，按已到齐处理。重定向每一跳都重新过 `CheckURL`（用 `http.Client` 的 `CheckRedirect`，在里面拿新 URL 重新解析、重新解析 IP、重新校）。

**覆盖清单：**
- `CheckURL`：http 与 https 放行；`file`、`ftp`、空 scheme 拒；回环四种写法（`127.0.0.1`、`127.1.2.3`、`[::1]`、`0.0.0.0`）拒；链路本地（`169.254.1.1`、`[fe80::1]`）拒；私有段（`10.`、`192.168.`、`172.16.`）放行——这一条是刻意的，测试要写明理由
- `CheckLocalPath`：根目录本身、根下的多级子路径放行；根外的拒；`/srv/iso2` 不被 `/srv/iso` 放行（按段比，不是字符串前缀）；`..` 穿越的拒；相对路径按进程工作目录解析之后判
- 远程下载：完整下一份；服务端只回 200 时从头再来；回 206 时从记录偏移续；中途失败后重试接着下（断点续传的第一个用例）
- **库里记的进度比盘上多**：手工把 `.part` 截短，再触发续传，断言按盘上的大小续，且仓储里的 `Fetched` 被改回实际大小
- SHA256：期望值不符时来源置 `failed` 并报 `iso_content_mismatch`；相符时置 `fetched`
- 重定向：每一跳都过 `CheckURL`——第二跳指向回环时要拒，并且**已经写进 `.part` 的字节要作废**（不能把半份回环内容当成取到）
- `FreeSpace`：返回两个目录的余量；目录不存在时报错并说清是哪个

- [x] **绿：** 实现。预期 PASS。
- [x] **重构 + commit：** `make check` 全绿后 commit（`feat(iso): 来源获取的本地路径与远程下载`）。

**风险：** 「按解析出的 IP 直连」要自己控 DNS，`httptest` 的服务端在 `127.0.0.1` 上——**测试会撞上回环拒绝**。所以 `CheckURL` 与拨号要能分开测：`CheckURL` 是纯函数，直接喂 IP；拨号那条用一个注入的 `dialControl` 或让 `httpClient` 接受一个「允许回环」的测试开关，开关的默认值是拒。别为了让测试通过就把回环检查关掉。另外 `minChecked[layerISO]` 在这个任务从 0 改成 1。

`upload.go` 的规则：

- `Register` 的 `kind` 是 `upload` 时登记一条上传来源，`size` 就是总大小
- `Upload`：`offset` 小于 0、或 `offset` 加读到的长度超过总大小，报 `iso_source_rejected`；通过了就按 `offset` 写进 `.part`，并 `SaveRange` 记下 `[offset, offset+n)`
- **不设收尾方法**——第 5 层的接口里没有它。字节齐不齐由本层自己判：`RangesOf` 合并之后的区间正好覆盖 `[0, TotalSize)` 就算齐，走 `finishFetch` 那条路（验 SHA256、改名、置 `fetched`）。控制台因此不需要显式收尾，也就没有「忘了收尾」这种失败
- 同一段重复上传只算一次：`SaveRange` 按 `(iso_id, role, start)` 覆盖，`RangesOf` 合并重叠区间，`Progress.Missing` 只报还没确认的部分

`recover.go` 的规则：

- `ListUnfinishedSources` 只给 `pending` 与 `fetching` 的；`failed` 与 `cancelled` 不恢复
- `Recover` 返回两类 `ToResume`：来源没取完的（`ResumeFetch`），以及来源全部 `fetched`、ISO 却还停在 `acquiring` 或 `importing` 的（`ResumeImport`）
- 制品目录里残留的 `.tmp-*` 由 `Import` 开头的清理负责，`Recover` 只报清单

**覆盖清单：**
- `Register` 三种 kind 各一例；同一个 ISO 先登主介质再登 netboot，`SourcesOf` 按 Role 排序取出、主介质在前
- `Upload` 按序写、按乱序写都一样；同一段传两次只确认一次（`Progress.Missing` 不变）
- `offset` 为负、或写越过总大小，报 `iso_source_rejected`，且不改变已确认的区间
- 不显式收尾：把 `[0, TotalSize)` 全部传完之后，来源自己变 `fetched`、`.part` 改名
- 刷新页面续传：新建一个 `Sources`、`Progress` 报出缺哪些区间，按缺的补上就能到 `fetched`
- `Cancel`：`pending`/`fetching` 都能取消，这个 ISO 的全部来源置 `cancelled`，ISO 仍是 `acquiring`；**不把 ISO 置为 failed**
- `Retry`：`failed`/`cancelled` 能重试，`Fetched` 归零、区间清空、来源回到 `pending`
- `Reimport`：`failed` 的 ISO 能直接重新导入，不用重新获取字节（spec §5.1 第 5 步）；`ready` 的报 `ErrConflict`
- `Recover`：`pending`/`fetching` 的来源进清单，`failed`/`cancelled` 的不进；字节到齐却没导完的 ISO 进清单（`ResumeImport`）；`Recover` 自己不起协程
- `Progress` 的 `Missing` 合并重叠区间、按 Start 升序；remote 与 local 是一个区间或没有
- `FreeSpace` 返回两个目录的余量；目录不存在时报错并说清是哪个

- [x] **绿：** 实现。预期 PASS。
- [x] **重构 + commit：** `make check` 全绿后 commit（`feat(iso): 分片上传、取消重试与启动恢复`）。

**风险：** `Recover` 要起协程去取字节，而本层约定不起协程。定下来的做法是：`Recover` 只遍历并**返回**要恢复的清单，起协程归装配点；导入的重跑同理，由装配点调 `Import`。这个边界要写进 `doc.go`，否则下一个任务会顺手在 `Recover` 里起协程。

`Identify` 的顺序：格式 → （unattend 时先解 editions）→ 系 → 版本与架构。`Identified.Editions` 只在 unattend 填。

五种 probe 的解析规则：

- `treeinfo`：读 `.treeinfo`，按 INI 解析，取 `[general]` 的 `version` 与 `arch`。系级线索用的 `name=` 在同一个段里，识别时一起读出来比对。
- `diskinfo`：读 `.disk/info`，一行文本。Debian 的形如 `Debian GNU/Linux 13.6.0 "Trixie" - Official amd64 NETINST Binary-1 with firmware-1 20250803-13:06`，版本是第一个字段里的点分版本号，架构是 `amd64`/`arm64` 字样；Ubuntu 的形如 `Ubuntu-Server 24.04.3 LTS "Noble Numbat" - Release amd64 (20250819)`。**取版本与架构的确切规则要真 ISO 坐实**，首版按这两个样例写，并在 `media_test.go` 的 `pending` 清单里记一条；测试里把这两个样例文本钉住，改规则先改测试。
- `products`：读 `media.1/products`，管道分隔的产品清单。**架构从 `boot/<arch>/loader/` 的目录名取，不从 `products` 取**——SUSE 的架构一定体现在引导器路径上，这一条可靠；版本按 `products` 里的版本字段取，确切的字段序标「待真机核实」记进 `pending` 清单，首版按「文件里第一个形如 `15.6`/`16.0` 的点分版本号」取，并在测试里钉住样例。
- `bootcfg`：读 `boot.cfg` 与 `efi/boot/bootx64.efi`。**架构从引导器路径取**：`bootx64.efi` 就是 x86_64，这一条可靠。**版本取不到**——ESXi 的 `boot.cfg` 里只有 `title=Loading ESXi installer` 这类字样，不带版本号，旧系统也从来没有从内容里取到过它。所以首版实现成「认不出版本就报 `iso_version_missing`」，**ESXi 路径首版因此导不出 ready 的 ISO**。这不是遗漏，是明确的失败：`media_test.go` 的 `pending` 清单记一条、spec §8 记一条。候选的坐实路径（第 7 层真机时定）：`imgpayld.tgz` 里的版本文件，或 `s.v00` 模块里的构建串。**不要为了让 ESXi 能导入就猜一个取法**——猜错的版本会成为制品目录里的一段路径，错了要到真装机才发现。
- `wim`：解 XML 索引，`<VERSION>` 给版本（`<MAJOR>.<MINOR>.<BUILD>` 取前两段），`<ARCH>` 给架构（`0`/`9` 是 x86_64，`12` 是 aarch64），`<IMAGE>` 逐个给 NAME 与 FLAGS。

**覆盖清单：**

- kickstart 五系：`.treeinfo` 的 `name=` 写哪个发行版就归哪个系；写一个不在清单里的名字报 `iso_series_unrecognized`，并且说明里带上认出的格式
- Debian 与 Ubuntu 的 `.disk/info` 互换内容：Debian 的被认成 preseed、不被认成 autoinstall（`131d659`）

### 任务 7：解出制品与清单

**目标：** 把识别出的介质解成制品集，写 `ISO.Artifacts`，验完整之后原子落盘、置可用。（C4、C5、附录 A `3468d64`、`41fe0ee`）

- 创建：`internal/iso/extract.go` —— 解出制品
- 创建：`internal/iso/import.go` —— 导入编排
- 测试：`internal/iso/extract_test.go`、`import_test.go`

**接口契约：**

```go
// Import 把一个 ISO 从「字节到齐」导到「可用」。它是阻塞的，由装配点放进看护协程。
// 入参不合前提（记录不存在、来源没取完）返回 Problem 列表，不返回半成品。
func (s *Sources) Import(ctx context.Context, isoID string) error

// 三段都是已验证安全的标识，不会目录穿越。
func (s *Sources) artifactRoot(series catalog.Series, version string, arch catalog.Arch) string
```

`import.go` 的流程照规格 §5.1，逐步都是：

1. `GetISO` 读记录；`SourcesOf` 确认全部来源 `fetched`，否则返回问题
2. 打开主介质的 ISO 9660 视图，`Identify`
3. `Identified.Series` 与记录的 `Series` 不同 → 失败，报 `iso_series_mismatch`，参数给声明值与识别值（C3）
4. 附加来源：记录里没有 `catalog.ExtraSourceOf(series)` 要的那条 → `iso_extra_source_invalid`；取到了就打开它、识别、比版本（`SameVersion`）
5. 解到 `{artifactRoot}.tmp-{isoID}/`：按 `catalog.RequiredRoles(series)` 逐个角色取文件
6. 按 `catalog.RepoPaths(series)` 验仓库树完整，缺一条报 `iso_repo_incomplete`
7. 逐个角色核对文件在盘上真实存在且非空，缺一个报 `iso_artifact_missing`（第 3 层契约：「The importer must validate real existence/completeness」）
8. 写 `ISO.Artifacts`：角色 → 相对 `{Artifacts}` 的路径。目录角色以 `/` 结尾。**rel 的合规（非空、无前导 `/`、无 `.` 与 `..` 段）在这里保证**——`catalog.ArtifactURL` 只拼不查，这一层漏了查，渲染出的地址就能穿出制品目录
9. `os.Rename` 把 `.tmp-{isoID}` 换成正式目录——**这是本层唯一改制品目录的地方**
10. `UpdateISO` 置 `ready`，记录必须过 `model.ISO.Validate`（C5，由仓储兜底）；若记录在这期间被废弃，仓储报 `ErrImmutable`，清理临时目录、不报成导入失败

`extract.go` 的取角色规则：

| 格式 | kernel / initrd | stage2 | repo | iso | live-root |
|---|---|---|---|---|---|
| kickstart | ISO 的 `images/pxeboot/{vmlinuz,initrd.img}` | 解出树的 `install/` 子树（含 `.treeinfo` 与 `images/install.img`） | 按 `.treeinfo` 的 `packagedir` 定根（`3468d64`） | | |
| preseed | netboot 包的 `install.amd/{vmlinuz,initrd.gz}` | | | | |
| autoinstall | ISO 的 `casper/{vmlinuz,initrd}` | | | 复制整张原始 ISO | |
| autoyast | ISO 的 `boot/x86_64/loader/{linux,initrd}` | | 解出树根 | | |
| agama | 同 autoyast | | 解出树根 | | ISO 的 `LiveOS/squashfs.img` |
| esxi-ks | | | | | |

ESXi 单独一段，**首版走不到这里**——任务 6 取不出版本，导入在识别之后就报 `iso_version_missing` 结束。所以 ESXi 的解出代码本任务先不写，只写一条测试钉住「ESXi 的合成 ISO 导入到识别为止、报 `iso_version_missing`、制品目录里什么都没有」。等第 7 层真机坐实了版本取法，再回来补这一段。真要写时的形状（现在记下，免得将来重新想）：解出完整树到 `esxi-tree/`（含原始 `boot.cfg` 的字节，第 3 层的 `FileAux` 要调用方提供原始内容，本层是它的出处），`mboot` 指到树内的 `efi/boot/bootx64.efi`，**不要再复制一份**——真实 ESXi ISO 里没有 `mboot.efi`，那是 PXE 部署的惯例名字（旧系统实证过），而树内那个路径本来就是它。**纯 ISO 9660 文件名小写化由 iso9660 负责**（`41fe0ee`）。

**覆盖清单：**
- **六种格式**（kickstart、preseed、autoinstall、autoyast、agama，加任务 8 的 unattend）各一套合成 ISO，导入后 `Artifacts` 的角色齐全、rel 合规、目录角色以 `/` 结尾

## 留给后续层的约定

- **第 5 层**：接口由控制台声明、本层实现（总 spec §6.1「由调用方声明一个只含所需操作的接口」），`internal/iso` 不 import console。两边对齐的签名见 `specs/2026-10-11-layer5-console-design.md` §6.1，本层多两处：`Register` 与 `Upload` 带 `role`（一个 ISO 可以有多条来源），四个写方法带 `a store.Audit`（登记来源要审计，总 spec §6.2 第 8 条）。`cmd/lober` 用 `var _ console.ISOSource = (*iso.Sources)(nil)` 兜住。控制台自己不碰字节；建 ISO 前调 `FreeSpace` 查余量（spec §5.1 第 1 步）。进度只读，不自己写。
- **第 5 层装配点**：注入暂存目录、制品目录、SMB 目录、Windows 工具目录、允许登记的本地目录；启动时调 `Recover` 拿到要恢复的清单，把每件事分别放进看护协程（spec §6.2 第 6 条、§6.3）。`Recover` 只遍历并返回清单，不起协程——起协程归装配点。
- **第 5 层删除编排**：审计 Store.DeleteISO 之前持久化 `DeletionSnapshot{ISO, Sources}`；删除成功后调用 CleanupDeleted，并保留快照重试到成功。本地原件不会清理，仍存在的数据库记录和他人所有权目录不会清理。Recover 不扫描已经删除的记录。
- **第 7 层**：网关只读仓储里的 ISO 记录与 `ISO.Artifacts`，不调本层。真装后确认 Windows 是否需要按固件分两套制品，需要就回到第 1 层给 `model.ISO` 加固件维度。
- **任何一层要改识别规则、仓库判据或必需角色**：只改 `catalog` 一处。它们是随程序发布的静态事实（C1），改了要发新版本。
- **真 ISO 的开关**是 `LOBER_TEST_REAL_ISO`（`internal/iso/isotest` 读它）：设了就跑真 ISO 用例，没设就跳过。与 PostgreSQL 的 DSN 不同——那边没有库就等于存储层零覆盖，必须失败；这边只是缺一份几 GB 的本地镜像，其余导入测试仍覆盖着解析与抽取的逻辑分支。
