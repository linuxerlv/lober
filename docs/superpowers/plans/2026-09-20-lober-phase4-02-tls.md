# P4-02 TLS 与 mTLS 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成。与 P4-01、P4-04 并行。**P4-03（Secure Boot）依赖本计划。**
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 把机器面与人面的传输从明文 HTTP 换成 TLS，解除 §9.1 末段
「token 与默认拒绝是唯一防线」这个约束。

**架构：这个计划的大部分工作不在 Go 代码里。** §1.5 已经为它做了三件准备：
所有 URL 从配置来且 scheme 不写死、用域名不用 IP、首跳脚本不烧进 iPXE 二进制。
**所以服务端侧应当是「改配置而非改代码」** —— 任务 1 验证这个前提是否真的成立。

**真正贵的部分在 iPXE 侧**（§1.5 的原话）：
**iPXE 走 HTTPS 需重新编译**（带 crypto、用嵌入方式把内网 CA 放进二进制），
而之后每次证书轮换都要重编重发引导文件。

**这个成本是本计划的主要内容**，任务 3 到 5 都在处理它。

**技术栈：** 内网 CA；nginx 的 TLS 配置；iPXE 的自行编译

**SPEC 依据：** §1.5 传输层决定与三件准备、§9.1 末段、§11 Phase 4、附录 B 的 nginx 模块项

### 任务 1：验证「改配置而非改代码」是否成立

**产出文件：** `docs/phase4-tls-前提验证.md`

**为什么需要这一步：** §1.5 说三件准备做到了就能「部署变更而非代码变更」。
**先验证那三件事真的做到了**，而不是假设 —— 若有遗漏，
本计划的工作量会从「改配置」变成「改代码再改配置」。

**要验证的三项：**

1. **所有 URL 从配置来，scheme 不写死。**
   验证方式：把配置里的两个基址改成 https，跑全部测试，
   **确认渲染出的 URL 都变了** —— 而不是某处硬编码了 http
2. **用域名不用 IP。** 验证方式：全文搜索配置样例与模板，
   确认没有 IP 字面量出现在 URL 位置（**证书的 CN 要对上域名**）
3. **首跳脚本不烧进 iPXE 二进制**，而是由 DHCP 给出地址

**顺带验证 Phase 1 的一个设计是否够用：**
渲染器的测试里有一条「产出中不含字面 `http://`」的断言 ——
**它应当在这次改成 https 后仍然通过**（因为它查的是字面量，而 scheme 来自配置）。
若那条断言写成了「不含 http:// 但允许 https://」之类，那是一个要修的测试。

**发现遗漏时的处置：** 补齐它作为本任务的一部分，
**并记录下来** —— 那说明 §1.5 的准备工作有一处没落实，
而知道是哪一处对将来的类似准备有参考价值。

**验证：** 三项各有验证结果；把基址改成 https 后全部测试通过。

**完成标志：** commit `docs: verify the three TLS prerequisites from §1.5`

### 任务 2：内网 CA 与证书签发

**产出文件：** `deploy/ca/README.md`、签发脚本

**为什么需要这一步：** 气隙环境没有公共 CA 可用，必须自建。

**要做的四件事：**

1. **建 CA**（根证书与私钥），**私钥离线保存**
2. **签发服务端证书**：机器面与人面各一个（或一个含两个域名的）
3. **公钥分发**：网关侧不需要（它是服务端），**但 iPXE 与控制台浏览器需要**
4. **轮换流程**：证书有效期与轮换步骤

**第 3 条的两个分发目标成本差异巨大：**

| 目标 | 分发方式 | 成本 |
|---|---|---|
| 控制台浏览器 | 导入 CA 到运维的机器或浏览器 | 低，一次性 |
| **iPXE** | **嵌入二进制，重新编译**（§1.5） | **高，每次轮换都要重编重发** |

**所以证书有效期的选择有一个具体约束：它决定 iPXE 二进制的重编频率。**

**建议：服务端证书给较长有效期（数年），并在 CA 证书上给更长的。**
理由：嵌入 iPXE 的是 **CA 证书**而非服务端证书 ——
只要 CA 不换，服务端证书轮换不需要重编 iPXE。

**这条要写清楚**，因为它是「让 TLS 的运维成本可接受」的关键：
**嵌 CA 而非嵌服务端证书，于是常规轮换不触碰 iPXE。**

**一条安全要求：CA 私钥不能放在装机服务器上。**
那台机器在装机 VLAN 上有服务暴露 —— 而 CA 私钥泄露意味着整个信任体系失效。

**验证：** CA 与证书签发脚本可跑；证书的域名与配置里的基址一致。

**完成标志：** commit `deploy: internal CA with long-lived root for iPXE embedding`

### 任务 3：nginx 的 TLS 配置

**产出文件：** `deploy/nginx/lober.conf`（改）

**为什么需要这一步：** nginx 是唯一入口（§1.4），TLS 终结在它这里。

**两个 server 块都要改**，但配置不同：

| 面 | 协议版本要求 | 理由 |
|---|---|---|
| 人面 | 可以只开较新的 TLS 版本 | 客户端是运维的浏览器，可控 |
| **机器面** | **要考虑 iPXE 的 TLS 支持范围** | iPXE 的 crypto 实现有限，**支持的协议版本与密码套件都比浏览器少** |

**机器面的协议与套件配置要按 iPXE 的实际支持来定** ——
**这是附录 B 式的待核实项**：要在编译出带 crypto 的 iPXE 之后实测它能协商上什么。
**先配一个宽松的，实测后收紧。**

**三条不要忘的：**

1. **保留 HTTP 监听并重定向到 HTTPS？机器面不要。**
   iPXE 的重定向跟随行为不确定，而首跳脚本的地址由 DHCP 给出 ——
   **直接把 DHCP 里那个 URL 改成 https 更干净**。人面可以做重定向
2. **制品的 location 也走 TLS。** 那是几 GB 的传输，
   **要确认 TLS 的开销可接受** —— 现代 CPU 上 AES-NI 让它几乎免费，
   但要实测（老机器上可能不是）
3. **签名链接（P2-04）与 TLS 叠加时，签名里的 URI 部分不含 scheme** ——
   所以换 scheme 不影响签名。**要有测试确认这一点**

**验证：** `nginx -t` 通过；**用 curl 以 HTTPS 取一次制品与一次引导脚本**；
确认签名链接在 HTTPS 下仍然有效。

**完成标志：** commit `deploy(nginx): TLS termination with iPXE-compatible ciphers`

### 任务 4：iPXE 的重新编译

**产出文件：** `deploy/ipxe/README.md`、构建脚本

**为什么需要这一步：** §1.5 说清了这是 HTTPS 在这套栈里最贵的部分。

**要做的三件事：**

1. **开启 crypto 支持**（编译选项）
2. **把 CA 证书嵌进二进制**（§1.5 提到的那种嵌入方式）
3. **为四种架构各编一个**（BIOS、IA32 UEFI、x64 UEFI、ARM64 UEFI）

**构建必须在有外网的机器上做**（要拉 iPXE 源码与工具链），
与前端构建同理（§12.3）。**产出四个二进制带进内网。**

**一条要记录的：编译出的二进制的 sha256。**
Phase 1 的部署文档已经要求记录 iPXE 二进制的校验值 ——
自编的更要记，因为它们不能从官方下载处复核。

**两个可能的坑要在 README 里预警：**

| 坑 | 表现 | 应对 |
|---|---|---|
| 嵌入的 CA 格式或路径不对 | iPXE 报证书验证失败 | 编译后用一次实际请求验证，不要只看编译成功 |
| **二进制变大** | TFTP 传输变慢（crypto 让二进制大出可观比例） | 这是 UEFI HTTP Boot 的动机之一（见任务 6） |

**第二个坑的量级要实测并记录** —— 它是判断「要不要做 UEFI HTTP Boot」的依据。

**一条运维流程要写进文档：证书轮换时的重发步骤。**
换 CA 时要重编四个二进制、替换 TFTP 目录里的文件、
**而正在装机的机器不受影响**（它们已经拿到二进制了）。

**验证：** 四个二进制都能编出；**用其中一个实际引导一台机器并成功取到 HTTPS 的引导脚本**。

**完成标志：** commit `deploy(ipxe): self-built binaries with embedded internal CA`

### 任务 5：mTLS —— 范围与取舍

**产出文件：** `docs/phase4-mtls-决策.md`、（若做）nginx 与客户端配置

**为什么需要这一步：** §11 Phase 4 写的是「TLS + mTLS」。
**但 mTLS 在机器面有一个根本性的困难要先说清。**

**困难：裸机在获得身份之前没有凭据。**

§4.2 说明了这个协议事实：**首次请求必然无认证**
（机器此刻只有固件，不可能持有凭据）。mTLS 要求客户端证书 ——
而一台刚上电的裸机从哪里拿证书？

**三个可能的答案，各有代价：**

| 方案 | 代价 |
|---|---|
| 证书嵌进 iPXE 二进制 | **全网共用一个客户端证书** —— 那等于没有客户端身份，只是多一道共享秘密 |
| 每台机器一个证书 | 要按机器编译 iPXE 二进制，**运维上不可行** |
| **机器面不做 mTLS，只人面做** | 机器面的准入仍靠 §9.1 的三道闸门 |

**推荐第三种，并把理由写进决策文件。**

**机器面不做 mTLS 不是降级，因为：** 那三道闸门（默认拒绝、
SN 加 MAC 双因子、attempt 封顶）针对的是「谁能装机」，
而 mTLS 针对的是「谁能连上来」—— **前者是更强的约束**。
一个持有共享客户端证书但 SN 不在清单里的机器，仍然拿不到 token。

**人面做 mTLS 是有意义的**：客户端是运维的机器，数量少、可管理，
而它防的是「有人拿到了密码但不在授权设备上」。
**但它与已有的密码认证是叠加而非替代** —— 不要因为上了 mTLS 就放松密码要求。

**若决定人面做 mTLS，要处理一个运维问题：证书分发与吊销。**
运维换机器、离职时要吊销 —— 而吊销列表的维护是一个持续负担。
**在只有个位数运维的场景下，这个负担可能超过收益** ——
决策文件里要权衡这一点。

**验证：** 决策文件写明机器面不做 mTLS 的理由；若人面做了，客户端证书验证生效。

**完成标志：** commit `docs: mTLS scope decision with the bare-metal identity problem`

### 任务 6：UEFI HTTP Boot（附属任务）

**产出文件：** `deploy/dnsmasq/lober.conf`（扩展）、核对记录

**为什么需要这一步：** §11 把它列在 Phase 4。**放在本计划里是因为它与 TLS 相关** ——
任务 4 实测出的「crypto 让二进制变大」是它的主要动机。

**它是什么**（§1.2）：**不是绕过 iPXE，而是用 HTTP 把 iPXE 本身载入内存**，
省掉 TFTP 那段慢传输。

**要加的 DHCP 配置两项**（§1.3 末段与附录 B）：

1. **HTTP Boot 的架构码**（与 PXE 的架构码不同，**具体值待核实** —— 附录 B 列了这一项）
2. **厂商类别选项的匹配**（附录 B 提到它的必要性待核实）

**两项都是附录 B 的待核实项**，所以本任务的第一步是抓包确认固件实际发什么 ——
与 Phase 1 核对 option 93 同一方法。

**为什么这是低优先级**（索引里的排序理由）：
**TFTP 只传几十 KB 到几 MB 的 iPXE 二进制**（§10 失败模式 8 的规避手段：
「TFTP 只发最小 iPXE 二进制，之后全走 HTTP」）。
即使 crypto 让它大出几倍，仍然是秒级传输。

**所以做它的判据是：任务 4 实测的二进制大小让 TFTP 传输成为可感知的延迟。**
若不是，这一项可以不做 —— **§1.2 已经写明「HTTP Boot 是纯增量，
实测出 TFTP 瓶颈后再加，届时网关代码无需改动」。**

**一条重要的兼容性要求：加 HTTP Boot 不能影响已有的 PXE 路径。**
两者靠架构码区分，**要有测试或实机验证确认原有的四条 PXE 分流仍然工作**。

**验证：** 抓包确认架构码；一台支持 HTTP Boot 的机器走通；
**原有的 PXE 路径不受影响**。

**完成标志：** commit `deploy: UEFI HTTP Boot alongside existing PXE paths`

## 上了 TLS 之后可以放松的与不能放松的

**可以放松的一条**（§1.5 的代价一节）：
应答文件里的敏感内容处理可以不再那么严格 ——
但**建议保持现状**（root 不设可复用密码、注入 SSH 公钥、
不放域管凭据）。理由：那些做法本身是好实践，而 TLS 只保护传输
不保护「应答文件落在目标机器磁盘上」那一份（§9.5 的凭据清理仍然必要）。

**不能放松的三条：**

1. **§9.1 的三道闸门** —— TLS 防的是窃听与中间人，防不了「有任务的机器被装错系统」
2. **§9.2 的客户端 IP 判定** —— nginx 仍是反代，那个陷阱仍然存在
3. **§9.5 的凭据清理** —— 理由见上
