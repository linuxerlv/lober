# P2-05 控制台 P2 页面 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成（M6 的端点已有，M8 的 P1 页面已有）。
> 与 P2-01 至 P2-04 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 补齐 §12.6 标 P2 的三个页面 —— hook 管理与审批、制品集导入、磁盘 dry-run。

**架构：** 纯前端工作。**三个页面对应的后端端点在 Phase 1 的 M6 里已全部实现** ——
MVP 期这三件事用 API 直接顶（§11 Phase 2 明确说了这个过渡安排）。

**所以这个计划的主要内容不是「让功能可用」，而是「让危险操作在界面上显出危险」。**
hook 以 root 身份在分区之前运行，能力等同「擦掉这台机器所有盘」（§9.4）——
审批流的界面设计是本计划的核心。

**技术栈：** 沿用 M8 的框架、表格适配器与表单转换层

**SPEC 依据：** §12.6 页面清单、§9.4 权限分级、§2.2 hook 的注册期校验、
§8.2 dryrun 与 preview 的价值

---

## 三个页面的定位差异

| 页面 | 使用者 | 频率 | 界面重点 |
|---|---|---|---|
| hook 管理与审批 | hook 作者、审批人 | 低（一个 hook 写一次，用很久） | **让危险显出危险**；版本与 digest 的对应关系 |
| 制品集导入 | 管理员 | 低（一个 ISO 导一次） | 异步进度与失败原因 |
| 磁盘 dry-run | 装机操作员 | 中（调策略时反复用） | **快** —— 贴数据、出结果、改参数再来一次 |

**dry-run 要做成一等公民、给显眼入口**（§12.6 末段）—— 别埋进二级菜单。
理由：它把模板调试周期从「上电等十分钟」压到秒级，UI 不给入口等于白做。

### 任务 1：hook 列表与版本视图

**产出文件：** hook 列表页

**为什么需要这一步：** hook 是本系统最危险的用户输入 —— 列表页要让运维一眼看出
「哪些 hook 是激活的、哪些在 pre 阶段、哪些等着审批」。

**列表要显示六列：** 名字、阶段、状态、支持的家族、作者、当前版本。

**两条视觉要求：**

1. **`pre` 阶段的 hook 要有明显标记。** §9.4 说清了：`pre` 能碰分区，
   所以激活它需要审批。列表上看不出阶段的话，审批人要点进去才知道自己在批什么
2. **状态用四种明确的呈现**（草稿、待审批、已激活、已停用）。
   **「待审批」要醒目** —— 它是一个需要有人行动的状态，而不是一个中性状态

**版本视图的核心是 digest。** 每个版本显示版本号、digest 前若干位、作者、
审批人、审批时间。

**digest 要能完整复制。** 理由：排查「这台机器当初跑的是哪个版本的 hook」时，
任务详情页显示的是 digest（§3.5 的失败详情字段之一），
运维需要拿那个值到这里对照。**截断显示但提供完整复制** 是这个需求的解。

**一条不要做的事：不要提供「编辑 hook 正文」的直接入口。**
hook 正文不可变（§2.7），修改即新版本。界面上应该是「基于此版本创建新版本」，
而不是一个看起来能改的编辑框 —— 后者会让作者以为自己在改一个东西，
而实际产生了新 digest，已有模板仍 pin 旧的。

**验证：** 列表能按阶段与状态过滤；`pre` 阶段有标记；digest 可完整复制。

**完成标志：** commit `feat(web): hook list with stage emphasis and version digests`

### 任务 2：hook 编辑与校验反馈

**产出文件：** hook 编辑页

**为什么需要这一步：** M6 的校验端点（语法检查加注册期校验）产出的信息要展示好 ——
否则作者会绕过它。

**编辑页的四块：** 元信息表单（名字、阶段、家族、解释器、超时、是否必需）、
正文编辑区、参数 schema 编辑区、校验结果区。

**校验结果要分三级呈现：**

| 级别 | 来源 | 呈现 |
|---|---|---|
| 错误 | 语法错误、阶段非法、requires 引用了不存在的 fact 键 | **阻止保存** |
| 警告 | 静态检查发现脚本引用了未声明的变量 | 允许保存但要显眼 |
| 提示 | 该解释器跳过了语法检查 | 说明原因 |

**第三级不能省。** M6 对 PowerShell 与 ash 跳过语法检查并在响应里说明原因 ——
**界面要把那个说明显示出来**，否则作者以为「检查通过了」，
而实际上根本没检查。

**警告级的价值要在界面上体现。** 静态检查发现的「脚本引用了 `$LOBER_FOO`
但它不在 fact 命名空间里」是最常见的拼写错误，而它的运行时表现是
「变量为空导致 hook 行为异常」—— 从机器侧日志极难看出是拼错了名字。
**警告文案要直接给出建议**（「是否想写 `LOBER_FOO_BAR`？」这类）。

**参数 schema 的编辑要有子集约束的提示**（§12.7）：
超出子集的会在注册时被拒，**界面应当提前告知哪些字段不被支持**，
而不是让作者写完保存时才失败。

**一条界面行为：保存前必须先校验。** 不校验直接保存的入口不要给 ——
它会让「校验」变成一个可选步骤，而那正是注册期校验想避免的
（§7.5：把运行时意外提前为注册时错误）。

**验证：** 三级校验结果各有对应呈现；跳过语法检查时有说明；
未校验时保存按钮不可用。

**完成标志：** commit `feat(web): hook editor with three-tier validation feedback`

### 任务 3：审批流界面

**产出文件：** 审批交互（可以在列表页或详情页内）

**为什么需要这一步：** §9.4 要求激活 `pre` 阶段 hook 需审批（草稿 → 待审批 → 激活）。
**审批是这个系统里第二危险的动作**（第一是建任务）。

**审批界面必须显示四样：**

1. **完整的 hook 正文** —— 审批人要看的就是这个。不要折叠、不要只给摘要
2. **阶段与它的能力边界说明** —— 审批 `pre` 阶段的 hook 时要写明
   「此 hook 在分区之前以 root 运行，可以擦除任何磁盘」
3. **digest** —— 审批的是这个 digest 对应的内容，将来对照用
4. **作者与提交时间**

**第 2 条是本任务的核心。** 审批人可能不是写 hook 的人，也可能不熟悉装机流程 ——
**界面要告诉他这次点击授权了什么能力**。不说明的后果是审批变成橡皮章。

**两条防误操作的要求：**

- **审批需要二次确认**，确认框里重复显示阶段与能力说明
- **审批人不能是作者**（若 M6 的端点没做这条校验，这是一个契约变更请求 ——
  上报而不是在前端绕过）。理由：自审自批等于没有审批

**驳回也要有入口，且要能填理由。** 只有「批准」的界面会让审批人在不确定时
选择不作为，而那会让 hook 永远卡在待审批 —— 作者不知道为什么。

**验证：** 审批界面显示四样；能力说明随阶段变化；二次确认存在；
驳回能填理由。

**完成标志：** commit `feat(web): hook approval with explicit capability disclosure`

### 任务 4：制品集导入页

**产出文件：** 制品集列表与导入页

**为什么需要这一步：** 导入是异步 job（§2.1），而异步的进度与失败原因需要界面呈现 ——
否则运维只能看到一个「导入中」然后不知道发生了什么。

**列表要显示七列：** 名字、OS 家族、版本、架构、固件、状态、导入错误。

**固件一列要有说明。** §2.1 的固件字段对运维是反直觉的：
Linux 四家是「通用」，而 **Windows 同一版本需要导两个制品集**。
列表上看到两个名字相似的 Windows 制品集时，运维需要知道为什么 ——
给那一列一个悬浮说明或在页面上给一段简短解释。

**导入表单的核心：输入是服务器本地路径，不是文件上传。**

**界面要解释为什么。** §2.1 说清了：气隙环境下几 GB 走浏览器体验很差，
运维 scp 到指定目录再登记更实际。**不解释的后果是运维找上传按钮找不到，
以为功能没做完。**

**进度呈现的三种状态：**

| 状态 | 呈现 |
|---|---|
| 导入中 | 轮询刷新（导入是分钟级，不需要 SSE） |
| 就绪 | 显示 manifest 校验值 |
| 失败 | **显示具体失败原因** |

**失败原因必须原样显示。** M7 的导入 job 产出的是具体原因
（「识别不出 OS 家族」「缺少内核文件」「目标目录无写权限」），
这些直接展示比翻译一遍有用。

**「校验完整性」要给入口。** 它重算 manifest 并报告缺失文件 ——
这是「机器引导时报 404」之后的第一个排查动作，藏起来等于让运维去翻 API 文档。

**MVP 不支持的家族要明确呈现。** 识别出 Windows 或 ESXi 时导入会置失败并说明
是 MVP 限制（M7 的任务 9）—— 界面要把这个原因与「真的出错了」区分开，
否则运维会以为是自己的 ISO 有问题。

**验证：** 导入中能看到状态变化；失败原因原样显示；校验完整性有入口；
固件列有说明。

**完成标志：** commit `feat(web): artifact set import with async progress and reasons`

### 任务 5：磁盘 dry-run 页

**产出文件：** dry-run 页面

**为什么需要这一步：** §8.2 说它与 preview 是开发期性价比最高的两个端点。
**要做成一等公民、给显眼入口。**

**页面的两种输入方式**（对应 P2-02 扩展后的端点）：

1. **选一个任务**，用它的历史采集数据跑 —— 「这台机器换用另一个策略会选哪块盘」
2. **手工贴硬件事实** —— 「还没有机器但想验证策略」

**输出的三块：**

1. **选中的主盘**（以及 RAID 成员，若策略产出）
2. **「为什么这么选」的说明** —— 这是 provider 返回的，原样显示
3. **对比**（P2-02 的扩展）：当前策略与请求策略的结果并排

**第 2 块不能省也不能改写。** 运维看到「选了第二块盘」无法判断对不对，
看到「选了容量最大的盘：1.8 TB，另两块分别是 480 GB 与 480 GB」才能判断。

**界面要支持快速迭代：改策略参数后立刻重跑。** 这是「把调试周期压到秒级」的
实际含义 —— 若每次都要重新填一遍硬件事实，那个收益就没了。
**输入区的内容要在重跑之间保留。**

**一条要显示的警示：dry-run 的结果不代表实际装机会这么选。**
实际装机用的是机器当时上报的硬件事实，而 dry-run 用的是历史数据或手工输入。
**硬盘更换、插槽变化都会让结果不同** —— 界面上要有一句话说明这个界限，
否则 dry-run 会被当成保证。

**验证：** 两种输入方式都能出结果；说明原样显示；改参数后能快速重跑且输入保留；
入口在一级菜单。

**完成标志：** commit `feat(web): disk dry-run as a first-class page`

### 任务 6：路由、权限与气隙复核

**产出文件：** 路由定义、权限映射

**为什么需要这一步：** 三个新页面要接进路由与权限，并复核气隙约束仍然成立。

**三个页面的角色可见性**（按 §9.4 与 §12.5 的角色表）：

| 页面 | 可见角色 |
|---|---|
| hook 管理 | hook 作者、hook 审批人、管理员 |
| 制品集导入 | 管理员 |
| 磁盘 dry-run | 装机操作员及以上（**它是只读操作，不该限制太严**） |

**dry-run 放宽的理由：** 它不产生任何变更，而装机操作员正是最需要它的人 ——
限制成管理员专用会让操作员在调策略时去找管理员，或者干脆不用它。

**按钮级权限：** hook 的「创建新版本」需要写权限，「审批」需要审批权限 ——
**两者不能混**（§9.4：创建与审批是不同的权限）。

**气隙三检查要重跑**（M8 的任务 15 定义的那三条）：
新页面若引入了新的图标或新的第三方资源，那三条 grep 会发现。
**这是每次加页面都要跑的检查，不是一次性的。**

**另加一条越界检查：** 确认本计划没有修改 M6 在 `internal/console/` 下的 Go 文件 ——
三个页面对应的端点 Phase 1 已实现，本计划不该碰后端。
**若发现端点缺东西，上报契约变更而不是自己加。**

**验证：** 三个页面按角色可见；按钮级权限生效；气隙三检查无匹配；
越界检查通过；`pnpm build`、`pnpm typecheck`、`pnpm lint` 全过。

**完成标志：** commit `feat(web): wire P2 pages into routes and permissions`

## 这个计划的真正目标

三个页面的功能在 Phase 1 就能用 API 顶（§11 已说明）。**所以本计划的价值不在
「让功能可用」，而在两件事：**

1. **让 hook 审批这个动作真正起到审批的作用** —— 审批人看得见完整正文、
   知道自己授权了什么能力、且不能自审自批。做不到这三点的审批流是橡皮章，
   而它把守的是「以 root 在分区前执行任意代码」这个能力
2. **让 dry-run 真的被用起来** —— 一等公民的入口、快速迭代的交互、
   原样呈现的判断依据。埋进二级菜单的 dry-run 等于没做
