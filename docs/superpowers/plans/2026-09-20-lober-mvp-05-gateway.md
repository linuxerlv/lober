# M5 网关机器面 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** M1 契约与地基必须已完成，特别是 `docs/contracts/http-machine.md`。
> 本模块与 M2–M4、M6–M8 并行，只通过 `internal/core/contract` 通信。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 实现机器面的六个 HTTP 端点与一个 syslog UDP 接收器，
契约以 `docs/contracts/http-machine.md` 为准。

**架构：** 一个 Server 类型持有六个接缝（Store、状态机、渲染器、日志存储、时钟、基址配置），
用标准库的 ServeMux 路径参数路由。**网关只做 HTTP 层的事** ——
状态转换交给状态机、文本生成交给渲染器，它自己负责解析请求、构造渲染上下文、
把结果写成 iPXE 能消费的形态。

**这是一个无认证的 HTTP 端点，有权告诉机器「擦盘重装」**（§9.1）。MVP 无 TLS，
所以 token 与默认拒绝是唯一的防线，不能降级实现。

**技术栈：** 标准库 `net/http`（1.22+ 路径参数）、`net`、`net/http/httptest`

**SPEC 依据：** §4 全节、§6 全节、§8.1、§9.1、§9.2、§1.6

### 任务 1：测试桩与 Server 骨架

**产出文件：** `stub_test.go`、`server.go`

**为什么需要这一步：** 并行开发要求本模块不依赖 M3/M4 的实现。桩先写好，
后面七个任务都用它。

**三个桩：状态机（八个方法）、渲染器（两个方法）、日志存储（两个方法）。**
时钟用 M1 的可控时钟，Store 用 M1 的内存实现。

**桩的形态：每个方法背后一个函数字段。** 构造时给全部字段填「正常返回」的默认实现，
测试里只覆盖关心的那一个。这比「为每种场景写一个桩类型」省得多，

**Server 的依赖结构要把六个接缝都列出来**，用一个参数结构体传入而不是长参数列表 ——

首跳脚本、引导决策、应答文件（三个路径参数）、信号（三个路径参数）、
facts 的读与写（两个路径参数）。

**测试要锁住的行为：** 本任务只要求桩能编译、Server 能构造、路由表注册了预期的路径。
路由表的断言放任务 8。

**验证：** `go test ./internal/gateway/ -run TestServerConstruct -v` 通过。

### 任务 2：客户端 IP —— 只在 loopback peer 时信任头部

**产出文件：** `clientip.go`、`clientip_test.go`

**为什么需要这一步：** nginx 反代让直连 peer 变成回环地址（§1.6），
这会静默破坏三件事：审计日志记全回环、按客户端限速失效、
将来的制品签名对不上（nginx 校验时用真实客户端 IP，Go 签发时看到回环）。

**所以要从 nginx 注入的头部取真实 IP —— 但必须加一个条件判断。**

**判定规则：仅当直连 peer 是 loopback 时才信任那个头部，其余情况一律用真实 peer。**

**不加这个判断的后果：** 网关端点本身无认证，**任何人可以伪造那个头部冒充其它机器
请求装机脚本**。装机 VLAN 上一台失陷主机就能用别的机器的身份取应答文件。

**实现要点：**

- 从请求的远端地址切出主机部分（它带端口）
- 解析成 IP 后判是否 loopback —— **要覆盖 IPv6 的回环**，不能只比较字符串 `127.0.0.1`
- 是 loopback 且头部非空则用头部值，否则用真实 peer
- **头部值本身也要解析校验**：伪造者可能塞进非 IP 的内容，那会污染审计日志

**测试要锁住的行为：**

- loopback peer 加头部 → 用头部值
- **非 loopback peer 加头部 → 用真实 peer**（这是安全关键那条）
- loopback peer 无头部 → 用真实 peer
- **IPv6 回环也被识别为 loopback**
- 头部含非 IP 内容时回落到真实 peer

**验证：** `go test ./internal/gateway/ -run TestClientIP -v` 全过。

**完成标志：** commit `feat(gateway): trust X-Real-IP only from loopback peers`

### 任务 3：首跳脚本端点

**产出文件：** `bootscript.go`、对应测试

**为什么需要这一步：** DHCP 给出的 URL 必须是静态的，所以第一个响应是极小的静态引导片，
它负责把机器身份塞进第二跳的 query（§4.1）。

**要点：全网共用一份，不看机器身份、不做任何决策**（§4.7）。
它是**一路分流** —— 这正是「加一个新 OS 家族不需要改 DHCP 与 nginx」的原因。

**内容是两行：** shebang 加一行 chain 命令。chain 的 URL 指向引导决策端点，
query 里带五个 iPXE 变量（序列号、MAC、UUID、架构、平台），**末尾加上失败回退到 shell**。

**五个变量的作用：** 前三个是身份查找键（§4.3），后两个是 §4.6 一致性校验的输入 ——
它们不是冗余留痕，是第二层分流的必要输入。

**实现要点：**

- **网关地址从配置的基址来**，不写死（§1.5）
- **五个 iPXE 变量要原样输出**，不要被 Go 的模板引擎当成自己的占位符处理
- Content-Type 用纯文本

**测试要锁住的行为：**

- 响应含 chain 命令且指向引导决策端点
- **五个 iPXE 变量原样出现在输出里**
- 基址来自配置（换一个基址渲染，URL 跟着变）
- 响应不含字面 `http://`（scheme 来自配置的基址）

**验证：** `go test ./internal/gateway/ -run TestBootScript -v` 全过。

**完成标志：** commit `feat(gateway): static first-hop boot script`

### 任务 4：引导决策端点的 no_task 路径

**产出文件：** `boot.go`（第一部分）、对应测试

**为什么需要这一步：** 这是 §9.1 的第一道闸门「默认拒绝」，也是 §10 失败模式 1
（装完又从网络启动导致循环重装）的拦截点。

**实现流程：**

1. 解析五个 query 参数成探测结构，客户端 IP 用任务 2 的函数取
2. 按身份查 pending 任务
3. **查不到 → 返回 no_task 载荷，到此为止**

**三条不能妥协的约束：**

**一、始终返回 HTTP 200，即使没任务。** iPXE 对非 200 的处理是跳到首跳脚本里的
`|| shell` 分支 —— 那会把机器停在交互式提示符上等人。正确行为是让它回本地盘或
继续 PXE 轮询。

**二、载荷必须是 M1 提供的那个 no_task 脚本，逐字符照用。**
其中 `sanboot` 那行是失败模式 1 的唯一保护：**BIOS/MBR 模式下没有 `efibootmgr`**，
installer 装完无法把本地盘置顶引导顺序，这类机器完全依赖这一行回本地盘。
对真正的空盘机器，`sanboot` 自然失败、效果与继续轮询一致 ——
一行同时覆盖两种情况。

**三、不产生任何记录。** 不建任务、不改状态、不写事件表、不告警（§4.2、§0.1）。
数据中心里任何网络引导优先的机器重启都会撞一次这个端点，量大且全是噪声 ——
建任务、记状态、发告警都会把噪声变成负担。需要取证时 nginx access log 已经记下了。

**测试要锁住的行为：**

- 无匹配任务时状态码是 200（**不是 404**）
- **响应体逐字符等于 M1 的 no_task 脚本**
- **请求后 Store 里事件数为 0、任务数不变** —— 这条对应第三条约束
- 五个 query 全空时也不崩（白牌机 SN 可能留空）

**验证：** `go test ./internal/gateway/ -run TestBootNoTask -v` 全过。

**完成标志：** commit `feat(gateway): boot endpoint no_task path with sanboot payload`

### 任务 5：引导决策端点的命中路径

**产出文件：** `boot.go`（第二部分）、`rendercontext.go`、对应测试

**为什么需要这一步：** 这是 §0.1 的范围起点 —— 签出 token 之后责任全在本系统。

**实现流程：**

1. 查到 pending 任务后，**先做 MAC 双因子校验**（见下）
2. 调状态机的「开始引导」（它内部做 precheck、attempt 计数、签 token、状态转换）
3. 失败则按类型处置：precheck 错误与 attempt 超限都回 no_task 载荷
   （任务已被状态机置 failed）
4. 成功则构造渲染上下文，调渲染器出菜单，返回

**MAC 双因子校验是硬要求**（§4.3、§9.1 第二道闸门）：**SN 与 MAC 都要对上才继续**。

只校 SN 不够的理由：白牌机与部分 ODM 机器的序列号可能留空、填
`To Be Filled By O.E.M.`、甚至整批重复。单靠一个可能重复的标识去决定「擦哪台机器的盘」
是不可接受的。

校验方式：任务上记录的 MAC 与探测带来的 MAC 归一化后比对，不一致则**回 no_task**
（不是报错）—— 对机器而言这与「没有任务」无法区分，这正是想要的：
不给攻击者「SN 猜对了」的反馈。

**attempt 计数由状态机管，网关不自己加。** 这条要写进注释 —— 两处都加的后果是
每次引导消耗两个额度，运维只有一次半的机会。

**渲染上下文的构造是网关的主要职责之一。** 要取齐：任务、模板的 pin 版本、
制品集、主机、**按 digest 取回的 hook 正文并合并参数**、fact 表、基址、两个 token、
syslog 目标、**机器实际上报的固件模式**。

**finalize token 在这一步签发**（调状态机），因为它要被写进 `%post`（§6.4）。

**测试要锁住的行为：**

- 命中任务且校验通过 → 响应是菜单（含内核行），状态变 booting
- **SN 对但 MAC 不对 → 回 no_task，且不签 token**（安全关键）
- precheck 失败 → 回 no_task 载荷，且任务已 failed
- attempt 超限 → 回 no_task 载荷
- **渲染上下文的字段完整** —— 用一个记录入参的渲染器桩断言各字段非空
- **网关没有自己修改 attempt** —— 用桩记录状态机被调用次数与传入参数

**验证：** `go test ./internal/gateway/ -run TestBootGrant -v` 全过。

**完成标志：** commit `feat(gateway): boot grant path with MAC two-factor check`

### 任务 6：应答文件端点

**产出文件：** `answer.go`、对应测试

**为什么需要这一步：** 应答文件是装机的实际指令。它的暴露控制用状态门控（§4.4）。

**实现流程：**

1. 从路径段取任务 id、token、文件名
2. 按 token 查任务（用途是装机 token）
3. **交叉校验路径里的任务 id 与 token 解出的任务一致**
4. 状态门控：仅 `booting` 与 `installing` 可服务（用 M1 的状态集合）
5. 调状态机标记应答文件已取（它幂等）
6. 构造渲染上下文，调渲染器，返回纯文本

**第 3 步不能省。** 不校验的后果是可以拿 A 任务的 token 配 B 任务的 id 去取应答文件 ——
虽然 token 查询已经绑定了任务，但路径里那个 id 会被用于构造渲染上下文，
不一致时会渲染出张冠李戴的内容。

**状态门控用状态而非一次性失效**（§4.4）：一次性失效会直接掐死正常重试。
仅当状态在集合内时提供，其余回 403。

**错误响应的形态要分两种，这是个刻意的设计：**

| 情形 | 响应 |
|---|---|
| token 无效或状态不允许 | **403 空响应** —— 此时不该产出任何内容 |
| 渲染失败（模板错误、参数校验不过） | **200 加一份纯注释的文本** |

第二种的理由：installer 拿到 404 或 500 的行为各家不同（有的重试、有的直接 panic），
而拿到一份语法合法但内容为注释的应答文件则会明确失败，并在自己的 syslog 里留下
可读的原因 —— 而那条 syslog 会被本系统的接收器收到（§6.5）。

**文件名校验交给渲染器**（M1 的契约写明那是渲染器的责任）。**网关不要按 OS 家族
分支选文件名** —— 这条要写进注释，避免后来者在网关里加一个家族判断。

**测试要锁住的行为：**

- 正常路径返回渲染结果，且状态机的「已取」被调用
- token 无效 → 403 空响应
- **状态不在门控集合内 → 403**（用 done 状态验证）
- **路径 id 与 token 解出的任务不一致 → 403**
- 渲染失败 → 200 加注释文本（不是 5xx）
- **重复请求两次都成功**（幂等，对应 cloud-init 取两个文件）

**验证：** `go test ./internal/gateway/ -run TestAnswer -v` 全过。

**完成标志：** commit `feat(gateway): answer file endpoint with state gating`

### 任务 7：信号端点

**产出文件：** `signal.go`、对应测试

**为什么需要这一步：** 状态机由信号驱动（§6.1）。这个端点是机器侧唯一的主动上报通道。

**实现流程：**

1. 从路径段取任务 id、token、阶段名
2. **阶段名查表校验**（用 M1 的信号表），表里没有的回 400
3. 按 token 查任务，**两种用途都试**：先当装机 token 查，查不到再当 finalize token 查
4. **若命中的是 finalize token，校验该信号在允许集合内**，不在则回 403
5. 读 query 的退出码与序号，读 body 作为日志正文
6. **hook-report 信号额外读 digest 参数**（见下）
7. 日志正文交给日志存储落文件
8. 调状态机应用信号
9. **返回 204，无论信号是否被接受**

**第 9 条是刻意的。** 机器侧的 `signal()` 会重试三次（§6.3），
序号重复是正常现象而不是错误。返回错误的后果是机器白重试两次，
而那两次都会被同样地去重 —— 纯粹浪费装机时间。

**第 4 条的权限限制**（§6.4）：finalize token 只能发重启后阶段的那几个信号。
装机 token 能发全部。**不加限制的后果是：finalize token 写在目标系统的磁盘上、
TTL 24 小时，拿到它就能伪造整个装机流程的信号。**

**第 6 条的 digest 参数：** §3.5 要求失败事件带 hook digest，但 §6.3 的参考实现
只传了退出码与序号 —— digest 是 shell 里的本地变量，从未进入 HTTP 调用。
这是 SPEC 自身的缺口，M1 的契约已补了这个 query 参数。

digest 的处理规则三条：

- **只在 hook-report 信号时读取**，其余信号带了也忽略
- 格式是 64 位十六进制小写，**按此校验**
- **不合格时忽略该参数而非拒绝整个信号** —— 上报失败绝不中断装机（§6.3），
  一个畸形 digest 不该让机器装不完

**测试要锁住的行为：**

- 十一个流程信号各自被接受并回 204
- **未知阶段名回 400**
- **重复序号仍回 204**（不是 409 或 500）
- **finalize token 发装机期信号回 403**
- finalize token 发允许集合内的信号成功
- **合法 digest 被传给状态机；畸形 digest 被忽略但信号仍被应用且回 204**
- 非 hook-report 信号带 digest 时 digest 被忽略
- 日志正文被交给日志存储

**验证：** `go test ./internal/gateway/ -run TestSignal -v` 全过。

**完成标志：** commit `feat(gateway): signal endpoint with finalize token scoping`

### 任务 8：facts 端点、syslog 接收器与路由核对

**产出文件：** `facts.go`、`syslog.go`、对应测试

**为什么需要这一步：** facts 是吃掉「需要新端点」这类需求的通用原语（§5.5）；
syslog 是三条辅助通道中不可替代的一条（§6.5）。

**facts 的两个端点：**

- **写**：body 是纯文本，每行一个键值对。空行与注释行忽略。
  **不用 JSON**（§6.2）：installer ramdisk 里没有 jq，手工拼 JSON 转义会在
  日志带引号或换行时坏掉
- **读**：返回同样的纯文本格式，供后续阶段的 hook 消费

两个端点都用装机 token 或 finalize token 都可（firstboot 的 hook 也要读 facts）。

**syslog 接收器的要点：**

**它的不可替代性**（§6.5）：当 anaconda 炸在依赖解析、磁盘写坏、仓库 404 时，
**hook 一行都没跑到、信号完全静默**，而 syslog 里有确切的错误行。

- 接收函数接收源地址与原始字节
- **按源 IP 归档到对应任务**：装机阶段机器还在装机 VLAN，用它的 IP 反查
  「当前处于装机中且客户端 IP 匹配」的任务
- **匹配不到的行落一个公共文件，不要丢弃** —— 那些行可能来自一台还没建任务
  就在报错的机器，是有用的取证材料
- 单条日志不解析结构（syslog 的格式各家不同），原样存

**归档依据是源 IP 这件事有个已知限制要写进注释：** 重启后业务网生效，
`booted` 之后的信号源 IP 会变（§5.7），此时 syslog 若还在发就归档不到。
这是可接受的 —— 重启后的诊断主要靠信号，syslog 的价值集中在 installer 阶段。

**路由核对：** 写一个测试遍历预期的六条路径，断言每条都能路由到非 404
（用最小合法请求）。这条测试的价值是抓「注册路径时写错一个字符」——
那种错误在集成前发现不了，而集成时的表现是「机器拿不到应答文件」。

**测试要锁住的行为：**

- facts 写入后能读出，格式是每行一个键值对
- 空行与注释行被忽略
- **facts 端点接受两种 token**
- syslog 收到的行被归档到匹配 IP 的任务
- **匹配不到的行落公共文件而不是被丢弃**
- 六条路由全部可达

**验证：** `go test ./internal/gateway/ -v` 全过。

**完成标志：** commit `feat(gateway): facts endpoints, syslog receiver and route audit`

### 任务 9：手工验证服务器

**产出文件：** `cmd/gateway-devserver/main.go`（或一个测试辅助程序）

**为什么需要这一步：** §11 Phase 1 的验证行要求「curl 模拟机器打点，整条链本地跑通」。
在 M9 装配完成之前，本模块要能独立验证一遍 —— 否则问题会攒到集成时才暴露。

**做法：** 一个小程序，用 M1 的内存 Store 加一个**真的会做状态转换的简易状态机**
（不是桩），起一个本地 HTTP 服务，预置一台主机与一个 pending 任务。

**为什么不用桩：** 桩返回固定值，curl 脚本看不到状态真的在推进。
要观察 `pending → booting → installing → rebooting → initializing → done`
真实发生，就需要一个会改内存 Store 的实现。这个简易实现只服务于手工验证，
**不要让它流入生产代码路径** —— 放在独立的 `cmd/` 下或测试文件里。

**要能走通的序列：** 取首跳脚本 → 取菜单（拿 token）→ 取应答文件 →
按顺序打十一个信号 → 确认状态是 done → **再取一次菜单确认拿到 no_task**。

**在文件注释里说明 syslog 这条通道 curl 覆盖不了**（它是 UDP），
由任务 8 的自动化测试覆盖 —— 不要假装测过了。

**验证：** 手工按上面的序列跑一遍 curl，观察状态变化与最后的 no_task。

**完成标志：** commit `test(gateway): dev server for manual curl walkthrough`

## 职责边界提示

网关**不做**这些事，它们属于别的模块：

| 不做 | 属于 |
|---|---|
| 状态转换判定、attempt 计数、precheck 调用 | M3 状态机 |
| 文本生成、文件名与 OS 家族的对应 | M4 渲染器 |
| 制品的字节传输 | nginx（§1.4：制品走 location 直接发盘，不经 Go） |

越界的代价不是「代码难看」，是两处判定不一致 —— 而不一致的表现往往是
「某些机器偶尔装错」，那是最难查的一类故障。
