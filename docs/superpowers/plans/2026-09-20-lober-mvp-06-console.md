# M6 控制台人面 API 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** M1 契约与地基必须已完成，特别是 `docs/contracts/http-console.md`。
> 本模块与 M2–M5、M7–M8 并行，只通过 `internal/core/contract` 通信。
> **M8（WebUI）对着同一份契约开发，两边都不得私自改契约。**
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 实现 `/console/v1` 下的全部端点、RBAC、SSE 与审计，
契约以 `docs/contracts/http-console.md` 为准。

**架构：** 一个 Server 类型持有接缝，按资源分文件。响应统一走 `apierr` 的包裹
（§12.5 的框架约定），唯一例外是 SSE。认证用 bcrypt 校验加不透明的内存 token ——
不做 JWT、不做 refresh token。

**建任务即授权装机**（§3.2）。这一个 API 调用就能让目标机器下次网络启动时被擦盘，
所以「SN 只能从主机清单选取」是硬要求而非建议 —— 删掉 armed 之后它是唯一的人工确认点。

**技术栈：** 标准库 `net/http`（1.22+ 路径参数）、`golang.org/x/crypto/bcrypt`、
`net/http/httptest`

**SPEC 依据：** §8.2、§8.3、§9.4、§2.2、§2.3、§12.5、§12.7、§12.8、§3.2

### 任务 1：会话、认证与 RBAC

**产出文件：** `session.go`、`auth.go`、`rbac.go`、对应测试

**为什么需要这一步：** 其余所有端点都挂在认证与授权之后。

**认证方案：bcrypt 校验密码 + 不透明的随机 token 存内存表。**

三个选择的理由：

| 选择 | 理由 |
|---|---|
| 不做 JWT | 需要即时吊销（运维离职、误操作后锁账号）。JWT 要么带黑名单（等于还要存储），要么无法吊销 |
| 不做 refresh token | 框架默认关闭（§12.5），单 access token 对个位数用户足够 |
| 会话存内存 | 重启即全员登出是可接受的 —— 装机系统不是 7×24 交互系统，重启是计划内的运维动作 |

**会话表要带过期时间**，TTL 从配置来。**不做滑动过期** —— 固定过期更容易推理，
而运维的一次装机会话通常在 TTL 内完成。

**四个认证端点**（端点名与框架默认约定对齐，§12.5，**不要改名**）：
登录返回 access token、取用户信息返回含角色列表的结构、取权限码返回字符串数组、登出。

**RBAC 的五个角色与权限码**（§9.4、§12.5）：

| 角色 | 权限码 |
|---|---|
| viewer | 无（只读） |
| operator | 建任务、重试、取消 |
| hook-author | 写 hook |
| hook-approver | 审批 hook |
| admin | 配置 provider、导入制品，以及以上全部 |

**没有 arm 相关的权限码** —— armed 状态已删除（§3.2）。

**两条权限分配的理由要写进注释：**

- **建任务的权限不是「只是填个表」**（§9.4）：这一个动作就能让目标机器下次网络启动时
  被擦盘，权限分配按此理解
- **写 hook 是独立权限，与建任务分开**：hook 以 root 身份在分区之前运行，
  能力等同「擦掉这台机器所有盘」

**中间件的两层：** 先认证（无 token 或无效 token 回未认证），再授权
（按端点要求的权限码检查）。**授权失败与认证失败要用不同的错误码** ——
前者说明「登录了但没权限」，后者说明「该重新登录」，UI 的处置不同。

**测试要锁住的行为：**

- 正确密码登录成功并返回 token；错误密码失败
- **失败响应不区分「用户不存在」与「密码错误」**（都回同一个错误）
- token 过期后被拒
- 登出后 token 立即失效
- 五个角色各自的权限码正确
- **operator 调写 hook 的端点被拒 403**
- **viewer 调任何写端点被拒**
- 无 token 访问受保护端点回未认证

**验证：** `go test ./internal/console/ -run 'TestAuth|TestRBAC|TestSession' -v` 全过。

**完成标志：** commit `feat(console): bcrypt auth, in-memory sessions and RBAC`

### 任务 2：审计与响应约定

**产出文件：** `audit.go`、`server.go`、对应测试

**为什么需要这一步：** 每个写操作都要记操作人（§9.4）。做成中间件避免十几个 handler
各写一遍（且必然漏几个）。

**审计记录的五项：** 时间、操作人、动作、目标资源 id、客户端 IP。

**动作命名用「资源.动作」形式**（如 `task.create`、`hook.approve`），
便于将来按前缀筛选。

**只审计写操作**（POST/PUT/DELETE），读操作不记 —— 读的量大且价值低，
需要时 nginx access log 有记录。

**响应约定**（§8.2、§12.5）：统一走 `apierr` 的包裹，`code` 非 0 即失败、
`message` 可直接展示。**唯一例外是 SSE 端点** —— 它是事件流不是 JSON。

**客户端 IP 的取法与 M5 一致**：只在直连 peer 是 loopback 时信任 nginx 注入的头部
（§1.6）。**审计日志记全回环地址就失去了追溯价值** —— 而这个错误不会有任何报错。

**测试要锁住的行为：**

- 写操作产生审计记录，含五项且操作人正确
- 读操作不产生审计记录
- 审计记录里的客户端 IP 是头部值（loopback peer 时）
- **审计写入失败不影响主流程**（记日志继续）—— 审计存储故障不该让运维无法建任务

**验证：** `go test ./internal/console/ -run TestAudit -v` 全过。

**完成标志：** commit `feat(console): audit middleware and response envelope`

### 任务 3：主机清单

**产出文件：** `host.go`、对应测试

**为什么需要这一步：** MVP 没有 discovery image（硬件采集是 Phase 2），
所以主机清单只能手工录入 —— §7.4 认可这条路径（Inventory provider 失败时允许手工兜底）。
**这个列表是建任务页 SN 字段的唯一数据源**（§4.3 硬要求）。

**两个端点：** 查询（带文本搜索与分页参数）、录入（需导入权限）。

**录入的三条校验：**

1. **MAC 归一化后入库，非法值回校验错误。** MAC 是 §4.3 双因子的一半，
   格式不统一会让校验假阴性 —— 而假阴性的表现是「建了任务但机器一直装不上」，
   运维会以为是引导问题而去查 DHCP
2. **架构与固件必填**（§4.3 末条）。缺了它们建任务时无法过滤该机器可装的 OS 列表，
   固件不兼容的组合要等到机器实际引导时才被 §4.6 拦下 —— 那时运维已经在机房了
3. 取值必须是 M1 枚举内的字面量，不接受自由文本

**文本搜索在本 handler 层做，不下推到 Store**（M1 契约已说明）：
取回后在 Go 里对序列号、MAC、机架位做大小写不敏感的子串匹配。主机数是百级。

**搜索参数不是可选的便利功能。** 主机数超过一页而运维选不到目标机器时，
他们会去想办法绕过「必须从清单选」这个约束 —— 而它是删掉 armed 之后唯一的人工确认点。
**让正确的路走得通，是这个参数存在的理由。**

**列表响应的形态**（M1 契约的分页约定）：`data` 就是数组、不带总数。
不传分页参数时用默认上限 1000。

**测试要锁住的行为：**

- 录入后能查出，字段完整
- **三种 MAC 格式（大写冒号、小写连字符、无分隔）入库后归一化为同一形式**
- 非法 MAC 回校验错误
- **缺架构或缺固件回校验错误**
- 枚举外的架构值被拒
- 搜索对三个字段都生效且大小写不敏感
- 录入需要导入权限（operator 调用被拒）

**验证：** `go test ./internal/console/ -run TestHost -v` 全过。

**完成标志：** commit `feat(console): host inventory with normalized MAC and required arch/firmware`

### 任务 4：制品集与 hook

**产出文件：** `artifact.go`、`hook.go`、对应测试

**为什么需要这一步：** 两组 CRUD，各有一处需要小心的校验。

**制品集四个端点：** 登记（触发异步导入 job）、列表、校验完整性、删除。

- **登记的入参是服务器本地路径，不是上传流**（§2.1）：气隙环境下几 GB 走浏览器
  体验很差，运维 scp 到指定目录再登记更实际
- **删除仅当已停用且无引用**，撞引用完整性时回对应错误码（§2.7）
- **校验完整性重算 manifest** 并报告缺失文件

**hook 六个端点：** 创建、列表、更新（建新版本）、校验、列版本、审批。

**更新是建新版本而不是改旧版本**（§2.7）：hook 正文不可变，改正文即新版本新 digest，
所以模板 pin 的 digest 不会被偷换。

**注册期校验的四项**（§2.2、§7.5 —— 把运行时意外提前为注册时错误）：

1. **阶段是白名单内的值**（用 M1 的判定方法）
2. **requires 声明的 fact 键都在 v1 契约内**（用 M1 的查询函数）。
   声明了不存在的 fact 键意味着那个 hook 运行时会读到空值 —— 注册时就该发现
3. **contract 版本要求能被满足**
4. **params_schema 在 §12.7 的子集内** —— 超出子集的在注册时就拒绝，
   而不是等渲染时静默丢字段

**另加一项静态检查（产出警告而非错误）：** 拿 params_schema 与脚本正文比对，
脚本引用了某个 `LOBER_` 变量但既不在 schema 也不在 fact 命名空间中 → 警告。
**这能拦掉大量拼写错误** —— 而拼写错误的运行时表现是「变量为空导致 hook 行为异常」，
从机器侧日志很难看出是拼错了名字。

**校验端点的语法检查：** bash 类的用 `bash -n`（子进程调用，**要设超时**）。
**PowerShell 与 ash 在 MVP 下跳过语法检查，并在响应里说明原因** ——
不要假装检查过了，那会让作者以为脚本没问题。

**测试要锁住的行为：**

- 制品集删除在有 active 模板引用时回对应错误码
- hook 更新产生新版本且旧版本仍可取
- **四项注册期校验各自拦下对应的非法输入**
- 静态检查对拼错的变量名产出警告（但不阻止注册）
- **跳过语法检查的解释器在响应里明确说明**
- 语法检查的子进程有超时保护

**验证：** `go test ./internal/console/ -run 'TestArtifact|TestHook' -v` 全过。

**完成标志：** commit `feat(console): artifact sets and hooks with registration-time validation`

### 任务 5：模板、表单 schema 与 preview

**产出文件：** `template.go`、对应测试

**为什么需要这一步：** preview 是开发期性价比最高的两个端点之一（§8.2）——
装机模板的错误反馈周期极长（建任务 → 上电 → 等数分钟 → 失败 → 翻日志），
这个端点把它压到秒级。

**四个端点：** 创建、更新（建新版本）、取表单 schema、preview。

**表单 schema 由三段聚合**（§8.3）：

1. **固定字段**：序列号（用主机选择控件，**不是自由文本输入**）、OS 与版本、主机名、业务 IP
2. **模板声明的必填字段**
3. **所有 hook 引用的 params_schema 合并去重**

聚合结果必须在 §12.7 的子集内。**新增一个需要填 VLAN ID 的 hook 时表单自动多一项，
UI 代码不动** —— 这是这个端点存在的意义。

**preview 的做法：** 用假数据构造渲染上下文调渲染器，返回应答文件与引导菜单两段纯文本。
**不建任务、不签 token、不落库。**

**preview 的假数据要有一个固定的形态**（固定的假 SN、假 IP、假 token），
这样运维两次 preview 看到的差异只来自模板改动。

**保存模板时要校验所有 hook 引用**（§2.2 末段）：引用的 digest 存在、
阶段与 hook 声明的一致、家族兼容。**这是 hook 家族限制的真正校验点** ——
hook 自己的家族列表为空表示不限，而模板绑定了具体制品集，此时才能判定。

**测试要锁住的行为：**

- 更新产生新版本
- 表单 schema 含三段的字段，且序列号字段标记为主机选择控件
- **聚合结果在子集内**（用一个超出子集的 hook schema 验证被拒）
- preview 返回两段文本且**不产生任何任务或 token**
- 保存模板时引用了不存在的 digest 被拒
- 保存模板时 hook 家族与制品集不兼容被拒

**验证：** `go test ./internal/console/ -run TestTemplate -v` 全过。

**完成标志：** commit `feat(console): templates, aggregated form schema and preview`

### 任务 6：任务端点 —— 建任务是唯一的授权动作

**产出文件：** `task.go`、对应测试

**为什么需要这一步：** 建任务即授权装机（§3.2）。删掉 armed 之后，这个端点的正确性
承担了原先两道闸门的责任。

**建任务的六步顺序，不能变：**

| 步 | 动作 | 为什么在这个位置 |
|---|---|---|
| 1 | 按主机清单 id 取 Host | **SN 与 MAC 从这里来，不接受请求里的 SN 字符串** |
| 2 | 取模板的 pin 版本与制品集 | 后续校验与决策都要它 |
| 3 | 校验固件兼容 | 建任务时先拦一道（§4.6 末段：库内记录值的校验有价值但不能替代引导时的校验） |
| 4 | **调参数决策接口** | 失败即不建任务 —— 这是 §7.4 的阻塞语义 |
| 5 | 写库（任务 + 首条事件，同一事务） | 决策结果作为固化参数一起写入（§2.6） |
| 6 | 发布「任务已创建」生命周期事件 | **只是通知，不是决策点** |

**第 1 步是安全关键。** 请求体里若带了 SN 字段，**忽略它或直接拒绝请求** ——
自由文本打错字符、恰好撞上某台生产机的序列号，那台机器某天网络启动就会被擦盘
（§10 失败模式 2b）。

**第 4 步不能挪到第 6 步之后。** 事件总线是 fire-and-forget 的（M1 契约已说明）,
「任务已创建」事件发出时任务已经落库了 —— IPAM 此时失败已经来不及阻塞。
SPEC §7.5 的图示描述的是因果关系，不是实现机制。

**其余五个任务端点：** 列表（按状态与 SN 过滤）、详情（含失败详情六字段）、
事件列表、重试、取消。

**重试要把状态机的拒绝错误正确映射成错误码**（§3.4、§8.2）：
三种不可重装的失败原因对应一个专门的错误码，`apierr` 已有映射。
**不要在 handler 里自己判断可否重装** —— 那会出现两处判定，而状态机那处才是权威。

**测试要锁住的行为：**

- 建任务成功后状态是 pending
- **请求体里带 SN 字段时被忽略或拒绝**（安全关键）
- **参数决策失败时 Store 里不得出现任何任务** —— 这条是 §7.4 的执行点，
  靠 UI 或文档约定都不够
- 固件不兼容的组合在建任务时被拒
- 同一主机已有非终态任务时回对应错误码
- **三种不可重装的失败原因重试时回拒绝重装的错误码**（逐一验证）
- 六种可重装的失败原因重试成功
- 取消后任务进终态
- 建任务、重试、取消各自需要对应权限码

**验证：** `go test ./internal/console/ -run TestTask -v` 全过。

**完成标志：** commit `feat(console): task endpoints with blocking param resolution`

### 任务 7：SSE 事件流

**产出文件：** `stream.go`、对应测试

**为什么需要这一步：** 任务详情页的实时日志（§12.6）。装机要几十分钟，
运维需要看着它推进 —— 轮询做不到这个体验，且几百台机器同时轮询会压垮 API。

**这个端点不套响应包裹** —— 它是事件流。

**五条实现要点：**

1. **三个响应头**：事件流的 content-type、禁用缓存、
   **以及一个禁用代理缓冲的头部**作为 nginx 配置的兜底（§1.4 已关缓冲，
   但两处都设的成本接近于零，而漏一处的表现是「日志看起来完全冻住」）
2. **事件 id 取任务事件的序号**，客户端重连时带上它，服务端据此续传（§12.8）——
   **不从头重放**：一个装了一小时的任务有几百条事件，重放会让重连变成一次全量传输
3. **每条事件后必须 flush**，否则 Go 的 http 包会缓冲到一定大小才发
4. **任务进终态时发一条终态事件后主动关流**，前端收到即停止重连（§12.8）
5. **客户端断开时要能退出循环** —— 监听请求上下文的取消。
   不处理的后果是连接泄漏：运维在任务列表与详情间来回切换会攒住一堆 goroutine

**事件来源的实现方式，两个选项：**

| 方式 | 取舍 |
|---|---|
| 轮询 Store 的事件表（按序号递增） | 简单、无状态、进程重启不丢；延迟等于轮询间隔 |
| 订阅事件总线 | 实时；但要处理「订阅前已产生的事件」与多订阅者的扇出 |

**MVP 选轮询**，间隔取 1–2 秒。理由：装机事件的产生频率是分钟级
（阶段边界加 hook 报告），1 秒延迟对运维无感；而轮询的简单性换来的是
「进程重启后重连能继续」这个实实在在的好处。

**测试要锁住的行为：**

- 响应头三项正确
- 已有事件被立即推送，格式含 id 行与数据行
- **带续传 id 的请求只收到该序号之后的事件**
- **任务终态时收到终态事件且流被关闭**
- **请求上下文取消后 handler 返回**（用超时验证，不返回就是泄漏）
- 每条事件后有 flush（用一个记录 flush 次数的响应记录器验证）

**验证：** `go test ./internal/console/ -run TestStream -v` 全过，**且测试有超时保护**。

**完成标志：** commit `feat(console): SSE stream with Last-Event-ID resume`

### 任务 8：磁盘 dry-run 与路由核对

**产出文件：** `dryrun.go`、对应测试

**为什么需要这一步：** dry-run 是与 preview 并列的两个高价值端点之一（§8.2）——
磁盘策略决定擦哪块盘，能用录制的硬件事实先跑一遍是安全上的实质收益。

**做法：** 接收策略名与一批磁盘描述，调磁盘规划 provider，返回布局与**「为什么这么选」
的说明**，不落地。

**说明必须返回。** 运维看到「选了第二块盘」无法判断对不对，
看到「选了容量最大的盘：1.8 TB，另两块分别是 480 GB 与 480 GB」才能判断。

**路由核对：** 遍历契约文档里的全部端点路径，断言每条都注册了且返回非 404。
这条测试抓的是「路径写错一个字符」—— 那种错误集成前发现不了，
而集成时的表现是 WebUI 某个页面整体报错。

**同时核对两件与 M8 的约定：**

- **全部列表端点的响应 `data` 是数组、不带总数字段**（M1 契约的分页约定）
- **除 SSE 外全部端点都套响应包裹**

这两条写成遍历式的测试 —— M8 对着同一份契约开发，不一致的代价是前端整体解包失败。

**测试要锁住的行为：**

- dry-run 返回布局与说明，说明非空
- 未知策略名被拒
- **全部契约端点可达**
- **全部列表端点的响应形态一致**（数组、无总数）
- **除 SSE 外全部端点套包裹**

**验证：**

- `go test ./internal/console/ -v` 全过
- `go build ./...` 接口断言成立
- `make check` 全绿
