### 任务 1：装配 —— 把七个模块接到一起

**产出文件：** `cmd/lober/wire.go`、`wire_test.go`

**为什么需要这一步：** 装配点的价值在于**它是唯一能发现「某个接口谁都没实现」的地方**。
所以先写一个断言全部依赖都已满足的测试，再写装配代码。

**实现流程：**

1. 建三个存储目录（制品、日志、数据库所在目录）。**先建目录再开库** ——
   目录不存在时失败点会推迟到第一条日志写入，而那时机器已经在装了
2. 开 SQLite 并跑迁移
3. 构造基础件：系统时钟、Store、日志存储、事件总线
4. 构造状态机的四个依赖：token 签发器、precheck 器、日志存储、事件总线。
   **precheck 器需要一个文件系统视图**来检查制品是否存在 —— 用制品根目录包成
   `fs.FS` 注入，测试里换成内存文件系统
5. 构造渲染器（无依赖，纯函数）
6. 按配置构造七个 provider
7. 构造网关与控制台的 handler，各自注入所需接缝
8. 组装成一个持有全部组件的结构体返回

**设计要点：**

- **装配结构体的字段类型全部是 `contract` 的接口，不是具体类型。** 于是各模块的构造
  签名变化只影响装配代码一处 —— 这也是「改装配点不改模块」这条集成规则的物理保障。
- **字段要导出**，让测试能逐个断言「这个接缝接上了」。
- **必须接上建任务的同步决策接口**（§7.4）。漏了它的后果是 IPAM 失败也能建出任务，
  那台机器会带着空的业务 IP 配置装上去 —— 而这个错误不会有任何报错，只会在装完后
  发现机器连不上业务网。
- **各模块的构造函数签名以 M2–M7 的实际产出为准。** 若与本计划设想的不同，
  **改装配代码适配它，不要改模块** —— 装配点的职责就是吸收各模块的形态差异。

**测试要锁住的行为：**

- 七个接缝逐个非空，**特别是建任务的同步决策接口**（理由见上）
- **装配后 schema 已就绪** —— 用一次查询验证，而不是等第一个请求来了才发现库是空的
- **两个存储目录被自动创建**

**验证：** `go test ./cmd/lober/ -run TestBuildApp -v` 全过。

**完成标志：** commit `feat(cmd): wire all modules at the single assembly point`

### 任务 2：启动自检 —— 别等机器来了才发现制品缺文件

**产出文件：** `cmd/lober/preflight.go`、`preflight_test.go`

**为什么需要这一步：** SPEC §10 运维点一：nginx 按路径找文件、Go 按同一套路径签发 URL，
不一致即引导时 404。这条检查把「机器已经在机房上电、引导失败、运维翻日志」压缩成
「启动日志里一行告警」。

**实现流程：**

1. 列出全部制品集，**只检查 `ready` 状态的** —— importing 中的当然缺文件，
   failed 与 deprecated 的没人会用
2. 对每个制品集检查内核、全部 initrd、仓库、额外文件是否存在
3. 收集问题清单，逐条打错误日志

**设计要点：**

- **仓库是目录，存在性检查要落到它下面的 `repodata/repomd.xml`。** 空目录能
  stat 成功但对 installer 毫无用处 —— 检查目录本身等于没检查。
- **报告要带制品集名字，不只是路径。** 光给一个路径，运维还得自己反查该重导哪个制品集。
- **发现问题不让服务起不来，只打日志。** 一个坏掉的旧制品集不该阻止整个系统启动 ——
  那些机器的引导会在 §4.6 第三项被拒绝，届时有确切原因。这里的职责是让运维在启动日志里
  就看见，而不是等机器来。
- **文件系统通过 `fs.FS` 注入**，测试用内存文件系统 —— 不需要在测试里真的造文件。

**测试要锁住的行为：**

- 缺一个 initrd 时精确报出那个路径与所属制品集名
- **非 ready 状态的制品集一律不报** —— 三种状态各验一次
- 完整的制品集不产生任何问题报告（含额外文件与仓库的 repodata）

**验证：** `go test ./cmd/lober/ -run TestPreflight -v` 全过。

**完成标志：** commit `feat(cmd): startup preflight for artifact completeness`

### 任务 3：超时扫描循环 —— 独立于请求路径

**产出文件：** `cmd/lober/scanner.go`、`scanner_test.go`

**为什么需要这一步：** SPEC §3.3 要求每 30 秒扫一遍超时任务，且**不用 in-process timer** ——
进程重启定时器全丢，而任务的超时判定必须在重启后继续有效。

**实现流程：**

1. 启动时**立即扫一轮**
2. 之后按配置的间隔用 ticker 周期扫
3. 每轮调状态机的扫描方法，出错只记日志
4. 上下文取消时退出循环并记一条停止日志

**设计要点：**

- **启动时立即扫一轮**，不等第一个间隔：进程重启期间积压的超时要马上判出来。
- **出错不退出循环。** 数据库瞬时不可用之后，超时判定必须自己恢复 ——
  循环退出的后果是静默停摆到下次重启，而没人会注意到扫描循环不见了。
- **只依赖状态机的一个方法**（用一个单方法的窄接口声明），这样测试不必搭出整个状态机。

**测试要锁住的行为：**

- 循环按间隔重复执行，上下文取消后**函数确实返回**（不返回就是 goroutine 泄漏）
- **扫描出错后循环继续** —— 用一个总是返回错误的替身验证仍在累加调用次数
- **启动时立即执行一轮** —— 用一个很长的间隔验证计数仍变为 1

**验证：** `go test ./cmd/lober/ -run TestScanner -race -v` 全过，无竞态报告。

**完成标志：** commit `feat(cmd): timeout scan loop independent of the request path`

### 任务 4：两个 listener 加一个 UDP listener 的生命周期

**产出文件：** `cmd/lober/server.go`、`server_test.go`

**为什么需要这一步：** SPEC §1.1：网关与控制台是**同一个二进制的两个 listener，
不是两个进程** —— 状态机必须有唯一所有者，两个进程会立即撞上状态转换竞态与
reconcile 循环重复执行。两个 listener 是必须的：机器面端点天然无认证，
该风险面需用监听地址与防火墙物理隔开。

**实现流程：**

1. **先逐个 Listen，任一失败就关掉已开的并返回错误**
2. 三个都成功后才各起 goroutine 开始 Serve
3. 等上下文取消或某个 listener 报错
4. 优雅关闭：给在途请求一个有限的宽限期，然后等全部 goroutine 收尾

**设计要点：**

- **先 Listen 再 Serve 是刻意的。** 端口被占时必须立刻失败退出，不能让系统半开着跑 ——
  只有控制台起来、网关没起来的状态下，运维会以为一切正常而机器全装不了。
- **HTTP server 要设读头部超时，但不要设写超时。** SSE 是长连接（§12.8），
  设了写超时会在装机中途掐断运维正在看的日志流。
- **syslog 读循环要设读超时**，否则没有「连接关闭」事件可感知上下文取消 —— UDP 没有连接。
  超时后检查上下文再继续读。
- **syslog 缓冲区开到 8 KB。** 单条 syslog 按 RFC 建议不超过 2 KB，但 anaconda 的
  traceback 行可能更长，而截断会丢掉最关键的那部分。
- **收到的包要拷贝一份再交给 handler** —— handler 可能异步持有，而缓冲区下一轮就被覆写。
- **syslog handler 用装配点本地定义的接口声明**，不绑 M5 的具体类型名 ——
  M5 改名字时这里不用改。
- **实际绑定的端口要可读取**，测试用 `:0` 让内核分配端口。

**测试要锁住的行为：**

- 三个 listener 都能服务，各自返回自己的内容（证明没接错 handler）
- syslog 能收到 UDP 包
- **上下文取消后 run 函数返回且无错误**
- **端口被占时立刻失败** —— 对应「系统半开着跑」那个故障

**验证：** `go test ./cmd/lober/ -run TestRun -race -v` 全过。

**完成标志：** commit `feat(cmd): two HTTP listeners plus syslog UDP with graceful shutdown`

### 任务 5：入口与运行模式

**产出文件：** `cmd/lober/main.go`

**为什么需要这一步：** 把前四个任务串起来，并提供部署需要的两个运行模式。

**四个 flag：** 配置路径、打印版本、**只校验不起服务**、日志级别。

**实现流程：** 解析 flag → 设置日志 → 加载配置 → 装配 → 注册信号处理 →
跑启动自检 → 若是校验模式则到此返回 → 起扫描循环 goroutine → 起三个 listener 并阻塞

**设计要点：**

- **版本号由链接期注入。** 气隙环境里排查问题时，第一个问题永远是「装的是哪个版本」。
- **校验模式是给 systemd 的 `ExecStartPre` 用的**：配置写错时在这里失败，
  比起服务后第一个请求才崩好查。
- **日志输出到标准错误交给 journald 收**，不自己管轮转 —— 那是 systemd 的事。
- **信号处理同时接 SIGTERM（systemd stop）与 SIGINT（终端 Ctrl-C）。**

**测试要锁住的行为：** main 的装配逻辑已由任务 1 的测试覆盖，本任务只验证构建与两个
运行模式可用。

**验证：** 带版本注入构建后 `./lober -version` 打印版本；
`./lober -config <样例> -check` 在样例配置上通过；`make check` 全绿。

**完成标志：** commit `feat(cmd): main entrypoint with -check and -version`

### 任务 6：nginx 配置

**产出文件：** `deploy/nginx/lober.conf`、`lober-http-snippet.conf`

**为什么需要这一步：** nginx 是唯一入口，限速、日志、将来的 TLS 全部集中在这里（§1.4）。
配置骨架在 SPEC §1.4，本任务是把它落地并加两处 SPEC 没写的东西。

**两个 server 块：** 机器面只监听装机 VLAN 的具体 IP，人面只监听管理网的具体 IP。

**必须配对的六项：**

1. **`listen` 写具体 IP，不是 `0.0.0.0`。** 写成通配时一切功能正常、测试全过，
   只是装机 VLAN 上的裸机获得了访问控制台 API 的能力 —— 信任域被静默合并。
   **加防火墙规则兜底。**
2. **制品走 `location` 直接发盘，不得 `proxy_pass`。** 否则 4 GB 镜像流经 Go 进程，
   零拷贝、异步 IO、Range 请求全部失效。
3. **机器面全部关 gzip**（制品与引导脚本都要），否则 iPXE 会把压缩字节当内核加载。
   人面相反 —— 前端的 JS/CSS 该压。
4. **制品要开 `Accept-Ranges`**：wimboot 与 WinPE 依赖 Range 请求。
5. **仓库 location 要开 `open_file_cache`**：离线仓库是几十万小文件。
6. **SSE 的 location 必须关缓冲与缓存、放长读超时。** 默认缓冲会让装机日志
   看起来完全冻住。

**两处 SPEC 骨架之外要加的：**

- **信号端点单独设限流桶**（§10 运维点二）：信号回调量不小（数百台 × 每 30 秒），
  与引导端点共用限流桶会让一批机器的信号把另一批机器的引导挤掉。
  限流区声明只能在 `http` 层，所以要单独一个片段文件先被 include。
- **访问日志格式带上 query 与耗时。** nginx access log 是 iPXE 启动之后全链路的
  主要取证记录（§1.4）—— SN/MAC/UUID 都在请求 URI 里，grep 单机可得完整引导时间线；
  制品下载的字节数与耗时能直接看出传输是否中途断开。

**验证：** `nginx -t` 通过。另运行 `nginx -V` 确认编译带线程支持
（`sendfile` + 异步 IO 需要它）—— **离线装包前就要确认，内网补装不上**。
`secure_link` 模块是 Phase 2 才需要，MVP 缺它不影响。

**完成标志：** commit `deploy: nginx config with specific-IP binds and separate signal rate bucket`

### 任务 7：dnsmasq 配置（DHCP + TFTP）

**产出文件：** `deploy/dnsmasq/lober.conf`、`deploy/dnsmasq/README.md`

**为什么需要这一步：** DHCP 只需知道两件事：非 iPXE 客户端按架构给对应二进制，
已是 iPXE 的客户端给一个固定 HTTP URL。**唯一的耦合点是最后那行 URL。**

> **本任务整体属于部署期一次性核对，不是运行期功能（§0.1、§1.3）。** 这些码值配错的
> 后果都发生在机器取 iPXE 二进制那一步 —— 根本走不到网关。本系统对此没有检测手段，
> 排查入口是 DHCP/TFTP 日志与 BMC 控制台。把细节写进配置是为了**配置那一次就配对**。

**最容易踩且最难查的错误：option 93 的 7 与 9 必须都匹配，且 7 才是实测主流值**
（附录 A.1b）。RFC 4578 原文把 7 定义为 `EFI BC`、9 定义为 `EFI x86-64`，但勘误明确
指出两者应当互换 —— 实际 UEFI 固件用 7 上报 x86-64。**只配 9 的后果是 UEFI 机器
匹配不上任何 tag、拿不到引导文件名、固件静默跳到下一个引导项**，现场表现为
「机器毫无反应」。两个值归到同一 tag 即可，不需要两套制品。

**必须配对的七项：**

1. **只在装机 VLAN 的网卡上提供服务**，绝不写监听所有接口
2. **五条架构匹配规则**（option 93 的 0/6/7/9/11），7 与 9 同 tag
3. **user-class 匹配规则**（option 77）区分两个阶段 —— 没有这一层就是无限引导循环
   （§10 失败模式 3）
4. **阶段一按架构给二进制**，每条都带「不是 iPXE」的反条件
5. **阶段二给固定的 HTTP URL**，架构无关一条通吃
6. **未知架构不给任何引导文件名**，绝不兜底发某个二进制 —— 给错架构的二进制会让固件
   加载失败或挂死，比不引导更难查
7. **租期长于装机窗口**：若机器在取引导脚本与取制品之间换了 IP，将来上 secure_link 后
   签名会失效（§9.3）

**另外三项配置：** DNS 记录（用域名不用 IP，将来签证书时 CN 能对上）、
**本地 NTP**（时间不同步会让日志时序错乱，§10 失败模式 10）、开启 DHCP 日志。

**ARM64 那行 MVP 阶段可以不放二进制，但 tag 建议先留**（§1.3）：缺失时国产 ARM 平台
接入的首个症状同样是「机器毫无反应」；留着 tag 则 TFTP 会留下一条找不到文件的记录，
排查成本差一个数量级。

**README 要写清 TFTP 目录该放哪四个文件**（BIOS/IA32/x64/ARM64 各一个），
以及它们在 ipxe.org 的对应路径。气隙环境下这些二进制需从外网取得后带进内网 ——
下载后校验 sha256 并把校验值记进仓库。

**验证：** `dnsmasq --test --conf-file=<路径>` 通过。

**完成标志：** commit `deploy: dnsmasq config with option 93 values 7 and 9 both matched`

### 任务 7b：对接既有 DHCP —— ISC dhcpd 与 Kea 等价配置（**按需执行**）

**产出文件：** `deploy/dhcpd/lober.conf`、`deploy/kea/lober-dhcp4.json`、
`deploy/README-既有DHCP.md`

**这个任务只在无法使用 dnsmasq 时执行。** 判据：目标机房已有在运的 DHCP 服务，
且不接受再引入一个。**新部署一律用 dnsmasq 或 Kea，不要选 dhcpd** ——
它已于 2022 年 10 月 EOL（附录 A.12），最后维护版本之后 ISC 不再计划发版，
官方建议迁移到 Kea。**本任务对 dhcpd 的支持是「对接既有环境」，不是推荐**（§0.2）。

**为什么需要这一步：** §1.3 的两阶段引导逻辑（非 iPXE 客户端按架构给二进制、
已是 iPXE 的给固定 URL）在三种 DHCP 实现里的表达机制**完全不同**。
照抄 dnsmasq 的配置到另两种上不会工作，而失败的表现是「机器毫无反应」——
本系统对此零可观测性（§0.1）。

**三种实现的机制差异，这是本任务的核心认知：**

| | dnsmasq | ISC dhcpd | Kea |
|---|---|---|---|
| 机制 | tag 集合 | 条件链（if / elsif） | 独立的 class 数组 |
| 判定是否互斥 | 否，靠显式反 tag 排除 | **是**，elsif 天然互斥 | **否，所有 class 独立求值** |
| 阶段区分靠什么 | 反 tag | **条件顺序** | 需在每个 test 表达式内显式排除 |

**第三列的「独立求值」是本任务唯一需要特别小心的一点**（§1.3.2）。

#### ISC dhcpd 的三个要点

1. **条件顺序是硬要求：user-class 判定必须在架构判定之前。**
   顺序颠倒的后果是已经跑起 iPXE 的客户端再次匹配到架构分支、拿到 iPXE 二进制 ——
   **直接构成无限引导循环**（§10 失败模式 3）。dhcpd 没有 tag 机制，
   互斥完全依赖 elsif 的顺序，所以这条比 dnsmasq 那边更致命
2. **option 93 必须显式声明**（dhcpd 无内置的该选项名），声明为 16 位无符号整数
3. **未知架构必须落到显式的兜底分支并打日志。** 不写兜底分支时客户端拿不到引导文件名、
   固件静默跳过网络引导 —— **与「DHCP 没响应」的现场表现完全一致**，
   那条日志是区分二者的唯一依据。
   **绝不要在兜底分支里发某个二进制** —— 给错架构的二进制会让固件加载失败或挂死，
   比不引导更难查（§10 失败模式 4）

**一处必须实测的语法**（附录 B）：架构值的比较字面量写成双字节形式还是十进制整数。
社区通行写法是双字节，但**实施前要用 dhcpd 的配置测试模式与真机各验一遍** ——
写成十进制的行为不要凭空假设。同样要验的是条件里的「或」在 elsif 中的求值是否如预期。

#### Kea 的四个要点

1. **反条件宁可写重复也不要省。** 把「不是 iPXE」的反条件直接与进每个架构 class 的
   test 表达式，让至多一个 class 能命中 —— 与 dnsmasq 的反 tag 语义对齐。
   看着笨，但它换来的是**配置正确性不依赖 Kea 的 class 求值与选项合并顺序**
2. **option 93 在 Kea 里的符号名与 dhcpd 的自定义名不同。**
   **实测前建议先用数值形式引用** —— 符号名对不上时 Kea 直接启动失败，
   比静默不匹配好查
3. **无需显式声明 option 93**（Kea 内置标准选项定义），这是与 dhcpd 的实质差异
4. **未知架构不命中任何 class 也就拿不到引导文件名**，行为与 dhcpd 的显式兜底等效，
   **但 Kea 不会为此留日志** —— 需要日志时要靠钩子库或调高日志级别观察未分类报文。
   否则「机器毫无反应」这一症状在 Kea 下比 dhcpd 更难定位

**若确认 Kea 的成员判定函数可用，第 1 点的重复反条件可以简化** ——
前提是 iPXE 那个 class 的求值确实先于架构 class 完成（Kea 文档称 class 按定义顺序处理，
故它需放在数组首位）。**这条简化必须实测后再用**（附录 B）。

> **有实战踩坑记录**（附录 A.15）：有用户报告 UEFI 固件明确发架构值 7，
> 但 Kea 仍回了传统 BIOS 的引导文件 —— 与 §1.3 那条错误配置同源。
> **调试第一步永远是抓 DISCOVER 报文看固件实际上报什么，不要相信配置文件里的注释。**

#### 三种实现的共同收敛点

**不论用哪一种，第二阶段拿到的都是同一个引导脚本 URL，网关对此零感知**（§1.3 末段、§4.7）。
所以三份配置的差异**全部止于本任务** —— 它们不影响 Go 代码的任何一行。

**要在文档里写明这一点**，否则会有人以为换 DHCP 实现要改网关。

**另一条要写明的边界：DHCP 保证不了「目标 OS 正确」，只能保证「固件模式正确」。**
DHCP 视野里只有两个选项字段，看不到任务要装什么 OS —— 目标 OS 的引导形态由网关在
第二层决定（§4.5），两层的一致性由网关校验（§4.6）。

**验证：**

- dhcpd：用它的配置测试模式通过，**且在实验环境用真机验证两阶段各走对分支**
- Kea：用它的配置测试模式通过，**且验证一台 UEFI 机器不会同时命中两个 class**
- 两者都要抓一次 DISCOVER 报文，确认固件上报值与配置里的判定一致

**完成标志：** commit `deploy: ISC dhcpd and Kea equivalents for existing DHCP servers`

### 任务 8：systemd 单元、配置样例与密码哈希工具

**产出文件：** `deploy/systemd/lober.service`、`deploy/systemd/nginx.service.d/after-lober.conf`、
`deploy/lober.yaml.example`、`scripts/mkuser/main.go`

**为什么需要这一步：** 部署产物。三件东西各有一处容易配错的地方。

**systemd 单元的六项要点：**

1. **`ExecStartPre` 跑一次校验模式** —— 配置写错时在这里失败，比起服务后第一个请求才崩好查
2. **`TimeoutStopSec` 要长于装配点的优雅关闭宽限期**，否则 systemd 会在收尾完成前
   强杀进程
3. **需要绑定特权端口的能力**（syslog 在 514），但只给这一项能力，不给 root
4. **文件系统加固**（只读系统、私有 tmp、禁访问家目录），但**可写路径要包含
   数据库、制品、日志三处** —— 漏一处的表现是运行到一半才失败
5. **日志交给 journald**
6. **失败自动重启**，但有重启间隔

**nginx 的启动顺序 drop-in**（§1.6 第二条）：nginx 先起会返回 502。
加一个 `After=lober.service` 的 drop-in，或接受重启窗口内的 502（iPXE 会重试，
实际影响小）—— 两种都可接受，但要选一个而不是不管。

**配置样例要带注释说明每项的后果**，尤其三处必改项：两个监听地址的 IP、
基址 URL 的域名、**控制台 token 密钥**（空值时启动生成随机值，后果是重启即全员登出）。
另要在注释里列出五个角色与各自的权限码（§9.4），运维配用户时需要。

**密码哈希工具的三项要点：**

- **独立的小工具而不是主二进制的子命令**：它需要从终端读密码，而主二进制跑在 systemd 下
  不该有任何交互式代码路径
- **默认交互式读两次并比对**，另提供一个从标准输入读一行的开关供自动化使用
  （端到端脚本要非交互地造用户）。默认交互是为了不把密码留在 shell history 里
- **bcrypt cost 用 12 而非默认 10**：比默认慢约 4 倍，对个位数用户的登录频率毫无影响，
  但离线爆破成本高 4 倍
- **哈希打到标准输出、提示打到标准错误** —— 这样可以直接管道进配置文件
- **拒绝短密码**，并在提示里说明理由（这个账号能让机器被擦盘）

**验证：** 工具能构建；手动运行后得到 60 字符的 bcrypt 哈希；
`systemd-analyze verify` 对单元文件无告警。

**完成标志：** commit `deploy: systemd unit, config example and bcrypt hash tool`

### 任务 9：端到端验证脚本

**产出文件：** `scripts/e2e.sh`、`scripts/e2e/mkfixture.sh`

**为什么需要这一步：** SPEC §11 Phase 1 的验证行：**curl 模拟机器打点，整条链本地跑通，
不碰硬件。** 这个脚本是整个 MVP 的验收标准 —— 它绿了就说明九个模块装配正确。

**假制品树（`mkfixture.sh`）：** 造一个能通过 OS 家族识别的目录树 —— RHEL 系的特征文件、
冒充的内核与 initrd、仓库元数据文件。**不用真 ISO**：几 GB 的下载对一个每次提交都要跑的
脚本不可接受，而导入逻辑关心的只有特征文件与目录结构（§2.1 的识别表）。

**主脚本的九个阶段：**

| 阶段 | 做什么 |
|---|---|
| 1 | 造假制品树、建临时目录、构建二进制、用哈希工具造一个 admin 用户、写临时配置 |
| 2 | 起服务，轮询到就绪（不要 `sleep` 固定秒数） |
| 3 | 登录拿 access token |
| 4 | 录入一台主机、登记制品集、**轮询导入 job 到 ready** |
| 5 | 建模板、顺手验证 preview 端点（它不需要真任务就能跑） |
| 6 | **准入控制负面用例**（见下） |
| 7 | 模拟 iPXE 取引导脚本与菜单，从菜单里抠出装机 token |
| 8 | 取应答文件、从其中抠出 finalize token、按顺序打十一个信号 |
| 9 | **装完再引导一次，验证不循环重装** |

**第 6 阶段的四个负面用例是这个脚本最有价值的部分：**

1. **SN 对但 MAC 不对 → 拿不到菜单，回 sanboot**（§4.3 的双因子硬要求）
2. **完全陌生的机器 → 回 sanboot，且任务状态不变、事件表无新增**（§4.2、§0.1：
   `no_task` 不建任务不记状态不告警）
3. **架构不符 → 回 sanboot 且任务置 failed，失败原因可读为 precheck**（§4.6 硬拒绝）
4. **precheck 失败的任务允许 retry 并回到 pending**（§8.2 只禁两类超时，不扩大范围）

**第 8 阶段要顺带验证的四件事：**

- 应答文件含渲染器骨架三件套（内联参数、syslog 指向、firstboot 脚手架）
- **重复发同一个 seq 仍回成功** —— 机器侧会重试三次（§6.3）
- **延迟到达的早期信号不把阶段打回去**（§3.6 只进不退）
- **finalize token 发装机期信号被拒** （§6.4 权限受限）

**第 9 阶段要验证三件事：**

- 装完的机器再次引导拿到 sanboot 而**不是**装机菜单 —— 这是 §10 失败模式 1 的拦截点
- **终态任务的应答文件不再提供**（§4.4 状态门控）
- 事件表留下了完整时间线（任务详情页靠它）

**设计要点：**

- **轮询而非固定等待。** 固定 `sleep` 在慢机器上会假失败、在快机器上浪费时间，
  两种都会让人不信任这个脚本。
- **失败时打印具体原因与实际响应内容**，而不只是「断言失败」。
- **临时目录用 trap 清理**，包括杀掉后台进程。
- **端口用不常见的高位端口**，避免与开发机上其它服务撞。
- **syslog 那条通道 curl 覆盖不了**（它是 UDP）—— 由 M5 的自动化 UDP 测试覆盖，
  在脚本注释里说明这个分工，而不是假装测过了。

**验证：** `./scripts/e2e.sh` 九个阶段逐个打印通过标记，最后输出完整状态链。
依赖 `jq` 与 `curl`。

**另把它接进 Makefile** 作为一个独立目标。

**完成标志：** commit `test(e2e): full pending-to-done chain with curl, no hardware`
