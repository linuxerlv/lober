# P2-03 Provider 加载器：exec 与 http 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成，**且任务 1 的实测依据已收集**（见下）。
> 与 P2-01、P2-02、P2-04、P2-05 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 给 Phase 1 定义的七个 provider 接口加两种外部加载方式 ——
子进程（JSON 进 JSON 出）与 webhook。

**架构：** 加载器是接口的另一种实现，对调用方透明。`exec` 类型启动子进程、
标准输入给 JSON、标准输出读 JSON；`http` 类型发 POST、body 是 JSON。
两者共用一套请求与响应的编解码，以及一套超时、重试与熔断策略。

**这个计划有一个开工前提，不是形式要求。** SPEC §11 把加载器放在 Phase 2 并注明
「**此时已知哪些扩展点真需要外部集成**」；§7.6 进一步警告：过早做插件体系会
「花两周做加载、版本协商、隔离，然后发现实际只需要三个 shell 脚本」。
**所以任务 1 是收集依据，依据不足时应当推迟整个计划。**

**技术栈：** 标准库 `os/exec`、`net/http`、`encoding/json`、`context`

**SPEC 依据：** §7.2 三种加载器、§7.3 热更新要求、§7.4 失败语义、§7.6 MVP 不做插件

### 任务 1：收集实测依据 —— 决定要不要做，以及做哪几个

**产出文件：** `docs/phase2-loader-需求依据.md`

**为什么需要这一步：** 这不是流程形式。§7.6 的判断是：**接口边界是真正有价值的部分，
加载机制可以后补**。而「后补」的正确时机是「已知要接什么」——
提前做会做出一个没人用的抽象。

**要回答的四个问题，每个都要有 Phase 1 运行期的实际依据：**

1. **七个扩展点里，哪几个真的需要接外部系统？** 列出具体的外部系统名称与接入方式
   （REST API、命令行工具、数据库）
2. **每个需要外部集成的扩展点，用 exec 还是 http？** 判据见 §7.2：
   「几行 curl 的集成用 gRPC 是纯负担」，而 exec 在气隙环境里改一个 shell 脚本是
   30 秒的事
3. **有没有哪个扩展点其实是「有真逻辑」的？** 那类该用 gRPC（Phase 3），
   不要勉强塞进 exec
4. **纯决策的两个（模板解析、磁盘规划）需要外部化吗？** §7.6 的答案是不需要 ——
   规则表与具名策略够用，引入脚本引擎的信号是「规则表长出嵌套条件」。
   **如果 Phase 1 运行下来规则表还是平的，这两个就不做加载器**

**依据不足时的正确处置：推迟本计划，先用内置实现继续跑。**
把这个判断写进产出文件 —— 它是一次有记录的决定，不是遗漏。

**一个可操作的判据：** 如果四个问题里有三个答不出具体的外部系统名字，
说明还不知道要接什么 —— 推迟。

**验证：** 产出文件里四个问题各有具体答案，且列出了要做的加载器类型与扩展点清单。

**完成标志：** commit `docs: evidence for which provider loaders are actually needed`

### 任务 2：请求与响应的编解码约定

**产出文件：** `internal/provider/loader/protocol.go`、对应测试

**为什么需要这一步：** exec 与 http 两种传输共用同一套载荷格式。
先定死格式，两个加载器才能共用编解码与测试。

**协议的四条约定：**

1. **每次调用是一次独立的请求响应**，无状态、无会话。
   exec 每次启新进程，http 每次新请求 —— **这是崩溃隔离的基础**（§7.2：
   两种加载器都有完整的崩溃隔离）
2. **请求体含三部分**：扩展点名与方法名、协议版本、方法参数
3. **响应体含三部分**：是否成功、结果、错误信息。
   **错误用响应体里的字段表达，不用退出码或 HTTP 状态码** ——
   退出码只有一个字节，装不下「IP 池耗尽」与「认证失败」的区别，
   而运维需要看到区别
4. **协议版本对不上直接拒绝调用**（§7.3 的版本协商要求）

**方法名进载荷而不是进路径或参数：** 一个 provider 脚本要能处理同一接口的
多个方法（比如 IPAM 的申请与释放）。**写一个脚本处理两个方法比写两个脚本清楚** ——
它们共享连接外部系统的代码。

**编解码要处理的一个细节：** 时间与时长的表示。
用整数秒而不是 Go 的时长字符串 —— **外部脚本是 shell 或 Python 写的**，
解析 Go 的时长格式是额外负担。

**测试要锁住的行为：**

- 请求与响应的往返编解码
- 协议版本不匹配被拒绝
- **错误信息能完整传回**（不被截断成一个码）
- 时长字段是整数秒

**验证：** `go test ./internal/provider/loader/ -run TestProtocol -v` 全过。

**完成标志：** commit `feat(loader): request/response protocol with versioning`

### 任务 3：exec 加载器

**产出文件：** `internal/provider/loader/exec.go`、对应测试

**为什么需要这一步：** 气隙环境下 exec 是最实用的加载方式 ——
改一个 shell 脚本是 30 秒的事，改 Go 插件要在外网编译、打包、走审批、传入内网（§7.2）。

**实现流程：** 构造子进程、JSON 写标准输入、读标准输出、解析响应、等进程退出。

**五条必须处理的情形：**

1. **超时**：用上下文控制，超时后**杀掉进程组而不只是主进程** ——
   脚本可能已经 fork 了 curl，只杀主进程会留下孤儿
2. **标准错误单独收集并记日志**。脚本作者会往那里写调试信息，
   丢弃它等于让运维没法排查自己的脚本
3. **输出不是合法 JSON** → 明确的错误，**且错误信息里带上输出的前若干字节**。
   最常见的原因是脚本里有一句忘了删的 `echo`，而错误信息里看到那句话就能立刻定位
4. **进程非零退出但输出了合法响应** → 以响应为准（第 3 条约定：错误在响应体里）。
   同时记一条日志说明退出码不为零 —— 那是脚本的 bug，但不该让一次正常的
   「申请失败」变成「协议错误」
5. **可执行文件不存在或无执行权限** → 启动时就能发现，不要等第一次调用

**一条安全要求：** 脚本路径从配置来，**但要拒绝相对路径**。
相对路径的解析依赖进程的工作目录，而那个目录在 systemd 下与手工运行时不同 ——
现场表现是「手工测试好的脚本在服务里找不到」。

**测试要锁住的行为：**

- 正常调用的往返
- **超时后进程组被杀**（用一个 sleep 脚本验证，并确认子进程也退出了）
- 标准错误被收集
- **非 JSON 输出的错误信息里含实际输出的片段**
- 非零退出但有合法响应时以响应为准
- 相对路径被拒绝
- 不存在的可执行文件在构造时就报错

**验证：** `go test ./internal/provider/loader/ -run TestExec -v` 全过。
测试用的脚本放 `testdata/` 下，**要能在 Windows 开发机上跳过**（标记跳过并说明原因）。

**完成标志：** commit `feat(loader): exec loader with process-group timeout`

### 任务 4：http 加载器

**产出文件：** `internal/provider/loader/http.go`、对应测试

**为什么需要这一步：** 告警推送、CMDB 注册这类集成，对方往往已经有 webhook 接口 ——
让它直接收 POST 比包一层脚本简单。

**实现流程：** 构造 POST 请求、JSON body、读响应、解析。

**四条必须处理的情形：**

1. **超时**用上下文控制
2. **非 2xx 状态码**：按第 3 条协议约定，错误本该在响应体里 ——
   但外部服务可能返回一个 HTML 错误页。**此时要产出一个带状态码与响应片段的错误**，
   而不是「JSON 解析失败」（后者会让运维去查自己的 JSON，而问题在对方返回了 502）
3. **连接失败与 DNS 失败**要与「对方返回了错误」区分开 ——
   前者是网络问题，后者是业务问题，运维的处置不同
4. **认证**：配置里可以带一个固定的头部（token 或 API key）。
   **不要实现 OAuth 流程** —— 内网的外部系统多用固定 token，
   而 OAuth 的刷新逻辑是一个独立的复杂度来源

**一条安全要求：** **配置里的 token 不能进日志。**
记请求日志时要把配置的认证头部替换成占位符 —— 否则第一次排查就会把 token 写进 journald。

**测试要锁住的行为：**

- 正常调用的往返
- 超时生效
- **非 2xx 返回 HTML 时的错误信息含状态码与片段**
- 连接失败与业务错误可区分
- 固定认证头部被带上
- **日志里不含 token 原文**

**验证：** `go test ./internal/provider/loader/ -run TestHTTP -v` 全过（用 `httptest` 起假服务端）。

**完成标志：** commit `feat(loader): http loader with redacted credential logging`

### 任务 5：熔断与失败语义的落地

**产出文件：** `internal/provider/loader/breaker.go`、对应测试

**为什么需要这一步：** 外部集成会抖。§7.3 要求「连续失败 N 次标记 provider 不可用，
再按 §7.4 的失败语义处理」。

**熔断的三态与转换：**

| 态 | 行为 | 转出条件 |
|---|---|---|
| 闭合 | 正常调用 | 连续失败达阈值 → 断开 |
| 断开 | **不调用，直接按失败语义处理** | 冷却时间到 → 半开 |
| 半开 | 放一次调用探路 | 成功 → 闭合；失败 → 断开 |

**熔断后的行为按扩展点的失败语义分流**（§7.4，Phase 1 的失败语义表已定）：

- **阻塞建任务那几个**（IPAM、模板解析、磁盘规划）：熔断后建任务直接失败，
  **错误文案要说明是外部系统不可用而不是参数错误** —— 运维据此去查那个系统，
  而不是反复改表单
- **只告警那几个**（DNS、Notify）：熔断后跳过调用并记日志。
  **不要让 DNS 熔断影响任务状态**（§7.4：一次 DNS 抖动不能把装好的机器标成失败）

**熔断状态要能被观测。** 至少记进日志；更好的是在控制台的某处能看到
「哪个 provider 当前是断开的」—— 否则运维只会看到「建任务一直失败」而不知道原因。
**本任务只要求日志，控制台展示留给 P2-05 或后续。**

**重试与熔断的关系要想清楚：** 单次调用内部重试几次，还是不重试直接让熔断计数？
**选不重试。** 理由：这些 provider 的调用都在请求路径上（建任务或 ready 之后），
内部重试会把一次建任务的等待时间放大数倍，而运维面对的是一个转圈的页面。
**让它快速失败，由运维决定是否重试** —— 那也符合「决策要固化」的原则。

**测试要锁住的行为：**

- 连续失败达阈值后进入断开态，**且断开态下不再实际调用**
- 冷却后半开，半开成功则闭合、失败则重新断开
- **阻塞类 provider 熔断时建任务失败，错误文案指向外部系统**
- **只告警类 provider 熔断时任务状态不受影响**
- 单次调用不内部重试

**验证：** `go test ./internal/provider/loader/ -run TestBreaker -v` 全过。

**完成标志：** commit `feat(loader): circuit breaker honoring per-extension failure policy`

### 任务 6：配置与工厂集成

**产出文件：** `internal/config/config.go`（扩展）、`internal/provider/factory.go`（扩展）

**为什么需要这一步：** 把加载器接进 Phase 1 的按配置构造流程。

**配置形态：** 每个扩展点可以配「内置」「exec」「http」三种类型之一，
带各自的参数（exec 要可执行文件路径与超时，http 要 URL、超时与可选的认证头部）。

**这是一处契约变更**（配置结构变了），但影响面小 —— 走流程更新 M1 的配置结构与校验测试。

**校验要在启动时做，四条：**

1. 类型是三种之一
2. exec 的路径是绝对路径且文件存在可执行
3. http 的 URL 可解析且 scheme 是 http 或 https
4. **超时值有上限**（比如 60 秒）—— 配一个 10 分钟的超时会让建任务请求挂十分钟，
   而运维会以为系统死了

**工厂的构造逻辑：** 按类型构造，外部类型的实现包一层熔断。
**内置实现不包熔断** —— 它们是纯函数或本地查库，熔断没有意义。

**一条向后兼容要求：** 配置里不写类型时默认「内置」，
这样 Phase 1 的配置文件不改也能跑。

**测试要锁住的行为：**

- 三种类型各自构造出可用的实现
- 四条校验各自拦下对应的错误配置
- **未指定类型时默认内置**（Phase 1 的配置仍可用）
- 外部类型的实现带熔断，内置的不带

**验证：** `go test ./internal/config/ ./internal/provider/ -v` 全过；
**用 Phase 1 的配置样例跑一次校验模式，确认仍通过。**

**完成标志：** commit `feat(provider): wire exec/http loaders into the factory`

### 任务 7：热更新的两项（原子换与健康检查）

**产出文件：** `internal/provider/loader/reload.go`、对应测试

**为什么需要这一步：** §7.3 列了五项热更新要求。**其中三项只对 gRPC 有意义**
（in-flight drain、崩溃自动重启、协议版本协商已在任务 2 做了），
**exec 与 http 天然不需要**：每次调用是独立的进程或请求，没有「已加载的实例」要替换。

**所以本任务只做两项：**

1. **原子换实现**：改配置后重新构造 provider，用一次原子的指针替换 ——
   在途调用仍用旧实现（它们是独立的进程或请求，不受影响）。
   **不要用「先停再换」** —— 那会让替换期间的建任务失败，而替换本该是无感的
2. **健康检查与回滚**（§7.3）：新实现构造后先调探活，
   **失败则保留旧实现并拒绝本次 reload** —— 而不是换上一个不通的实现

**探活对两种类型的含义：** exec 是用探活方法名调一次脚本；http 是发一次探活请求。
**脚本或服务端不实现探活方法时视为通过**（返回「未实现」不算失败）——
否则会强迫所有外部脚本都加一段探活代码，而多数集成不需要。

**reload 的触发方式：** 一个信号（比如 SIGHUP）或一个管理端点。
**选信号** —— 它不需要认证，而管理端点要考虑权限；且 systemd 的 `reload` 动作
可以直接映射到发信号。

**要写进注释的一条：** **配置文件的重读也要走校验**，
校验失败则整个 reload 失败、保留原配置 —— 不要部分应用。

**测试要锁住的行为：**

- 原子替换后新调用用新实现，**在途调用不受影响**
- **探活失败时保留旧实现且 reload 返回错误**
- 未实现探活方法的外部实现视为通过
- 配置校验失败时整体不应用

**验证：** `go test ./internal/provider/loader/ -run TestReload -race -v` 全过。

**完成标志：** commit `feat(loader): atomic reload with health check and rollback`

### 任务 8：心跳接进定时轮询

**产出文件：** `cmd/lober/heartbeat.go`、对应测试

**为什么需要这一步：** Phase 1 的 M7 实现了两个心跳探测器，但没有接进定时轮询 ——
它们目前没有调用方。本任务补上，**它是本计划里唯一与加载器无关的部分**，
放这里是因为它也属于「provider 的运行期集成」。

**轮询循环的形态与超时扫描循环一致**（M9 的那个）：
按配置间隔、启动时立即跑一轮、出错不退出。

**探测范围**（§6.6）：状态在 booting、installing、rebooting、initializing 四者之内
**且已知可探测地址**的任务。

**两种地址来源：** installing 阶段用引导请求记录的客户端 IP；
initializing 阶段用表单里的业务 IP。

**探测结果只记录，不改任务状态**（§7.4 的失败语义是只记录）。

**为什么不改状态：** §6.6 说清了 —— **ICMP/TCP 在你最关心的故障里全是正常的**。
anaconda 卡在依赖解析时内核活着、网络通着，探测成功但装机实际上已经卡死。
**它能替代存活判断，替代不了进展判断。** 所以探测失败只是一条诊断线索
（「机器层面出事了」），而不是判定依据。

**一条建任务时的校验要求**（§6.6 末段）：若要用业务 IP 探测就绪，
**建任务时要校验业务 IP 对服务端可达**。若业务网与管理网不通，探测永远失败 ——
表单校验时就要告知，不要等装完才发现。**或者允许配置「不探测，靠人工确认完成」。**

**测试要锁住的行为：**

- 循环按间隔运行，上下文取消后返回
- 探测范围只含四个状态且有地址的任务
- **探测失败不改任务状态**
- 两种地址来源各自生效
- 业务 IP 不可达时建任务给出提示（或按配置跳过探测）

**验证：** `go test ./cmd/lober/ -run TestHeartbeatLoop -race -v` 全过。

**完成标志：** commit `feat(cmd): heartbeat polling loop, record-only semantics`

## 边界提醒

**exec 与 http 两种就够**（§7.2）。gRPC 是 Phase 3，且只给「有真逻辑的集成」
（IPAM、CMDB 那类）用。**Starlark 更要等信号** —— §7.6 说清了引入它的信号是
「规则表开始长出嵌套条件，或运维反复要求这批机器特殊处理」。

**Go 的 plugin 构建模式已明确排除**（§0.2、§7.2）：要求编译期完全对齐、
无法卸载、更新必须重启进程、panic 直接带走网关、**Windows 完全不支持**
（本地开发环境就过不去）。它是唯一需要重启且唯一无崩溃隔离的方案 ——
不要因为「看起来是原生方案」而重新考虑它。
