# Lober Phase 2 实现计划索引

> **前置：Phase 1 MVP 全部完成并在实机跑通过一台机器。**
> 见 `2026-09-20-lober-mvp-00-index.md`。
>
> 写法与 Phase 1 一致：**不写代码**，每个任务给「为什么需要 / 设计要点 / 实现流程 /
> 测试要锁住的行为 / 验证 / 完成标志」。

**目标：** SPEC §11 Phase 2 —— 从「一台 Rocky 装通」扩展到「三个 Linux 家族 + 服务端
硬件决策 + 外部系统集成 + 制品授权」。

**Phase 2 与 Phase 1 的本质差异：** Phase 1 是把链路打通，Phase 2 是让它能面对真实机房的
多样性。多样性来自三处：OS 不止一种、硬件不止一种配置、外部系统必须对接。
**三处各有一个「不要过度设计」的边界**，写在各计划里。

---

## 开工前提：Phase 2 是「实测之后」的工作

SPEC §11 对 Phase 2 的两项标了条件：

| 项 | 条件 |
|---|---|
| 每机架 HTTP cache | **实测出带宽瓶颈后**再做 |
| `exec` / `http` provider 加载器 | **此时已知哪些扩展点真需要外部集成** |

这两条不是客套话。**在没有实测数据前做缓存是猜测性优化**；在不知道要接哪个 IPAM 前
做加载器会做出一个没人用的抽象（§7.6 已经警告过：会花两周做加载、版本协商、隔离，
然后发现实际只需要三个 shell 脚本）。

**所以 P2-03 与 P2-04 的第一个任务都是「收集实测依据」**，依据不足时应当推迟而不是硬做。

## 三处「不要过度设计」的边界

| 计划 | 边界 |
|---|---|
| P2-01 多 OS | **不要为了对称而抽象**。三个家族的应答文件格式差异是本质的（kickstart 是脚本、autoinstall 是 YAML、preseed 是 debconf 键值），强行抽出一个统一模板会让三种都别扭。共用的只有 hook 阶段映射与 fact 注入 |
| P2-02 采集 | **只采服务端会用到的字段**。采一堆没人消费的硬件事实会让 fact 契约（只增不删，§5.4）背上永久负担 |
| P2-03 加载器 | **exec 与 http 两种就够**（§7.2）。grpc 是 Phase 3，且只给「有真逻辑的集成」用 |
