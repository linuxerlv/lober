# Lober Phase 4 实现计划索引

> **前置：Phase 3 全部完成（或其中的按需项已有明确的推迟结论）。**
>
> 写法与前三期一致：**不写代码**。

**目标：** SPEC §11 Phase 4 —— 生产化。TLS 与 mTLS、Secure Boot、UEFI HTTP Boot、
并发限流与失败重试与告警接入、desync 增量传输、审计报表。

**Phase 4 与前三期的本质差异：前三期在加功能，Phase 4 在加保障。**
七项里有四项是「系统已经能用，但生产环境要求更高」：TLS、Secure Boot、
并发限流、审计报表。另外三项是性能与便利：UEFI HTTP Boot、desync、失败重试。

**这一期的排序原则与前三期不同：按「不做的代价」排，不按依赖排。**

| 项 | 不做的代价 | 优先级 |
|---|---|---|
| 并发限流 | **一批机器同时装会打满 HTTP**（§10 运维点），装机成功率下降 | 高 |
| TLS | 应答文件与 token 在装机 VLAN 上明文（§1.5 的代价） | 高（若 VLAN 隔离不彻底） |
| 审计报表 | 误装事故后无法快速回答「谁在什么时候建了那个任务」 | 中 |
| Secure Boot | **无法在开启 Secure Boot 的机器上装机** —— 而新服务器默认开启 | 中（取决于机器） |
| UEFI HTTP Boot | TFTP 传输慢一些（但只传几十 KB 的 iPXE 二进制） | 低 |
| desync | 镜像传输流量大 | 低（**仅在实测有收益时**，§11） |
| 失败重试 | 偶发故障要人工重试 | 低 |

## P4-02 与 P4-03 已决定不实施（2026-09-21）

**决定：TLS/mTLS 与 Secure Boot 都不做。** 理由是 CA 体系与签名链的搭建与维护复杂度
过高，而收益在当前环境下不足以抵消它。

**两份计划文档保留**，因为它们记录了完整的技术分析 —— 将来若安全要求变化，
那些分析仍然有效（特别是 P4-02 任务 2 的「嵌入 CA 而非服务端证书，
于是常规轮换不重编 iPXE」与 P4-03 任务 1 的「先问能否批量关闭 Secure Boot」）。

**不做 TLS 的直接后果要记住，它不是零成本的：**

| 后果 | SPEC 依据 |
|---|---|
| **token 与默认拒绝是唯一的防线**，不能降级实现 | §9.1 末段、§1.5 |
| 应答文件与 token 在装机 VLAN 上是明文 | §1.5 的威胁模型 |
| **前提：装机 VLAN 必须真正隔离、不路由到办公网** | §1.5 明确把这条列为前提 |
| 应答文件里的敏感内容处理要保持严格 | §1.5 的缓解手段：root 不设可复用密码、注入 SSH 公钥、不放域管凭据 |
| §9.5 的凭据清理仍然必要 | 同上 |

**不做 Secure Boot 的后果：** 开启 Secure Boot 的机器无法用本系统装机。
**应对方式是 P4-03 任务 1 已经分析过的那条路径** —— 装机时关闭 Secure Boot，
装完按需开启。该任务的分析指出：**这是完全可接受的运维流程，
成本远低于三级签名链的维护**，前提是安全策略允许且能批量操作固件设置。

**部署时要确认的一件事**（原本由 P4-02 覆盖）：装机 VLAN 的隔离是真的 ——
M9 的部署验收里已有一条「从装机 VLAN 访问控制台监听地址必须失败」的交叉验证，
**那条现在从「兜底检查」升级为「唯一保障」**。

## 为什么 P4-03 是 PoC 计划而不是实现计划

SPEC §11 Phase 4 对 Secure Boot 的原话：
**「建议先做独立 PoC，技术风险最高」**。附录 B 也把它列为待验证项，
要核实的是「三级签名的具体机制与密钥注册流程」。

**技术风险高在哪：** 引导链要变成三级，每一级都独立签名 ——
而中间那一级（自签的 iPXE）需要把自己的证书注册进固件的信任列表，
**那个注册动作在不同厂商的固件里操作方式不同，且部分固件不支持**。

**所以 P4-03 的产出不是代码，而是一个结论：**
「这套方案在我们的机器上能否走通、代价多大」。走得通才写实现计划。

**写成 PoC 计划的实际差异：** 每个任务的产出是一个验证结果与记录，
而不是一个 commit 的功能；验收标准是「问题有答案」而不是「测试通过」。

## desync 为什么没有计划

§11 标注「**仅在实测有收益时**」。附录 A.11 确认了技术事实，
但**附录 B 明确写「实际场景下的 chunk 复用率与流量节省量级需自行实测，
本轮相关论断被否决」。**

P3-03 的末尾已经把需要的输入数据列出来了（镜像大小、传输耗时、
**镜像版本的更新频率与每次更新的内容变化量**）。

**有了那两个数才能算出复用率，才能判断是否值得。**
在那之前立计划是本末倒置 —— 而 P2-04 的缓存与 P4-01 的限流是更便宜的替代方案。

## SPEC 中明确不做、也不进任何计划的

这些是 §0.2 的显式排除项与附录 B 里已过时的调研项，**列在这里以免被当成遗漏**：

| 项 | 为什么不做 |
|---|---|
| 带外管理（Redfish / IPMI）自动开关机 | §0.2：误操作风险最高，一个错的 SN 配上自动开机即可擦掉生产机。**人工上电是安全特性** |
| 让机器走到 iPXE（改引导顺序、挂虚拟介质） | §0.2：范围起点是 booting；运维在 BMC 里做更快更准 |
| 第 2 步之前的失败检测与告警 | §0.2：判据全在固件与 DHCP 里，本系统零可观测性 |
| 跟踪「没有任务的机器来过」 | §0.2：常态噪声，nginx access log 已零成本记下 |
| 自研 DHCP / TFTP / ProxyDHCP | §0.2：成熟实现直接复用 |
| Go plugin 构建模式 | §0.2、§7.2：需重启、无崩溃隔离、Windows 不支持 |
| 机器侧直连 IPAM / CMDB / DNS | §0.2：全部收敛到服务端 provider |
| 开源方案对比（Cobbler / Foreman / MAAS 等） | 附录 B 的调研项，**但项目已决定自研** —— 该项已过时 |
| 国产 OS 与 ARM64 适配 | 附录 B 列为待验证，**但 §11 未列入任何 Phase** —— 见下方说明 |

### 国产 OS 与 ARM64：需要一个范围决定

附录 B 列了「openEuler / 麒麟 / UOS / Anolis 的应答文件机制差异，
及 ARM64（飞腾 / 鲲鹏）平台的引导差异」为待验证项，
**而 §11 的四期都没有列入它。**

**这是 SPEC 自身的一处空白，不是计划的遗漏。** 三条相关线索：

- §1.3 专门为 ARM64 留了 DHCP 的架构 tag，并提醒「缺失时国产 ARM 平台接入的
  首个症状同样是机器毫无反应」
- §1.3 的部署核对清单里有「**尤其是国产 ARM 平台是否规范地报 11**」
- 附录 B 把这两件事列为待验证

**所以基础设施已经为它留了位置，但适配工作没有排期。**
若目标机房确有这类机器，需要一份独立的适配计划 —— **那要先回答一个事实问题：
那几个国产发行版的应答文件机制是各自独立的，还是都兼容 RHEL 的 kickstart？**
（openEuler 与 Anolis 是 RHEL 系衍生，可能直接复用 Phase 1 的渲染器；
麒麟与 UOS 需要确认。）

**在回答这个问题之前不要立计划** —— 若它们都兼容 kickstart，
工作量只是加几个识别特征文件；若各自不同，那是一份与 P2-01 同等规模的计划。
