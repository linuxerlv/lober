# P3-03 镜像封装流水线与直写通道 实现计划

> **数据层迁移说明**：本文记录的是数据层仍为 SQLite 时的情况，数据层已于
> 2026-09-24 迁移到 GORM + PostgreSQL（见
> `docs/superpowers/specs/2026-09-24-gorm-postgres-migration-design.md`），
> 正文保留当时原貌，未作修改。

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 2 全部完成。与 P3-01、P3-02、P3-04 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 建立镜像封装流水线（外网侧），并在装机链路上加一条镜像直写通道
（内网侧），与已有的 installer 驱动通道并存。

**架构：两条通道并存，分工明确**（§11 Phase 3）：

| 通道 | 定位 | 覆盖 | 机制 |
|---|---|---|---|
| installer 驱动（已有） | **兜底** | 新 OS 版本、特殊机型、调试 | 引导 installer，它读应答文件 |
| 镜像直写（新增） | **主力** | 批量与一致性要求 | 引导一个最小环境，它把镜像写到盘上 |

**为什么兜底通道不能废：** 新 OS 版本发布时镜像还没封装好；
特殊机型的驱动问题往往要在 installer 里现场调；调试时需要能停在 shell 里看
（§2.3 的失败处置策略）。**镜像直写做不到这三件事。**

**这个计划有两半，一半在外网一半在内网。** 封装流水线跑在有外网的构建机上
（气隙内网装不上构建工具的依赖，与前端构建同理，§12.3）；
直写通道跑在内网。**两半之间的接口是「一个带签名与清单的镜像文件」** ——
任务 2 定义它。

**技术栈：** 封装用 Packer（Windows / ESXi，必须引导真 installer）加
mkosi 或 osbuild（Linux）加 virt-customize（增量定制）；
校验用 sha256 与 cosign 的 key-based 签名

**SPEC 依据：** §11 Phase 3、§9.6 镜像签名、§2.1 制品集模型、附录 A.11、附录 B

### 任务 1：镜像制品的数据模型

**产出文件：** `internal/core/model/inventory.go`（扩展）、conformance 套件扩展、
内存实现扩展

**为什么需要这一步：** 两条通道并存要在数据模型上体现，
**而不是给镜像直写另建一套模型** —— 后者会让任务、模板、制品集这三层各自分叉。

**做法：制品集加一个「通道」字段**，取值是「installer 驱动」或「镜像直写」。

**这是契约变更，走 M1 的流程**（改接口 → 改 conformance → 改内存实现 → 通知）。

**镜像直写的制品集，路径结构里要多三样：**

| 项 | 作用 |
|---|---|
| 镜像文件 | 要写到盘上的那个 |
| **镜像的 sha256 与签名** | §9.6 的完整性与来源校验 |
| **分区布局描述** | 镜像写完后要调整的分区（扩展根分区到整盘之类） |

**第三项的存在理由：** 镜像是固定大小的，而目标机器的盘大小不一。
写完后要扩展分区，而怎么扩展取决于镜像内部的分区结构 ——
**这个信息只有封装时知道，所以要随镜像一起交付**。

**选集逻辑要相应扩展**（§2.1 的四元组查表）：
现在是五元组（家族、版本、架构、固件、通道）。
**模板要能指定用哪条通道** —— 同一个 OS 版本可能两条通道都有制品。

**一条兼容性要求：通道字段缺省为 installer 驱动。**
这样 Phase 1 与 Phase 2 导入的全部制品集不用迁移。

**测试要锁住的行为：**

- 通道字段的两个取值都能存取，**缺省是 installer 驱动**
- 镜像直写的制品集必须有镜像文件、签名与分区布局三项，缺任一则导入失败
- 五元组选集：同一 OS 版本的两条通道制品集能被分别选中
- **已有的四元组查询仍然工作**（向后兼容）
- conformance 套件的新断言在内存与 SQLite 两个实现上都过

**验证：** `go test ./internal/core/... ./internal/store/sqlite/ -v` 全过。

**完成标志：** commit `feat(model): image-write channel as an artifact set dimension`

### 任务 2：封装流水线与交付物格式

**产出文件：** `pipeline/` 目录下的构建定义、`pipeline/README.md`

**为什么需要这一步：** 封装跑在外网构建机上，产出要能带进内网。
**两半之间的接口必须先定死**，否则内网侧无法开发。

**交付物是一个目录，含四样：**

1. 镜像文件（压缩后的）
2. 清单文件（含 sha256 与分区布局描述）
3. 清单的签名
4. 元信息（家族、版本、架构、固件、封装时间、源 ISO 的 sha256）

**第 4 项里的源 ISO 校验值是为了可追溯**（与 §2.1 的同名字段对应）：
「这个镜像是从哪个 ISO 封装的」在排查时是第一个问题。

**压缩用 zstd**（§11 Phase 3 明确）。理由是解压速度 ——
镜像直写的瓶颈在写盘与解压，而 zstd 的解压速度远高于同压缩率的其它算法。

**三类 OS 的封装工具不同**（§11 Phase 3、附录 B 的「镜像构建工具边界」）：

| OS | 工具 | 关键约束 |
|---|---|---|
| Linux | mkosi 或 osbuild | 两者的实际能力与 OS 覆盖范围**需自行核实**（附录 B 列为待验证） |
| Windows / ESXi | Packer | **必须引导真 installer**（§11 Phase 3 明确）—— 没有别的办法产出可用的镜像 |
| 增量定制 | virt-customize | 在已有镜像上改，不重新封装 |

**附录 B 把「镜像构建工具边界」列为待验证项**，所以本任务的第一步是核实工具能力，
而不是直接写构建定义。**核实结论要写进 README** —— 包括哪个工具覆盖哪些 OS、
哪些 OS 暂时没有可用工具。

**一条流水线的设计要求：封装过程要可重现。**
同一份输入（ISO 加定制脚本）两次封装应产出功能等价的镜像。
**不要求字节级相同**（时间戳与随机生成的机器 id 会不同），
但要求**清单里的软件包列表相同** —— 那是「可重现」在实践中的可验证形式。

**验证：** 核实结论写进 README；至少一个 Linux 发行版的封装能跑通并产出四样交付物；
两次封装的包列表一致。

**完成标志：** commit `feat(pipeline): image packaging with zstd and manifest`

### 任务 3：镜像签名与校验

**产出文件：** `internal/imports/signature.go`、`pipeline/sign.sh`、对应测试

**为什么需要这一步：** §9.6 的标题就是结论：**气隙下 sigstore 的无密钥模式走不通。**

**为什么走不通：** 无密钥模式依赖两个外部服务 —— 一个签发短期证书的服务
（需外网 OIDC）与一个透明日志服务。**气隙环境两者均不可达。**

**所以用基于密钥的签名**（§9.6）：用私钥对清单签名，公钥预置在网关中。

**三条实现要求：**

1. **签的是清单而不是镜像本身。** 镜像有几 GB，签它要完整读一遍；
   而清单里有镜像的 sha256 —— 签清单等于间接签了镜像，且清单只有几 KB
2. **公钥预置在网关的配置里**，不从网络取。取公钥的通道若不可信，
   整个签名机制就没有意义
3. **校验在导入时做，不在装机时做。** 装机时再校验意味着每次装机都要读一遍镜像 ——
   而导入时校验一次、之后靠文件系统的完整性即可。
   **要在注释里写明这个取舍**：它假设制品目录不会被恶意篡改，
   而那个假设由文件权限（§文件系统契约的权限一节）保证

**§9.6 的最后一句要落实：「不要指望默认流程能跑。」**
意思是 cosign 的文档与示例默认都是无密钥模式 —— 照抄会在第一步就卡住。
**要在 README 里写明用的是基于密钥的模式，并给出完整的命令形态。**

**一个操作性问题要解决：私钥放哪。**
它不能在内网（内网只做校验），也不该在每个开发者的机器上。
**建议放构建机并限制访问** —— 而这个决定要写进文档，
因为它是「谁能封装出被系统信任的镜像」这个权限问题的答案。

**测试要锁住的行为：**

- 正确签名的清单校验通过
- **篡改清单后校验失败**
- **篡改镜像（使 sha256 不符）后导入失败**
- 公钥缺失时导入拒绝（不是跳过校验）
- 签名格式不识别时报明确错误

**验证：** `go test ./internal/imports/ -run TestSignature -v` 全过。

**完成标志：** commit `feat(imports): key-based image signature verification`

### 任务 4：直写环境的引导与写盘

**产出文件：** `internal/render/imagewrite.go`、golden file

**为什么需要这一步：** 镜像直写要先引导一个最小环境，再由它把镜像写到盘上。
**那个最小环境不是 installer** —— 它只需要网络、一个解压器与一个写盘工具。

**最小环境的选择，两个方向：**

| 方向 | 取舍 |
|---|---|
| **复用某个发行版的 installer ramdisk 但不跑 installer**（推荐） | 它已经有网络与工具链，且我们已经在传输它；只需传一个不同的 init 参数 |
| 自建一个最小 initramfs | 更小更快；但要自己维护驱动集合 —— 而新网卡与新存储控制器的驱动是持续的负担 |

**推荐第一种。** 理由：驱动覆盖是自建 initramfs 最大的隐性成本，
而 installer ramdisk 的驱动集合由发行版维护。**代价是它比必需的大** ——
但传输那几十 MB 不是瓶颈（附录 A.4 提到千兆网下几百 MB 的镜像数秒下完）。

**写盘流程的五步：**

1. 从网关取写盘脚本（内含目标盘、镜像 URL、校验值）
2. 流式下载并解压镜像，**直接写到目标盘** —— 不落地到临时文件
3. **写完后校验**：重读写入的数据算 sha256 与清单比对
4. 按清单里的分区布局描述扩展分区
5. 挂载新系统的根分区，落进 firstboot 脚手架与凭据

**第 2 步的「不落地」是必须的：** 目标机器可能没有足够的临时空间放一个几 GB 的文件，
且落地会让写盘时间翻倍。

**第 3 步的回读校验不能省。** 写盘是这条通道唯一的破坏性操作 ——
静默的写入错误（坏道、控制器问题）会产出一个看起来装好但会随机崩溃的系统。
**回读一遍是发现它的唯一方式。**

**第 5 步让镜像直写与 installer 驱动在 firstboot 之后汇合** ——
两条通道的 firstboot 机制相同（§5.8 的脚手架），所以用户的 firstboot hook
在两条通道上行为一致。**这是两条通道唯一的共用部分，要保持。**

**信号点的映射：** 没有 pre/packages/post 三阶段，改为：

| 信号 | 位置 |
|---|---|
| pre-start / pre-done | 取到写盘脚本、准备目标盘前后 |
| packages-start / packages-done | **写盘的前后**（这一步对应装包，是最长的阶段） |
| post-start / post-done | 分区扩展与 firstboot 脚手架落盘的前后 |
| rebooting 及之后 | 与 installer 驱动通道相同 |

**阶段超时预算要复核**（§3.3）：写盘的耗时与装包不同量级 ——
几 GB 的镜像在千兆网下几分钟，而 packages 的预算是 60 分钟。
**预算够用，不需要改** —— 但要在注释里写明这个复核结论，
避免后来者以为忘了调整。

**测试要锁住的行为：**

- 写盘脚本含五步，且写盘是流式的（**脚本里不出现临时文件路径**）
- **回读校验在写盘之后、分区扩展之前**（顺序错了会校验到已被改动的数据）
- firstboot 脚手架与 installer 驱动通道用同一套生成逻辑
- 信号名都在 M1 的信号表内
- 目标盘来自服务端决策（by-id 路径）

**验证：** `go test ./internal/render/ -run TestImageWrite -v` 全过。

**完成标志：** commit `feat(render): image-write channel with read-back verification`

### 任务 5：模板层的通道选择与实机验证

**产出文件：** `internal/console/template.go`（扩展）、
`deploy/verified-imagewrite-<日期>.md`

**为什么需要这一步：** 两条通道并存要让运维能选，且选择要有默认值。

**模板上指定通道**（任务 1 已加字段）。**默认值的选择：**

**默认 installer 驱动。** 理由：它是兜底通道，对新 OS 版本与特殊机型总是可用；
而镜像直写要求那个版本已经封装过。**默认选一个可能没有制品的通道会让建任务失败**，
而运维不一定知道为什么。

**建任务时的校验：** 选了镜像直写但该版本没有对应制品集时，
**错误文案要说明「该版本尚未封装镜像，可改用 installer 驱动」** ——
给出可行的下一步，而不只是报错。

**实机核对清单：**

- [ ] 镜像直写装完一台机器，系统可正常启动
- [ ] **回读校验生效**：故意用一个 sha256 不符的清单，确认写盘后被拒绝
- [ ] 分区扩展后根分区占满整盘
- [ ] **同一个 firstboot hook 在两条通道上行为一致**（这是共用部分的验证）
- [ ] 两条通道的装机耗时对比记录下来 —— **这是「镜像直写作主力」这个定位的依据**，
      若实测没有明显优势，那个定位要重新考虑
- [ ] 签名校验：用一个未签名或签名错误的镜像，确认导入被拒绝

**倒数第二条是对整个 Phase 3 这一部分的价值验证。** §11 把镜像直写定位为
「覆盖批量与一致性要求」的主力 —— 若实测发现它只比 installer 驱动快一点，
那这条通道的维护成本（封装流水线、签名体系、第二套写盘逻辑）就不划算。
**把数据记下来，让这个定位有据可依。**

**完成标志：** commit `feat(console): template channel selection with verification record`

## desync 增量传输：**本期不做，只留调研结论**

§11 把它放在 Phase 4 且标注「仅在实测有收益时」。附录 A.11 确认了它的技术事实
（是 casync 格式的 Go 实现、可互操作、带 Go 库 API、命令行非直接替换），
**但附录 B 明确写「实际场景下的 chunk 复用率与流量节省量级需自行实测，
本轮相关论断被否决」。**

**本任务只做一件事：把任务 5 记录的镜像大小与传输耗时整理成 Phase 4 的输入。**

判断依据：**增量传输的收益取决于 chunk 复用率**，而复用率取决于
「相邻两个镜像版本有多少相同内容」。若机房里同时在用的镜像版本只有两三个、
且每个都装几十台机器，那**同一镜像的重复传输才是大头** ——
那是缓存（P2-04）该解决的问题，不是增量传输。

**增量传输真正有价值的场景是「镜像版本频繁小幅更新」。**
把任务 5 的数据加上一个观察项：**镜像版本的更新频率与每次更新的内容变化量**。
有了这两个数才能算出复用率。

**完成标志：** 数据整理进 `docs/phase4-desync-输入数据.md`

## 边界提醒

**不要让镜像直写取代 installer 驱动。** §11 写明了分工：
installer 驱动作兜底，覆盖新 OS 版本、特殊机型、调试。

**具体的三个场景：** 新 OS 发布当天机房就要装它（镜像还没封装）；
某个机型的网卡在镜像里没驱动（要在 installer 里现场加）；
装机失败要停在 shell 里查（§2.3 的失败处置 —— 镜像直写的环境里没有 installer 的诊断工具）。

**这三个场景都是「少数但关键」的** —— 它们出现时若只有镜像直写通道，
运维就只能手工装机，而那意味着这套系统在最需要它的时候不可用。
