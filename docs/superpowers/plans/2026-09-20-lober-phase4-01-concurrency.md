# P4-01 并发限流、失败重试与告警接入 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成。与 P4-02、P4-04 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 让系统在「一批机器同时上架」这个真实场景下不退化。

**架构：** 三件相对独立的事。限流是状态机层的准入控制（不是 HTTP 层的 —— 见任务 1）；
失败重试是扫描循环的扩展；告警接入是 Notify provider 的实际使用。

**这份计划在 Phase 4 里优先级最高。** §10 的运维点明确列了
「并发装机打满 HTTP」这个失败模式，而它的触发条件是本系统的常规用法 ——
一次上架几十台机器（§3.2 提到批量装机是常态）。

**技术栈：** 状态机层的计数与排队；沿用 Phase 1 的扫描循环与 Notify provider

**SPEC 依据：** §10 的两个运维点、§11 Phase 4、§3.3 扫描循环、§7.4 Notify 的失败语义

### 任务 1：并发上限与排队

**产出文件：** `internal/statemachine/admission.go`、对应测试、配置扩展

**为什么需要这一步：** §10 的运维点：**并发装机打满 HTTP。**
一批机器同时上电时，几十台同时拉几 GB 的仓库会让传输全部变慢 ——
而慢到超过阶段预算时，它们会一起超时失败。**失败的原因看起来是超时，
实际是带宽争抢** —— 这类故障极难从单台机器的日志看出来。

**限流做在状态机层，不是 HTTP 层。** 这是本任务最重要的设计决定。

**三条理由：**

1. **HTTP 层的限流（nginx 的那种）只能拒绝请求，而拒绝一个引导请求意味着
   那台机器要么停在 iPXE 要么进 shell** —— 都不是好结果。状态机层可以让它
   「拿到 no_task 载荷回本地盘或继续轮询」，机器会自己再来（§4.2 的常态行为）
2. **要限的是「同时在装的机器数」而不是「每秒请求数」。** 前者与带宽占用直接相关，
   后者不相关 —— 一台机器拉仓库时请求频率很低但带宽占满
3. **状态机知道任务状态，HTTP 层不知道。** 判断「现在有几台在装」需要查状态

**判定的位置：开始引导那一步**（签发 token 之前）。
超过上限时**返回一个「稍后再来」的结果，让网关回 no_task 载荷** ——
那台机器会继续 PXE 轮询并在下一轮再试（固件的正常行为，§0.1 第一条）。

**关键细节：超限时不要消耗 attempt 计数，也不要置失败。**
理由与 precheck 失败相反 —— precheck 失败是「重试必然同样失败」，
而超限是「稍后重试就会成功」。**消耗 attempt 的后果是三轮排队之后任务失败，
而它本该只是等一会儿。**

**计数的口径：** 状态在 booting 或 installing 的任务数。
**不计 rebooting 与 initializing** —— 那两个阶段不占带宽
（机器在重启或在跑初始化脚本）。

**上限的默认值要给一个保守的数并说明怎么调**：
它取决于机架上行带宽与单机的仓库拉取量。**在配置注释里给出估算方法** ——
用 P2-04 任务 5 的实测数据（单机传输量与链路带宽）算。

**一条要避免的实现方式：不要用内存计数器。**
进程重启后计数会丢，而重启期间已经在装的机器仍在占带宽 ——
重启后放行一批新机器会造成真正的拥塞。**每次判定时查库计数**，
任务表是百级，这个查询很便宜。

**测试要锁住的行为：**

- 未达上限时正常签发 token
- **达到上限时返回「稍后再来」，且 attempt 未增加、任务仍是 pending**
- 计数只算 booting 与 installing 两个状态
- **进程重启后计数正确**（用一个预置了在装任务的库验证）
- 上限设为 0 时表示不限（向后兼容 Phase 1 的行为）

**验证：** `go test ./internal/statemachine/ -run TestAdmission -v` 全过。

**完成标志：** commit `feat(statemachine): concurrency admission with retry-friendly rejection`

### 任务 2：排队的可观测性

**产出文件：** `internal/console/task.go`（扩展）、事件写入

**为什么需要这一步：** 限流生效时，运维看到的现象是「建了任务但机器一直没开始装」——
**与「机器没上电」的表现完全一致**。不给可观测性就是制造一个新的排查难题。

**两处要加：**

1. **被限流拒绝时写一条事件**（不改状态，只记事件）。
   文案要写明「因并发上限排队中，当前在装 N 台，上限 M 台」
2. **任务列表的 pending 状态要能区分两种情形**：
   「等待机器引导」与「已被机器请求但因并发上限排队中」

**第 2 条的实现方式：** 不加新状态（那会破坏 §3.1 的状态机），
而是在任务详情里根据「最近是否有被拒事件」判断并显示。

**这条不加新状态的约束要写进注释** —— 加一个 `queued` 状态很诱人，
但它会让状态机多一条转换、让 §3.4 的重装判定多一个分支、
让 M8 的文案多一种情形。**而收益只是省掉一次事件查询。**

**一个容易过度的地方：不要为每次被拒都写事件。**
一台机器在 PXE 轮询下每隔几十秒就会请求一次 —— 每次都写事件会让事件表爆掉。
**做法：同一任务在一段时间窗口内只写一条**（比如五分钟），
后续的被拒只更新那条事件的时间戳或干脆忽略。

**测试要锁住的行为：**

- 被拒时写事件，文案含当前数与上限
- **同一任务在窗口内不重复写事件**
- 任务详情能区分两种 pending 情形
- **未新增状态**（状态机的状态集合不变）

**验证：** `go test ./internal/statemachine/ ./internal/console/ -run TestQueueVisibility -v` 全过。

**完成标志：** commit `feat(console): surface admission queueing without a new state`

### 任务 3：信号端点的限流上限

**产出文件：** `deploy/nginx/lober.conf`（调整）

**为什么需要这一步：** §10 的第二个运维点：**心跳与信号回调量不小**
（数百台 × 每 30 秒）。P2-04 已经给信号端点分了独立的限流桶，
**但没有设上限** —— 分桶只防止它挤掉引导端点，不防止它自己打满。

**要加的是桶的速率与突发上限。**

**估算方法要写进配置注释：** 单台机器的信号数是固定的
（§6.1 的十一个流程信号加每个 hook 一次上报），而装机过程是几十分钟 ——
所以单机的信号频率很低。**真正的峰值来自「一批机器同时进入同一阶段」**，
那会产生一个尖峰。

**所以突发上限要给得宽松，速率可以给得紧。**
这与常规的限流直觉相反 —— 因为这里的流量是尖峰型而非持续型。

**一条不能设错的：超限时的返回码。**
nginx 默认返回 503。**机器侧的上报函数会重试三次然后放弃**（§6.3），
而放弃的后果是那个阶段的信号丢失 —— 状态机会停在上一个阶段直到超时。

**所以信号端点的限流上限必须给得足够宽**，宁可让它偶尔打满 HTTP
也不要丢信号 —— **丢信号会造成一个假失败，而那比传输慢严重得多。**

**要在配置注释里写明这个取舍。**

**验证：** `nginx -t` 通过；**用一批并发请求验证限流生效但正常装机流量不受影响**。

**完成标志：** commit `deploy(nginx): signal endpoint rate limit tuned for burst traffic`

### 任务 4：失败重试

**产出文件：** `internal/statemachine/scan.go`（扩展）、配置扩展

**为什么需要这一步：** §11 Phase 4 列了「失败重试」。
但**这一项要非常小心** —— 自动重试的对象是「擦盘重装」。

**核心约束：只有可重装的失败原因才能自动重试**（§3.4）。
Phase 1 的 `Reinstallable()` 判定已经是权威，**本任务直接用它，不要另写判断。**

**三条限制，缺一条都不能上这个功能：**

1. **只自动重试 attempt 未达上限的任务** —— 否则会无限重装
2. **要有一个独立的开关，默认关闭。** 自动重装是一个需要运维明确同意的行为
3. **自动重试的次数要有独立上限**，且比手工重试严格 ——
   建议自动只重试一次，之后必须人工介入

**第 2 条的默认关闭是刻意的。** §3.2 已经说明「建任务即授权」的残留风险
（那台机器一旦网络启动就会装机，而本系统没有远程关机手段）——
**自动重试把那个风险窗口从「一次」变成「多次」**，
而运维可能没意识到自己开启了这个行为。

**自动重试要写审计记录**，操作人记为系统而非某个用户。
**理由：误装事故的追溯需要能区分「人建的任务」与「系统自动重试的任务」**（P4-04 的报表依据）。

**哪些失败值得自动重试？** 建议只对两种：

| 失败原因 | 为什么值得 |
|---|---|
| booting 超时 | 常见原因是网络抖动或制品传输失败 —— 重试大概率成功 |
| 安装阶段失败且退出码指向瞬时问题 | 比如仓库暂时不可达 |

**precheck 失败不要自动重试** —— §4.6 说「重试必然同样失败」。
**required hook 失败也不要** —— 那是脚本或环境的确定性问题。

**所以自动重试的判定是两层：先看可否重装，再看是否在「值得自动重试」的白名单里。**

**测试要锁住的行为：**

- 开关默认关闭时不自动重试
- **三种不可重装的失败原因永不自动重试**（即使开关开启）
- 只对白名单内的失败原因自动重试
- 自动重试次数有独立上限，用尽后不再重试
- **自动重试写审计记录，操作人是系统**
- attempt 达上限的任务不自动重试

**验证：** `go test ./internal/statemachine/ -run TestAutoRetry -v` 全过。

**完成标志：** commit `feat(statemachine): opt-in auto-retry for transient failures only`

### 任务 5：告警接入

**产出文件：** `internal/provider/notify.go`（扩展）、配置

**为什么需要这一步：** Phase 1 的 Notify provider 是内置的「记日志」实现。
生产环境要接真的告警系统。

**用 P2-03 的 http 加载器接** —— 不需要新机制。**本任务的工作是把告警内容做对。**

**四类事件要发告警**（§7.5 的生命周期事件里的两个加两个补充）：

| 事件 | 告警等级 | 内容要点 |
|---|---|---|
| 任务失败 | 高 | **失败原因 + 是否可重装** —— 后者决定运维能不能直接点重试 |
| 任务就绪 | 低（或不告警） | 批量装机时这类通知量大，建议汇总而非逐台 |
| **重启超时 / 初始化失败** | **高，且文案必须与「装机失败」区分** | §3.4 明确：两者处理方式完全不同（前者不能重装） |
| provider 熔断 | 中 | P2-03 的熔断状态，运维要知道外部系统挂了 |

**第三行是本任务的核心要求。** §3.4 的原话：
「告警文案要与『装机失败』明确区分 —— 两者处理方式完全不同」。

**具体差异：** 装机失败的机器可以直接重试；
**重启超时或初始化失败的机器已经装好了，重试会擦盘** ——
告警文案里要写「该机器系统已安装完成，请勿重装，需人工登录处理」。

**告警内容要含 §3.5 的诊断字段** —— 至少阶段、失败原因、
**距上次信号多久**（那一项区分「机器活着但脚本错了」与「机器层面出事」）。

**一条降噪要求：同一任务的同一失败不重复告警。**
扫描循环每 30 秒跑一次，若实现不当会对同一个失败任务反复告警。
**做法：告警在状态转换到 failed 的那一刻发一次**，不在扫描时发。

**测试要锁住的行为：**

- 四类事件各自触发告警
- **不可重装的失败，告警文案含「请勿重装」的明确提示**
- 告警内容含诊断字段
- **同一失败不重复告警**
- 告警发送失败不影响任务状态（§7.4 的只告警语义）

**验证：** `go test ./internal/provider/ -run TestNotifyAlerts -v` 全过。

**完成标志：** commit `feat(provider): alert routing with reinstall-safety wording`

## 一条要想清楚的取舍

**限流与「尽快装完」是矛盾的。** 限流会让一批机器分批装完，总耗时变长。

**但不限流的后果不是「都慢一点」，而是「一批都失败」** ——
因为阶段超时预算是固定的（§3.3），带宽争抢会让传输时间超过预算。

**所以这个取舍的本质是：宁可慢，不要失败。**
失败的机器要人工介入（查日志、判断能否重试、重新触发），
而那个人工成本远高于多等十分钟。

**若运维反馈「太慢了」，正确的应对是提高带宽或加机架缓存（P2-04），
不是放开限流。**
