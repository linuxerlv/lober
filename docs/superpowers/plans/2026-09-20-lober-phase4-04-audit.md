# P4-04 审计报表 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成。与 P4-01、P4-02 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 让「误装事故之后能快速回答发生了什么」成为可能。

**架构：** Phase 1 已经在写审计记录（M6 的审计中间件）与任务事件（append-only）。
**本计划不新增采集，只做查询与导出** —— 这是它工作量小但价值明确的原因。

**这份计划的驱动场景很具体：一台生产机被误装了。**
运维要在几分钟内回答四个问题 —— 而 Phase 1 的数据里有答案，
但要靠翻数据库或 grep 日志。**本计划把那四个问题做成报表。**

**技术栈：** 沿用 Phase 1 的审计表与事件表；导出用 CSV

**SPEC 依据：** §9.4 权限分级、§11 Phase 4、§12.4 水印带操作人、§2.5 事件表

---

## 驱动场景：误装事故的四个问题

这四个问题决定本计划做什么。它们的共同点是**都要跨表关联**，
而单表查询答不出来。

| 问题 | 需要关联什么 |
|---|---|
| **谁在什么时候建了那个任务？** | 审计表的建任务记录 + 任务表 |
| **当时选的是哪台机器、哪个模板、哪个制品集？** | 任务表的 pin 字段 + 三张引用表 |
| **那个任务用了哪些 hook？谁写的、谁批的？** | 任务的 hook digest 列表 + hook 表的作者与审批人 |
| **从建任务到擦盘之间发生了什么？** | 事件表的完整时间线 |

**第三个问题是最容易答不出的。** 任务 pin 的是 hook 的 digest（§2.6），
而要从 digest 反查「谁写的、谁批的」需要查 hook 表 ——
Phase 1 有这个能力（按 digest 反查），但没有把它接进一个面向事故的视图。

### 任务 1：任务溯源视图

**产出文件：** `internal/console/audit.go`（扩展）、对应测试

**为什么需要这一步：** 把上面四个问题做成一个端点，输入是任务 id。

**返回的五块：**

1. **创建信息**：操作人、时间、客户端 IP（从审计表取）
2. **pin 的三项**：模板与版本、制品集、hook digest 列表 ——
   **每项都要解析成可读信息**（模板名、制品集名、hook 名与作者与审批人）
3. **完整事件时间线**（从事件表取，含非信号来源的事件）
4. **失败详情**（若失败）：§3.5 的六个字段
5. **后续操作**：重试、取消等（从审计表取，含 P4-01 的自动重试）

**第 2 块的解析是本任务的核心价值。** 光给 digest 与版本号，
运维还要自己去查三张表；解析好了就是一屏能看完的信息。

**一个数据完整性问题要处理：被引用的对象可能已被停用或删除。**
§2.7 保证了「被 active 模板引用的不能删」，但**模板本身可以在任务终态后被删**。
**此时溯源视图要显示「该模板已删除」并给出 pin 的版本号** ——
而不是报错或显示空白。

**这条要有测试。** 事故往往发生在几个月后，而那时相关对象可能已经清理过。

**权限：** 溯源视图含操作人信息，**建议只给管理员与审计角色**。
但要注意：§9.4 没有定义「审计角色」—— **若需要它，那是一个契约变更**（角色表加一项）。
**建议先只给管理员**，等真有专职审计人员时再加角色。

**测试要锁住的行为：**

- 五块内容都返回，pin 的三项都解析成可读信息
- hook 的作者与审批人正确关联
- **被引用对象已删除时显示提示而不是报错**
- 含自动重试的操作记录
- 非管理员访问被拒

**验证：** `go test ./internal/console/ -run TestTaskProvenance -v` 全过。

**完成标志：** commit `feat(console): task provenance view resolving all pinned references`

### 任务 2：操作审计查询

**产出文件：** `internal/console/audit.go`（扩展）、对应测试

**为什么需要这一步：** 另一个方向的问题：**「某个人在某段时间做了什么」**
（人员变动或权限审查时要用）。

**查询条件四项：** 操作人、时间范围、动作类型、目标资源。

**四项都可选且可组合。** 常用组合：某人某段时间的全部操作、
某类动作（比如全部的建任务）的全部记录。

**要处理的一个规模问题：审计表会持续增长。**
每次写操作一条记录，而装机高峰期一天可能几百条。
**几年后它会有几十万条** —— 查询要有索引（Phase 1 的 schema 已有时间索引）
与分页（M1 契约的分页约定：默认上限 1000）。

**不做的一件事：审计记录的清理或归档。**
理由：审计数据的保留期是合规要求而非技术决定 ——
**在不知道那个要求之前不要实现自动清理**，误删审计记录是不可恢复的。
**要在文档里写明这一点**，并给出手工归档的建议做法。

**测试要锁住的行为：**

- 四项条件各自与组合生效
- 分页正常，默认上限生效
- 时间范围的边界包含性明确（**左闭右开还是全闭要定死并写进注释**）
- 非管理员访问被拒

**验证：** `go test ./internal/console/ -run TestAuditQuery -v` 全过。

**完成标志：** commit `feat(console): audit log query with composable filters`

### 任务 3：装机统计报表

**产出文件：** `internal/console/report.go`、对应测试

**为什么需要这一步：** 前两个任务面向事故，这个面向日常 ——
**运维要能回答「这个月装了多少台、失败率多少、失败集中在哪个阶段」**。

**三张报表：**

| 报表 | 内容 | 用途 |
|---|---|---|
| 装机量 | 按时间段的任务数，按状态分组 | 容量规划、汇报 |
| **失败分布** | 按失败原因分组的计数与占比 | **找出最需要改进的环节** |
| 阶段耗时 | 各阶段的耗时分布（中位数与高分位） | 发现哪个阶段变慢了 |

**第二张最有价值。** §3.4 的失败原因分类是有诊断含义的 ——
若失败集中在「引导超时」说明网络或制品传输有问题，
集中在「required hook 失败」说明某个 hook 不可靠，
集中在「precheck」说明建任务时经常选错机器（**那是 §10 失败模式 2b 的信号**）。

**所以失败分布报表要能下钻到具体任务** —— 看到「precheck 失败 12 次」之后，
运维要能点进去看是哪 12 个任务、是不是同一个人建的。

**第三张的实现要注意：阶段耗时要从事件表算，不是从任务表。**
任务表只有当前阶段的进入时间，而完整的阶段耗时要靠事件的时间差。
**这意味着一个任务的阶段耗时只有在它有完整事件序列时才能算** ——
中途失败的任务只有部分阶段有数据，**报表要正确处理这种情况**（跳过而非算成 0）。

**一条统计口径要定死：用中位数与高分位，不用平均值。**
理由：装机耗时的分布是长尾的（少数机器因重试或慢盘耗时远超常规），
**平均值会被那些异常值拉高到没有参考价值**。

**测试要锁住的行为：**

- 三张报表各自正确
- **失败分布能下钻到任务列表**
- **阶段耗时正确跳过数据不完整的任务**（不算成 0）
- 统计用中位数与高分位
- 时间段边界的包含性与任务 2 一致

**验证：** `go test ./internal/console/ -run TestReports -v` 全过。

**完成标志：** commit `feat(console): provisioning reports with failure-reason breakdown`

### 任务 4：CSV 导出

**产出文件：** `internal/console/export.go`、对应测试

**为什么需要这一步：** 报表要能带出系统 —— 汇报、离线分析、
或提交给审计方。

**三个导出入口：** 审计查询结果、装机统计、任务溯源。

**格式选 CSV 而非 Excel 或 PDF。** 理由：
CSV 无需第三方库（标准库有）、能被任何工具打开、
**在气隙环境里不依赖任何外部渲染服务**。

**四条实现要求：**

1. **流式写出，不在内存里拼完整文件** —— 几十万条审计记录会撑爆内存
2. **带 UTF-8 的字节顺序标记** —— 否则某些表格软件打开中文会乱码。
   **这是国内环境的实际需求**，不加的后果是运维拿到一个乱码文件
3. **导出动作本身要写审计** —— 导出审计记录是一个敏感操作
4. **列名用中文**（面向运维），但**文件名用英文加时间戳**（避免跨平台的文件名问题）

**第 2 条容易被认为是多余的** —— 但它是「运维能直接用」与「运维要先转码」的区别。

**一个规模保护：导出要有行数上限**（比如十万行），
超过时提示缩小时间范围。**理由：一个无界的导出请求会占满连接与磁盘 IO** ——
而那会影响正在装机的机器（同一个进程）。

**测试要锁住的行为：**

- 三个入口都能导出，格式是合法 CSV
- **含字节顺序标记**
- 流式写出（**用一个大数据集验证内存占用不随行数线性增长**）
- 导出动作写审计
- 超过行数上限时提示而非截断（**截断会产出一个看起来完整但不完整的文件**）

**验证：** `go test ./internal/console/ -run TestExport -v` 全过。

**完成标志：** commit `feat(console): streaming CSV export with BOM for local tooling`

### 任务 5：报表页面

**产出文件：** 前端报表页（`web/apps/web-ele/src/views/reports/`）

**为什么需要这一步：** 三张报表加两个查询要有界面 —— 否则只有 API 会让它们不被使用。

**一个页面四个标签：** 装机统计、失败分布、审计查询、任务溯源。

**失败分布要做成可下钻的** —— 点一个失败原因跳到过滤后的任务列表。
**这是这张报表的主要用法**，不可下钻就只是一个数字。

**任务溯源的入口要放在任务详情页上**，而不只在报表页 ——
事故排查时运维是从任务详情页开始的。

**图表的取舍：装机量与阶段耗时用图表，失败分布用表格。**
理由：失败分布的每一行都要能点击下钻，而图表的点击目标不如表格清晰。

**一条气隙要求**（§12.4）：**若要引入图表库，确认它是本地依赖而非 CDN 加载**。
M8 的任务 3 删掉了仪表盘，而那是「唯一用图表库的地方」——
**所以图表库可能已经不在依赖里了**。若要用它，要重新加进依赖并跑一遍气隙三检查。

**或者：用 CSS 画简单的条形图。** 两张图表都是简单形态
（时间序列的柱状与耗时的分布），不值得为它们引入一个图表库 ——
**而引入的代价是气隙环境下多一个要检查的依赖**。

**建议用 CSS 方案**，并在注释里写明理由。

**权限：** 报表页只给管理员（与任务 1、2 的端点权限一致）。

**验证：** 四个标签都能用；失败分布可下钻；气隙三检查无匹配。

**完成标志：** commit `feat(web): reports page with drill-down failure breakdown`

## 这份计划为什么值得做

**它不加任何装机能力，但它决定事故之后的处置速度。**

§3.2 承认了一个残留风险：建任务即授权，而选错 SN 的后果是一台生产机被擦盘
（§10 失败模式 2b）。**那个风险没有被消除，只是被缓解了**
（SN 从清单选、MAC 双因子、建任务确认框显示三项）。

**所以事故迟早会发生一次。** 而那时的两个问题是：
**发生了什么，以及怎么防止再次发生。**

第一个问题靠任务溯源回答。第二个问题靠失败分布报表 ——
若 precheck 失败集中在某个人建的任务上，那是培训问题；
若集中在某个机型上，那是 discovery 记录的固件模式不准。
**没有报表，这两种情况看起来一样。**
