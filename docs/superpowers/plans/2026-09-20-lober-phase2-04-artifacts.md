# P2-04 制品授权与带宽 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成。与 P2-01 至 P2-03、P2-05 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 给大制品加签名授权（HMAC 加过期），并在实测出带宽瓶颈后加每机架缓存。

**架构：** 签名由 Go 签发、由 nginx 校验 —— **Go 完全不在数据路径上**（§9.3）。
缓存是机架内一个 nginx 反代，回源到中心。两件事都是部署层的改动加少量 Go 代码。

**这个计划的后半部分有开工前提。** SPEC §11 把每机架缓存标注为
「**实测出带宽瓶颈后**」再做 —— 在没有数据前做缓存是猜测性优化，
而它引入的故障模式（缓存不一致、回源风暴）是真实的。**任务 5 是收集依据。**

**技术栈：** nginx 的签名链接模块与代理缓存；Go 侧只做 HMAC 签发

**SPEC 依据：** §9.3 制品授权分三类、§1.4 nginx、§10 运维点「并发装机打满 HTTP」、
§11 Phase 2

## 制品授权分三类，不要试图统一

§9.3 把制品按授权方式分三类。**统一处理是做不到的**，理由各自不同：

| 类别 | 授权方式 | 为什么只能这样 |
|---|---|---|
| 离线仓库（RPM / deb 包） | **开放，不授权** | installer 按仓库元数据自行构造 URL 拉取几万个包，**无法让它给每个 URL 带签名**；而内容本就是公开的 |
| 大制品（内核、initrd、镜像、WIM） | nginx 签名链接（HMAC 加过期） | Go 只签发 URL，完全不在数据路径上 —— 4 GB 镜像流经 Go 进程会让零拷贝失效（§1.4） |
| 少量敏感大文件 | 由 Go 校验后交 nginx 发字节 | 无需额外模块，但每文件多一次往返 |

**Phase 2 只做第二类。** 第一类不做（开放是正确的），
第三类 MVP 与 Phase 2 都没有这类文件 —— 等真有了再做。

**一个要想清楚的问题：这层授权防的是什么？**

不是防「外人下载内核」（那没有价值）。**防的是 token 横向传播** ——
把签名绑定到客户端 IP 后，一台机器的引导 URL 不能被另一台机器使用。
在 MVP 无 TLS 的前提下（§1.5），这减小了「装机 VLAN 上已失陷主机」这个风险面。

**所以签名里绑 IP 是这个功能的核心，不是可选项。** 但它带来两个边缘情况，见任务 2。

### 任务 1：签名签发

**产出文件：** `internal/gateway/siglink.go`、对应测试

**为什么需要这一步：** 渲染菜单时要把制品 URL 换成带签名的 URL。

**签名的三个输入：** 过期时间戳、URI 路径、客户端 IP，加一个共享密钥。
**顺序与分隔必须与 nginx 的校验配置完全一致** —— 差一个字符就恒不匹配，
而现场表现是「机器取制品一律 403」。

**哈希算法与编码：** nginx 那个模块用 MD5 加 base64url，并且要求**去掉填充字符**。
**这里有两处容易错**：用了标准 base64（含加号与斜杠，在 URL 里会被转义）、
或保留了填充等号。两者都会让校验失败。

> **MD5 在这里是 nginx 模块的要求，不是我们的选择。** 它用于防篡改而非防碰撞 ——
> 攻击者要伪造一个签名需要知道密钥，而 MD5 的碰撞弱点对 HMAC 式用法影响有限。
> **要在注释里写明这一点**，否则后来者会以为是疏忽而去「改进」它，
> 而改了就与 nginx 的校验对不上。

**密钥从配置来**，且**启动时校验非空与最小长度**。
空密钥的后果是所有人都能算出签名 —— 而功能看起来完全正常。

**客户端 IP 的取法与 Phase 1 一致**：只在直连 peer 是 loopback 时信任 nginx 注入的头部
（§1.6）。**这条在这里尤其要紧**：Go 签发时看到的 IP 与 nginx 校验时看到的必须是
同一个，否则签名恒不匹配（§1.6 明确指出了这个陷阱）。

**过期时间的取值：** 要覆盖整个装机窗口内的制品下载。
**不要用装机 token 的 90 分钟** —— 制品下载可能在装机后期（比如 Ubuntu 的
squashfs），而签名过期会让下载失败且无法重试。**建议给装机 token 的两倍**，
并在注释里写明理由。

**测试要锁住的行为：**

- 签名的三个输入任一改变则签名改变
- **编码是 base64url 且无填充字符**
- 密钥为空或过短时构造失败
- 过期时间戳的计算正确（用可控时钟）
- **同一输入两次签发结果相同**（确定性 —— 否则无法与 nginx 对齐）

**验证：** `go test ./internal/gateway/ -run TestSignedLink -v` 全过。

**完成标志：** commit `feat(gateway): signed artifact URLs bound to client IP`

### 任务 2：两个边缘情况的处置

**产出文件：** `internal/gateway/siglink.go`（扩展）、配置与文档

**为什么需要这一步：** 绑 IP 带来两个真实的失效场景（§9.3 末段明确提到）。

**边缘情况一：路径上有 NAT。**

若网关与机器之间有 NAT，nginx 看到的是 NAT 后的地址，而那可能与 Go 签发时看到的不同 ——
**签名恒不匹配，所有机器都取不到制品**。

**处置：给一个「不绑 IP」的配置开关。** 默认绑（安全性优先），
但允许在有 NAT 的环境关掉。**关掉时要在启动日志里打一条明确的告警** ——
说明 token 横向传播的防护已失效，这样运维知道自己放弃了什么。

**不要试图自动检测 NAT。** 检测不可靠，而一个误判会让整个机房装不了机。
让运维显式配置。

**边缘情况二：装机过程中 IP 变化。**

机器在「取引导脚本」与「取制品」之间更换了 DHCP 租约导致 IP 变化时，签名失效。

**处置：租约时间设得长于装机窗口。** 这是部署配置项 ——
Phase 1 的 dnsmasq 配置里已经写了「租期必须长于装机窗口」，本任务要把理由
补充完整（原来只提到将来上签名会失效，现在那个「将来」到了）。

**另一个诱因要写进文档：`booted` 之后的信号源 IP 会变**（§5.7：
重启后业务网生效）。**但那时制品下载已经结束** —— 所以这个变化不影响签名。
要写清这一点，否则会有人以为需要为重启后阶段也签发 URL。

**测试要锁住的行为：**

- 不绑 IP 的开关生效（签名不含 IP 分量）
- **开关关闭时启动日志有告警**
- 绑 IP 时不同 IP 得到不同签名

**验证：** `go test ./internal/gateway/ -run TestSignedLinkNAT -v` 全过。

**完成标志：** commit `feat(gateway): opt-out of IP binding for NAT environments`

### 任务 3：nginx 校验配置

**产出文件：** `deploy/nginx/lober.conf`（修改制品 location）

**为什么需要这一步：** 签名的校验在 nginx 侧，配置与 Go 的签发逻辑必须逐字符对齐。

**要改的是制品 location**：加签名校验指令、加签名串的构造表达式、
加两个判定分支。

**两个判定分支的语义不同，都要有：**

| 判定结果 | 含义 | 返回 |
|---|---|---|
| 空 | 签名不匹配或格式错误 | 403 |
| 零 | **签名正确但已过期** | 410 |

**区分这两个是有价值的：** 403 说明签名算错了（配置不一致或有人乱试），
410 说明是时间问题（过期时间设太短）。合并成一个码会让排查多走一圈。

**离线仓库的 location 不加校验**（§9.3 第一类，开放）。
**这条要在配置注释里写明理由**，否则会有人「顺手统一」了而导致 installer 拉包全失败 ——
而那个故障发生在装机中期，日志里是几万条 403。

**编译依赖：** 签名链接模块不是默认编译进去的。
**Phase 1 的部署文档已经要求确认这一项**，本任务要把它从「Phase 2 才需要」
改成「现在需要」。若发行版的 nginx 包没带这个模块，两个选择：
换一个带的包，或改用第三类授权方式（Go 校验后交 nginx 发字节）。
**在部署文档里写清这个岔路**。

**验证：** `nginx -t` 通过；**用 Go 签发一个 URL，用 curl 实际取一次确认 200**；
改一个字符后确认 403；用一个已过期的时间戳确认 410。

**完成标志：** commit `deploy(nginx): secure link validation for large artifacts`

### 任务 4：签名的端到端验证

**产出文件：** `scripts/e2e.sh`（扩展）

**为什么需要这一步：** 签发与校验分在两个进程里（Go 与 nginx），
**单元测试无法覆盖「两边对齐」这件事** —— 而那正是最容易错的地方。

**扩展端到端脚本，加三个断言：**

1. 菜单里的制品 URL 带签名参数
2. **用那个 URL 实际取一次制品，返回 200**
3. **把签名改一个字符后取，返回 403**

第 2 条是核心。它要求端到端脚本的环境里有 nginx —— 而 Phase 1 的脚本只起 Go。

**两个选择，选一个并说明理由：**

| 方案 | 取舍 |
|---|---|
| 脚本里起一个 nginx | 覆盖真实校验；但依赖开发机装了 nginx 与那个模块 |
| **在 Go 侧写一个模拟校验的测试**（推荐作为补充） | 无外部依赖；但验证的是我们对 nginx 行为的理解，不是 nginx 本身 |

**建议两者都做：** Go 侧的模拟校验进 `make check`（每次提交都跑），
起 nginx 的完整验证作为一个独立的手工步骤记进部署核对清单
（**它属于部署期一次性核对** —— 配对一次之后签名逻辑不再变）。

**要在脚本注释里写明这个分工**，否则后来者会以为 `make check` 已经覆盖了
nginx 的行为。

**验证：** 扩展后的端到端脚本通过；手工用 nginx 验证一次并记进核对清单。

**完成标志：** commit `test(e2e): signed artifact URL verification`

### 任务 5：带宽实测 —— 决定要不要做缓存

**产出文件：** `docs/phase2-带宽实测.md`

**为什么需要这一步：** SPEC §11 把每机架缓存标注为「实测出带宽瓶颈后」再做。
**在没有数据前做缓存是猜测性优化**，而它引入的故障模式是真实的（见任务 6）。

**要测的四项：**

1. **单机装机的制品传输量**：内核加 initrd 加仓库拉包，实际下载了多少字节
   （nginx access log 里的字节数字段可以直接统计 —— Phase 1 的日志格式已经带上了）
2. **并发装机时中心节点的出口带宽占用**：一批机器同时装时的峰值
3. **单机装机的耗时分布**：其中传输占多少，安装动作占多少
4. **机架到中心的链路带宽**：这是缓存能改善的上限

**判断是否需要缓存的依据：**

**并发峰值接近或超过机架上行带宽时才需要。** 若峰值只用了链路的三成，
缓存带来的收益是「装机快几十秒」，而代价是多一个服务、多一套缓存失效问题。

**另一个更便宜的替代方案要先评估：状态机的并发上限**（§10 运维点「并发装机打满 HTTP」）。
限制同时 provisioning 的机器数并排队，能在不引入新组件的前提下削峰。
**若排队能接受（运维不在意一批机器多花十分钟），就不做缓存。**

**依据不足或结论是不需要时，任务 6 不执行** —— 把判断写进产出文件，
那是一次有记录的决定。

**验证：** 产出文件里四项都有实测数据，且有明确结论（做缓存 / 做并发限流 / 都不做）。

**完成标志：** commit `docs: bandwidth measurements and caching decision`

### 任务 6：每机架缓存（仅在任务 5 结论支持时执行）

**产出文件：** `deploy/nginx/rack-cache.conf`、部署文档章节

**为什么需要这一步：** 任务 5 实测出机架上行带宽成为瓶颈。

**形态：** 机架内一台机器上起 nginx 反代，缓存制品，回源到中心。
**机架内的机器通过 DHCP 拿到指向本机架缓存的制品基址。**

**这意味着制品基址要能按机架不同** —— 而 Phase 1 的基址是全局配置的一个值。
**两种实现方式：**

| 方式 | 取舍 |
|---|---|
| **DHCP 按网段给不同的基址**（推荐） | 零 Go 代码改动；每个机架一个 DHCP 作用域 |
| 网关按客户端 IP 选基址 | 集中配置；但要在渲染时做机架判定，Go 代码要改 |

**推荐第一种。** 理由：机架划分本来就体现在网段上，而 DHCP 已经按网段配置了 ——
让引导链多一层按机架的分流违背 §4.7 的设计（分流点只有三个，职责严格不重叠）。

**缓存配置的四条要点：**

1. **只缓存大制品，不缓存仓库的元数据文件。** 元数据会随仓库更新而变，
   缓存它会让机器拿到过期的包列表 —— 而那个故障的表现是「装机中途报某个包不存在」
2. **缓存键要含完整 URI**（不含签名参数 —— 否则每台机器的签名不同，缓存永不命中）
3. **回源时要透传签名参数** —— 中心的 nginx 仍要校验
4. **缓存容量与淘汰策略**：制品集是几 GB 量级，容量要够放当前在用的两三个制品集

**第 2 条与第 3 条有一个张力要处理：** 缓存键不含签名，但回源要带签名 ——
这意味着**第一个请求的签名被用于回源，之后的命中不校验签名**。
**这削弱了 IP 绑定的防护**（机架内的机器之间可以共用缓存）。

**这个取舍要写进文档并让运维知情：** 机架内的信任边界变成了「整个机架」而非「单台机器」。
若不可接受，就不做缓存而改用并发限流。

**一个新增的故障模式要写进部署文档：回源风暴。**
缓存未命中时多台机器同时回源会放大而非削减中心压力。
nginx 有防止并发回源的选项（让第一个请求回源、其余等待），**必须开启**。

**验证：** 机架内两台机器先后装机，第二台的制品下载命中缓存
（看缓存节点的日志）；中心节点的出口流量显著下降。

**完成标志：** commit `deploy: per-rack artifact cache with origin-storm protection`

## 一条不要做的事

**不要给离线仓库加签名。** installer 按仓库元数据自行构造几万个包的 URL，
无法让它带签名（§9.3）。若有人提出「为了一致性给仓库也加上」，
后果是装机在拉包阶段全面失败，而日志里是几万条 403 ——
排查时很容易误以为是仓库损坏。
