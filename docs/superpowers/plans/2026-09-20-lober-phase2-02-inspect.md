# P2-02 硬件采集与服务端决策 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 1 全部完成。与 P2-01、P2-03 至 P2-05 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 在 `pre` 阶段采集硬件事实上报为 fact，服务端据此决策磁盘与网卡，
再把具体设备标识写进应答文件。

**架构：** 三步 —— 机器侧采集脚本（渲染器骨架生成）、服务端接收与决策、
决策结果回写为 fact 供后续阶段消费。**决策在服务端做，不在机器上做**（§5.6）。

**为什么决策必须在服务端：** 也可以在 `pre` 里用 shell 动态算磁盘，但那把逻辑推到
机器上 —— **失败时无日志可看、无法复现、无法 dry-run**。服务端决策可调试、
可 dry-run、可审计。这是 §5.6 的核心论点，本计划的全部结构都由它决定。

**技术栈：** 机器侧用 installer ramdisk 里必然存在的工具（见任务 1）；
服务端沿用 Phase 1 的 DiskPlanner 接口

**SPEC 依据：** §5.5 facts KV、§5.6 先采集再决策、§10 失败模式 5 与 6

---

## 数据流

```
pre 阶段（机器上）        →  服务端                    →  应答文件（机器上）
采集 lsblk/lspci/         接收 fact、调 DiskPlanner     渲染时写入具体设备标识
dmidecode/ethtool         与网卡决策、结果回写 fact      （by-id / WWN，不是 sda）
```

**中间那一步是本计划的价值所在。** 没有它，模板里只能硬编码 `/dev/sda` 与 `eth0`，
而那两个名字都会漂移（§10 失败模式 5 与 6）。

**一个时序上的硬约束：采集必须在分区之前，而决策结果要在分区时可用。**
这意味着 `pre` 阶段内部要分两段：先采集上报，再等服务端的决策结果，然后才分区。
**第二段是一次同步的 HTTP 读** —— 见任务 4 的取舍。

### 任务 1：采集脚本

**产出文件：** `internal/render/inspect.go`、对应测试

**为什么需要这一步：** 采集脚本由渲染器骨架生成（§5.1 的物理约束：
那是机器本地的动作，服务端只能提供内容）。

**采集四类事实**（§5.6）：

| 类别 | 工具 | 采什么 |
|---|---|---|
| 磁盘 | `lsblk` | by-id 路径、型号、容量、是否旋转盘 |
| 网卡 | `ip` 与 `ethtool` | 名字、MAC、link 状态、PCI 路径 |
| 主板与内存 | `dmidecode` | 厂商、型号、内存容量 |
| CPU | `/proc/cpuinfo` 或 `nproc` | 核心数 |

**工具可用性是第一个要解决的问题。** installer ramdisk 里没有完整的工具集：

- `lsblk` 与 `ip` 在三个家族的 ramdisk 里都有
- **`ethtool` 在 Debian 的 ramdisk 里可能缺失** —— 缺失时降级为只读 `/sys` 下的
  link 状态文件
- **`dmidecode` 在部分精简 ramdisk 里缺失** —— 缺失时降级为读 `/sys/class/dmi/id/` 下的文件

**所以每类采集都要有降级路径，且降级后仍产出同样的 fact 键。**
不降级的后果是 Debian 的采集整体失败，而失败的表现是「磁盘决策拿不到数据」——
那会阻塞装机。

**采集脚本的三条行为要求：**

1. **单项采集失败不中断整体** —— 采到的部分照样上报
2. **输出格式是纯文本键值对**（与 facts 端点的格式一致，§6.2：
   ramdisk 里没有 jq）
3. **磁盘列表要用 by-id 路径**，从 `/dev/disk/by-id/` 反查，
   **优先 WWN 形式**（最稳定）；同一块盘有多个 by-id 链接时选择规则要确定
   （否则两次采集结果不同，决策也就不确定）

**测试要锁住的行为：**

- 生成的脚本含四类采集，每类都有降级路径
- **输出格式是键值对**，键名在 M1 的 fact 命名空间内或是约定的采集专用键
- **单项失败不中断**（用一个不存在的命令验证脚本仍继续）
- by-id 的选择规则确定（同一输入两次得到同一结果）

**验证：** `go test ./internal/render/ -run TestInspect -v` 全过。
**另在实机核对：三个家族的 ramdisk 里采集脚本都能跑出完整结果。**

**完成标志：** commit `feat(render): hardware inspect script with per-tool fallbacks`

### 任务 2：采集事实的接收与解析

**产出文件：** `internal/gateway/facts.go`（扩展）、`internal/provider/hwfacts.go`（新）

**为什么需要这一步：** facts 端点在 Phase 1 已经能收纯文本键值对，
但采集来的磁盘与网卡是**列表**，要从扁平的键值对还原成结构。

**编码约定要定死并写进契约文档：**

磁盘列表与网卡列表用「带序号的键」表达（比如磁盘 0 的型号、磁盘 0 的容量、
磁盘 1 的型号……）。**不要用分隔符拼进一个值** —— 型号字符串里本来就含空格，
而容量是数字，混在一起解析容易出错。

**解析要宽容但不猜：** 缺字段的条目跳过并记日志，**不要用零值补齐** ——
一块「容量为 0」的盘参与磁盘决策会让 largest 策略选错。

**解析结果转成 Phase 1 定义的硬件事实结构**（M1 契约里那个），
供 DiskPlanner 与网卡决策消费。

**这个编码约定要写进 `docs/contracts/http-machine.md`** ——
它是机器侧脚本与服务端解析的共同契约，两边独立修改会静默失配。

**测试要锁住的行为：**

- 完整的键值对能还原出磁盘与网卡列表
- **缺字段的条目被跳过而不是用零值补齐**
- 序号不连续时（采集时某块盘失败）仍能还原其余的
- 未知键被保留为普通 fact（供 hook 消费）而不是丢弃

**验证：** `go test ./internal/gateway/ ./internal/provider/ -run TestHWFacts -v` 全过。

**完成标志：** commit `feat(gateway): parse inspected hardware facts into structures`

### 任务 3：网卡决策

**产出文件：** `internal/provider/nicplanner.go`、对应测试

**为什么需要这一步：** §10 失败模式 6：**网卡命名漂移导致装完网络不通、
机器失联需人到现场。** 这是仅次于装错盘的严重故障 —— 机器装好了但连不上，
所有远程手段都失效。

**决策要输出两样：** 装机网卡（当前通着的那块）与业务网卡（要配业务 IP 的那块）。

**判据的优先级：**

1. **MAC 精确匹配** —— 主机清单里记录的 MAC 是最可靠的判据
2. **link 状态** —— 装机阶段通着的那块就是装机网卡
3. **PCI 路径** —— 同型号多网卡时用它区分板载与扩展卡

**输出的是 MAC 而不是接口名。** 应答文件里要用 MAC 绑定网卡配置
（三个家族都支持按 MAC 匹配），**再固化接口命名策略** ——
两者结合才能让重启后的名字与装机时一致。

**固化命名策略的含义：** 内核的可预测接口命名会因固件升级、插卡位置变化而改变。
在引导参数里显式固定命名策略（要么全用传统名，要么全用可预测名），
**不要让它取决于目标系统的默认值** —— 那个默认值在不同发行版不同版本间会变。

**一条容易忽略的约束：** 业务网卡的配置**写而不激活**（§5.7）。
本任务只负责决策出「哪块卡」，激活时机的控制在 Phase 1 的渲染器骨架里已经做了 ——
但要有测试确认两者配合正确（决策出业务网卡后，生成的配置确实是「写不激活」的）。

**测试要锁住的行为：**

- MAC 精确匹配优先于 link 状态
- 无 MAC 匹配时按 link 状态选装机网卡
- 同型号多网卡时 PCI 路径生效
- **输出是 MAC 而非接口名**
- 零网卡或全部 down 时返回明确错误
- **决策结果落进应答文件后是「写配置不激活」形态**

**验证：** `go test ./internal/provider/ -run TestNICPlanner -v` 全过。

**完成标志：** commit `feat(provider): NIC decision by MAC with link-state fallback`

### 任务 4：pre 阶段的两段式与决策回写

**产出文件：** `internal/gateway/facts.go`（扩展）、`internal/render/inspect.go`（扩展）

**为什么需要这一步：** 采集在分区之前，而分区需要决策结果 ——
所以 `pre` 阶段内部必须分两段，中间等服务端算完。

**两种实现方式，要选一个：**

| 方式 | 机制 | 取舍 |
|---|---|---|
| **同步读（推荐）** | 上报后立即读 facts 端点取决策结果 | 简单，一次往返；但要求服务端在上报的响应路径上就算完决策 |
| 轮询 | 上报后循环读直到出现决策键 | 容忍服务端异步算；但要处理超时，且延长装机时间 |

**选同步读。** 决策是纯函数（磁盘规划无 IO，§7.2），算完只要毫秒级 ——
没有异步的必要。**在上报事实的处理里顺带跑决策并回写 fact**，
机器侧紧接着读一次就能拿到。

**但要处理一个失败模式：决策失败时机器该怎么办。**

决策失败的原因可能是「一块盘都没采到」或「raid1-ssd 策略但 SSD 不够」。
**此时不能让机器继续分区** —— 它会用一个空的设备标识去分区，
而那在不同 installer 下的行为不同（有的报错、有的选默认盘）。

**处置：机器侧读不到决策键时，主动上报一个失败信号并中止安装。**
中止要走模板配置的失败处置（§2.3 的 `on_failure`）—— 调试期停在 shell、
生产期重启并上报。

**这条是本任务最重要的部分**：它把「服务端决策不出来」这个情况变成一个
有明确原因的失败事件，而不是「机器装到一半停住」。

**回写的决策键**用 M1 fact 命名空间里已有的（主盘那个键），
网卡决策的结果加新键 —— **新增 fact 键是契约变更**（§5.4 只增不删），
要走流程并更新 M1 的键清单与那张快照测试。

**测试要锁住的行为：**

- 上报事实后决策结果立即可读
- **决策失败时 facts 里没有决策键**（而不是有一个空值）
- 生成的采集脚本在读不到决策键时上报失败信号并中止
- 新增的 fact 键已加入 M1 的清单与快照测试

**验证：** `go test ./internal/gateway/ -run TestInspectRoundTrip -v` 全过；
M1 的 fact 快照测试仍全绿（说明新键已正确登记）。

**完成标志：** commit `feat(gateway): synchronous decision writeback for the pre stage`

### 任务 5：模板的磁盘策略从配置提到模板级

**产出文件：** `internal/core/model/authoring.go`（已有字段的启用）、
`internal/provider/resolve.go`（扩展）

**为什么需要这一步：** Phase 1 的磁盘策略来自全局配置。Phase 2 有了真实的多机型场景，
**策略应当随模板而定** —— 不同机型用不同策略是这个功能的主要用例。

**M1 的模板类型已经有磁盘策略字段**，Phase 1 只是没用它（用的是全局配置）。
本任务把决策的策略来源改为「模板优先，全局配置兜底」。

**by-model 策略的型号串也要能在模板级指定** —— 全局只配一个型号串对多机型无意义。
这需要模板上加一个字段（**契约变更**，走流程）。

**一个兼容性注意：** 已有的任务 pin 了模板版本（§2.6），
所以改模板不影响在跑的任务 —— 这条 Phase 1 已经保证。**本任务不要引入
「按全局配置重算已有任务的磁盘决策」那种逻辑** ——
决策已固化进任务的参数，重算会让同一任务前后决策不一致。

**测试要锁住的行为：**

- 模板指定策略时用模板的
- 模板未指定时回落全局配置
- by-model 的型号串能在模板级指定
- **已固化决策的任务不受模板改动影响**（改模板后重新渲染，决策仍是原值）

**验证：** `go test ./internal/provider/ -run TestDiskPolicySource -v` 全过。

**完成标志：** commit `feat(provider): template-level disk policy with config fallback`

### 任务 6：dry-run 端点接上真实采集数据

**产出文件：** `internal/console/dryrun.go`（扩展）

**为什么需要这一步：** Phase 1 的 dry-run 要运维手工贴硬件事实。
有了采集之后，**应当能直接用某台机器的历史采集结果跑策略** ——
那才是这个端点真正好用的形态（§8.2 说它是性价比最高的两个端点之一）。

**扩展两处：**

1. **接受一个任务 id 作为输入**，取那个任务的采集事实跑策略 ——
   「这台机器如果换用 raid1-ssd 策略会选哪两块盘」是运维的真实问题
2. **返回对比**：当前策略的结果与请求的策略的结果并排 ——
   光给一个结果，运维还要自己回忆当前是什么

**保留手工贴事实的入口**（Phase 1 的形态）—— 它用于「还没有机器但想验证策略」的场景。

**测试要锁住的行为：**

- 按任务 id 能取到采集事实并跑出结果
- 任务无采集事实时返回明确错误（而不是空结果）
- 手工贴事实的入口仍可用
- 对比结果含两个策略的输出

**验证：** `go test ./internal/console/ -run TestDryRun -v` 全过。

**完成标志：** commit `feat(console): dry-run against recorded hardware facts`

## 边界提醒

**只采服务端会用到的字段。** fact 命名空间是只增不删的对外契约（§5.4）——
采一堆没人消费的硬件事实（BIOS 版本、每根内存条的序列号、每个 PCI 设备的完整描述）
会让那个契约背上永久负担，而删除它们需要一个双写版本周期。

**判断标准：这个字段现在有哪个决策或哪个 hook 要用它？** 答不出来就不采。
将来真需要时再加一个键是简单的；删一个已发布的键不简单。
