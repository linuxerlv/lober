## 开工判断：先回答四个问题

**产出文件：** `docs/phase3-grpc-starlark-判断.md`

这不是流程形式。§7.2 给了明确判据，而误判的代价是做出一个无人使用的抽象层
（§7.6 已警告过这个具体后果）。

**gRPC 的三个判断问题：**

1. **P2-03 落地后，哪些 provider 用了 exec 或 http？它们够用吗？**
   「够用」的反面是具体的：脚本太长难维护、需要连接池或长连接、
   需要在多次调用间保持状态、单次调用的启动开销成为瓶颈
2. **那些不够用的集成，是「有真逻辑」的吗？**（§7.2 的判据：
   IPAM、CMDB 那类属于有真逻辑；DNS 注册、告警推送那类「几行 curl 的集成用 gRPC 是纯负担」）
3. **它们的实现方要不要用 Go 写？** gRPC 加载器的收益之一是插件可以用任何语言写，
   但 hashicorp 那套的 Go 侧支持最好 —— 若实现方打算用 Python，
   exec 加一个长驻进程可能更简单

**Starlark 的两个判断问题：**

4. **模板解析的规则表现在有多少条？有嵌套条件吗？**
   §7.6 的信号是「规则表开始长出嵌套条件」—— 平的规则表说明还不需要
5. **运维提过多少次「这批机器特殊处理」？** 这是另一个信号。
   若一次都没提，说明具名策略与规则表覆盖了实际需求

**三个问题以上答不出具体依据 → 推迟对应的那一半。**

**验证：** 五个问题各有基于生产运行的具体答案，且有明确结论。

## 第一半：gRPC 加载器

### 任务 1：协议定义与握手

**产出文件：** `internal/provider/loader/grpc/` 下的接口定义与握手配置

**为什么需要这一步：** gRPC 加载器的插件是独立进程，双方要先就协议版本达成一致。

**用 hashicorp/go-plugin**（§7.2 指名）。它提供进程管理、握手、
双向通信与崩溃检测 —— 自己实现这些是几周的工作。

**七个 provider 接口各自要有 gRPC 形式的定义。**
**但不要一次全做** —— 只做任务 0 的判断里确认需要的那几个。
其余保持只有内置与 exec/http 两种实现，将来需要时再加。

**协议版本协商是硬要求**（§7.3 最后一项）：**版本对不上直接拒绝加载。**
不拒绝的后果是插件与主程序对同一个方法的参数理解不同 ——
而那类错误的表现是「provider 返回了无意义的结果」，极难追溯。

**一个与 exec/http 不同的设计点：连接是长驻的。**
这带来两个新问题（exec 与 http 没有）：

| 问题 | 处理 |
|---|---|
| 插件崩溃 | go-plugin 会检测到；要自动重启并指数退避（§7.3 第四项） |
| 在途调用 | 替换插件时要等在途调用结束（§7.3 第二项，见任务 3） |

**测试要锁住的行为：**

- 握手成功后能调用方法
- **协议版本不匹配时拒绝加载**
- 插件进程崩溃后被检测到
- 只有判断里确认需要的接口有 gRPC 定义

**验证：** `go test ./internal/provider/loader/grpc/ -run TestHandshake -v` 全过。

**完成标志：** commit `feat(loader): gRPC plugin protocol with version handshake`

### 任务 2：原子换与健康检查

**产出文件：** `internal/provider/loader/grpc/reload.go`、对应测试

**为什么需要这一步：** §7.3 的第一与第三项。P2-03 已经为 exec/http 做过这两项，
但 gRPC 的情况不同 —— 那里每次调用是独立进程，这里有个长驻进程要替换。

**换二进制要原子**（§7.3 第一项）：用版本目录加一个符号链接，reload 时切链接。
**不要用覆盖写** —— 运行中的进程可能读到半个文件。

**健康检查与回滚**（§7.3 第三项）：新插件拉起后先探活，
**失败则保留旧进程、拒绝本次 reload**。

**这里有个顺序要求：先拉起新进程并探活，再切换指针，最后停旧进程。**
顺序错了（先停旧的）会让替换期间的调用全部失败 ——
而在气隙环境里 reload 往往是为了修一个正在影响装机的问题，
替换期的失败会让运维以为修复没生效。

**测试要锁住的行为：**

- 符号链接切换后新调用走新版本
- **探活失败时旧进程仍在服务，reload 返回错误**
- 替换期间没有调用失败
- 覆盖写被拒绝（或至少有一条检测）

**验证：** `go test ./internal/provider/loader/grpc/ -run TestReload -race -v` 全过。

**完成标志：** commit `feat(loader): atomic gRPC plugin swap with health gate`

---

### 任务 3：在途调用的排空

**产出文件：** `internal/provider/loader/grpc/drain.go`、对应测试

**为什么需要这一步：** §7.3 第二项。这是 gRPC 加载器**唯一** exec/http 完全不需要的机制 ——
后两者每次调用独立，没有「在途」的概念。

**做法**（§7.3 给了形态）：用一个带计数的门包住调用点 ——
停止新请求进入、等在途调用结束（**带超时**）、再停旧进程。

**超时的处理要明确：超时后仍然停旧进程。**
理由：一个卡住的调用不该无限期阻塞 reload —— 而 reload 往往是在修问题。
**但要记一条日志说明有调用被强制中断**，那是排查「为什么某个任务的 provider 调用失败」的线索。

**一个容易错的地方：门的计数要在正确的位置增减。**
在发起调用前加、在收到响应或出错后减 —— **用延迟执行保证异常路径也会减**。
漏减的后果是排空永远等不到零，而 reload 永远超时。

**测试要锁住的行为：**

- 排空期间新调用被拒绝
- 在途调用完成后旧进程才停
- **超时后旧进程仍然被停，且有日志**
- **调用出错时计数也正确减少**（用一个总是出错的插件验证排空能完成）

**验证：** `go test ./internal/provider/loader/grpc/ -run TestDrain -race -v` 全过。

**完成标志：** commit `feat(loader): in-flight drain with bounded wait`

### 任务 4：熔断复用与工厂集成

**产出文件：** `internal/provider/factory.go`（扩展）、配置扩展

**为什么需要这一步：** 把 gRPC 接进按配置构造的流程。

**熔断直接复用 P2-03 的实现** —— 它是按扩展点的失败语义分流的（§7.4），
与加载方式无关。**不要为 gRPC 写第二套熔断。**

**配置加第四种类型**（内置、exec、http、grpc），gRPC 的参数是插件目录路径
（那个含版本目录与符号链接的）。

**启动校验：** 符号链接存在且指向一个可执行文件；协议版本能协商成功。
**后者意味着启动时会拉起一次插件** —— 这是有意的：
配置写错时在启动时发现，而不是第一次装机时。

**向后兼容：** 配置里不写类型时仍默认内置，P2-03 的配置不改也能跑。

**测试要锁住的行为：**

- 四种类型各自构造成功
- gRPC 类型的启动校验拉起插件并协商版本
- **符号链接缺失或指向非可执行文件时启动失败**
- 熔断对 gRPC 类型生效（复用同一实现）
- P2-03 的配置样例仍能通过校验

**验证：** `go test ./internal/config/ ./internal/provider/ -v` 全过。

**完成标志：** commit `feat(provider): wire gRPC loader into the factory`

## 第二半：Starlark 决策引擎

### 任务 5：为什么是 Starlark 而不是 JS 或 Lua

**产出文件：** `internal/provider/starlark/doc.go`（包文档）

**为什么需要这一步：** 这个选择有一个具体理由，写进包文档以免将来被「优化」掉。

**§7.2 的原话：选 Starlark 而非 JS 的理由是确定性 ——
「这套系统会擦盘，磁盘规划函数若行为不完全确定则故障无法复现」。**

**Starlark 的四个默认约束正对应这个需求：**

| 约束 | 对应的风险 |
|---|---|
| 默认无 IO | 决策函数去读文件或发网络请求，结果就依赖外部状态 |
| 无时钟 | 「周三装的机器选另一块盘」这类不可复现的行为 |
| 无随机 | 同上，且更隐蔽 |
| 值冻结 | 决策过程中修改输入，让「同样的输入」变得没有意义 |

**这四条要在嵌入时保持默认，不要为了方便而放开。**
若某个决策确实需要外部数据，正确做法是**把那个数据作为输入传进去**
（由 Go 侧取好），而不是让脚本自己去取。

**包文档要写明这一点**，因为「让脚本能读个配置文件多方便」是一个很自然的想法，
而放开之后就再也收不回来了。

**完成标志：** commit `docs(starlark): why deterministic-by-default matters here`

### 任务 6：磁盘规划的 Starlark 形态

**产出文件：** `internal/provider/starlark/diskplanner.go`、对应测试

**为什么需要这一步：** 磁盘规划是两个纯决策扩展点之一，也是**风险最高的那个** ——
它决定擦哪块盘。

**输入与输出沿用 Phase 1 的接口形态**：输入是磁盘列表与意图，
输出是布局加「为什么这么选」的说明。

**说明这一项在 Starlark 形态下更重要。** 内置策略的行为是固定的五种，
运维知道 largest 是什么意思；而脚本可以做任意判断 ——
**若它不解释自己选了什么，dry-run 就失去价值**（§8.2）。

**所以：脚本不返回说明时，视为脚本错误而拒绝使用它的结果。**
这比「用一个默认说明补上」好 —— 后者会让运维看到一句无信息的话而以为看过了。

**三条执行约束：**

1. **执行要有超时** —— 一个死循环的脚本不该挂住建任务
2. **执行要有步数上限** —— 超时之外的第二道防护（Starlark 支持这个）
3. **脚本的语法与执行错误要给出行号** —— 运维要能定位到自己写错的那一行

**dry-run 端点自动适用**（P2-02 已扩展它）：Starlark 策略也走同一个端点。
**这是 Starlark 能被安全使用的前提** —— 一个不能 dry-run 的擦盘决策脚本
不该被允许上线。

**测试要锁住的行为：**

- 一个简单脚本能正确选盘并返回说明
- **不返回说明的脚本被拒绝**
- 超时与步数上限各自生效
- 语法错误带行号
- **脚本试图做 IO 时失败**（验证默认约束未被放开）
- 同一输入两次执行结果相同（确定性）

**验证：** `go test ./internal/provider/starlark/ -v` 全过。

**完成标志：** commit `feat(starlark): disk planner with determinism guards`

### 任务 7：脚本的审批与灰度

**产出文件：** `internal/console/` 的相关扩展、文档

**为什么需要这一步：** **决策脚本的危险程度与 hook 相当** ——
hook 以 root 在分区前运行，而决策脚本决定分区分到哪块盘上。

**所以要复用 hook 的审批机制**（§9.4 的分级）：
草稿 → 待审批 → 激活，且**激活需要审批**。

**P2-05 已经做了 hook 的审批界面** —— 决策脚本复用它，
但**审批界面要显示 dry-run 的结果**：审批人看一段 Starlark 代码很难判断对错，
看到「用这三种典型硬件配置跑出来的选盘结果」就能判断。

**这是本任务的核心要求：审批时必须附带 dry-run 结果。**
没有它的审批是橡皮章，而它把守的是擦盘决策。

**灰度的做法：** 脚本激活后先在少量模板上用，**不要一次替换全部模板的策略**。
这条是运维纪律而非代码机制 —— 但要写进文档，
并建议在模板列表上能看出「哪些模板用了脚本策略」。

**权限要求：** 写决策脚本的权限**与写 hook 分开**（§9.4 的精神：
provider 配置是最高权限，走代码评审）。决策脚本比 hook 影响面更大 ——
一个 hook 影响用它的那些任务，一个决策脚本影响用那个模板的所有机器。

**测试要锁住的行为：**

- 脚本走草稿到激活的审批流
- **审批接口返回 dry-run 结果**
- 写决策脚本的权限与写 hook 的权限分开
- 未激活的脚本不会被用于真实决策

**验证：** `go test ./internal/console/ -run TestStarlarkApproval -v` 全过。

**完成标志：** commit `feat(console): decision script approval with mandatory dry-run`

## 一条不要重新考虑的排除项

**Go 的 plugin 构建模式已在 §0.2 与 §7.2 明确排除，不要因为「gRPC 要起子进程
看起来重」而回头考虑它。**

它的问题是结构性的：要求主程序与插件编译期完全对齐（同一 Go 版本含补丁号、
所有共享依赖同版本、同构建标志）、无卸载机制、同路径重复加载返回缓存对象
（改文件无效）、**更新已加载插件必须重启进程**、插件 panic 直接带走网关、
**Windows 完全不支持**（本地开发环境就过不去）。

**它同时是唯一需要重启且唯一无崩溃隔离的方案** —— 而这两点恰好是
provider 体系最需要的两个特性（§7.2 的表格里三种方案都有完整的崩溃隔离）。
