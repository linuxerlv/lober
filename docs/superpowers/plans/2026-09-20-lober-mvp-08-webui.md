# M8 控制台 WebUI 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** M1 契约与地基必须已完成（提供 `docs/contracts/http-console.md`）。
> 本模块与 M2–M7 并行。与 M6 对着同一份 HTTP 契约开发，两边都不得私自改契约。
> **只碰 `web/` 与 `internal/console/ui/`，不要动 M6 在 `internal/console/` 下的 handler 文件。**
>
> **本计划描述做什么与为什么，不给代码。** 环境变量的具体取值与偏好项在 SPEC §12.4
> 已定稿，本计划引用它而不重抄。

**目标：** 把 vue-vben-admin 5.x 的 Element Plus 应用精简后接上真后端，
构建产物内嵌进 Go 二进制，交付 P1 的六个页面。

**架构：** 前端源码在 `web/`（精简后的 monorepo），构建产物直接输出到
`internal/console/ui/dist`，由一个 Go 文件用 `go:embed` 内嵌并提供 handler。
定制全部收敛在四处，框架本体保持原样以便升级（§12.9）。

**气隙是主要约束。** npm 装不了、CDN 图标取不到、统计脚本必须删 —— 本计划里三分之一的
要点都源自这一条。

**技术栈：** Vue 3 · Vite · TypeScript · Element Plus · vxe-table · pnpm。
**具体版本号以任务 1 的实机核对结果为准**，不照抄 SPEC（§12.9 提到 5.x 仍在快速迭代）。

**SPEC 依据：** §12 全节

## 文件结构

| 路径 | 职责 |
|---|---|
| `web/` | 精简后的 vben monorepo，根 package.json 在这里 |
| `web/apps/web-ele/` | 唯一保留的 UI 应用 |
| `web/UPSTREAM_PIN.md` | pin 的上游 commit 与实机核对记录 |
| `internal/console/ui/embed.go` | `go:embed` 与 handler（**本模块唯一的 Go 文件**） |
| `internal/console/ui/dist/` | 构建产物（是否入库见任务 12） |

**定制只允许出现在四处**（§12.9）：`apps/web-ele/src/**`、`apps/web-ele/.env*`、
`apps/web-ele/index.html`、根 `package.json` 的 scripts。
`packages/**` 与 `internal/**` 保持原样（删文件不算改），升级就是覆盖这两棵树。

### 任务 1：核对上游实际版本并 pin commit

**产出文件：** `web/UPSTREAM_PIN.md`

**为什么需要这一步：** SPEC §12 按某个时点的上游 main 写成，而 §12.9 与附录 B 都指出
5.x 仍在快速迭代（那一带已经换过构建工具、CSS 框架、TypeScript 大版本，
表单底层也换过）。**照抄 SPEC 里的版本号与目录名会在第一步就对不上。**

**实现流程：**

1. clone 上游仓库到临时位置
2. 记录当前 main 的 commit hash 与日期
3. 核对五项并把**真实输出**写进记录文件：
   - 根 package.json 与目标应用的实际版本号
   - §12.2 精简清单里涉及的目录是否都还在原处
   - 请求封装里响应拦截器的字段名（§12.5 依赖它）
   - 偏好设置文件里各覆盖项的字段路径（§12.4 依赖它）
   - Node 与 pnpm 的版本要求
4. **选定一个 commit 作为 pin**，写进记录文件

**要求填真实命令输出，不要照抄 SPEC 文本。** 这份记录的全部价值在于「它反映的是
实际情况」—— 抄一遍 SPEC 等于没核对。

**pin commit 而不是跟 main**（§12.9）：在装机功能开发中途跟版，
会把「装机逻辑坏了」和「前端框架升级坏了」两类问题混在一起排查。
**升级当独立任务做。**

**验证：** 记录文件里五项都有实际输出；pin 的 commit hash 明确。

**完成标志：** commit `docs(web): pin upstream commit with verified version facts`

### 任务 2：clone 与仓库级精简

**产出文件：** `web/` 整棵树

**为什么需要这一步：** 上游有五个 UI 应用、演示代码、文档站源码、
不适用的 CI 与发布脚本。**5.0 起官方不再提供精简仓库或精简分支**（§12.1），
精简方式就是克隆全仓再删。

**实现流程：**

1. **按任务 1 记录的 pin commit hash clone**，不用 main 的头
2. 删除仓库级的七类对象（§12.2）：四个非目标 UI 应用、mock 后端、演示工程、
   文档站源码、版本管理配置、上游 CI、docker 部署脚本
3. **`packages/**` 与 `internal/**` 全留** —— 框架本体与构建配置，删了跑不起来
4. 删除 mock 后端时**同时把开发环境的 mock 开关置关**：
   我们有真后端，mock 只会掩盖契约不一致
5. 根 package.json 的 scripts 只留目标应用的开发与构建，加 lint 与类型检查

**不必为了体积删框架的插件包**（§12.2）：那个包用子路径导出，
没 import 就不进 bundle —— 图表与富文本编辑器留在源码树里不产生构建成本。

**验证：** `pnpm install` 成功；`pnpm build:ele`（或核对后的实际脚本名）成功。

**完成标志：** commit `feat(web): clone pinned upstream and strip to single app`

### 任务 5：环境变量

**产出文件：** `web/apps/web-ele/.env`、`.env.development`、`.env.production`

**为什么需要这一步：** 九个变量的取值在 §12.4 已定稿，照它配。

**其中四项的理由要理解而不是照抄：**

| 变量 | 值 | 理由 |
|---|---|---|

其余五项（标题、命名空间前缀、base、归档、PWA 与开发工具与 mock 全关）按 §12.4。

**产出文件：** `web/apps/web-ele/src/api/console/*.ts`、`src/router/routes/**`

**为什么需要这一步：** 前端与后端的唯一接触面。按 `docs/contracts/http-console.md` 写，
**不要凭猜测加字段**。

**认证四个接口的端点名要与框架默认约定对齐**（§12.5）——
框架的登录流程会调那几个名字，改名就要改框架代码。

**资源接口按契约文档分组**：主机、制品集、hook、模板、任务、dry-run。

### 任务 9：三个列表页

**产出文件：** 任务列表、主机清单、模板列表三个页面

**为什么需要这一步：** P1 的三个列表页形态相同，一起做能保证风格一致。

**统一用框架的表格适配器**（§12.6），不要每个页面各写一套表格加分页 ——
后者的代价是六个页面六种翻页行为。

**分页用客户端模式**（M1 契约的分页约定）：一次取回后本地分页，不读总数、
不传分页参数。理由是规模：内网装机控制台的主机与任务都是百级。

> 适配器的具体 API 形态以任务 1 核对的实际代码为准。若它提供更简的纯本地模式就用那个；
> 若只暴露「代理请求」模式，就在请求回调里返回全量数组、不构造总数。
> **实现前先看一眼实际的适配器文件**，不要按本计划的描述猜。

**任务列表的三个特殊要求：**

1. **按状态过滤、按 SN 搜索**（服务端参数）
2. 行内提供重试与取消操作，各自按权限码显示
3. **`pending` 状态的文案必须是「等待机器引导，随时可能开始装机」**，
   **不要显示成中性的「未开始」**（§12.5）—— 建任务即授权，那台机器一旦网络启动就会
   开始装机，文案要让运维看见这个事实

**主机清单的特殊要求：** 提供搜索输入框，用契约里的搜索参数（服务端过滤），
**不是本地过滤** —— 主机数超过一页时本地过滤选不到目标机器。

**模板列表的特殊要求：** 右侧常驻 preview 面板（§12.6）。

**验证：** 三个页面能列出数据、过滤生效、翻页正常；`pnpm typecheck` 无错误。

**完成标志：** commit `feat(web): task, host and template list pages`

### 任务 10：表单 schema 转换层

**产出文件：** `web/apps/web-ele/src/adapter/form-schema.ts`

**为什么需要这一步：** 服务端返回 JSON Schema，而框架表单吃的是自己的 schema 数组
（§12.7）。中间必须有一层映射。

**为了让映射是全函数而不是「大部分能渲染」，服务端输出限定在一个子集内**（§12.7）：
五种类型、七项校验、三项展示、三个扩展字段（控件类型、排序、依赖关系）。

**超出子集的在 hook 注册时就被拒绝**（M6 的职责），所以本层可以假定输入合法 ——
但**遇到不认识的控件类型仍要报错而不是静默降级为文本输入**：
静默降级的后果是运维在一个文本框里填 IP，而前端校验不生效。

**八种控件类型的映射**（§12.7）：文本、多行文本、密码、数字、开关、下拉、IP、
**主机选择**。最后一个是本系统特有的（下一个任务）。

**前端校验只是体验，不是防线**（§12.7）。这条要写进文件头注释 ——
服务端仍按 §5.6 对表单值做类型白名单强校验，那些值会进 kickstart 脚本。

**验证：** 写一个可重复执行的手工验证脚本或一小段检查代码，
用一份覆盖全部八种控件的 schema 跑一遍映射，确认输出的字段数与控件类型正确；
不认识的控件类型触发报错。

**完成标志：** commit `feat(web): JSON Schema subset to form schema mapping`

### 任务 12：建任务页 —— 唯一的授权动作

**产出文件：** 建任务页面

**为什么需要这一步：** **这是唯一的授权动作，按危险动作做**（§12.6、§3.2）。

### 任务 13：SSE 与任务详情页

**产出文件：** SSE 的 composable、任务详情页

**为什么需要这一步：** 装机要几十分钟，运维需要看着它推进。

**用 fetch 流而不是浏览器内置的事件源 API**（§12.8）。

**理由是个具体的安全考虑：** 内置 API **不能设请求头**，用它就只能把 token 塞进
query string，而 **token 进 query 会落进 nginx access log** —— 而 §9.5 刚要求清理
带 token 的记录。用 fetch 加可读流则能正常带认证头。

**四个实现要点**（§12.8）：

1. **断线用指数退避重连，重连带上最后收到的事件 id**，服务端按它续传，不从头重放
2. **组件卸载必须中止请求** —— 否则列表与详情来回切会攒住一堆连接
3. 服务端已回禁用代理缓冲的头部，前端无需处理
4. **任务进终态时服务端主动关流，前端收到终态即停止重连** ——
   不停的话会对一个已完成的任务无限重连

**任务详情页的四块内容**（§12.6）：状态机时间线、事件表、实时日志、
**失败详情的六个字段**（§3.5）。

**失败详情那六项要全部显示**：阶段、退出码、是哪个 hook、日志尾部、
installer 原始报错、**距上次信号多久**。最后一项区分度很高 ——
刚收到信号说明机器活着是脚本问题，很久没信号说明机器层面出事，
两个排查方向完全不同。

**验证：** 打开详情页能看到日志实时追加；任务完成后连接关闭且不重连；
切走页面后连接被中止（浏览器开发者工具网络面板确认）。

### 任务 15：交付方式与气隙验收

**产出文件：** `web/README.md`

**为什么需要这一步：** **构建必须在有外网的机器上做**（§12.3）——
气隙内网装不上依赖，这不是能绕的事。交付方式要明确下来。

**三种做法，MVP 采用第一种**（§12.3 的推荐顺序）：

1. **开发机或 CI 构建，只把产物带进内网** —— MVP 采用
2. 外网预取依赖灌满离线仓库，整体带进内网后离线安装
3. 内网起私有 registry 镜像上游 —— 只有当内网确实需要改前端时才值得

**依赖锁文件必须提交。** 产物是否入库取决于交付方式：
内网只能拿到 git 仓库就必须提交，走发布包则不必。**在 README 里写明选了哪种。**

**最终气隙验收的三条 grep 检查**（可重复执行的命令）：

- 产物里无第三方统计脚本的域名
- 产物里无公共 CDN 的域名
- 路由定义里无在线图标名

**另加一条越界检查：** 确认本模块没有修改 `internal/console/` 下 M6 的任何 Go 文件。

**验证：** 三条 grep 无匹配；越界检查通过；`pnpm lint` 与 `pnpm typecheck` 无错误。

**完成标志：** commit `docs(web): delivery method and air-gap verification`
