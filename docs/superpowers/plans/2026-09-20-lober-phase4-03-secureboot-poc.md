# P4-03 Secure Boot PoC 计划

> **面向 AI 代理的工作者：这是 PoC 计划，不是实现计划。**
> 每个任务的产出是一个**验证结果与记录**，不是一个功能 commit。
> 验收标准是「问题有答案」而不是「测试通过」。
>
> **前置：** P4-02（TLS）完成 —— 本计划要用到那里建的 CA 与自编 iPXE 的经验。
>
> **本计划描述要验证什么与为什么，不给代码。**

**目标：** 回答一个问题 —— **在我们的机器上，开启 Secure Boot 的情况下能否用这套系统装机，
代价多大。**

**为什么是 PoC 而不是实现：** SPEC §11 Phase 4 的原话是
**「建议先做独立 PoC，技术风险最高」**；附录 B 把它列为待验证项，
要核实的是「三级签名的具体机制与密钥注册流程」。

**技术风险高在哪：引导链要变成三级，中间那一级需要注册进固件的信任列表 ——
而那个注册动作在不同厂商的固件里操作方式不同，且部分固件不支持。**

**这个 PoC 的价值在于：它可能得出「走不通」的结论，而那个结论同样有用** ——
它意味着要么放弃在开启 Secure Boot 的机器上装机、
要么在装机时临时关闭它（一个可以接受的运维流程）。

**SPEC 依据：** §11 Phase 4、附录 B 的 Secure Boot 项、§1.1 组件清单的 iPXE 一行

---

## 先理解问题：为什么 Secure Boot 会挡住这套系统

**Secure Boot 的机制：** 固件只加载被它信任的密钥签名过的引导程序。
信任的密钥预置在固件里（通常是微软的与厂商的）。

**我们的引导链现在是两级：** 固件 → iPXE → 目标 OS 的内核。

**问题出在中间那级：** iPXE 二进制是我们自己提供的（Phase 1 从官方取，
P4-02 之后是自编的）—— **它没有被固件信任的密钥签名过**，所以会被拒绝加载。

**标准解法是三级链：** 固件 → 一个被微软签过的中间引导器 →
自签的 iPXE → 目标 OS 的内核。

**中间那一级的作用：** 它被固件信任（微软签过），
而它自己维护一份独立的信任列表 —— 把我们的签名密钥注册进那份列表，
它就会加载我们的 iPXE。

**注册动作是本 PoC 的核心风险**：它需要在每台机器上做一次，
而做法依赖固件实现。

### 任务 1：确认机器侧的事实

**产出：** `docs/secureboot-poc/01-机器事实.md`

**为什么先做这个：** 后面的工作量取决于机器的实际情况。
若机房里的机器都能方便地关闭 Secure Boot，整个 PoC 可能不必做。

**要回答的五个问题：**

1. **机房里的机器有多少台开启了 Secure Boot？** 新服务器通常默认开启
2. **能否批量关闭？** 通过 BMC 或固件配置工具批量改设置 ——
   **注意：这与 §0.2 排除的「带外自动开关机」不同**，
   那条排除的是自动上电与改引导顺序，而一次性的批量固件配置是部署动作
3. **关闭 Secure Boot 是否被安全策略允许？** 有些环境有合规要求
4. **固件是否支持向中间引导器的信任列表注册密钥？**
   这一项要实际查一台机器的固件设置界面
5. **厂商与型号的分布** —— 若只有一两种型号，PoC 的范围小得多

**若第 2 与第 3 个问题的答案是「能批量关且允许」，
本 PoC 可以就此结束并记录结论：** 装机时关闭 Secure Boot，装完后按需开启。
**那是一个完全可接受的运维流程**，成本远低于三级签名链的维护。

**这一条要认真评估，不要因为「关掉安全特性听起来不好」而跳过它。**
装机 VLAN 是隔离的（§1.5 的前提），而装机过程本身是受控的 ——
在这个窗口内关闭 Secure Boot 的风险远小于维护一套签名体系的复杂度。

**完成标志：** 五个问题各有答案；给出「继续 PoC」或「改用关闭 Secure Boot 的流程」的结论

---

### 任务 2：中间引导器的获取与验证

**产出：** `docs/secureboot-poc/02-中间引导器.md`

**仅在任务 1 的结论是「继续」时执行。**

**要验证的三件事：**

1. **从哪里获取被微软签过的中间引导器？**
   它通常随主流 Linux 发行版分发 —— 而我们要确认：
   **拿发行版 A 的那个中间引导器去链载我们的 iPXE 是否可行**
   （它可能被配置为只链载发行版 A 自己的引导器）
2. **它的版本与固件的撤销列表。** 固件会维护一份被撤销的签名列表 ——
   旧版本的中间引导器可能已被撤销。**要确认拿到的版本没被撤销**
3. **它在我们的目标机型上能否加载** —— 实机验证，不要只看文档

**第 1 条是最可能卡住的地方。** 中间引导器的行为是「加载一个特定名字的下一级」，
而那个名字与路径可能是固定的 —— 意味着我们的 iPXE 要改名或放在特定位置。

**要记录的：具体的加载路径要求与命名要求。**

**完成标志：** 三个问题各有答案；一台目标机型上中间引导器成功加载

---

### 任务 3：iPXE 的签名与密钥注册

**产出：** `docs/secureboot-poc/03-签名与注册.md`

**要验证的四件事：**

1. **生成签名密钥对**（与 P4-02 的 TLS CA 是不同的密钥 ——
   **要记录清楚两者的区别**，混淆会造成排查困难）
2. **给自编的 iPXE 签名** —— 签名格式与工具要确认
3. **把公钥注册进中间引导器的信任列表** —— **这是本 PoC 的核心风险点**
4. **注册是否需要在每台机器上手工做？** 若是，那是一个按机器的部署步骤 ——
   **要评估它的工作量**

**第 3 与第 4 条决定这个方案是否可行。**

**若注册需要在每台机器上交互式操作**（在固件界面里点击确认），
那意味着每台新机器上架时要人到机房 —— **而那与这套系统「自动化装机」的目标冲突**。

**要探索的替代路径：** 某些固件支持通过一个文件或 BMC 接口批量注册。
**若存在这条路径，要记录具体做法** —— 它是这个方案可行的前提。

**完成标志：** 四个问题各有答案；一台机器上完成注册并成功引导自签的 iPXE

---

### 任务 4：目标 OS 内核的签名链

**产出：** `docs/secureboot-poc/04-内核签名.md`

**为什么这一级也要验证：** 三级链的最后一跳是 iPXE 加载目标 OS 的内核 ——
**而 Secure Boot 开启时，那个内核也要被信任的密钥签名过。**

**两种情况：**

| 情况 | 处理 |
|---|---|
| 目标 OS 是主流发行版 | 它的内核已被发行版签名，而那个签名链从中间引导器起是完整的 —— **可能可以直接工作** |
| 目标 OS 是自封装的镜像（P3-03） | **镜像里的内核要自己签**，或保持发行版原样的内核 |

**要验证的：iPXE 加载一个发行版签名的内核时，签名验证是否生效且通过。**

**一个可能的意外：iPXE 的内核加载可能绕过固件的签名验证** ——
它是自己实现的加载器，不一定调用固件的验证接口。
**若真是这样，Secure Boot 在这一级实际上是失效的** ——
**那是一个要记录的重要事实**：它意味着整个三级链提供的保护比预期弱。

**这一条要老实验证并记录，不要因为「那样就白做了」而回避。**
知道保护的实际边界比假设它完整更有价值。

**完成标志：** 内核这一级的验证结果已记录，含「签名验证是否真的生效」的结论

---

### 任务 5：综合结论与建议

**产出：** `docs/secureboot-poc/05-结论.md`

**要给出的四项：**

1. **可行性结论**：走得通 / 走不通 / 走得通但代价不可接受
2. **若走得通，完整的部署流程**：从获取中间引导器到每台机器的注册
3. **维护成本评估**：密钥轮换时要做什么、新机型上架时要做什么、
   **中间引导器被撤销时要做什么**（最后一项是最麻烦的）
4. **建议**：实施 / 改用关闭 Secure Boot 的流程 / 混合（部分机器用一种）

**第 3 条的第三项要特别评估。** 中间引导器被固件撤销时，
所有依赖它的机器都无法引导 —— 而那个撤销由厂商推送的固件更新带来，
**不在我们控制范围内**。这是这个方案的一个结构性风险。

**若结论是「改用关闭 Secure Boot 的流程」，要产出那个流程的文档**：
装机前关闭、装完后是否开启（**开启会不会让刚装的系统起不来？要验证**）、
以及批量操作的方式。

**最后一句要写进结论：这个 PoC 花了多少时间。**
它是将来评估类似「技术风险最高」项目的参考数据。

**完成标志：** 四项都有结论；**若建议实施，则另写一份实现计划**（本 PoC 不含实现）

## PoC 验收

- [ ] 五个阶段的产出文件都存在
- [ ] **任务 1 的结论明确** —— 若是「改用关闭流程」，后续任务可不执行，
      那是有效的 PoC 结论
- [ ] 若继续：每个任务的问题都有基于实机的答案（**不是文档推测**）
- [ ] 结论含可行性判断、部署流程、维护成本、建议四项
- [ ] **内核那一级的签名验证是否真的生效已经查清**
- [ ] 中间引导器被撤销的风险已评估
- [ ] 若建议实施：另有一份实现计划

## 这个 PoC 可能的三种结局，都是成功

1. **走得通且代价可接受** → 写实现计划
2. **走得通但代价不可接受**（比如每台机器要人工注册）→
   记录下来，改用关闭 Secure Boot 的流程。**省下了一次注定难维护的实施**
3. **走不通** → 明确告知运维「开启 Secure Boot 的机器不能用本系统装机」，
   让他们在采购或分配时避开，或接受装机时临时关闭

**第 2 与第 3 种结局的价值不低于第 1 种。** §11 建议先做 PoC 的理由就是这个 ——
**在投入实施之前知道它会不会成，比实施到一半发现不成好得多。**
