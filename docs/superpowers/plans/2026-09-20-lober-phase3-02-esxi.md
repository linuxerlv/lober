# P3-02 ESXi 支持 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。
>
> **前置：** Phase 2 全部完成。与 P3-01、P3-03、P3-04 并行。
>
> **本计划描述做什么与为什么，不给代码。**

**目标：** 让 ESXi 走通 —— 渲染引导配置文件、用 kickstart 脚本驱动无人值守，**仅 UEFI**。

**架构：** ESXi 的应答文件机制反而与 RHEL 最接近（都叫 kickstart，
且 ESXi 原生支持首次启动段），**但引导形态完全不同** ——
它有自己的引导器与一个必须由网关渲染的引导配置文件。

**为什么那个配置文件必须由网关渲染而非 nginx 静态发**（§2.1 末段）：
它含 per-task 的应答文件 URL（带 token），所以是「内容因主机而异」的那一类（§1.4 的分界线）。

**仅 UEFI 是一个范围决定，不是暂未实现**（§0.3、§1.2）：
传统 BIOS 需经 syslinux 的一个模块，依赖 iPXE 的 COMBOOT 支持 ——
**而那个支持仅存在于 BIOS 构建，且部分预编译二进制未开启**（附录 A.14）。
Phase 1 与 Phase 2 都明确排除，Phase 3 **默认也不做**。

**技术栈：** ESXi 的引导器与引导配置文件；kickstart（ESXi 方言）

**SPEC 依据：** §0.3、§1.2、§2.1、§4.5、§4.6、§6.5 末段、附录 A.7–A.9、A.14

---

## 四个必须先接受的事实

前三条来自附录 A.7–A.9，第四条来自附录 A.14：

1. **kickstart 脚本可从多种协议获取**，安装器自身可走网络引导或光盘引导 ——
   两者彼此独立。我们用网络引导加 HTTP 取脚本
2. **脚本位置靠一个引导选项指定，不设则脚本化安装无法启动。**
   这个选项要写进引导配置文件的内核选项行
3. **用 U 盘引导时应答文件不能放在同一个 U 盘上** —— 与我们的网络引导路径无关，
   但要知道这条约束存在（将来若加 U 盘引导路径会撞上它）
4. **传统 BIOS 的引导器依赖旧版 syslinux，且 GRUB2 无法链载 ESXi 的 UEFI 引导器** ——
   两条 ESXi 引导路径机制不同、不可互换

**由第 2 条推出本计划的核心工作：引导配置文件的渲染。**
它不是一个静态文件 —— 里面有三处要改写（见任务 2）。

### 任务 1：制品集导入

**产出文件：** `internal/imports/extract_esxi.go`、对应测试

**为什么需要这一步：** ESXi 的 ISO 结构与三个 Linux 家族都不同。

**识别特征是两个文件同时存在**（§2.1 的表）：引导配置文件与 UEFI 引导器。
**两者缺一个就不是可用的 ESXi 制品** —— 单靠一个会误判。

**抽取要产出的三类：**

| 类别 | 说明 |
|---|---|
| UEFI 引导器 | 放进制品目录，菜单里当「内核」用 |
| **引导配置文件模板** | 从 ISO 里取出原始版本，作为渲染的输入 |
| 模块文件（众多） | ESXi 的引导要加载几十个模块，全部搬到制品目录 |

**第三类的数量要注意：** ESXi 的模块有几十个，且引导配置文件里按顺序列出。
**抽取时不要重排顺序** —— 那个顺序是引导要求的。

**固件字段固定为 UEFI**（§2.1 的表），**导入时不接受其它值** ——
若有人试图把 ESXi 制品集标为 BIOS，导入就应拒绝，理由写明是 MVP 与 Phase 3 的范围决定。

**完整性校验要覆盖全部模块文件**（§4.6 第三项）。缺一个模块的表现是
「ESXi 引导到某一步停住」—— 而那个错误信息不会指出缺哪个文件。
**所以导入时的清单校验比 Linux 侧更重要。**

**测试要锁住的行为：**

- 两个特征文件同时存在时识别为 ESXi，**只有一个时不识别**
- 模块文件全部搬运且**顺序保持**
- 固件字段只接受 UEFI，其它值被拒
- 缺模块文件时导入失败且原因具体

**验证：** `go test ./internal/imports/ -run TestESXi -v` 全过。

**完成标志：** commit `feat(imports): ESXi artifact set, UEFI only`

### 任务 2：引导配置文件的渲染

**产出文件：** `internal/render/esxi.go`、golden file

**为什么需要这一步：** §2.1 明确：这个文件含 per-task 的应答文件 URL，
**所以由网关渲染，不放 nginx 静态**。

**三处必须改写**（§2.1 的 ESXi 特例说明）：

| 改写项 | 原值 | 改成 | 不改的后果 |
|---|---|---|---|
| 前缀路径 | ISO 内的相对路径 | **HTTP 路径** | 引导器去本地找文件，找不到 |
| 内核选项 | 无应答文件参数 | **加上应答文件 URL** | 脚本化安装无法启动（附录 A.8） |
| 模块路径 | 带前导斜杠 | **去掉前导斜杠** | 路径拼接出双斜杠或绝对路径，取不到模块 |

**第三项是最容易漏的。** 前缀已经是 HTTP 路径时，模块路径若保留前导斜杠，
拼出来的 URL 会是错的 —— 而现场表现是「引导器报某个模块取不到」，
而运维会去查 nginx 而不是查这个渲染。

**渲染的输入是导入时保存的原始配置文件**，输出是改写后的版本。
**不要从零生成那个文件** —— 它含几十个模块的清单与若干 ESXi 版本相关的参数，
从零生成意味着要理解每一项，而它们随 ESXi 版本变化。

**改写的实现方式：逐行处理原始文件**，只改那三类行，其余原样输出。
这样新 ESXi 版本加了新参数时不会被丢掉。

**测试要锁住的行为：**

- 三处改写各自正确
- **模块路径的前导斜杠被去掉**（单独一条断言）
- 未涉及的行原样保留（用一个含未知参数的输入验证）
- 应答文件 URL 从基址拼出、token 在路径段
- golden file 覆盖一份真实的 ESXi 引导配置文件改写结果

**验证：** `go test ./internal/render/ -run TestESXiBootCfg -v` 全过。

**完成标志：** commit `feat(render): ESXi boot config rewriting with three substitutions`

### 任务 3：菜单与 ESXi 方言的 kickstart

**产出文件：** `internal/render/menu.go`（补 ESXi 分支）、`internal/render/esxi.go`（扩展）

**为什么需要这一步：** 菜单形态与应答文件都与 RHEL 的 kickstart 有差异。

**菜单只有一行**（§4.5）：UEFI 引导器作为「内核」，带一个指向渲染后的引导配置文件的选项。
**没有 initrd 行** —— ESXi 的模块由引导配置文件列出，不走 iPXE 的 initrd 机制。

**`plat` 不是 UEFI 时不下发此菜单**（§4.5 的注明、§4.6 的硬拒绝）。
Phase 1 的 precheck 已实现这条（固件兼容矩阵里 ESXi 只支持 UEFI）——
**本任务要有测试确认它对 ESXi 确实生效**。

**ESXi 方言 kickstart 与 RHEL 的三处差异：**

1. **原生支持首次启动段**（§5.2 的映射表）—— 不需要 Linux 侧那套 systemd oneshot 脚手架。
   **这是 ESXi 唯一比 Linux 简单的地方**
2. **没有 post-nochroot 阶段**（§5.2 的表里那一格是空的）——
   模板若给 ESXi 配了该阶段的 hook，**保存模板时就要拒绝**
3. **syslog 的配置方式不同**（§6.5 末段）：用 ESXi 自己的命令行工具设置日志主机，
   而不是 kickstart 里的一行指令

**第 1 条让 firstboot 的实现简化，但信号语义要保持一致** ——
原生首次启动段里仍要发 `booted`、`init-start`、`init-done`、`ready`，
用 finalize token（§6.4）。

**第 2 条要落实在模板保存的校验里**（M6 的职责）：
这是一个跨模块的要求，**要在本任务里明确指出并确认 M6 的校验覆盖它**。
若 M6 的现有校验只看「hook 声明的家族与制品集兼容」而不看「该家族是否支持该阶段」，
那是一个需要补的校验点。

**测试要锁住的行为：**

- 菜单一行结构，带引导配置文件选项，**无 initrd 行**
- BIOS 机器的 ESXi 任务被 precheck 拒绝
- kickstart 用原生首次启动段，且四个信号都在
- **配了 post-nochroot 阶段 hook 的 ESXi 模板保存被拒**
- syslog 配置用 ESXi 的方式

**验证：** `go test ./internal/render/ ./internal/console/ -run ESXi -v` 全过。

**完成标志：** commit `feat(render): ESXi menu and native firstboot kickstart`

### 任务 4：实机核对与 BIOS 路径的 PoC 决策

**产出文件：** `deploy/verified-esxi-<日期>.md`

**为什么需要这一步：** ESXi 的失败点集中在引导阶段，且错误信息普遍模糊。

**核对清单：**

- [ ] UEFI 机器成功引导 ESXi 安装器
- [ ] **全部模块都能取到**（引导日志里不应有取不到的模块）
- [ ] 引导配置文件的三处改写都生效（前缀是 HTTP、有应答文件参数、模块路径无前导斜杠）
- [ ] 应答文件被取到且脚本化安装真的启动了（**不设那个参数时会退回交互式安装** ——
      主动验证一次这个区别）
- [ ] 原生首次启动段执行，四个信号都收到
- [ ] **故意给一台 BIOS 机器建 ESXi 任务，确认被拒绝并置失败**（§4.6 的验证）

**倒数第三条要主动验证。** 附录 A.8 说「不设则脚本化安装无法启动」——
确认那个失败形态（是报错还是退回交互式）对排查很有价值：
若是退回交互式，现场表现会是「机器停在安装界面等人」而不是一个失败态。

#### BIOS 路径的 PoC 决策

**默认不做。** 只在「届时确有 BIOS 机器需装 ESXi」时才做（§11 Phase 3）。

**若要做，先做独立 PoC 而非直接实现**，要验证三件事（附录 B）：

1. **iPXE 的预编译二进制是否开启了 COMBOOT 支持** ——
   附录 A.14 指出「仅存在于 BIOS 构建，且部分预编译二进制未开启」。
   未开启就要自行编译 iPXE
2. **syslinux 的那个模块能否经 iPXE 的 COMBOOT 走通** —— 这是整条路径的关键一跳
3. **旧版 syslinux 的获取与维护成本** —— 附录 A.14 提到它依赖的是一个很旧的版本

**PoC 的结论有两种，都要记录：**

- 走得通 → 那时再写实现计划，且 §0.3 的固件矩阵与 §2.1 的固件字段约束要相应放宽
  （**这是契约变更，走流程**）
- 走不通 → **记录下来并明确告知运维「BIOS 机器不能装 ESXi」**，
  让他们在采购或分配机器时避开这个组合。这比留一个「将来也许支持」的悬念有用

**完成标志：** commit `docs: ESXi verification record and BIOS path PoC decision`

## 边界提醒

**不要为了「支持完整」而实现 BIOS 路径。** 它的机制与 UEFI 路径完全不同
（附录 A.14：两条路径机制不同、不可互换），意味着第二套引导逻辑、
第二套制品结构、第二套排查经验。

**而它的收益取决于一个事实问题：机房里到底有没有 BIOS 机器要装 ESXi。**
ESXi 的硬件兼容列表本身就偏向较新的服务器，而那些机器基本都是 UEFI ——
先确认这个需求真实存在，再决定是否投入。
