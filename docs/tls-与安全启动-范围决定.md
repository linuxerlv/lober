# TLS 与 Secure Boot 范围决定

> **本文档写给谁**：接手这个项目的人，不是当前的开发者。你可能会在几个月
> 或几年后打开这份文档，需要在完全不记得当时讨论过程的情况下，快速理解
> 「为什么机器面到今天还是明文 HTTP」「为什么 Secure Boot 没做」「这是
> 疏漏还是决定」。本文档只回答这些问题，不重复展开各文件已有的技术细节
> ——技术细节的权威来源标在每一节末尾，供你按需深入。
>
> **一句话结论**：TLS 全量方案（机器面 TLS + mTLS）与 Secure Boot 已经
> **放弃**，不是推迟；浏览器 ↔ 控制台之间的 HTTPS 已经**做了**；机器面
> （装机端 ↔ 网关）永久保持明文 HTTP，这不是安全性打了折，是两个信任域
> 风险画像不同、防线本来就不在同一层的合理结果。

---

## 1. 决定一览表

| 范围 | 决定 | 状态 |
|---|---|---|
| 浏览器 ↔ 控制台（人面 HTTPS） | **做** | 已落地，见 `deploy/nginx/lober.conf` 人面 server 块 |
| 装机端 ↔ 网关（机器面 TLS） | **放弃**（不是推迟） | 机器面永久保持明文 HTTP |
| 机器面 mTLS | **放弃**（早于本次决定，见 `docs/phase4-mtls-决策.md`） | 协议本身不成立（裸机装机前无身份） |
| 人面 mTLS | **未做，未来可选** | 早前的权衡见 `docs/phase4-mtls-决策.md`，本次决定未改变这一条 |
| Secure Boot（三级签名链） | **放弃**（不是推迟） | 见第 3 节 |

## 2. 为什么放弃机器面 TLS：成本集中在 iPXE 重新编译

### 2.1 这条成本从哪来

`SPEC.md` §1.5 的原话：

> HTTPS 在这套栈里最贵的部分是 iPXE 需重新编译（带 crypto、用 `TRUST=`
> 嵌内网 CA），之后每次证书轮换都要重编重发引导文件，叠加 Secure Boot
> 签名链后风险与工期都显著上升。

`deploy/ipxe/README.md` 展开了这条成本的技术细节：Lober 官方分发的预编译
iPXE 二进制（`undionly.kpxe`、`snponly.efi` 等）**默认不带 crypto 支持**，
要让 iPXE 走 HTTPS，必须重新编译并用 `TRUST=` 把内网 CA 证书嵌入二进制。
这两件事都只能在编译时完成，运行时无法后补。

`deploy/ca/README.md`「有效期与轮换节奏」一节进一步指出：CA 证书轮换（区别
于服务端证书的常规轮换）会触发**重新编译全部四种架构的 iPXE 二进制**，
并重新分发到 TFTP 目录——这是全链路最贵的一步操作，且是**持续性**成本，
不是一次性的。

### 2.2 本次范围切法：把这块成本整块切掉

本次决定：**机器面永久保持明文 HTTP，只在浏览器 ↔ 控制台之间上 HTTPS。**

这个切法直接绕开了上面整段成本——机器面不上 TLS，意味着：

- iPXE **完全不需要重新编译**，继续用官方预编译二进体（当前 MVP 现状）。
- 内网 CA（`deploy/ca/`）签发的证书**只用于人面域名**，机器面域名不需要
  签发证书，签了也不会被用到。
- 证书轮换只影响 nginx 加载的人面证书文件，**不触碰 iPXE、不触碰 TFTP
  分发**——这正是 `deploy/ca/README.md` 里「服务端证书轮换」这条本来就
  轻量的路径，而「CA 轮换触发 iPXE 重编译」这条昂贵路径因为机器面根本
  不引用任何证书而**不会被触发**（除非未来重新决定给机器面上 TLS，见
  第 5 节）。

### 2.3 与原方案的对比

原方案（`deploy/nginx/lober.conf` 此前的「TLS 增量」备选段）是「两面都上
TLS」：机器面与人面各有一个 443 server 块，且要求先编译带 crypto 的 iPXE、
实测它能协商上什么密码套件，再回头收紧 nginx 配置——这是一条「先做贵的
那部分，再迭代收紧」的路径。

本次决定不是把这条路径推迟，是**把机器面那一半直接删除**：`deploy/nginx/
lober.conf` 里原有的机器面 TLS server 块、以及要求先编译 iPXE 才能推进的
启用步骤，已经从该文件中移除（该文件顶部有一节专门说明移除了什么、为什么，
以及保留并改写到人面 server 块的内容）。

## 3. 为什么放弃 Secure Boot：内核这一级的保护形同虚设

### 3.1 调研做了什么

`docs/secureboot-poc/` 下五份文档是一次完整的技术调研（01 机器事实、
02 中间引导器、03 签名与注册、04 内核签名、05 综合结论），核实了三级
签名链（固件 → shim → 自签 iPXE → 目标内核）的每一层机制。

### 3.2 结论：走得通，但代价不成比例

`docs/secureboot-poc/05-结论.md`「可行性结论」表格给出的分层判断：

| 层级 | 是否走得通 |
|---|---|
| shim 的获取与链载 iPXE | 走得通 |
| iPXE 的自签名 | 走得通 |
| 密钥注册进固件 MOK 列表 | 走得通，但**强制逐台交互**（协议设计要求物理/带外确认，不是能优化掉的实现细节） |
| 内核这一级的实际保护 | **形同虚设**（iPXE 主动解锁 shim 的验证接口，内核签没签不影响能否启动） |

决定性因素：**这条链最后一跳本来就不提供实质保护**，而维护整条链要付出
「每台新机器上架时一次不可自动化的 MOK 交互确认」这项与本项目「自动化
装机」这个核心价值主张直接冲突的成本。`05-结论.md` 还引用了 iPXE 官方
对 Secure Boot 的立场（「UEFI Secure Boot is primarily a form of
pay-to-play security theatre」）作为独立于本项目工程判断的佐证。

### 3.3 与机器面 TLS 决定的关系

`05-结论.md`「五、与本项目的衔接」一节已经指出，Secure Boot 签名链与
iPXE TLS 编译共享同一份「自编译 iPXE」基础设施（都需要一台能编译 iPXE
的外网机器）。本次决定同时放弃两者，这份共享基础设施**两边都不需要再
搭建**——但这不是「因为不做 A 所以顺带不做 B」的连带关系，两者是基于
各自独立的成本/收益分析分别得出「放弃」结论的，只是恰好共享了一部分
从未被搭建的基础设施。

## 4. 机器面明文的安全论证：防线本来就不在传输层

**这是本文档最容易被误读的地方，必须写清楚：机器面保持明文，不代表机器面
的安全性比人面差一个量级，是因为机器面的防线本来就不建立在传输层上。**

### 4.1 三道闸门与 token 都在协议层，与 scheme 无关

`SPEC.md` §9.1 的核心风险描述：「一个无认证的 HTTP 端点，有权告诉机器
『擦盘重装』」。应对手段是三道闸门叠加：

1. **默认拒绝**——`/v1/boot` 查不到 `pending` task 即返回 `no_task`，
   只有有任务的主机才签发 token。
2. **SN 从清单选取 + MAC 双因子**——不接受自由文本，两个键都对上才签发。
3. **attempt 计数封顶**——同一任务窗口内菜单最多取 3 次，超过即 failed。

这三道闸门判断的是「这台具体的机器，有没有被运维明确授权装机」，判据是
机器的身份属性（SN、MAC）与业务状态（是否存在 pending 任务）——**这个
判断发生在应用层，与请求走 HTTP 还是 HTTPS 无关**。换成 HTTPS，闸门的
逻辑不会有任何变化，因为它们从来不依赖传输层提供的任何保证。

`SPEC.md` §9.1 原文：「MVP 无 TLS，故 token 与默认拒绝是唯一的防线，
不能降级实现。」——这句话在本次决定之后**仍然成立**：机器面依然无 TLS，
token 与默认拒绝依然是唯一的防线，这条判断没有被本次决定改变。

### 4.2 人面 HTTPS 换来的是什么：实质保护，不是形式合规

浏览器 ↔ 控制台的 HTTPS 保护的是**登录凭据（用户名/密码）与 access
token**——控制台走的是密码认证（`SPEC.md` §9.4），这类凭据一旦在管理网
被明文嗅探到，攻击者能直接冒充运维登录，做出建任务、批准 hook 等有实际
破坏力的操作。这与机器面的风险模型完全不同：机器面没有「凭据」这个概念
可以被窃听——token 是响应中签发给已通过三道闸门校验的机器，不是提前
存在、可以被截获后重放到别处的东西（token 的用途与生命周期见
`SPEC.md` §4.2、§4.3）。

**这是两个信任域不同风险画像的合理差异，不是妥协**：人面存在「凭据被
窃听后可重放」这个风险，机器面的核心风险是「错误的机器被装机」，后者
的防线天然长在协议层。给机器面上 TLS 不会让三道闸门变得更强，给人面上
TLS 直接消除了一类真实存在的凭据窃听风险。

### 4.3 §1.5 的缓解措施仍然有效且不可放松

`SPEC.md` §1.5 在「MVP 明文 HTTP」决定下，专门为应答文件中的敏感内容
列出了缓解原则——**这些原则不是「上了 TLS 就可以取消」的临时补丁，
是与传输层是否加密无关的独立防线，本次决定后必须原样保留**：

- **root 不设可复用密码，注入 SSH 公钥并关闭密码登录**——应答文件
  （kickstart/preseed/autoyast/unattend 等）被截获也换不成持久访问。
- **`unattend.xml` 不放域管凭据**，用最小权限专用加域账号，或把加域
  挪到装机后另一通道。

这两条措施对应的实现在 `deploy/lober.yaml.example` 的
`gateway.root_ssh_public_keys` 字段（该字段留空时 `config.Validate`
直接拒绝启动，见该文件的字段注释）——**机器面仍是明文，这两条措施
一条都不能松，本次决定没有改变这一点，也不应该被误读为「因为机器面
反正是明文，这两条措施显得不那么重要了」**。恰恰相反：正因为机器面
永久保持明文（不是临时状态），这两条措施的重要性是长期的，不会随着
「以后再上 TLS」而降低优先级。

### 4.4 威胁模型与前提

`SPEC.md` §1.5 描述的威胁模型：「交换网络上被动嗅探需要端口镜像或装机
VLAN 上已有失陷主机，风险面是内部人员与已失陷主机，不是任意旁观者。」
**前提是该 VLAN 真正隔离、不路由到办公网**——这条前提是本系统无法自行
校验的，需要运维在网络层面确认（`deploy/README.md` 第 0 节前提条件第 2
条已强调这一点）。本次决定不改变这个前提要求：机器面明文的安全论证
完全依赖「装机 VLAN 真正隔离」这个外部条件成立，如果这个条件不成立，
问题不在于「该不该上 TLS」，而在于网络隔离本身没有做到位。

## 6. 将来若改变主意：入口在哪，为什么那时仍然贵

这份文档不是「永久关闭」的死胡同。如果未来有理由重新考虑机器面 TLS 或
Secure Boot（例如：合规要求变化、威胁模型的前提条件不再成立即装机 VLAN
不再能保证隔离、批量 MOK 注册路径被证实存在），重新启用的入口是：

1. **机器面 TLS**：从 `deploy/ipxe/README.md` 与 `deploy/ipxe/build-ipxe.sh`
   开始——`TRUST=` 嵌 CA 的机制与编译脚本已经就位，需要做的是：
   - 重新在 `deploy/nginx/lober.conf` 里加回机器面的 443 server 块
     （本次改动已把它移除，需要参考 git 历史或重新参照人面 server 块
     的结构编写）。
   - 实际编译带 crypto 的 iPXE，实测它能协商上什么协议版本与密码套件，
     再回头收紧 nginx 配置的 `ssl_protocols`/`ssl_ciphers`（这条「先编译
     后收紧」的顺序要求本身没有过时，只是本次决定后暂时不需要执行）。
   - 重新走一遍 `deploy/ca/README.md` 的证书轮换流程，把机器面域名也
     纳入证书签发范围。
   - **为什么那时仍然贵**：`TRUST=` 机制没有变得更便宜，CA 轮换触发
     iPXE 重编译这条成本结构性地存在，不会因为时间推移而消失——除非
     iPXE 项目本身的架构发生变化（例如支持运行时加载信任锚点而不需要
     编译时嵌入），这属于本项目无法控制的上游变化。

2. **Secure Boot**：从 `docs/secureboot-poc/05-结论.md`「二、若走得通，
   完整的部署流程」开始——七步流程已经写清楚。
   - **为什么那时仍然贵**：MOK 交互确认是协议设计要求的物理/带外操作，
     不是本项目的实现选择，除非固件层面出现批量注册的替代路径（`05-
     结论.md` 提到的 Redfish 可能性，本环境未能核实），这一步始终无法
     自动化。且内核签名这一级的保护「形同虚设」这条结论是 iPXE 当前
     实现的架构事实（主动解锁 shim 验证接口），不会因为时间推移而改变，
     除非 iPXE 项目自己改变这个设计。

3. **人面 mTLS**（与本次决定关系较远，但同属「传输层加固」话题）：
   从 `docs/phase4-mtls-决策.md`「若人面做了 mTLS」一节开始，注意该文档
   已指出 `deploy/ca/issue-cert.sh` 需要先扩展才能签发客户端证书。
